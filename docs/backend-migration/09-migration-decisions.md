## D11 핵심 데이터 개념 — 사용자·실제 게임 원정대·서버 저장의 역할 (2026-10-16 사용자 확정)

이 절은 이후 설계·구현·Backend 협업에서 반드시 유지할 핵심 제품 기준이다.

- **앱 사용자1명은 실제 게임 원정대 여러 개를 등록·인증할 수 있고, 각 원정대는 그 원정대에 소속된 캐릭터 목록을 가진다.** 원정대는 앱이 임의로 묶은 캐릭터 그룹이 아니라 로스트아크 API가 제공하는 실제 게임 원정대(사용자가 설명한 게임 한 계정 단위)다. 서로 다른 원정대의 캐릭터를 이름/직업/표시 편의로 합치지 않는다.
- **원정대 구성의 기준은 로스트아크 API 캐릭터 목록**이다. 앱 사용자와 원정대의 귀속·인증은 우리 서버가 관리한다. API 목록으로 게임 내 소속을 확인하는 것과 특정 앱 회원의 소유 인증은 서로 다른 책임이다.
- **우리 서버는 매 화면/매 요청마다 로스트아크 API를 반복 호출하지 않도록 수집 결과를 저장하고 앱 기능에 제공한다.** 이 저장 자료와 현재 회원/소유·사용 자격을 바탕으로 앱 사용 캐릭터 확인과 향후 파티 모집·그룹 생성/활동을 처리한다. 서버 자료 조회와 provider에서 새로 수집·반영하는 갱신을 동일 동작으로 취급하지 않는다.
- **원정대 소속 전체 목록 / 앱에서 사용할 활동 캐릭터 선택 / 표시 여부·순서·개수는 별개**다. 전체 소속은 API 기준이며 활동 선택·표시 설정은 그 위의 앱 사용자 설정이다. 표시 개수/숨김으로 원정대 구성이나 자동 검사 대상을 줄이지 않고, 신규 소속 추가로 활동/대표를 자동 선택하지 않는다.
- 앱 실행 중 환경·회원별1회 갱신은 **실제 API 원정대 목록 갱신→서버 반영/현재 목록 재조회→유효 활성 대상 확정→상세 검사**를 포함한다. 나이스단OFF는 해당 계열 상세 검사 제외/기존 빌드 보존이며 목록 갱신 제외가 아니다. 서버에는 기존 최소 요약/설정을 저장하고 상세 원본은 기존 로컬 정책을 따른다. 이 절이 전체 Armory 원문 서버 저장 승인을 뜻하지 않는다.
- **인증에 사용한 특정 캐릭터가 사라져도 원정대의 기존 사용자 귀속·인증은 유지**한다. 해당 캐릭터의 사용 자격/이력·현재 조회 기준 교체는 원정대 인증과 분리한다. 정상 목록에서 추가·누락을 판단하되 실패/부분 응답을 삭제·인증 해제 근거로 삼지 않는다. 타회원/종료ID 권한 승계 금지와 기존 서버 권한·충돌 검사는 유지한다.

이 원칙을 API에 없는 영구세대 증거를 모든 일상 조회에 추가 요구하거나, 기기 로컬 목록을 서버 소유권으로 간주하거나, 화면마다 provider를 호출하는 구조로 바꾸지 않는다. 현재 제공/미구현 범위와 작업 순서는 NEXT_WORK, 세부 자동갱신은23·원정대 생명주기는26을 따른다.

## D10 조회용 저장·소유 인증·활동 권한 분리 — 사용자 확정 (2026-10-16)

최신 UX 보완: 기존 캐릭터 관리 화면(사용 선택·대표·표시 순서/개수)을 재사용해 서버에 연결한다. 대표가 없을 때만1700이상 사용 가능한 대상 중 아이템레벨 최고로 초기1회 선정한다. 이미 대표가 있으면 유지하고 변경은 성공 확인 때만 반영/확정 실패는 그대로 둔다. 아래 ‘인증만으로 대표 자동선택 안 함’은 이 최초1회 초기값 예외를 제외하며 재실행/레벨 변화 재선정·전체 활동 자동추가·메인 자동전환을 하지 않는다. 응답 유실은 서버 확정 실패로 오인하지 않으며 이를 별도 사용자 복구 단계로 확대하지 않는다. 공통 minimumItemLevel=1700을 재사용한다.


사용자가 ‘인증 전 조회용 등록 허용, 인증 후 활동 허용’ 추천안을 채택했다. 미인증 서버 등록을 폐지하거나 인증 뒤에만 Registration을 생성하도록 재설계하지 않는다. 비로그인 전투력/상세 빌드 사용 제한은 과거 로컬 기능 보존 원칙의 이번 사용자 승인 변경이며, 범위 밖 정상 기능을 제거하는 근거가 아니다.

- 비로그인: 원정대 기본 목록 검색, 캐릭터명·직업·아이템 레벨만 로컬 조회 자료로 기록. 사용자별 서버 등록/저장, 전투력·상세 빌드 조회/검사 및 캐릭터를 이용한 모집/참가/그룹 활동 불가.
- 로그인·미인증: 서버에 조회용 원정대를 명시 저장/복원 가능. ‘조회용 저장 · 인증 필요’로 표시하며 소유 원정대로 안내하지 않는다. 기본 정보만 제공하고 본인 전투력/상세 빌드 기능·활동 캐릭터/대표 설정·모집/참가/그룹 활동 권한은 부여하지 않는다.
- 로그인·인증 완료: 현재 서버 소유/canonical을 재확인하고 해당 본·부원정대의 앱 사용 캐릭터와 대표를 명시 선택·전체 atomic 저장한다. 본인 전투력·상세 빌드 확인/저장은 허용하며 실제 활동은 선택·현재 사용 자격·레이드/동시참가 등 기존 조건을 추가로 만족해야 한다. 인증만으로 메인 전환/활동 자동추가/대표 자동선택하지 않는다.
- 검색 결과 주 버튼은 ‘인증하고 사용하기’, 보조는 ‘조회 목록에 저장’. 미인증 저장을 ‘소유 인증 완료’로 표시하지 않는다. 등록별 인증 진입은 대상 registration_id를 전달하고 성공 후 응답 registration_id로 현재 소유·전체 canonical 목록을 재조회해 사용 캐릭터 선택으로 연결한다.
- 자동 상세1회는 선택된 활동 캐릭터 전체 대상, 나이스단 OFF 제외/기존 빌드 보존 유지. visible/count·선호역할은 활동 자격과 별개다. 소유 상실/의심/퇴역·회원/환경 변경 시 현재 자격을 재검증하고 미인증 경로로 상세 기능을 우회하지 않는다.

제품 화면 흐름은 [핵심 흐름 지도](../feature-definitions/LOSTPARTY_CORE_USER_FLOW_OVERVIEW.md)의 최신 절, 실제 단계는 NEXT_WORK다. Backend의 인증용 내부 장비 조회는 소유 증거 확보 절차이며 미인증 사용자에게 상세 빌드를 제공하는 기능과 다르다. 이번 결정은 코드·계약·서버 구현 완료, 기본flag 변경, 기존 개발자료 삭제나 재구축을 의미하지 않는다. 원래 환경/DB/키를 유지하며 새 guest 쓰기 필드 제한·옛 값 비노출을 구현 대상으로 삼고 과거 자료를 이번에 삭제/이전하지 않는다.

## D09 제품 기능·UI/UX 유지 / Firebase 전용 구현 제거 — 사용자 확정 (2026-10-16)

장기간 Flutter 개발에서 확정된 기능·설정·UI/UX는 동일하게 유지한다. 사용하지 않는 것은 Firebase 기반 구현이며, 과거 Firebase 전용 연결/저장·인증·운영/배포 설계를 신규 서버 요구로 공유하거나 다시 연결하지 않는다. Backend에는 새 서버에 필요한 제품 정책·설정의 의미/저장·복원 범위와 현재 연결/미완료 상태만 공유한다.

구 자료 승계 경로는 제거·분리 대상이나 오래된 화면/로컬 DB/정수ID/순수 분석 모델을 일괄적으로 ‘사용하지 않는 기능’으로 분류하지 않는다. 제품 기능과 UX는 새 데이터 경계로 유지·대체하고 Firebase 전용 부분을 제거한다. 메뉴 존재는 신규 서버 구현 완료/새 기능 일괄 승인과 다르다. [공유 기준31](31-app-product-policy-handoff.md)을 따른다.

## D08 개발 → 베타 → 운영 데이터 수명 — 사용자 확정 (2026-10-16)

현재는 **1단계 개발**이다. 이 정책은 아래 초기 제안과 과거 보존형 전환 계획보다 우선한다.

1. 현재 사용 중인 개발환경과 개발 데이터를 유지하며 개발을 계속한다. 기존 Firebase 자료 import를 하지 않는다는 정책을 현재 개발자료 폐기·별도 빈 환경 구성·기초 재인수 지시로 확대하지 않는다. 지금 초기화하지 않는다. 개발자료 보존형 이전/복원 리허설도 선행 조건이 아니다.
2. 베타 사용자를 모집하고 운영을 준비한다.
3. 베타 시작 전 개발하면서 사용한 모든 사용자와 서버 기록을 삭제해 새 출발한다. 실제 실행 시 대상 환경·자료·초기화 영향 범위를 확정한다. 이 정책 기록은 지금 DB/볼륨/Firebase/기기 삭제 명령을 실행하라는 지시가 아니다.
4. 베타에서 생성한 사용자 자료는 큰 이슈가 없으면 보존한 채 서비스 운영으로 이어간다. 베타 시작 이후의 구조 변경은 이 보존 책임을 전제로 계획한다.

신규 DB를 구성하는 테이블/제약·버전 관리와 새 기능의 정상 동작에 필요한 소유권·수명·멱등 검증은 유지한다. Alembic 파일이 있다는 이유만으로 기존 자료 import라고 해석하지 않지만, 개발 자료를 살리기 위한 변환·호환 작업을 자동으로 필수화하지도 않는다. 이미 게시된 변경 파일은 새 빈 DB 구성 필요성을 대조한 뒤 다루며 일괄 삭제/squash하지 않는다.

새 시스템에서 새로 만든 회원 자료의 저장·재로그인/기기 간 복원·개인 키·로컬 상세/영속 대기는 제품 기능으로 유지한다. 기존 기기 자료 보존 화면·schema13/정수ID writer 호환을 새 시스템의 필수 조건으로 두지 않는다. 구 경로의 실제 제거와 로컬 상태 정리는 별도 코드 작업으로 영향 범위를 정하고 수행한다.

[Backend 정책 재확인6206662757](https://github.com/heo0328/lostparty-backend/issues/8#issuecomment-6206662757): 기존 테스트 DB 백업→격리복원→보존 migration 리허설 계획은 폐기됐다. 그 확장은 Backend 판단 오류라고 회신했으며 Flutter P1/P2의 구조 관리 코드 요청과 구분했다. 실제 데이터 삭제/이관·환경 전환·구 경로 제거 완료를 의미하지 않는다.

## D01 기존 사용자·데이터 이관 없음 — 사용자 확정

FastAPI/PostgreSQL 서버는 빈 상태로 시작한다. Firebase UID/Player·게임 계정/Character·파티·그룹·신청·완료/이력·알림·운영자 배정을 import하거나 새 계정에 연결하지 않는다. 사용자는 소셜 로그인으로 신규 계정을 만들고 게임 원정대 인증과 그룹/파티 활동을 다시 시작한다.

기존 사용자 매핑·credential 증명·기기 분실 복구·고아 문서 census·변환 도구·dual-write·데이터 이전 리허설은 이번 서버 개발 완료 조건에서 제외한다. 소스 분석00~05는 기존 기능의 동작과 위험을 이해하는 근거이며 export/import 지시서가 아니다.

**실행 경계:** 이 정책은 기존 Firebase 프로젝트/Auth/Firestore/백업의 실제 삭제 승인이 아니다. 빈 신규 DB를 준비하는 실행도 backend 구현 단계에서 한다. 파괴적인 초기화·배포·운영 서비스 종료는 별도 시점에 대상과 결과를 검토해 실행한다. 이번 작업은 문서만 수정한다.

## D02 기술과 계약 소유 — 사용자 확정

Flutter 및 향후 Swift/SwiftUI, Python3/FastAPI/Pydanticv2/SQLAlchemy2/Alembic/PostgreSQL/pytest, REST+WebSocket, 기능별 모듈형 모놀리스다. Windows11/WSL2 Ubuntu/Docker Desktop/Compose 개발, Caddy와 Lightsail Linux amd64 운영을 전제로 한다. S3/FCM은 필요 시 선택한다. 초기 Cognito/Lambda/API Gateway/RDS/Redis/Kafka/Kubernetes/마이크로서비스는 제외한다.

서버·프론트 저장소를 분리한다. backend 저장소가 OpenAPI와 WS 계약의 원본을 관리하고 frontend는 승인된 version을 참조한다. GitHub Issue 후보는06에만 작성했다. 이번 문서에서 endpoint/DTO/SQL table·물리 key/DDL를 확정하거나 생성하지 않는다. 여기의 논리 개념은 backend 설계의 입력이다.

## D03 비로그인과 회원 생성 — 사용자 확정

비로그인은 실행·허용된 공개 읽기만 수행하며 guest UID/Player/회원/사용자별 서버 데이터를 만들지 않는다. 식별이 필요한 액션은 로그인 알럿을 표시하고 서버도 미인증 요청을 거절한다. Firebase Anonymous Auth와 anonymous account 대체 시스템은 만들지 않는다.

로그인 성공 후에만 신규 내부 사용자와 제공자 identity를 원자적으로 만든다. 반복/동시 첫 로그인은 같은 검증 identity에 새 사용자를 중복 생성하지 않아야 한다. OAuth 요청의 state/nonce/PKCE 거래 정보는 인증 프로토콜의 짧은 수명 검증 자료이며 guest 회원·관심/이력 자료가 아니다. 비로그인 행동 추적/guest profile로 확장하지 않는다.

## D04 공개 읽기 경계 — 설계 제안

| 행위 | 제안 기본안 | 미확정/조건 |
|---|---|---|
| 공개 모집 목록·필터/페이지 | guest 허용 | title/raid/difficulty/schedule/모집상태·자리수·참여조건 등 최소 모집 정보 |
| 공개 모집 상세 | guest 허용 | 위 상세와 슬롯의 role/class,필요한 Character 표시 Snapshot. 이름 노출 범위는 backend 계약 승인시 확인 |
| 그룹 검색/공개 요약 | guest 허용 후보 | 그룹명·대표 표시·인원 등 공개 요약에 한정. private 요청·member 전체 접근 없음 |
| 본인 그룹·내 현황·신청·완료 | 로그인 필요 | 내부 principal에 따른 자기 scope |
| 생성/신청/참가·게임 인증·운영 액션 | 로그인 필요 | 로그인 외 각 role/소유권·상태 검증 추가 |

public 응답은 allowlist로 별도 구성하고 전체 entity serialization을 사용하지 않는다. 이메일/OAuth subject/Auth UID/token·내부 운영 역할·신청자/투표·소유권 차수·차단/분쟁·private group 관계/이벤트 audience는 공개에서 제외하는 설계다. hidden/group 모집은 public list/detail에서 거절한다. internal ID의 공개 표현과 Character 이름 정책은 명세에서 결정한다.

로그인 후 자동 쓰기 재실행은 기본적으로 하지 않는 설계다. 같은 화면으로 복귀해 사용자가 다시 확인하고, 재실행 시 최신 상태를 다시 읽는다. 이 문장은 사용자 최종 승인 전 제안이며 로그인 알럿 자체는 확정 요구다.

## D05 로컬 데이터 — 파괴적 초기화 미승인, 격리 제안

기존 Drift 계정·빌드·filter·읽음 설정을 삭제할지 유지할지는 사용자 결정이 남아 있다. 서버 이관 없음과 기기 데이터 삭제는 별개다. 이번 문서의 안전한 전환 기본안은 로컬 원본 보존 + server environment/principal 구분이다.

Firebase server IDs/주간 상태/party history receipts/group 관계/cleanup journal은 새 서버에 authoritative 데이터로 보내지 않는다. 과거 journal을 새 서버로 자동 replay하지 않는다. 로그인한 신규 계정의 과거 서버 ID가 아닌 fresh 조회/게임 인증으로 새 관계를 만든다. build/local preference를 재사용할 경우 표시/입력 후보 자료로만 쓰고 ownership·완료·운영 권한으로 인정하지 않는다.

local namespace 변경/보관/archive/삭제 구현·앱 schema migration은 frontend 작업에서 정책 결정 후 작성한다. 현재 `raid_cycle_schedule.dart` 등 앱 코드를 수정하지 않는다.

## D06 신규 서버 기본 설계안

- 내부 사용자 ID와 소셜 identity,게임 원정대/Character identity는 분리한다. 표시명·email·원정대명으로 사용자 자동 병합하지 않는다.
- 게임 소유권은 서버 challenge로 재인증한다. 기존 Firebase 소유권은 인정하지 않는다. 새 서버에서 발생하는 이후 소유권 이전은 소유 차수를 증가시켜 과거 참가/완료/권한과 구분한다.
- 운영자는 기존 Firebase assignment를 승계하지 않는다. 첫 운영자 부여는 별도 운영 절차로 검증한 신규 계정에 수행하며 공개 API self-promotion을 두지 않는다.
- 파티/그룹/주간 상태는 server authoritative 명령이다. role·actor·count·event audience를 클라이언트가 확정해 보내지 않는다. 기존8인/50인/50그룹과 주차 규칙은 기능 기준으로 유지하는 설계이며 변경하려면 별도 제품 결정이다.
- access/refresh·세션·public fields/로컬 설정 정책의 제안과 미결정은11/12에서 관리한다. 설계 문서 작성이 배포·코드 구현 승인이 아니다.
