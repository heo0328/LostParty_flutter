## 선택 일괄 완료의 복구 보존 경계 — Native 연결·계정 표시 복구 확인 (2026-11-10)

사용자 승인 [설계37](37-raid-scheduling-and-multi-raid-planning.md#selected-batch-completion)의 상세 공대장/개인 복수 완료 확장은 [Issue47](https://github.com/heo0328/lostparty-backend/issues/47)에서 별도로 요청했다. 기존 완료 오류/계정 복구 인수와 구분하며 고정44eb4ba3 계약의 신규 wire/기능을 Native에 연결했다. 사용자는 일반 흐름 대부분 정상과 BUG-034 수정 뒤 내 계정 표시 정상화를 확인했다. 실제 보고 범위의 인수이며 세부 결과는 NEXT_WORK/BUG-034를 따른다.

- 현재 단일 원요청/query·body·key/token·snapshot·ACK와 구형 단건 해석을 보존한다. 신규 복수에는 원 선택 집합과 ACK 검증 근거를 보관하고 정확히 대조한다. 복원 시 최신 전체 선택/plan으로 원문을 재구성하지 않는다.
- 상세 복수 완료의 결과불명은 같은 종류·room/T·원선택 집합으로 재진입하며 선택 변경을 막는다. 내 계정의 누른1개 고정 진입은 해당 단건 요청만 복구하며 복수 요청을 대신 실행하지 않는다.
- BUG-034: 고정44eb4ba3의 개인 승계 batch 원ACK는 effect.after.revision이null일 수 있다. 이때만 같은 원ACK의 known group_policy와 room/T/cycle/세대·after scope/group·before 대비 유지/+1을 대조해 검증용 효과를 구성한다. 원ACK·journal은 재작성하지 않고 현재 GET으로 증거를 대체하지 않는다. 일반 그룹 ACK 검사는 유지한다. 탈퇴 반영으로 방이 사라져도 레이드 현황의 batch pending 전용 진입에서 기존 잠긴 확인창으로 명시 재시도한다. 2026-11-10 사용자가 내 계정 표시 정상화를 확인했으며 실제 보고 범위는 BUG-034/NEXT_WORK에서 관리한다.
- 완료 안내의 확인창 전용 수명·취소는 표시 종료이며 서버/원요청 취소가 아니라는 의미·늦은 ACK 강제이동 차단·ACK 성공 후 조회만 복구를 유지한다. 원ACK 부재/현재 GET만으로 성공 합성·pending 자동 삭제를 하지 않는다.
- 기존 participation 단일 owner 저장/transport를 재사용한다. 별도 큐·다중 저장·종결 API·계정 초기화나 BUG-033 현재 상태 채택의 범위 확대는 포함하지 않는다. 실제 betaWire2 앱 경로에 신규 기능을 연결했다. batch 두 종류만 ACK1MiB를 허용하고 기존 명령256KiB·원본 단건 schema/해석은 유지한다. 새 ACK 근거는 선택·효과·이력proof·예상 결과/revision·확인 시각을 저장하며 인증정보/전체 화면 상태는 저장하지 않는다.

## 완료 오류 안내 UX — 사용자 협의 정리 (2026-11-09)

현재 완료 오류/복구 수정은 2026-11-10 사용자 디바이스 테스트 통과다. 기존 계정 복구는 문구 수정 전에 완료됐고 이후 버튼명/안내 표시만 조정했다. 묶음 선택 일괄 완료는 위 별도 승인 설계/Issue47을 따르며 상세 완료 알럿/명령에 적용됐고 계정의 단건 동작은 유지한다.

사용자 승인 설계에 따라 이번 완료 오류에만 적용한다. 단순함·빠름·편리함을 우선하며 앱 전체 오류 개편·별도 종결 API·복구 큐·다중 요청 저장·Backend/DB 변경은 제외한다. 기존 로그인·권한·회원 격리·중복 방지와 단일 저장 슬롯을 유지한다.

### 표시·요청 수명과 성공 후 복귀

- 완료 안내는 회원·환경·방·실제 주차·종류·대상·확인창 인스턴스에 귀속한다. 공용 배너의 완료 오류/pending·후속 조회 실패 전파를 차단하고 비완료 배너는 유지한다.
- 첫 오류부터 취소 가능하며 뒤로가기/바깥 터치로도 닫는다. 취소는 표시 종료이며 저장 요청 삭제/서버 취소가 아니다. 늦은 오류는 다시 나타나지 않고 늦은 성공은 자료/ACK를 반영하되 다른 화면을 강제로 이동시키지 않는다.
- Controller의 원요청 상태와 메모리의 CompletionDialogFeedback을 분리했다. 같은 방/주차/완료 종류의 기존 진입점과 계정의 일치 참가 항목만 복구용으로 다시 진입할 수 있다. 새 대상 선택은 막고 원 레이드 식별로 현재 plan의 표시명을 확인한다.
- 재시도는 기존 Controller/transport의 원method/path/query/body/key·snapshot·ACK를 사용한다. 다른 완료 종류·대상으로 바꾸거나 보관 조건을 완화하지 않는다.
- ACK 후 조회 실패는 해당 열린 창에서 조회만 다시 실행한다. 이 동안 성공 이벤트의 조기 이동을 막고 닫기/조회 복구 후 기존 복귀를 한 번만 수행한다. 회원·환경 전환은 해당 안내/진단을 무효화한다.

### Backend 회신과 유지하는 한계

[최종 회신6738491069](https://github.com/heo0328/lostparty-backend/issues/17#issuecomment-6738491069)으로 확인 대기는 해소됐다. 기존 API로 상태 표시·원요청/ACK 복구가 가능하며 같은 종류/대상의 완료 중복 효과는 서버 CAS로 차단한다. 현재 상태 표시를 원ACK 성공 합성·pending 삭제와 혼동하지 않는다. 개인 완료와 공대 완료는 별도 결정이며 자동 전환하지 않는다. Backend의 격리 HTTP6PASS는 Native/기기 시험과 구분한다.

단일 슬롯의 다른 작업 제한과 장기 미해결의 안전 종료는 이번에 해결하지 않는다. 이를 위해 새 구조를 선행 도입하지 않으며 오류창 취소·조회/화면 이동은 가능하게 한다. 기존 조회만으로 pending을 삭제하거나 자동 새 명령을 보내지 않는다. 누락 캐릭터 자료 준비는 기존 후속이다.

현재 완료 오류/계정 복구 연결은 최종 전체 Flutter2,856PASS·분석0이며 사용자 디바이스 인수는2026-11-10 통과했다. 기존 계정은 문구 수정 전에 복구됐으며 이후에는 표시만 조정했다. 상세 경과는 DEV_LOG, 남은 누락 테스트와 묶음 완료 후속·사용자 지시 보관은 NEXT_WORK를 따른다. dev 병합·배포·Issue 종료는 이번 보관에 포함하지 않는다.

### 계약 생성·원요청 수명

`extract_roster_wire.py`의 고정 hash·출처를 새 기준으로 갱신한 뒤 기존 생성 절차로 betaWireSchema를 재생성한다. 생성물 직접 수선이나 필수조건 완화는 하지 않는다. original schema는 그대로 두고 DTO·명령/journal 버전·검증 snapshot 형식도 변경하지 않는다. response 예시 자체가 변하지 않았으므로 과거 합성 자료의 출처까지 새 자료인 것처럼 치환하지 않는다.

새 요청은 현재 계약의 지원 method/path에서만 query를 만들고, 최초 송신 전 원문·키·query를 고정한다. 저장 원요청은 새로운 BetaContract.query를 거치지 않고 원method/path/query/body/key·snapshot·ACK로 복원한다. 새 query가 선택적이므로 과거 무옵션 요청의 유효성을 유지할 수 있으며 별도 이전/재작성은 필요하지 않다. 새 조회를 통해 과거 토큰을 교체하거나 저장 query에 옵션을 삽입하지 않는다. 확정 거절은 기존 정리 후 사용자 재확인·새 명령, 결과불명은 기존 복구를 따른다.

### 검증과 담당

Native는 실제 betaWire2 DI와 같은 reader/repository/adapter/controller→명령 freeze/저장/송신의 query 연결을 검증한다. 완료 context 조회·확정 재조회·POST가 일치하는지와 업데이트 전 원요청 복원·ACK 복구/거절 정리, 추가 일정5개·계정3개를 직접 보호한다. legacy mock 또는 테스트가 query를 직접 맞춘 사례만으로 완료하지 않는다. 서버 암호화·권한/트랜잭션과 실제 HTTP 일치/불일치는 Backend17신규/영향114PASS 근거이며 Native가 같은 시험을 실행했다고 합산하지 않는다.

만료/stale·완료 기록/M·P/다음주·회원/환경 수명, 연타·응답 유실/저장 실패·성공ACK 후 GET만 복구도 영향 시험에 포함한다. 최종 전체 Flutter 시험/분석과 diff·포맷을 거쳐 Native 연결 완료를 판정하고, 사용자 기기에서 정상 완료/갱신·오류 가독성/복사를 확인한 뒤 BUG-032 인수를 기록한다. 개발 주소를 유지하며 서버 재배포·DB 변경·Penpot·에이전트 기기 조작·운영/APK 게시·Issue 종료는 제외한다. 실행 순서/결과·남은 항목은 NEXT_WORK/DEV_LOG에 둔다.

확장 응답 전체를 실제 스키마로 검증한 뒤 경고·presence·참가 문맥을 분리해 기존 본문 DTO에 연결한다. 새 필수·nullable·union 검증을 생략하거나 알 수 없는 필드를 무조건 버리는 완화는 하지 않는다. `apply/join`에는 없는 교체 actor를 만들지 않으며 기록 조회와 기존 ACK 형태를 보존한다. 구버전 제한 응답은 영향받은 방·실제 주차·세대에 한정해 해석하고 앱 전체 오류로 확대하지 않는다.

캐릭터 원본·설정·기존 참가와 완료 Snapshot은 그대로 보존한다. 누락 숨김은 일반 계정 표시·신규 선택의 투영에 적용한다. 주간 참가 확인·완료·탈퇴가 사용하는 공용 캐릭터 원본을 필터로 잘라내지 않는다. presence는 다른 생명주기/소유/활동/자격 오류와 구분하고 캐시에도 원정대·소유 범위와 revision을 함께 보관한다. 과거 캐시에 presence가 없으면 미확인이며 정상으로 단정하지 않는다. 옵션 없는 응답이 기존 유효 관찰을 지우거나 범위가 달라진 관찰을 승계하지 않도록 반영 조건을 검증한다.

일부 완료 후 변경에서는 **남은 활성 참가 전체(M)**만 새 캐릭터로 바꾸고 **완료·종료분(P)**은 당시 캐릭터·역할·기록으로 보존한다. 후보의 `actor.assignments`, 미리보기의 대상, 최종 명령의 `assignments`·`target_items`가 M과 정확히 일치해야 한다. M/P와 현재 캐릭터·참가 binding도 같은 주차·세대·revision인지 검증하며 기존 엄격한 전체 일치 검사를 없애는 방식으로 해결하지 않는다. 상세 현재 카드·일정·주차 전환·추가 명령도 서버의 같은 활성 참가 해석을 소비하고 완료분 정렬로 현재 캐릭터를 고르지 않는다.

원정대 갱신과 참가 변경은 기존 명령·CAS·원요청 복구를 재사용한다. 새 명령을 만들 때만 지원 query를 확정하며 이미 저장된 요청은 본문·멱등 키·query·검증 Snapshot과 원 ACK를 그대로 재사용한다. ACK 후 재조회 실패 때문에 성공 명령을 다시 실행하거나 새 키로 복제하지 않는다.

| `account_bootstrap.dart`·`ServerCharacterLifecycleClient`·격리 캐시 | presence 전달·저장·범위 검증. `MemberAccountViewModel`의 공용 원본과 일반 표시 분리 |

현재 `MemberWeeklyViewModel`은 계정 section의 `visible`을 소비하므로 일반 목록 숨김을 공용 `visible` 변경으로 바로 구현하면 기존 참가가 사라질 수 있다. 일반 표시 투영을 분리하고 주간 참가/정리 경로를 회귀 보호한다. 경고용 새 서버 호출을 View에 직접 넣지 않는다.

| 계기 | 조회·무효화 범위 |
|---|---|
| 앱 시작·백그라운드 복귀 | 서버 경고 요약. 기존 초기 원정대 갱신 정책은 유지 |
| 목록·상세 진입/주차 선택 | 해당 범위의 필요한 서버 상태. 유효 자료·동일 진행 조회 재사용 |
| 원정대 갱신 성공 | 해당 계정 자료와 본인 전체 요약, 영향받은 방·주차 목록/열린 상세 |
| 변경·완료·탈퇴 성공 | 본인 요약·관련 주간 계정 참가 상태·해당 방/주차 목록·상세 |
| 활동 선택 저장·관리에서 복귀 | 관련 계정/후보·참가 문맥 재확인. 자동 참가 변경 없음 |
| 무변경 상세→목록 복귀 | 기존 캐시 유지. 전체 재조회나 게임 API 수집 추가 없음 |

게임 API 수집은 기존 초기 갱신 또는 사용자가 누른 해당 원정대 새로고침에서만 수행하며 서버 저장 상태 GET과 구분한다. 같은 진행 조회는 공유하되 그 사이 명령이 성공하면 완료 뒤 최신 조회를 이어 수행해 명령 전 응답이 최신 상태를 덮지 않게 한다. 회원·환경·실제 주차·방 세대·참가 관계/요청 세대를 확인해 늦은 응답을 폐기한다. 로그아웃·권한 상실 때 타인 자료를 즉시 무효화하고 리스너는 소유자의 종료 시 해제한다.

WebSocket은 구현하지 않는다. 후속에서는 이벤트를 동일한 범위 무효화·재조회 진입점에 연결할 수 있는지 검토한다. 이번 설계에 polling·구독 계약·전면 상태관리 교체를 추가하지 않는다.

### 구현 순서와 검증 완료 조건

[Backend 보완 결과](https://github.com/heo0328/lostparty-backend/issues/17#issuecomment-6722487011)를 로컬 문서·실제 계약 해시와 Native 기존 소비 경계에 대조해 [수용](https://github.com/heo0328/lostparty-backend/issues/17#issuecomment-6722805010)했고, 후속 [실제 개발서버 반영](https://github.com/heo0328/lostparty-backend/issues/17#issuecomment-6722917497)까지 확인했다. 사용자 확정 순서인 **두 항목 선처리 → Native 결과 대조 → Native 구현**의 선행 대기는 해소됐다. 실행 image ce59926c…/DB0036 유지·실행 소스/계약 일치 보고를 접수했다. 후속 [고정 구현 게시](https://github.com/heo0328/lostparty-backend/issues/17#issuecomment-6722956197)로 caffaf3405a53be941250132a2b50779943b15f6 원격 기준도 확보됐다. 실행/계약은 동일하다는 Backend 인계를 받았다. 이번 확인은 Native 실제 연결/기기 인수 통과가 아니다.

이번주 전체 완료 후 아직 참가하지 않은 다음주 신규 참가/개설에서는 현재 선택이 없으며 완료P를 기본 선택으로 사용하지 않는다. GET context는200/selection=null/permission.allowed=false/reason=CHARACTER_SELECTION_REQUIRED이고, 형식이 유효해도 미선택 context에 임의 선택을 넣은 POST는409/같은 사유다. null·빈 필수값 같은 형식 오류의 기존400과 구분한다. 기존 캐릭터 선택에서 character_id/selected_role을 명시해 새 context를 받고 현재 신규 자격을 검증한다. 이미 N 참가가 있으면 N 자체의 active 선택·자리/noop·누락 경고/수동 교체를 유지하며 C 완료P로 바꾸지 않는다. 이는 Backend와 사용자가 추가 확인한 범위이며 새 제품 미결정은 없다.

Native의 nullable selection·permission/selectionReady와 명령 권한 검사를 재사용한다. CHARACTER_SELECTION_REQUIRED의 안내·확정 거절 분류와 미선택 상태에서 기존 캐릭터 선택으로 들어가는 진입을 연결했다. 새 경로/본문/필수 nullable 변경이나 저장 원요청/원ACK 재작성은 하지 않는다. 혼합 M/P 일정 제출/확인·탈퇴/자동승계·혼합 참가자 후계자·다음주 신규 발급과 rollback/후속 재시도 통과는 Backend의 격리 검증 보고이며 Native 신규 시험/실회원 인수로 확대하지 않는다.

Native 연결은 `BackendApp`에서 presence·경고 opt-in을 명시 활성화한다. 재사용 계정/reader 모듈의 opt-in은 호출자가 정하며 실행 중 구계약 fallback/자동 협상은 없다. `RosterIssueController`가 앱 시작·복귀/초기 갱신·명령 이후 요약을 소유하고, 권한 있는 상세·주차/페이지 캐시는 각 소유자가 관리한다. 명령 중 조회는 dirty 후속 조회로 보완하며 기존 참가 명령의 목록/상세 갱신과 경고 요약 통지를 분리해 중복 무효화를 줄인다. presence는 기존 캐시 payload의 독립 필드에 저장해 DB 구조 변경 없이 원본을 보존하고 동일 원정대/소유/roster/lifecycle 범위의 옵션 생략 응답에서만 이전 관찰을 유지한다.

부분 교체의 후보·미리보기·plan은 같은 binding/M을 대조하고 최종 assignments CAS에는 M만 담는다. plan assignment에는 party_no/slot_no가 없으므로 해당 값은 binding으로 보호하고 실제 본문의 ID/revision/item/round/character/role을 직접 비교한다. 완료P와 raw 목록은 제거하지 않는다. 활동 관리 저장·취소 뒤 기존 sheet에서 후보를 다시 읽고 명시 확정하며, 실제 경로/자동 검증 상태와 사용자 기기 항목은 NEXT_WORK/DEV_LOG를 따른다.

1. 실제 OpenAPI·지원 옵션 조합과 DTO/확장 응답 검증을 연결한다.
2. presence 원본 보존·일반 표시 분리, M/P 교체와 공통 현재 참가 해석을 연결한다.
3. 앱 공통 경고 상태·명령 성공 후 범위 갱신·실패/늦은 응답 처리를 연결한다.
4. 기존 화면 배지·안내·활동 관리 왕복을 실제 Router/DI 경로에 연결한다.
5. 아래 경계 자동 검증 후 전체 `flutter test`·`flutter analyze`를 수행하고 사용자에게 기기 확인 항목을 전달한다. 중간 단계마다 같은 전체 시험을 반복하지 않는다.

| 보호 경계 | 자동 검증/담당 |
|---|---|
| 주차별 독립 권한·정상 0/미조회/권한 없음 | Backend가 최종 공개 권한을 검증. Native는 DTO·표시 범위와 권한 상실 후 잔존 정보 방지 검증 |

| 늦은 응답·활동 선택 왕복 | Native가 회원/환경/주차/관계 전환, 명령 중 조회 완료, 낡은 후보/확정 폐기 검증. 서버 최종 CAS는 유지 |

사용자 기기 확인은 구현 후 기존 정상 참가/신청·완료·탈퇴, 양 주차 경고와 권한, 해당 원정대 갱신/지속 누락 시 변경, 일부 완료 기록 보존, 활동 관리 저장·취소 후 원래 방/주차 복귀에 한정해 안내한다. 설치·조작은 사용자가 수행한다. 현재는 이 시험을 실행하지 않았다. 기존 내부23PASS·후속 격리 HTTP7PASS·과거 Native 후보 파서 결과와 이번 설계 검토를 신규 Native 기능 통과로 합산하지 않는다.

이번 설계 완료 기준은 사용자 확정 UX·실제 계약·일반 앱 연결 지점·자료/명령 수명·회귀 책임·후속 순서가 기록되고 이전 서버 대기가 최신화되는 것이다. 일반 앱 DI/Router→조회/명령→성공 후 갱신 연결과 자동 검증은 확인했으며 실제 회원 명령·기기 인수는 NEXT_WORK의 사용자 확인 단계로 남긴다.

## 사용자 최신 확정 — 원정대 인증과 구성 목록

원정대 구성은 로스트아크 API 캐릭터 목록을 기준으로 판단하며 별도 외부 동일성/영구세대 증거를 일상 갱신의 필수 조건으로 요구하지 않는다. A회원이 C로 인증한 B원정대는 C의 개명·삭제와 무관하게 인증/기존 소유를 유지한다. 인증 이력/대상과 현재 조회 기준을 분리하고 B의 현재 캐릭터로 조회 기준을 복구한다. 정상 조회 모두에 같은 서버/이름이 보이는 사이의 미관측 삭제·재생성은 API 한계로 구분할 수 없으며 현재 목록 관찰을 유지한다. 실제 누락/개명·이름재사용이 관찰되면 아래 기존 새ID/사용차단·이력 정책을 적용하고 타회원/종료ID의 권한을 승계하지 않는다. 실패/부분 목록은 소멸/원정대 인증 취소 근거가 아니다. [76번째](https://github.com/heo0328/lostparty-backend/issues/8#issuecomment-6212824900)가 아래 과거 ‘본인 일상 갱신에도 추가 연결 근거 필수’ 설명의 해당 범위를 정정한다. 실퇴역/삭제 기능의 구현 완료를 뜻하지 않는다.


최신 인계(2026-10-15): Backend L1a[6186038066](https://github.com/heo0328/lostparty-backend/issues/8#issuecomment-6186038066)/L1b[6186143574](https://github.com/heo0328/lostparty-backend/issues/8#issuecomment-6186143574) 구현·원본게시 완료. 실제DB/실행API 미적용·live증거보류는유지한다. Flutter는 [계약30](30-scoped-storage-write-contract.md)의 S1 격리 캐시 구현/전체1311PASS·분석0과 [결과6187076006](https://github.com/heo0328/lostparty-backend/issues/8#issuecomment-6187076006) 회신을 마쳤으며 다음은 S2 조회 adapter다. 아래 미회신/설계전용은 해당 시점의 이력이다.

## 최신 L1 수용·착수 요청 (2026-10-15)

사용자 진행 승인으로 공식 조사/보완과 실제 Flutter 연결 구조를 대조해 [연결 계약29](29-scoped-character-identity-design.md)를 작성하고 [L1a/L1b 착수 요청6185091368](https://github.com/heo0328/lostparty-backend/issues/8#issuecomment-6185091368)을 게시·재조회했다. 기존 ID/NameClaim·차단/캐시/fencing 기반과 V2 현재 상태/이력 GET의 코드·격리 시험·원격 게시만 수용한다. 2026-10-15. 현재는 사용자 정책 확정과 기술 검토 단계다. 기능 코드/DDL/실자료·서버는 변경하지 않았다. 전체 빌드 자동 갱신의 선행 설계이며, 원정대 정합성과 미래 파티 연결 계약을 함께 구분한다. 기존 계약13의 자동 이름 추적 제외/누락 자료 보존 정책을 아래 확정 범위에서 새로 설계한다. 자동 개명 추적은 도입하지 않는다.

## 1. 사용자 확정 정책

- 인증된 원정대의 정상적인 전체 조회에서 새 이름이 나타나면 새로운 내 캐릭터로 등록한다. 신규 활동/대표 자동 선택이나 파티 참가를 뜻하지 않는다.
- 정상적인 전체 조회에서 사라짐이 확인된 기존 캐릭터는 서버·이름·직업·마지막 전투력·아이템레벨만 소멸 이력으로 남기고 운영 캐릭터 자료를 삭제한다. 실패/부분 응답만으로 삭제하지 않는다.
- A→B 개명도 A 소멸 이력+기존 자료 정리, B 신규 등록이다. A의 dealer/support 빌드·선호 역할·표시/주간 개인설정을 B에 복사하지 않는다. A와 B의 동일 인물/캐릭터 관계를 자동 확정하지 않는다.
- 기존 파티·완료 이력은 당시 Snapshot을 보존한다. 개인 캐릭터 자료 삭제로 과거 공동 기록을 연쇄 삭제하지 않는다. 활동/대표를 잃으면 재선택이 필요하다.
- 미완료 파티에서는 기존 회원의 자리와 참가 당시 정보를 유지한다. 파티원에게 기존 캐릭터 확인 필요 경고를 표시하고, 본인이 유효한 캐릭터로 명시 변경하거나 탈퇴한다. 원정대 변화로 자동 교체/탈퇴시키지 않는다.
- 이상 감지된 이전 캐릭터는 소멸 확정/삭제를 기다리지 않고 신규 파티 생성·참가 신청/즉시 참가·승인·참가 캐릭터 변경 대상·그룹 생성/가입/선택에 사용할 수 없게 한다. 기존 참가의 표시/정리 권한과 새 사용 자격을 구분한다. 새 이름을 포함해 레이드 조건을 만족하는 본인의 다른 캐릭터로 참가 변경할 수 있다.
- 다른 원정대가 옛 이름을 사용하는 경우도 신규 캐릭터다. 옛 캐릭터 ID·회원·참가 자리·완료/참가 점유를 승계하지 않는다.

### 이상 감지와 확정 소멸의 두 단계

사용자 최신 설명에 따라 사용 중단과 삭제를 별도 단계로 둔다. 캐릭터별 누락 등 서버가 근거를 갖고 이상을 감지한 상태(suspect/확인 필요)는 즉시 새 사용을 차단하고 미완료 파티의 모든 참가자에게 경고를 표시한다. 단순 네트워크/조회 실패만으로 특정 캐릭터의 이상이나 소멸을 확정하지 않는다. 전체성 증거 부족은 자료 삭제 보류의 근거이며, 이미 감지한 캐릭터의 신규 사용을 허용하는 근거가 아니다.

이후 정상 전체 조회의 소멸 확정이면 간략 이력 후 개인자료를 정리하고 이전 ID를 종료한다. 확정 전 이상이 정당한 재조회로 해소됐을 때만 서버가 현재 귀속/생명주기를 검증해 사용 자격을 복원하는 안이다. 이미 종료한 ID는 이름 재등장만으로 복구하지 않는다. 정확한 감지/해소 증거와 DTO는 Backend 계약 검토에서 정의한다.

화면 후보의 숨김/비활성만으로 차단을 구현하지 않는다. 서버 최종 쓰기에서 현재 회원·원정대 귀속·캐릭터 생명주기/이상 상태와 revision을 재검증해 이미 열어 둔 화면·오래된 신청·동시 승인에서도 차단한다. 기존 참가자의 명시 변경/탈퇴는 본인 membership을 근거로 계속 허용하며, 이상 캐릭터를 새 대상에 다시 넣는 것은 거절한다. 이상 상태에는 새 자동 빌드 저장도 보류한다.

## 3. ID·소멸 이력·삭제 책임

표시 이력의 제품 데이터는 사용자 지정 다섯 값이다. 구현에는 이력 고유 ID·회원/원정대 귀속·이전 캐릭터 ID·소멸 확인 시각·관찰 revision 같은 최소 연결 메타데이터도 필요하다. 이름만으로 이력 소유자나 파티를 찾지 않는다. 마지막 전투력/레벨은 마지막 정상 확인값을 쓰며 없으면 null, 실패를0으로 기록하지 않는다. 전투력의 역할별 대표값 선택은 기존 선호 역할 표시 정책을 재사용하고 양 역할 원문을 이력에 복사하지 않는 안이다. 물리 저장소·보관기간·API와 정확한 DTO는 Backend 검토 전 미확정이다.

삭제 대상은 운영 목록·개인 빌드 raw JSON/역할별 Snapshot·선호 역할·캐릭터별 표시/주간 설정이다. 소멸 이력과 파티/완료 당시 Snapshot은 보존한다. 서버 FK/참가 참조를 유지할 때는 재사용 불가한 이전 ID의 최소 소멸 표식이 필요하며, 기존 전체 캐릭터 자료를 계속 저장하는 것과 구분한다. 물리 삭제/최소 참조 표식의 구현은 Backend가 소유한다.

이름은 현재 조회 주소일 뿐 영구 신원키가 아니다. 이전 이름이 다른 원정대에 나타나도 옛 canonical ID/account/owner를 새 캐릭터로 바꾸지 않는다. 소멸을 이미 확인한 뒤 같은 이름이 원래 원정대에 재등장하더라도 새 생명주기/새 ID로 다루는 안이며, 이력과 완료 기록을 되살리지 않는다. 관찰 사이에 삭제·재생성돼 이름/원정대가 같으면 현재 입력만으로 구분할 수 없다는 한계는 별도 기록한다.

## 4. 정상 전체 조회와 원자 변경 계획

1. 본인 세션과 인증된 원정대 소유/등록 revision을 확정한다. 조회/캐시/미인증 preview 성공으로 인증을 만들어 주지 않는다.
2. 해당 원정대 전체 페이지·동일 roster revision·중복/식별·원정대 소속·provider 완전성/신선도 검증을 통과한 서버 결과만 reconciliation 입력으로 받는다. Flutter 캐시 GET의 전체 페이지 수집은 provider 원본 전체성 증거와 다르다.
3. 추가/유지/소멸 후보를 계산한다. 증거 미확정 후보는 확인 필요로 보존하고 삭제/이름 재배정하지 않는다. 원정대별 변경 단위로 실패를 격리한다.
4. 동일 transaction 또는 검증 가능한 원자 계획에서 소멸 이력 중복 방지 → 개인 종속 자료 정리 → 활동/대표 재구성 상태 → 이름 현 점유 해제/신규 ID → revision 갱신을 처리한다. 중간 실패는 이전 상태를 보존한다. 서버/기기 사이를 하나의 DB transaction이라고 표현하지 않으며, 서버 확정 결과에 따라 기기 반영을 재시도 가능하게 만든다.
5. 파티는 별도 참조/표시 상태 갱신으로 기존 ID가 사용 불가임을 알린다. 대량 파티 후처리가 지연돼도 변경/승인 등 최종 명령은 원본 소멸 상태를 재검증한다. 정확한 전달/읽기 계약은 Backend 파티 설계 때 확정한다.
6. 오래된 summary/Armory/키/회원/이전 revision의 결과가 삭제한 ID를 복원하거나 새 ID에 저장되지 않게 요청별 유효성과 저장 직전 상태를 확인한다. 같은 명령 replay는 같은 소멸 사건/새 ID를 반환하고 이력을 중복 생성하지 않는다.

이전 조회 기준 이름이 사라지면 정상적으로 확인 가능한 같은 원정대 캐릭터로 조회 기준을 복구하거나 사용자에게 새 조회 이름을 받는다. 추측한 다른 원정대의 이름으로 자동 전환하지 않는다. 현재 live 증거 공백 때문에 이 설계만으로 삭제 기능 구현에 착수하지 않는다.

## 5. 진행 중 파티·신청·이름 재사용

예: 회원 U의 원정대 A/캐릭터 ID C1/이름 N으로 참가한 파티 P가 있다. N의 이상이 감지되면 곧바로 신규 사용을 차단하고, P는 U의 자리·원래 Snapshot과 함께 모든 참가자에게 `기존 캐릭터 확인 필요`를 표시한다. 소멸 확정 후에는 C1의 개인자료를 정리하되 P의 참가는 유지한다. 원정대 A의 새 이름 M은 새 ID C2다. 원정대 B의 다른 회원 V가 이름 N을 사용해도 새 ID C3이며 P를 읽거나 조작할 권한·자리를 얻지 않는다.

- 검증 없이 N→M을 개명으로 표시하지 않는다. U는 C2뿐 아니라 본·부계정 전체의 현재 유효한 본인 캐릭터 중 해당 레이드 조건을 만족하는 캐릭터를 선택해 변경할 수 있다. 정식 변경 성공 후 파티의 현재 표시와 변경 내역을 갱신한다. 그 전에는 원래 N과 확인 필요 상태를 표시한다.
- 파티원 모두가 조회할 수 있는 경고/변경 내역이 필요하다. 외부 알림/푸시 시스템 신설은 포함하지 않는다. 이름뿐 아니라 역할·수치/검증 요약은 새로 선택한 역할 Snapshot과 기존 정책으로 검증한다.
- 기존 회원 U만 자신의 참가 변경/탈퇴를 요청한다. 회원V가 같은 이름N을 얻었다는 이유로 U의 자리·권한·활성 점유·완료 기록에 접근하지 못한다. 최종 서버 검증은 user/character/account/lifecycle·소유 revision을 사용한다.
- 원래 참가 C1과 점유는 이름 재사용만으로 삭제/새 ID에 이전하지 않는다. U의 유효한 C2 변경 또는 탈퇴가 성공할 때 이전 점유와 새 점유/slot/revision·표시 Snapshot·변경 내역을 원자적으로 처리한다. 기존 파티 구성·역할·레벨/전투력·일정/레이드 점유 정책을 재사용한다.
- C1이 소멸했더라도 기존 참가자U가 변경/탈퇴할 수 있어야 한다. 기존 자리의 본인 여부와 기존 참가 revision을 검사하되, 이미 사라진 C1의 현재 소유 인증 성공을 탈퇴의 선행 조건으로 요구해 복구를 막지 않는다. 새 C2는 현재 유효한 본인 소유/참가 조건을 모두 검증한다.
- 파티장인 경우에도 자동 해산/승계하지 않는다. 명시적 변경/탈퇴에서 기존 승계·마지막1인 해산 정책을 적용한다. 완료/변경과 누락이 경합하면 한 revision 순서만 성공하고 완료된 Snapshot은 소급 변경하지 않는다.
- 승인 대기 신청의 C1은 이상 감지 시점부터 새 승인 불가다. 기존 신청 Snapshot을 다른 이름 보유자의 현재 정보로 갱신하지 않는다. 완료/취소/지난 회차 기록은 원래 Snapshot 유지, 반복방 다음 회차 선택은 유효한 새 캐릭터로 재검증한다.

현재 이름을 최신 프로필에서 재조회해 파티 Snapshot을 덮는 방식, 이름으로 party/member/raidState를 찾는 방식, 옛 canonical 행의 account/owner 변경으로 신규 이름 재사용을 처리하는 방식은 채택하지 않는다.

## 6. 최소 검증·다음 단위

- 정상 전체 응답에서 추가1/소멸1 → 이력1회·개인자료 정리·신규 ID/빈 빌드·대표 재구성. replay는 같은 결과, 중도 실패는 rollback.
- 실패/429/빈·부분 응답/페이지 revision 충돌/조회 기준404 → 기존 캐릭터·빌드·이력 불변. 단순200 비어있지 않은 부분 목록도 전체성 증거가 없으면 삭제0.
- A의 N→M 뒤 B가 N 사용: 양측 조회 순서(A먼저/B먼저), 같은 이름 동시 신규/재사용·오래된 cache/lease/replay에서 원정대/owner/파티 귀속이 섞이지 않음. 미확정이면 충돌/확인 필요로 보류하고 자동 이전 금지.
- 소멸 뒤 같은 이름 재등장·늦은 summary/Armory/다른회원·키교체 → 이전 ID 재활성/개인자료 부활/새 ID에 옛 결과 저장 없음. 동일 이름 동시/반복 관찰의 한계는 구분.
- 이상 감지 직후/소멸 정리 전에도 생성·신청·승인·즉시 참가·교체 대상·그룹 명령을 서버에서 거절한다. 감지 전 시작한 요청의 최종 commit도 새 상태를 검사한다. 조회 실패만으로 소멸 처리하지 않으며, 확정 전 해소와 확정 후 이름 재등장을 구분한다.
- 미완료8인 대표 파티에 한 명 소멸 → 자리/owner/Snapshot 유지·경고. 유효한 본인 교체/탈퇴만 성공, 타 회원/같은 이름 재사용자는 거절. 파티장/마지막1인/완료 경합은 상태 전이가 달라 최소 별도 사례.
- 삭제 직접 종속 build/weekly 고아0, 소멸 이력과 과거 공동 Snapshot 보존. 같은 회원 다른 기기 반영/replay·서버 확정 후 로컬 실패 복구의 인수 범위 구분.

Issue8에서 검토 요청한 범위는 (1) live 전체성/누락 증거 획득 가능성과 정책 (2) 현재 이름 점유·생명주기/이력·기존 FK/소유 추론 변경 (3) 정확한 원자 명령·DTO/멱등/로컬 반영 계약이다. 미래 파티 표시/명령 불변식은 요구로 인계하되 미구현 파티 전체를 이번 요청에서 함께 구현하지 않는다. 계약 회신 후 roster 서버 단위 → Flutter 정리/이력/조회 기준 복구 → 자동 빌드 연결 순서로 구현 단위를 확정한다.
