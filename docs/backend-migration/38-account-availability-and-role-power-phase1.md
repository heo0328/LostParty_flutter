# 이전 축소 1차 계획 기록 — 내 계정 시간 설정·역할별 최소 전투력

## 최신 범위 정정 — 통합 개발 목표로 전환

사용자가 이후 ‘그냥 한 번에 개발’ 방향으로 바꾸고 자동 조율/점유의 운영 질문에 답했다. **이 문서의 아래 기존 1차 축소 계획은 당시 결정 이력이며 최신 실행 범위가 아니다.** 현재는 내 계정·모집 조건·수동/조율 일정·회원 시간 점유·다일/다중 레이드까지 통합 개발 목표를 두고 설계부터 마무리한다. 설계/구현/시험은 내부 단계로 나누며, 모든 기능을 한 번에 코드 변경하거나 미결정 상태에서 구현하라는 의미로 확대하지 않는다. 채택/새 제안/미정은 [설계37 §10](37-raid-scheduling-and-multi-raid-planning.md#10-통합-개발-방향과-운영-질문-응답)을 따른다. 미래 실행을 제외했던 이전 #13 회신은 정정 대상이다.

## 아래는 폐기된 축소 범위의 변경 이력

현재 실행 계획은 NEXT_WORK와 설계37 §24이며 이 아래 제외 목록/완료 조건을 최신 지시로 사용하지 않는다.

2026-10-19 당시 사용자 범위 결정·후속 의미 정정 반영. 당시 상태: **1차 범위에는 확장 경계의 설계·확정이 필수로 포함됨. 경계 미확정·코드 미착수**. 상세 아이디어/변경 이력은 [설계37](37-raid-scheduling-and-multi-raid-planning.md)에 보존한다. 해당 내용을 생략하거나 요구 폐기로 간주하지 않는다.

## 1. 이번 결정

큰 경계는 지금 함께 설계 제안을 받아 대조하고 **1차 개발 안에서 확정한다**. 제안을 받는 것만으로 해당 단계를 완료하거나 경계 미정 상태에서 화면/API 구현을 먼저 시작하지 않는다. 시간 조율/다중 레이드의 실행 기능은 후속이지만 그 기능을 나중에 붙일 수 있는 데이터·수명·명령 경계의 확정은 이번 포함 범위다. 이번 1차 목표는 다음과 같다.

| 포함 | 범위 |
|---|---|
| 확장 경계 설계·확정(구현 선행) | 개인 시간표/방 참가/실제 일정·회원 시간 점유, 모집방/레이드별 항목, 참가·탈퇴·완료와 예약의 명령/원자성, 호환·확장 연결 지점을 제안·대조해 확정 |
| 내 계정 시간 설정 | 기존 시안의 위치/라벤더 카드·기본 접힘, 저장/취소·기존 값 편집, 요일 복수구간/+−, 익일 종료·5분 휠 |
| 모집 생성 | 기존 레이드/난이도·제목·숙련도·참가 흐름 유지, 최소 전투력 동시 적용/딜러·서포터 개별 입력 |
| 모집 상세 | 기존 카드·조작 유지, 역할별 최소 전투력 조건을 구분해 표시·소비 |

이번에 추가하지 않는 항목: 방의 새 수동 일정 입력/요일별 일정·동일시간 적용, 참가자 시간 조율/임계치 자동 출발확정·회원시간 점유/타임테이블 API, 시간 필터·교집합/실시간 갱신, 다일 재도전·다중 레이드/방 병합·묶음 전체 탈퇴, 새로운 그룹명/공개범위 왕복 UI. 기존부터 제공된 기능을 제거하는 의미는 아니다. 그룹 탈퇴자 진행 허용·비그룹 배지/공개범위 왕복은 확정 요구 이력으로 보존하고 이후 별도 구간에 반영한다. 기존 서버 활성화/필수 권한 계약과 충돌하면 해당 지점만 대조하며 무관한 신규 UI로 확대하지 않는다.

완료된 자동 갱신 결과의 X는 기존 승인된 내 계정 시안 요구로 보존한다. 시간표 저장/취소와 구분하며, 닫기 수명·실패 재시도 진입을 먼저 명시한 소규모 하위 항목으로 처리한다. 자동 갱신·저장 명령을 X로 취소/삭제하지 않는다.

## 2. 내 계정 편집 계약

- 로그인·인증 원정대 보유 조건과 시안 위치(결과창과 메인 계정 사이), 기존 회원/환경 scope를 따른다. 등록/인증 변화가 개인 시간표를 삭제하는 명령은 아니다.
- 펼침 때 저장된 시간표로 초안을 만들고 한 번에 편집한다. 저장 성공 후 접힘, 취소는 저장값 보존/초안 폐기 후 접힘. 저장 실패/충돌은 성공으로 닫지 않고 복구 가능한 초안을 유지한다.
- 수~화 다중 선택, 같은 요일 복수 시간. 첫 행 오른쪽 +, 추가 행 요일 자리 빨간 −. 잘못 추가한 행은 저장 전 제거 가능하다. 마지막 구간 제거/요일 해제 시 초안 처리와 재선택 복원 여부는 작은 상세 결정이다.
- 24시간제·5분 단위, 같은 날/다음 날을 명시한다. 휠 방식은 Flutter 기본 Cupertino 계열로 구현 가능하다. 같은 시각0시간/24시간 의미·구간 수 상한·겹침/인접 구간 정규화·KST 저장/표시는 Backend 제안과 함께 고정한다. Figma v1의30분 안내는 이번에 사용하지 않는다.
- 회원 서버 저장·새 실행/다른 기기 복원을 목표로 계약을 요청한다. 아직 API가 있다는 가정이나 최종 SQL/DTO 확정은 하지 않는다. 임시 기기 전용 저장을 최종 회원 저장처럼 제공하지 않는다.
- 1차 시간표는 개인 가능 시간일 뿐이다. 저장만으로 방 예약/가입 가능 보장·캐릭터 주간 점유·기존 방 일정 변경을 만들지 않는다. 이 구분을 앱 장문 경고로 늘어놓지 않는다.

## 3. 역할별 최소 전투력 계약

- 동시 적용 체크 시 기존 입력 하나, 해제 시 기존 자리의 딜러 입력과 오른쪽 서포터 입력. 두 값 모두 빈 상태를 표현할 수 있어야 한다. 기존 단일 입력값이 있는 자료를 임의 의미로 이행하지 않고 호환 정책을 확인한다.
- 동시 적용의 최초 체크는 기존 UX 보존을 위한 추천이며 사용자 명시 확정 전이다. 공통↔개별 전환 초안 보존/서로 다른 두 값을 하나로 바꿀 때 선택 기준은 구현 전 짧게 고정한다.
- 서버 저장은 선택 역할별 조건을 구분하고 상세에도 동일하게 표시한다. 참가/승인/직접가입 시 선택 참가 역할의 문턱만 검사한다. 다른 역할값/누락값0/화면 정수 반올림으로 판정하지 않는다.
- 현재 P1은 클라이언트 분석 표시 자료다. 역할별 비교값의 출처/신뢰·관측시각/stale/null/위조 검증 근거는 Backend와 확인해야 한다. ‘입력/표시 가능’과 ‘서버에서 참가 제한을 유효하게 강제함’은 다른 완료 단계다. 저장·표시만 구현해 참가 제한 완성으로 보고하지 않는다.
- 기존 모집 UI/기능을 재사용하되 실행 Backend의 모집 API/권한·지원 상태는 실제 Router/DI까지 확인해야 한다. 후보 구현 존재만으로 연결 완료로 간주하지 않는다.

## 4. 1차에서 반드시 설계·확정할 확장 경계

Backend에 **설계 제안**을 요청하고 Flutter 대조·필요한 사용자 결정 후 1차 기준으로 확정한다. 장래 실행 기능용 테이블/공통 프레임워크를 일괄 구현하는 요청은 아니다. 제안 수신·검토 대기와 경계 확정 완료를 구분한다.

1. 개인 가능 시간표와 방 참가, 확정 날짜 일정·회원 시간 점유의 독립 수명. 개인 시간표 수정이 미래 확정 예약을 자동 변경하지 않는 연결 방식.
2. 모집방과 레이드별 진행 항목의 구분. 현재 단일 레이드 API를 유지하며 묶음으로 확장 가능한 식별자/호환 방식과 현재 구조의 제약.
3. 참가/승인/탈퇴/완료·추후 일정 확정의 서버 명령/transaction 경계. 현재 캐릭터 raid/cycle 점유와 미래 회원 시간 점유를 중복 구현 없이 검사할 지점.
4. 묶음의 한도 계산·공통 참가/전체 탈퇴·부분 완료 정책 중 지금 고정해야 하는 것과 나중 결정 가능한 것. 추천안을 확정으로 승격하지 않는다.
5. 현 F1/F2/F3 후보 중 1차 개발에 재사용 가능한 부분과 수정할 부분, 개인 시간표 최소 GET/저장 계약, 역할별 조건/판정 신뢰 원천의 대안 및 미해결 항목.

산출물: 작은 데이터 관계도/명령 흐름, 1차 API·권한·버전/멱등·저장 수명·nullable 예시, 후속 확장 시 변경 범위/위험·대안 비교, 최소 회귀·인계 조건. 제안 수신 뒤 Flutter와 대조하며 사용자 제품 결정이 필요한 분기만 묻는다. 이 요청이 배포/DB migration/서버 활성화 승인은 아니다.

### 경계 확정 완료 조건

- 무엇이 회원/방/레이드 항목/실제 날짜 일정의 식별자이며 각 자료의 소유자·저장 수명·권한이 무엇인지 문서로 정한다.
- 개인 가능 시간 저장·방 참가·예약 확정을 분리하고, 나중 시간 점유 검사를 호출할 명령/원자성 경로를 정한다. 단순히 ‘추후 확장 가능’이라고 쓰는 것은 완료가 아니다.
- 단일 레이드에서 묶음으로 확장할 관계·기존 API/자료 호환 방법·완료/탈퇴 영향과 미정 제품 정책의 고립 지점을 명시한다. 지금 결정이 필수인 항목은 후속으로 넘기지 않는다.
- 합의 결과를 실제 1차 모델·Repository/서버 명령·Router/DI 소비 계획과 대조해, 구현이 경계를 거스르지 않는지 확인한다. 경계에 필요한 최소 구조는 1차 구현에 반영한다.
- 경계에 영향을 주는 미해결 항목이 남으면 해당 구현은 시작하지 않는다. 미래 알고리즘/화면의 세부 정책 중 1차 구조를 바꾸지 않는 부분만 후속으로 남길 수 있다.

## 5. 실행 순서·검증

1. 현재 요구를 보존하고 1차 범위를 문서/이슈에 공유한다(이번 구간).
2. Backend 저장·조회/역할판정 계약과 확장 제안을 수신해 관련 코드·권한/Router/DI·구자료와 대조하고 **위 경계 확정 완료 조건을 충족한다**. 그 다음 내 계정과 전투력을 작은 구현 구간으로 진행한다. 개별 저장 계약 준비만으로 경계 확정을 건너뛰지 않는다.
3. 내 계정 편집 연결과 최소 회귀를 완성한 뒤 관련 표적 시험/분석을 모아 실행한다. 구간마다 전체 Flutter 시험은 하지 않는다. 정상 UI는 사용자 디바이스 확인 한 묶음으로 전달한다.
4. 모집 생성·상세 전투력 입력/표시와 실제 서버 제한까지 연결하고 직접 영향 정책/권한 경계를 검증한다. 구현 준비 전에 해당 호출자/저장 경로에 맞는 정확한 시험 파일을 NEXT_WORK에 기록한다.
5. 사용자 인수·미확인을 분리해 기록하고 해당 단계 승인에 따라 커밋/dev 통합한다. 자동 조율/다중 레이드 미구현을 이유로 완료한 1차를 무기한 열지 않는다.

회귀 보호: 기존 회원/환경별 복원·로그인 후 화면 재구성·원정대 카드/왕관·활동/주간 설정·갱신 수명 유지, 편집 중 회원 변경/늦은 저장 응답·서버 충돌/응답 유실·다른 기기 수정, 전투력 무조건/딜러만/서포터만/동시 및 역할 불일치/누락 원천·기존 단일 문턱 자료. 자동 테스트는 이런 경계와 권한에 집중하고 정상 화면 조작을 무분별하게 중복 시험하지 않는다.

**현재 완료:** 요구 보관·1차 범위/제안 요청 정리. **1차 미완료:** 확장 경계 설계·합의·확정, Backend 고정 계약, 경계를 반영한 코드 구현·실기기 검증. 경계 설계는 별도 참고 작업이 아니라 1차 완료 조건이다. 문서만 바뀌므로 Flutter 시험/분석은 실행하지 않는다.
