# 사용자별 이용 한도·방 이용 제한 설계

기준: 2026-10-17 사용자 요청. **설계·협업 인계 단계이며 미구현**. 결제·구독·광고 도입은 이번 범위가 아니다. 기존 #12 그룹 및 #13 모집/파티 계약에 추가할 공통 정책이다.

## 확정 요구

2주차/활성방 집계 기준(2026-10-26 사용자 명확화): 한도10은 서버 기준 이번주/다음주 '참가 중' 목록에서 확인하고 이용할 수 있는 **현재 활성 참가방**의 제한이다. 단순히 미종료 persistent membership의 개수가 아니다. 같은 room C/N·생성자/참가 중복은1개, 어느 한 주차에 현재 유효한 참가방이 남으면 포함한다. 양 주차 모두 현재 활성 참가대상이 없으면 과거 관계/기록만으로 집계하지 않는다. 과거 주차 review_required/미종료 관계만 남은 항목도 현재 이용 가능한 참가방이 없다면 제외한다. [사용자 확정 전달](https://github.com/heo0328/lostparty-backend/issues/13#issuecomment-6410274718). 이전의 '지속관계가 남으면 무조건 한도 유지' 해석은 적용하지 않는다.

- 앱 사용자 UUID별로 그룹 정원, 생성·참가 그룹 수, 레이드 모집 관련 개수의 적용 한도를 서버 계정 데이터로 관리한다. 캐릭터·원정대·디바이스별 한도가 아니다. 새 기기/재로그인에도 같은 서버 기준을 사용한다.
- 기본 그룹 정원은 15명, 사용자 현재 가입 그룹 수는 생성 그룹을 포함해 5개다. 정원에는 그룹장/생성자를 포함한다. 종료된 가입은 제외한다. 이는 기본값이며 모든 사용자에게 영구 고정할 상수가 아니다.
- 차후 구독·광고 등으로 개인별 한도를 늘릴 수 있는 경계를 준비한다. 상품/가격/결제 SDK·영수증·광고 보상·유료 안내 화면은 구현하지 않는다.
- 한도 감소 시 기존 회원 자리·방·과거 완료 기록을 자동 삭제하지 않는다. 초과 사유와 한도 차원을 구분한다. 레이드 참가 수 초과는 해당 회원이 직접 참가한 공개/그룹 레이드에 적용한다. 그룹 가입 수 문제만으로 기존 그룹 운영을 정지하지 않는다.
- 제한 방은 다른 회원도 추가 모집/참가 확정, 캐릭터 변경, 완료 처리 및 다음 주도 함께하기를 통한 계속 진행이 차단된다. 반복방의 참가 관계를 보존하면서 한도를 우회할 수 없어야 한다.
- 조회와 제한 원인 확인, 본인 탈퇴 및 권한 있는 그룹장/파티장의 해당 회원 추방은 가능해야 한다. 탈퇴·추방은 기존 역할/권한과 기록 보존을 지키며 제한 해소 경로로 제공한다. 새로 광범위한 관리 권한을 부여하지 않는다.

## 사용자 추가 확정

1. 그룹 정원은 **현재 그룹장의 계정 한도**를 적용한다. 그룹장 변경 시 새 그룹장 한도로 재검사한다. 기본 정원 15명.
2. 레이드 한도는 **생성·참가를 합산해 현재 참가 중 목록에서 확인·이용할 수 있는 활성 모집방 수, 기본10개**다. 사용자 UUID 기준이며 생성/참가 및 같은 모집방의 C/N은 중복 계산하지 않는다. 다음주만 실제 참가 중인 활성방도 포함한다. 과거 주차의 미종료 관계만 있거나 현재 활성 참가대상이 없는 기록/관계 전용 항목은 제외한다. 완료/탈퇴/해산 후에도 반대 주차가 활성 참가방이면 해당 방1개는 유지하며, 양쪽 모두 집계 대상이 아니면 제외한다. 과거 이력/관계의 삭제·강제 종료 없이 집계 의미를 바로잡는다.
3. **개인 레이드 수 초과:** A가 직접 참가한 공개/그룹 레이드 모두 진행 제한이다. A의 그룹장/그룹원 관계만으로 기존 그룹 운영이나 A가 미참가한 그룹 연결방까지 막지 않는다. 일부 유지 방 선택은 없다. 탈퇴/추방/한도 해소 후 다른 원인이 없으면 해제한다.
4. **개인 가입 그룹 수:** 정확히5/5이면 기존 이용·그룹전용 레이드는 정상이며 새 그룹 생성/가입만 거절한다. 6/5처럼 초과하면 B의 새 그룹 생성/가입 및 그룹전용 레이드 새 생성/참가를 막고, B가 직접 참가한 기존 그룹전용 레이드 전체 진행도 차단한다. B가 참가하지 않은 그룹전용방/공개 레이드와 기존 그룹 운영에는 이 개인 초과를 전파하지 않는다. B의 탈퇴/추방/한도 해소 후 다른 원인이 없으면 해제한다.
5. **그룹 자체 정원 초과 — 명시적 상속 예외:** 현재 그룹장 한도 감소 등으로18/15이면 기존 그룹 운영·초과 안내는 유지하고 새 회원 확정을 막는다. 권한 있는 탈퇴/추방/그룹장 이전은 허용한다. **그 그룹의 모든 현재 그룹전용 레이드**는 해당 초과 원인 회원이 직접 참가했는지와 무관하게 진행 정지한다. 그룹원들의 일반 공개 레이드나 다른 그룹의 레이드로 전파하지 않는다. 인원 정리/한도 회복/유효한 그룹장 이전 후 현재 인원이 현재 정원 이내가 되고 다른 제한 원인이 없으면 해제한다. 앞선 ‘그룹 정원도 연결 레이드에 전파하지 않음’ 추천은 사용자 설명으로 폐기했다.
6. 공개6개+그룹전용4개=10/10이면 기존 레이드는 정상, 11번째 생성/참가 확정은 거절한다. 같은 방은1개, 생성자는 참가와 중복 집계하지 않는다. 정원15/15도 기존 운영 정상/신규 회원 확정만 거절한다. 한도 도달과 초과를 모든 차원에서 구분한다.

## 확정 영향표

| 원인 | 기존 그룹 운영 | 제한 레이드 | 영향 없는 레이드 |
|---|---|---|---|
| 개인 레이드 수 초과 | 유지 | 당사자가 직접 참가한 모든 공개/그룹 레이드 | 당사자 미참가 방 |
| 개인 가입 그룹 수 초과 | 유지 | 당사자가 직접 참가한 그룹전용 레이드 | 일반 공개 레이드/당사자 미참가 방 |
| 그룹 자체 정원 초과 | 유지·새 회원 확정 차단 | 그 그룹의 모든 그룹전용 레이드 | 그룹원들의 일반 공개/다른 그룹 레이드 |

제한 레이드의 진행 정지는 다른 회원의 추가 모집/참가 확정·캐릭터 변경·완료·다음주 계속 진행도 포함한다. 조회/탈퇴/권한 있는 추방·정리/이전은 회복 경로로 보존한다. 여러 원인이 있으면 모두 해소되어야 진행을 허용한다. 그룹 전용방의 공개 전환/연결 변경은 제한 원인을 숨기는 우회로 자동 허용하지 않으며 기존 권한과 별도 명령표에서 검증한다. 과거 방·회원·완료 이력은 삭제하지 않는다.

세 사용자 질문은 모두 답변 완료다. 정원 초과 때 기존 그룹 운영은 유지하되 그 그룹전용 레이드는 전부 정지한다는 마지막 설명이 앞선 추천보다 우선한다.

승인 대기 신청·초대는 Backend 명세에서 확정 membership과 구분해 미집계로 제안했다(사용자 최종 집계 계약 검토 항목): 확정된 현재 활성 참가방 기준 집계와 신청/수락 시점 재검증을 적용하며 기본 레이드 숫자 10도 계정 유효 한도 조회로 처리한다. 한도 도달(used == limit)은 기존 방 차단이 아니라 추가 증가만 거절하며, 기존 사용 초과는 used > limit일 때다.

## 서버 계약 제안 — 명칭/스키마는 Backend 확정

- 계정별 유효 한도와 정책 revision을 서버에서 조회·검증한다. 계정에 연결한 한도 레코드/관련 테이블 등 물리 구조는 Backend 소유다. 일반 사용자 쓰기로 한도나 정상 상태를 바꿀 수 없다.
- 확장 가능 필드의 예: 그룹 정원 한도, 현재 가입 그룹 한도, 레이드 생성/참가 한도, 유효 시각·revision. BM 소스·중첩 우선순위는 도입 시 별도 설계하며 현재는 숫자 정책 경계만 준비한다.
- 상태 예: normal / over_limit 및 구체 reason(그룹 수/정원/레이드 수), 현재 사용량·적용 한도, 방 내 원인 membership 참조, 동작별 permissions. 단일 bool만 저장해 원인이나 회복 조건을 잃지 않는다. 공개 검색에는 개인 구독/결제 정보나 전역 사용자 UUID를 노출하지 않는다.
- 상태는 서버의 현재 한도·이번주/다음주의 실제 활성 참가대상·서버 시각으로 판정한다. 현재 참가목록과 한도는 같은 활성참가 의미를 공유하되, 화면의 선택탭/필터/페이지 개수를 로컬에서 세거나 일시 통신실패/한도에 따른 행동 제한 자체를 참가 종료로 해석하지 않는다. 캐시 상태나 만료 배치 작업 성공만 믿고 명령을 허용하지 않는다. 타이머/이벤트 기반 갱신을 쓰더라도 실제 쓰기 경계에서 현재 조건을 재검사한다.
- 한도 변경/만료, 가입·생성·수락, 탈퇴·추방, 그룹장 이전, 방 해산, 반복방 회차 전환에서 사용량/방 제한을 재평가한다. 관련 잠금·revision/CAS·멱등·트랜잭션 순서는 기존 정책과 통합하고 동시 가입/만료 경쟁을 막는다.
- 과거 성공 멱등 ACK를 새 진행 권한으로 재사용하지 않는다. 현재 조회/다음 명령은 현재 한도를 다시 검증한다. 소유권·활동 선택·참가 충돌·주간 원장은 기존 검사와 함께 유지한다.
- 감소/재가입/방 ID 재생성/주차 변경/그룹장 이전으로 사용 중인 관계가 집계에서 사라지는 우회를 방지한다. 과거 완료 이력과 현재 참가 관계를 별개로 집계한다.
- 회복을 위해 그룹장/파티장이 먼저 권한을 이전해야 한다면 기존 이전·후속 탈퇴 경로가 막히지 않는 명령표를 제안해야 한다. 단독 책임자·기존 해산 조건과 충돌 시 임의 완화하지 않고 검토 요청한다.
- 방 완료 차단을 개인 수동 체크나 다른 경로의 방 완료 명령으로 우회하지 못하도록 #11 주간 원장/#13 파티 명령의 경계를 대조한다. 방 관계가 없는 개인 수동 완료 전체를 무조건 차단하는 범위 확장은 하지 않는다.

## UI/UX 방향

기존 화면/카드/버튼 배치를 유지한다. 레이드 상세의 문제 회원에게 **‘최대 참가 횟수 초과’**를 표시한다. 문구는 참가 방 수 한도를 뜻하며 주간 클리어 횟수/신청 횟수와 혼동하지 않는다. i 아이콘은 현재 방 참가 관계라는 기존 의미를 유지한다.

하단 첫 레이드 현황 탭과 그룹 탭 아이콘 **우상단**에 각각 `현재 참가 모집방 수 / 개인 한도`, `현재 가입 그룹 수 / 개인 한도`를 표기한다(예:10/10,3/5). 그룹 탭 분모는 그룹정원15가 아니라 사용자 가입그룹 한도5다. 공개·그룹 모집 합산/기존관계 유지 기준은 서버와 같다. 원장 미지원/조회 실패를0이나정상으로 표시하지 않고 마지막 확인값/미확인을 구분하며, 탈퇴/추방·한도 변경/회원 전환 후 현재 조회로 갱신한다. Badge 배치 외 탭 구조·터치 영역 변경은 하지 않는다. 결제 유도 화면·새 유료 진입점은 만들지 않는다. 차단 이유와 허용된 탈퇴/추방 동작을 식별할 수 있어야 하며 본문 로딩 때문에 레이아웃이 움직이지 않도록 기존 원칙을 따른다.

## 작업 순서와 완료 조건

1. 확정 기준(현재 그룹장 정원15/가입 그룹5/생성·참가 모집 합산10/차원별 직접 참가방 제한)으로 Backend 기존 #12/#13 명세 영향 검토.
2. Backend가 계정별 한도/조회와 공통 쓰기 guard, 동작별 차단/회복 표·집계/원자성·반복방 경계를 설계해 회신. 독립적으로 확정된 경계부터 작업하고 확정한 한도/영향 범위를 명세에 반영한다.
3. Backend의 범위별 구현·경계 검증/호출 가능한 계약 인계 후 Flutter가 기존 화면에 표시·permissions를 연결한다.
4. 한도 감소/만료 경계, 정확히 한도, 동시 생성·가입, 완료·다음 주 우회 차단, 정상 회원의 방 차단, 탈퇴/추방 후 회복, 마지막 책임자·회원전환/재설치를 검증한다. 정상 UI 실기기 조작은 사용자 담당이다.

이번 문서 작성만으로 계정별 한도·제한 기능이 작동하지 않는다. 현재 환경/개발 자료를 유지하며 DB 초기화·자료 이전·배포·Git 통합은 하지 않는다.
