## 1. 문서 목적

이 문서는 LOSTPARTY 사용자가 게임 계정(원정대)을 등록·인증한 뒤 일반 레이드 모집과 그룹 기능을 사용하는 전체 흐름을 하나의 묶음으로 정리한다.

기존 계약 문서는 인증, 파티 명령, 그룹 membership과 읽기 모델을 각각 상세히 설명한다. 이 문서는 그 계약을 대체하지 않는다. 다음 내용을 연결해 이해하고 Notion 등에서 도식화할 수 있도록 상위 흐름과 책임 경계를 제공한다.

- LOSTPARTY 사용자와 게임 계정·Character의 관계
- 게임 계정 가등록과 원정대 소유 인증의 차이
- 인증된 Character로 일반 레이드 모집을 생성·신청·관리하는 흐름
- 그룹 생성·가입·관리 흐름
- 일반 모집과 그룹 전용 모집의 공통점과 차이
- 현재 구현이 확인된 구간과 아직 해결되지 않은 구간

세부 권한, 저장 필드와 Transaction 계약은 문서 마지막의 관련 계약을 따른다. 이 문서와 세부 계약이 충돌하면 최신 사용자 결정, 현재 코드 연결, 해당 기능의 최신 세부 계약 순으로 다시 대조한다.

### 2.2 반드시 구분할 개념

- **앱 사용자(Player)**와 **게임 계정(원정대)**은 같은 개념이 아니다.
- 게임 계정 하나에는 여러 Character가 속할 수 있다.
- 한 Player는 본계정·부계정 등 여러 게임 계정을 소유할 수 있다.
- 그룹 membership과 파티 권한은 Character가 아니라 Player를 기준으로 한다.
- 실제 레이드 참가는 Player가 소유한 Character 하나를 선택해 수행한다.
- 대표 Character와 그룹 대표 Character는 표시·추천 정보이며 Player 식별자가 아니다.
- 원정대 인증은 게임 계정과 Character의 현재 소유자를 증명하는 과정이다. 앱 재설치 후 기존 Player를 복구하는 로그인 기능과 같지 않다.

## 3. 게임 계정 등록과 원정대 인증

### 3.1 API 키와 가등록

```text
Lost Ark API 키 등록
  -> Character명 입력 또는 조회
  -> 원정대 Character 목록 조회
  -> 기기에 게임 계정과 Character를 가등록
  -> 아직 서버 소유 인증은 완료되지 않은 상태
```

- 사용자별 Lost Ark API 키는 기기의 secure storage에 저장한다.
- API 조회로 얻은 원정대·Character 정보는 인증을 진행하기 위한 후보이자 로컬 표시 데이터다.
- API에서 Character 정보를 조회했다는 사실만으로 해당 원정대의 소유권이 인증되지는 않는다.
- 과거 로컬 장비 Snapshot은 새 인증의 소유 증명으로 사용하지 않는다.

### 3.2 장비 변경 기반 원정대 인증

```text
인증할 Character 선택
  -> 최신 원정대와 장비 정보 재조회
  -> 무기·방어구 5부위 착용 확인
  -> 1~3개 지정 부위 안내
  -> 사용자가 게임에서 지정 장비 해제
  -> 앱에서 다시 확인
  -> 지정 부위 해제 + 나머지 부위 유지 판정
  -> GameAccountId·CharacterId 연결 또는 기존 서버 ID 재사용
```

- Challenge 유효시간은 시작 시점부터 10분이다.
- Challenge는 앱 메모리에만 존재한다. 앱 프로세스가 종료되면 인증 시도도 종료한다.
- 지정하지 않은 무기·방어구가 바뀌면 인증을 확정하지 않는다.
- 인증 성공 시 GameAccount와 소속 Character의 서버 관계를 현재 Player에게 연결한다.
- Character명은 바뀔 수 있는 표시값이므로 영속 식별자로 사용하지 않는다.
- 최신 원정대 조회에서 사라진 Character는 자동 삭제하지 않고 `missingFromLatestRoster` 상태로 보존한다.

### 3.3 인증 후 이용 자격

인증된 게임 계정을 하나 이상 가진 Player는 다음 멀티유저 기능의 실행 주체가 될 수 있다.

- 일반·그룹 레이드 모집 생성
- 모집 신청 또는 즉시 가입
- 확정 파티원으로 참가
- 그룹 생성·초대·가입
- 파티장·공대장·그룹장 권한 행사

각 명령은 화면의 로컬 표시만 신뢰하지 않고 현재 Auth binding, Player, Character 소유자와 GameAccount 관계를 다시 확인한다.

### 3.4 인증 이후 정보 갱신

- 내 계정 진입이나 수동 새로고침에서 원정대 Character 요약을 다시 조회할 수 있다.
- Character명·레벨·아이템 레벨 등 변경된 최소 정보만 갱신한다.
- 서버 Character는 Character명이 아니라 기존 `CharacterId`로 찾는다.
- API 또는 서버 반영에 실패하면 기존 값을 유지하고 재시도할 수 있게 한다.
- 파티 명령에서 서버 Character 정보가 오래됐거나 입장 조건에 미달하면 무조건 API를 호출하지 않고 내 계정 새로고침을 안내한다.

### 3.5 별도 문제로 분리된 항목

| 항목 | 현재 상태 | 이 문서에서의 취급 |
|---|---|---|
| 앱 재설치 후 기존 Player 복구 | 별도 브랜치에 보류 | 원정대 인증 흐름과 분리 |
| 다른 Player가 사용하던 원정대 재인증 | 소유권 이전 자체는 기존 계약에 존재 | 과거 파티·그룹 데이터 처리 정책은 보류 |
| 원정대 소유권 이전 시 기존 사회적 데이터 승계 | 정책 미확정 | 자동 승계한다고 간주하지 않음 |

## 4. 일반 레이드 모집의 전체 흐름

### 4.1 공통 사전 조건

모집 생성·신청·참가 Character 변경은 다음 조건을 공통으로 확인한다.

- 현재 AuthUid가 active Player에 연결돼 있음
- Player가 인증된 active 게임 계정을 보유함
- 선택 Character가 현재 Player 소유이고 활동 Character로 사용할 수 있음
- 선택 레이드·난이도의 입장 조건과 저장 역할을 만족함
- 같은 Player가 같은 방에 이미 참가하지 않음
- 같은 Character가 현재 주차의 동일 레이드에 이미 확정 참가하거나 완료하지 않음
- 다른 파티와의 일정 충돌이 없음
- 최소 전투력 등 모집 조건을 만족함

승인 대기 신청은 자리를 선점하지 않는다. 실제 점유는 모집 생성, 즉시 가입 또는 신청 승인 중 먼저 성공한 원자 명령에서 확정한다.

### 4.2 모집 생성

```text
레이드 모집 탭
  -> 모집 만들기
  -> 일반 레이드 선택
  -> 파티장 Character·역할 선택
  -> 레이드·난이도·제목·조건·일정 설정
  -> 조건과 현재 참가 상태 재검증
  -> 모집 + 파티장 membership + raidState 원자 생성
  -> 레이드 현황 > 진행 중에 표시
```

- 모집 생성자는 선택 Character로 즉시 확정 참가하며 파티장 또는 공대장이 된다.
- 대표 Character는 최초 추천값일 뿐 실제 파티장 Character로 강제하지 않는다.
- 레이드와 난이도는 사용자가 명시적으로 선택한다.
- 같은 레이드의 승인 대기 신청이 있더라도 생성 자체를 무조건 막지 않는다. 사용자 확인 뒤 확정 참가를 만들고 충돌 신청은 무효화·정리한다.
- 일반 모집은 `visibility=public`, `groupId=null`이 기본 관계다.

### 4.3 신청과 즉시 가입

#### 승인형 모집

```text
공개 모집 목록
  -> 모집 상세
  -> 참가 Character·역할 선택
  -> 조건 재검증
  -> 승인 대기 신청 생성
  -> 레이드 현황 > 신청 중
  -> 파티장 또는 승인권자의 승인/거절
```

- 동일 레이드의 여러 승인형 모집에 복수로 신청할 수 있다.
- 첫 확정 참가만 `raidState` 점유를 얻는다.
- 다른 모집에서 참가가 먼저 확정되면 남은 신청은 승인될 수 없으며 화면에서 무효 상태로 처리한다.
- 신청자는 승인 전까지 파티원이 아니며 자리 이동·완료·파티 관리 권한이 없다.

#### 즉시 가입 모집

```text
모집 상세
  -> 참가 Character·역할 선택
  -> 현재 조건과 빈자리 재검증
  -> membership + raidState 원자 생성
  -> 즉시 확정 참가
```

즉시 가입은 승인 대기 신청을 만들지 않는다. 동시에 요청해도 빈자리와 점유를 먼저 확정한 한 건만 성공해야 한다.

### 4.4 신청 승인과 거절

| 행동 | 실행 가능 주체 | 결과 |
|---|---|---|
| 신청 승인 | 파티장·공대장 또는 가입 승인권자 | 신청자를 확정 파티원으로 추가하고 자리·점유 확정 |
| 신청 거절 | 파티장·공대장 또는 가입 승인권자 | 신청을 거절 상태로 종료 |
| 신청 철회 | 신청자 본인 | 승인 대기 신청 종료 |
| 승인권 부여·회수 | 파티장·공대장 | 현재 파티원에게만 승인 권한 부여 또는 회수 |

가입 승인권자는 신청 승인·거절만 할 수 있다. 참가자 추방, 자리 관리, 모집 수정, 반복 설정, 책임자 이전과 방 해산 권한은 얻지 않는다.

### 4.5 파티 구성 관리

#### 자리 이동

- 파티장·공대장은 참가자의 `partyIndex`와 `slotIndex`를 조정할 수 있다.
- 8인 공격대에서는 빈자리 이동과 두 자리 교환을 지원한다.
- 같은 파티 안의 사용자·Character·역할 관계는 유지한다.
- 이동 뒤에도 파티 구성 제한과 한 자리 한 명 원칙을 만족해야 한다.

#### 참가 Character 변경

- 파티장과 일반 파티원은 완료 전 허용 상태에서 자신의 Character를 변경할 수 있다.
- 다른 Player의 Character로 바꿀 수 없다.
- 새 Character의 소유권, 입장 조건, 역할, 동일 레이드 참가·완료, 일정과 파티 구성 조건을 다시 검증한다.
- 승인 대기 신청이 충돌하면 명시적 확인 후 가능한 범위에서 정리한다.
- 현재 파티의 자리 위치는 유지한다.

#### 참가자 추방

- 파티장·공대장만 다른 확정 파티원을 추방할 수 있다.
- 대상과 영향을 확인한 뒤 membership과 현재 참가 점유를 함께 제거한다.
- 과거 완료 Snapshot은 변경하지 않는다.
- 빈자리가 생기면 수동 모집 설정과 함께 목록 재노출 여부를 다시 계산한다.
- 추방된 사용자의 같은 방 재신청을 정책적으로 금지하지 않는다.

#### 본인 탈퇴

- 일반 파티원은 허용 상태에서 자신의 membership과 현재 참가 점유만 제거한다.
- 일반 파티원은 방 전체를 해산할 수 없다.
- 과거 완료 Snapshot에서는 제거하지 않는다.

#### 파티장·공대장 탈퇴

```text
책임자 탈퇴
  -> 남은 파티원 있음: 가장 먼저 가입한 유효 멤버에게 자동 승계
  -> 남은 파티원 없음: 방 자동 해산
```

승계는 현재 참가 구성 안에서 처리하며 새 책임자에게 파티 관리 권한이 이동한다.

### 4.6 완료와 해산

#### 개인 완료

- 일반 파티원은 `내 Character 완료`로 본인 완료 Claim과 본인 탈퇴를 처리할 수 있다.
- 개인 완료가 방 전체의 회차를 완료시키지는 않는다.

#### 파티 전체 완료

- 파티장·공대장만 실행한다.
- 완료 당시 참가 구성을 불변 Snapshot으로 보존한다.
- 공동 완료를 같은 주차에서 방 전체 단위로 취소하는 기능은 제공하지 않는다.
- 잘못된 개인 완료 표시는 각 사용자가 내 계정에서 자신의 완료 체크를 해제해 정정한다.

#### 1회성 모집

```text
전체 완료
  -> 모집·구성 수정 종료
  -> 해산 단계
  -> 사용자 활성 목록에서 제거
```

#### 반복 모집

```text
이번 주 전체 완료
  -> 방과 membership 유지
  -> 다음 회차 준비 상태
  -> 다음 수요일 06:00에 새 회차 전환
```

반복 모집은 완료 후에도 다음 회차 준비를 위해 참가자 탈퇴·추가와 Character 변경을 허용한다. 과거 완료 Snapshot은 바꾸지 않는다.

#### 방 해산

- 파티장·공대장만 방 전체를 해산할 수 있다.
- 현재 참가자와 승인 대기 신청자에게 종료 상태를 전달한다.
- 화면에서는 활성 방에서 제거하지만 서버는 이벤트와 보존 정책을 위해 종료 상태를 일정 기간 유지할 수 있다.

## 5. 그룹 자체의 흐름

그룹은 레이드방이 아니다. Player들이 소속되는 공동 활동 공간이며, 그룹 membership과 레이드 membership은 서로 다른 관계다.

### 5.1 그룹 생성

```text
그룹 탭
  -> 그룹 생성
  -> 그룹명과 그룹 대표 Character 선택
  -> 현재 Player·인증 Character 재검증
  -> 그룹 + 그룹장 membership 생성
```

- 생성자는 첫 그룹장이 된다.
- 그룹은 최대 50명이며 한 Player가 가입할 수 있는 그룹도 최대 50개다.
- 그룹 대표 Character는 그룹 표시 정보다. Player 소유권이나 그룹장 권한의 영속 키가 아니다.

### 5.2 그룹 가입 경로

| 경로 | 승인 방식 | 단위 |
|---|---|---|
| 직접 초대 | 대상이 수락 또는 거절 | Character 검색으로 Player를 찾지만 초대 대상은 Player |
| 가입 신청 | 그룹장이 승인 또는 거절 | `groupId + playerId` |
| 초대코드 | 유효 코드 입력 후 즉시 가입 | 그룹 정원·가입 한도·신청 금지 재검증 |

- 자유 가입은 제공하지 않는다.
- 활성 초대·신청은 같은 그룹과 Player 조합에서 하나만 유지한다.
- Character나 원정대를 바꿔도 같은 Player의 신청 금지와 누적 신청 횟수를 우회할 수 없다.
- 그룹에 가입한 Player는 자신이 active 소유한 본·부계정의 활동 Character를 그룹 레이드 참가 후보로 사용할 수 있다.

### 5.3 그룹 권한

| 기능 | 그룹장 | 일반 멤버 |
|---|---:|---:|
| 그룹 정보 수정 | 가능 | 불가 |
| 사용자 초대 | 가능 | 가능 |
| 가입 신청 승인·거절 | 가능 | 불가 |
| 신청 금지·해제 | 가능 | 불가 |
| 멤버 추방 | 가능 | 불가 |
| 그룹장 이전 | 가능 | 불가 |
| 그룹 해산 | 가능 | 불가 |
| 본인 탈퇴 | 이전 또는 해산 필요 | 가능 |

### 5.4 그룹장 이전과 탈퇴

```text
현재 그룹장이 유효한 일반 멤버 선택
  -> 확인
  -> 대상 수락 없이 즉시 그룹장 이전
  -> 기존 그룹장은 일반 멤버로 유지
  -> 필요하면 별도 일반 탈퇴 실행
```

- 그룹장 이전과 기존 그룹장의 탈퇴를 한 명령으로 묶지 않는다.
- 이전 대상이 먼저 탈퇴하거나 상태가 바뀌면 이전을 거절하고 목록을 다시 읽는다.
- 그룹장 한 명만 남은 경우 이전할 수 없고 해산만 선택할 수 있다.
- 장기 미접속만으로 그룹장을 자동 교체하지 않는다.

### 5.5 그룹 해산


- 호출자가 현재 그룹장
- 그룹 상태가 active
- 그룹장 한 명만 남음
- 처리되지 않은 초대·가입 신청이 없음
- 활성 그룹 전용 레이드가 없음
- 활성 초대코드는 같은 해산 명령에서 폐기 가능

해산은 그룹을 soft delete 상태로 바꾸고 마지막 membership과 Player의 그룹 관계를 제거한다. 연결된 일반·반복 레이드방을 자동 해산하지 않는다.

## 6. 그룹 레이드와 그룹 전용방

### 6.1 핵심 정의

- 그룹 레이드도 생성·신청·가입·자리 이동·완료·해산은 일반 레이드 계약을 사용한다.
- 레이드 하나에는 그룹 하나만 연결할 수 있다.
- 그룹 레이드 생성 시 `그룹만 공개`가 기본값이다.
- 연결 그룹과 공개 범위가 추가될 뿐 별도의 파티 완료 체계를 만들지 않는다.

### 6.2 생성과 공개 범위

```text
모집 만들기
  -> 그룹 레이드 선택
  -> 현재 가입 그룹 하나 선택
  -> 그룹만 공개 기본 선택
  -> 일반 모집과 같은 Character·레이드 조건 입력
  -> 모집 원본 + 그룹 raidListing 원자 생성
```

| 상태 | 조회·신청 대상 | 그룹 탈퇴 이후 기존 파티 참가 |
|---|---|---|
| 그룹 전용 `visibility=group` | 현재 해당 그룹원 | 참가 자격 상실 및 제한적 정리 대상 |
| 전체 공개 `visibility=public` | 일반 공개 모집과 동일 | 일반 참가자로서 유지 |

- 전체 공개로 전환해도 생성 당시 `groupId`는 연결 이력과 그룹 필터를 위해 유지한다.
- 전체 공개에서 그룹 전용으로 되돌릴 때 비그룹 참가자나 유효 신청이 남아 있으면 전환을 거절한다.
- 그룹 전용 목록은 그룹의 `raidListings` Projection으로 제공하며 모집 원본과 같은 Transaction에서 동기화한다.

### 6.3 일반 모집과 그룹 전용 모집 비교

| 구분 | 일반 모집 | 그룹 전용 모집 |
|---|---|---|
| 모집 원본 | `recruitments/{id}` | 동일 |
| Group ID | 없음 | 하나의 `groupId` |
| 목록 공개 | 로그인 사용자의 공개 목록 | 해당 그룹원에게만 그룹 listing 공개 |
| 신청·즉시 가입 | 일반 참가 조건 확인 | 일반 조건 + 현재 그룹 membership 확인 |
| 파티장 권한 | 모집의 leader Player | 동일 |
| 그룹장 권한 | 없음 | 해당 방의 파티장이 되는 것은 아님 |
| 자리 이동·Character 변경·추방·완료 | 일반 파티 계약 | 동일한 계약 사용 |
| 그룹 탈퇴 효과 | 해당 없음 | 그룹 전용 상태에서만 참가 자격 상실 |
| 방 해산 | 파티장·공대장 | 파티장·공대장, 제한된 경우 그룹장 관리 명령 |

### 6.4 그룹장 전용 레이드 관리

- 현재 그룹장은 그룹 상세에서 활성 그룹 전용방을 관리할 수 있다.
- 그룹장이 해당 방에 참가하지 않아도 `전체 공개 전환` 또는 `모집 해산`을 요청할 수 있다.
- 이 권한은 그룹 해산을 막는 활성 그룹 전용방을 정리하기 위한 제한 권한이다.
- 그룹장은 이 권한만으로 신청 승인, 자리 이동, 참가 Character 변경, 완료, 반복 설정 변경 권한을 얻지 않는다.
- 그룹장 이전 직후 관리 권한은 새 그룹장에게 이동한다.

### 6.5 그룹과 레이드 생명주기 분리

```text
그룹 탈퇴/추방 != 레이드방 자동 탈퇴/추방
레이드방 탈퇴/추방 != 그룹 자동 탈퇴/추방
그룹 해산 != 연결 레이드방 자동 해산
```

- 그룹 전용방에서 그룹 자격을 잃은 참가자는 서버가 자격 상실을 다시 확인한 뒤 제한적으로 정리한다.
- 이 정리 동작은 일반 추방 권한을 모든 그룹원 또는 파티원에게 주는 기능이 아니다.
- 전체 공개로 전환된 그룹 연결 레이드는 그룹을 탈퇴해도 참가 자격을 유지한다.

## 7. 화면 기준 사용자 이동

현재 하단 탭은 다음 네 개다.

1. `레이드 현황`
2. `내 계정`
3. `레이드 모집`
4. `그룹`

설정은 별도 하단 탭이 아니라 내 계정의 설정 진입점을 사용한다.

| 화면 | 주요 역할 |
|---|---|
| 레이드 현황 > 진행 중 | 생성했거나 확정 참가한 방, 파티 관리와 완료 |
| 레이드 현황 > 신청 중 | 승인 대기 신청, 철회와 결과 확인 |
| 레이드 현황 > 완료 기록 | 완료·미완료 종료와 개인 기록 확인 |
| 내 계정 | 게임 계정·Character, 활동 Character, 주간 완료 관리 |
| 설정 | API 키, 원정대 인증과 앱 공통 설정 |
| 레이드 모집 | 공개·그룹 모집 조회, 신청, 새 모집 생성 |
| 그룹 | 내 그룹, 요청 현황, 그룹 검색·생성·관리 |

## 8. 권한 판단의 세 축

한 동작을 허용할지는 다음 세 축을 섞지 않고 함께 판정한다.

| 축 | 질문 | 예시 |
|---|---|---|
| Player 권한 | 이 사람이 이 동작의 주체인가? | 파티장, 승인권자, 그룹장, 신청자 본인 |
| Character 자격 | 선택 Character가 실제 참가 가능한가? | 현재 소유, 입장 레벨, 역할, 주간 참가·완료 상태 |
| 공개·소속 범위 | 이 방을 보고 신청할 관계가 있는가? | 공개 모집, 해당 그룹 membership, 그룹 전용 여부 |

예를 들어 그룹장은 그룹 전용방을 정리할 제한 권한이 있지만 자동으로 그 방의 파티장은 아니다. 반대로 그룹 전용방의 파티장은 파티를 관리할 수 있지만 그룹 전체의 가입 신청이나 그룹장 이전을 처리할 수 없다.

## 9. 도식화용 핵심 흐름

### 9.1 계정부터 레이드 참가까지

```text
[API 키 등록]
  -> [원정대·Character 가등록]
  -> [장비 변경 인증]
  -> {인증 성공?}
       아니오 -> [재확인 또는 새 Challenge]
       예 -> [GameAccount·Character 서버 연결]
  -> [활동 Character 선택]
  -> {사용 목적}
       모집 생성 -> [파티장 확정 참가]
       승인형 신청 -> [승인 대기] -> {승인?} -> [확정 참가]
       즉시 가입 -> [조건·빈자리 원자 검증] -> [확정 참가]
```

### 9.2 확정 참가 이후

```text
[확정 참가]
  -> {역할}
       파티장/공대장 -> [자리 관리 / 추방 / 전체 완료 / 해산]
       승인권자 -> [신청 승인·거절]
       일반 파티원 -> [본인 Character 변경 / 탈퇴 / 개인 완료]
  -> {방 형태}
       1회성 -> [전체 완료] -> [해산]
       반복 -> [이번 주 완료] -> [다음 회차 준비] -> [수요일 06시 전환]
```

### 9.3 그룹과 그룹 전용 레이드

```text
[Player]
  -> [그룹 생성 / 초대 수락 / 신청 승인 / 코드 가입]
  -> [그룹 membership]
  -> [그룹 레이드 생성]
  -> {공개 범위}
       그룹 전용 -> [그룹원만 조회·신청]
       전체 공개 -> [일반 모집과 같은 조회·신청]
  -> [일반 레이드 명령 재사용]
```

### 9.4 그룹과 레이드의 독립 관계

```text
[그룹 membership 변경]
  -X-> [레이드 membership 자동 변경]

[레이드 membership 변경]
  -X-> [그룹 membership 자동 변경]

[그룹 해산]
  -X-> [연결 레이드 전체 자동 해산]
```

`-X->`는 자동 연쇄하지 않는다는 뜻이다.

## 10. 현재 구현·검증 상태

### 10.1 확인된 주요 흐름

- 원정대 Character 등록과 장비 변경 인증
- 인증 Character를 이용한 레이드 모집 생성
- 일반·그룹 레이드 생성과 그룹 전용/전체 공개 전환
- 승인 대기 신청, 승인·거절, 즉시 가입의 기본 연결
- 8인 공격대 자리 이동과 자리 교환
- 참가 Character 변경의 기본 흐름
- 그룹 생성, 초대, 가입 신청, 초대코드 가입
- 일반 그룹원 탈퇴, 그룹장 즉시 이전, 이전 후 탈퇴, 1인 그룹 해산
- 파티·그룹의 Player 권한과 Character 참가 자격 분리

각 항목의 정확한 자동·실기기 검증 시점은 `AI_CONTEXT.md`와 `DEV_LOG.md`를 따른다.

### 10.2 BUG-022 작업 브랜치 상태

현재 브랜치 `fix/bug-022-party-permissions`에는 다음 수정이 존재한다.


- 앞의 두 수정은 아직 운영 배포와 현재 사용자 디바이스 확인 전이다.
- 재가입을 막는 제품 정책은 없다. 같은 방 재가입은 허용돼야 하므로 현재 실패는 미해결 결함이다.
- 실패를 피하기 위해 원자성, 소유권, 그룹 접근 또는 주간 참가 검증을 임의로 약화하지 않는다.

### 10.3 별도 보류 작업

- 앱 재설치 후 기존 Player와 사회적 데이터를 복구하는 로그인 연결 작업
- 타인이 사용하던 원정대를 다시 인증했을 때 과거 Player의 파티·그룹·신청을 처리하는 소유권 이전 정책
- 소유권 이전 과정에서 과거 데이터를 전역 순회하거나 자동 승계할지 여부

이 항목들은 현재 파티 권한 오류와 같은 작업으로 간주하지 않으며, 정책이 확정될 때까지 이 문서도 특정 처리 방식을 정답으로 선언하지 않는다.
