# 교류 행동 기반 캐릭터 자동 갱신 계약

## 0. 2026-09-05 앱 실행 1회 갱신으로 방향 전환 (A~C 반영)

실기기에서 교류 직전 자동 갱신이 거의 항상 실패(기존 Snapshot 계속 확인)하고 Armory 자동 갱신이 매우 느리다는 사용자 보고가 있었다. 나이스단 허용 UI는 정상이다. 통신 로그로 원인을 확정하지는 않았다.

사용자 결정:
- 파티 모집·그룹 생성·가입·상세 등 **현재 연결된 모든 교류 시점 자동 갱신 조건을 철회**한다.
- 자동 갱신은 **앱 실행 시 1회**로 정정한다.
- 갱신 대상은 active 소유권과 서버 Character ID가 있는 등록 Character 중 공통 기준 아이템 레벨 이상이며 원정대 이탈 상태가 아닌 본인 Character다. 현재 공통 기준은 1700이다.
- 1700을 각 기능에 중복 하드 코딩하지 않는다. 하나의 공통 정책 값(예: `CharacterUsageLevelPolicy.minimumItemLevel`)을 나이스단 판정과 앱 실행 갱신 대상 판정이 함께 사용한다. 이후 실제 사용 레벨대가 바뀌면 이 값 하나로 조정한다.
- 기존 나이스단 분류와 Player 단위 자동 갱신 허용 설정은 유지한다. 기준 레벨 이상 동일 직업 2명 이상 판정은 정상 동작하는 현재 자산을 재사용한다.
- 바드·홀리나이트·발키리·도화가를 포함한 직업별 역할·표기 데이터는 자동 테스트 통과만으로 실제 검증 완료 처리하지 않는다. 해당 직업 Character를 보유한 여러 실제 사용자 계정에서 캐릭터별 역할·아이템 레벨·전투력·보석 표기를 확인한다.
- 앱 실행 갱신은 Firebase·Player 세션·로컬 DB 초기화 후에도 첫 화면과 동시에 시작하지 않는다. 초기 경로인 내 레이드 현황의 진행 중·신청 중 첫 Snapshot(성공 또는 오류), 완료 기록 초기화와 알림 수 조회가 끝나고 첫 화면이 렌더링된 뒤 시작한다.
- 내 레이드 현황의 초기 로딩은 자동 갱신을 기다리지 않는다. 초기 로딩 완료 신호가 자동 갱신을 여는 단방향 장벽이며, 자동 갱신 실패는 첫 화면 진입을 차단하지 않는다.
- 앱 프로세스의 `MyApp` 수명당 한 번만 실행한다. 탭 이동, 화면 재진입, 수동 새로고침, 백그라운드 복귀에는 다시 실행하지 않는다.
- 갱신 중에는 하단 탭 바의 두 번째 `내 계정` 탭에 비차단 인디케이터를 표시한다. 개별 실패 확인 다이얼로그는 띄우지 않고, 완료 또는 일부 실패 후 인디케이터를 종료한다.
- A 공통 기준, B 교류 제거, C 앱 수명당 1회 조정기까지 반영했다. 첫 화면 로딩 장벽·인디케이터 연결은 D이며 실행 순서는 `../project/NEXT_WORK.md`를 따른다.

아래 §1~§9는 A~G 교류 직전 설계·구현 이력이다. 제품 방향과 충돌하면 **본 절과 NEXT_WORK가 우선**한다.

### 0.1 방향 전환 구현 구간

- A 공통 기준: `CharacterUsageLevelPolicy`의 단일 1700 경계를 나이스단과 앱 실행 갱신 대상 판정이 공유한다. `StartupCharacterRefreshEligibilityPolicy`는 active 소유권·서버 Character ID·원정대 소속·레벨 조건을 만족하는 본·부계정 등록 Character만 고른다.
- B 교류 제거(완료): 파티·그룹 후보 prefetch, 명령 직전 갱신과 확인 다이얼로그를 제거하고 기존 명령 검증을 보존했다. 교류 전용 래퍼는 삭제했으며 공통 Coordinator와 서버 최소 Snapshot 동기화 자산은 유지했다.
- C 시작 갱신(완료): 동일 Future를 재사용하는 앱 수명당 1회 조정기를 구현했다. 인증·적격 Character에 기존 Coordinator를 적용하고 나이스단 설정을 유지하며 캐릭터별 실패와 계정 로드 실패를 앱 진입에서 격리한다. 전체·완료·실패 상태 스트림은 D UI 연결에 사용한다.
- D 로딩·상태: 내 레이드 현황 초기 로딩 완료 장벽과 내 계정 탭 인디케이터를 연결한다.
- E 내 계정 UI: 인증·조회·부계정 추가 영역을 압축한다.
- F 통합 검증: 자동 회귀 후 여러 실제 사용자 계정과 직업 Character로 표기를 확인한다.

## 1. 목적과 현재 결정

LOSTPARTY에서 사용하는 활동 Character가 그룹·파티 등 다른 사용자와 교류하기 직전에 최신 Lost Ark Armory 정보를 확보한다. 기존 로컬 Build Snapshot, Firestore Character 최소 표시값, 그룹 membership Snapshot, 파티 신청·참가 Snapshot 구조는 유지한다.

이 작업의 주목적은 Firestore 조회 절감이 아니라 사용자가 Character 상세에 하나씩 들어가 `정보 가져오기`와 저장을 반복하는 불편을 줄이고, 교류 시점의 전투력·아이템 레벨·세팅 정확도를 높이는 것이다.

확정 사항:

- 일반 Character는 교류 후보 화면에서 백그라운드로 사전 갱신하고 실제 명령 직전에 선택 Character의 최신화를 보장한다.
- 명령은 갱신 전에 만든 값이 아니라 갱신 완료 후 확정한 Snapshot으로 새로 만든다.
- 나이스단 Character는 자동 갱신에서 제외하고 기존 수동 저장 Snapshot을 유지한다.
- 등록된 본·부계정 전체를 합쳐 아이템 레벨 1700 이상인 동일 직업 Character가 2명 이상이면 해당 직업군 전체를 나이스단으로 분류한다. 원정대가 달라도 보석을 옮겨 쓸 수 있으므로 GameAccount 경계로 나누지 않는다.
- 나이스단 자동 갱신 허용은 Character별 설정이 아니라 해당 사용자 나이스단 전체에 적용하는 하나의 로컬 설정이다.
- API 실패·역할 판별 실패·보석 대상 판별 실패는 기존 정상 Snapshot을 0 또는 불완전 응답으로 덮어쓰지 않는다.
- 다른 사용자의 목록·상세는 Lost Ark API를 대신 호출하지 않고 기존 서버 Snapshot을 읽는다.
- 신청·가입·참가 문서는 계속 명령 실행 시점 Snapshot을 저장한다. 이후 자동 갱신으로 과거 Snapshot을 덮어쓰지 않는다.
- 기존 분석기가 `ArmoryGem.Gems`와 `ArmoryGem.Effects.Skills`의 전체 반환 슬롯을 순회하는 구조는 재사용한다. 별도 슬롯 검사 체계를 중복 구현하지 않는다.
- 사전 갱신 성공 TTL은 5분, Armory API 최대 동시 요청 수는 3개로 시작한다.
- 기존 정상 Snapshot에는 강제 만료 기간을 두지 않는다. 자동 갱신 실패 시 마지막 정상 저장 시각만 알리고 사용자가 기존 정보로 계속할 수 있다.

## 2. 데이터 책임 경계

| 데이터 | 기준과 책임 |
|---|---|
| 원정대 목록 요약 | Lost Ark siblings API → 로컬 Drift. 기존 자동 요약 갱신 유지 |
| 일반 Character 현재 Build | 교류 시 Armory API 자동 조회 → 메모리 분석 → 역할별 로컬 Build Snapshot |
| 나이스단 Build | 사용자가 정상 세팅에서 저장한 역할별 로컬 Build Snapshot |
| Firestore Character | 소유권·활동 검증과 다른 사용자 표시를 위한 최소 최신값. 원본 Armory 저장소가 아님 |
| 그룹 membership | 가입·표시 갱신 시점 Snapshot |
| 파티 application/membership | 신청·가입·변경 명령 시점 Snapshot |
| 타 사용자 화면 | 상대방이 게시한 서버 Snapshot. 조회자가 상대 Character API를 호출하지 않음 |

서포터 겸용 직업은 Character 하나에 dealer/support Snapshot을 독립 보존한다. 자동 조회에서 감지한 현재 역할의 Snapshot만 갱신하고 반대 역할 Snapshot은 유지한다.

## 3. 자동 갱신 대상 구간

### 파티

- 모집 생성 Character 후보와 생성 실행
- 참가 신청·즉시 참가 Character 후보와 실행
- 참가 Character 변경 후보와 실행
- 반복 파티 다음 회차 Character 변경 후보와 실행

### 그룹

- 그룹 생성 Character 후보와 실행
- 그룹 가입 신청 Character 후보와 실행
- 직접 초대 수락 Character 후보와 실행
- 초대코드 가입 Character 후보와 실행
- 그룹 상세 진입 시 본인 활동 Character 표시 Snapshot 보강

### 보조 구간

- 내 캐릭터 관리에서 일반 활동 Character의 선택적 사전 갱신

공개 모집 목록, 레이드 현황 목록, 신청자·파티원·그룹원 등 다른 사용자 목록과 상세, 알림, 완료 기록, 필터 조작은 자동 갱신 트리거가 아니다.

## 4. 명령 직전 정합성 계약

화면 진입 사전 갱신만으로 명령의 최신성을 보장하지 않는다. 생성·신청·가입·변경 실행은 공통 `ensureFresh` 성격의 조정 단계를 거친다.

```text
사용자 명령
→ 선택 Character와 자동 갱신 제외 여부 확인
→ 동일 Character 진행 중 요청이 있으면 같은 작업 대기
→ 필요한 경우 Armory API 조회
→ 메모리 분석과 역할·보석 대상 판별
→ 감지된 역할의 로컬 Snapshot만 저장
→ 변경된 최소 표시값만 서버 동기화
→ 최신 Snapshot으로 조건 재검증 및 명령 재생성
→ 기존 그룹·파티 Transaction 실행
```

- 갱신·명령 진행 중 같은 실행 버튼의 중복 처리를 막는다.
- 응답은 Character ID와 요청 generation에 묶어, 선택 변경 뒤 늦게 온 응답이 다른 Character에 반영되지 않게 한다.
- 갱신 결과가 최소 조건이나 요청 역할을 바꾸면 명령 전에 다시 안내한다.
- API 실패 시 기존 정상 Snapshot이 없으면 명령을 차단한다. 기존 정상 Snapshot이 있으면 강제 기간 제한 없이 마지막 정상 저장 시각을 알리고 사용자가 계속 여부를 선택한다.
- 사전 갱신 성공 TTL은 5분이다. 같은 Character의 5분 이내 성공 결과는 재사용하되 사용자가 명시적으로 다시 갱신할 수 있다.
- Armory API 요청은 최대 3개까지 병렬 실행한다. 동일 Character 요청은 하나의 진행 작업을 공유하며 선택 Character의 명령 직전 요청을 후보 사전 갱신보다 우선한다.
- 재시도와 `429` 처리는 기존 오류 매핑을 유지하고 실제 계측에서 문제가 확인될 때만 별도 정책을 추가한다.

## 5. 나이스단 정책

판정 범위는 한 사용자가 앱에 등록한 본계정·부계정의 전체 원정대다. 원정대가 달라도 보석을 자유롭게 옮길 수 있으므로 GameAccount별로 분리하지 않는다.

- 원정대 전체 Character 중 아이템 레벨 1700 이상만 집계한다. 활동 Character 선택 여부와 레이드 참여 방식은 집계에서 제외 조건이 아니다.
- 정규화된 동일 직업 Character가 2명 이상이면 해당 직업군을 나이스단으로 판정한다.
- 나이스단은 일부 Character만 세팅을 돌려 쓰는 개념으로 취급하지 않는다. 판정된 동일 직업군 Character 전체가 기존 수동 Snapshot 흐름을 사용한다.
- 사용자는 캐릭터 선택 화면의 `나이스단 자동 갱신` 설정으로 나이스단 전체의 자동 갱신을 명시적으로 허용할 수 있다.
- 이 설정은 사용자 개인 동작 정책이며 다른 사용자에게 필요하지 않으므로 로컬 DB에만 저장하고 Firestore에는 보내지 않는다.
- 나이스단은 역할 판정과 독립이다. dealer/support 겸용 직업도 기본적으로 자동 Build 갱신을 하지 않는다.
- 수동 Snapshot에는 역할과 캡처 시각을 유지한다.
- 원정대 재조회로 직업별 1700 이상 Character 수가 바뀌면 나이스단 판정을 다시 계산한다. 조건이 사라지면 일반 자동 갱신을 적용하되 로컬 허용 설정은 휴면 상태로 보존하고, 조건이 다시 생기면 사용자의 이전 선택을 복원한다.

## 6. 서포터 겸용 직업과 보석 대상

대상 직업은 바드·홀리나이트·발키리·도화가다. 아주 드문 dealer 세팅을 기본 support로 덮어쓰지 않도록 현재 Armory의 깨달음 1티어 노드로 역할을 감지한다.

- 바드의 기존 `완벽한 화음`/`진실된 용맹` 판별과 세레나데 복합 보석 대상 구조를 일반화한다.
- 도화가는 support `저물어가는 달`/4티어 `묵법 : 접무`/아이덴티티 보석 `음양`, dealer `회귀`/4티어 `묵법 : 파죽`/아이덴티티 `떠오르는 달`을 기준으로 한다.
- 홀리나이트는 support `신성 보호`/4티어 `신성 해방`/아이덴티티 보석 `신앙`, dealer `신의 기사`/4티어 `심판자`/아이덴티티 `심판자`를 기준으로 한다.
- 발키리는 support `해방자`/4티어 `해방의 날개`/아이덴티티 `신앙`, dealer `빛의 기사`/4티어 `삼위일체`/아이덴티티 `종언의 빛`을 기준으로 한다.
- 위 명칭은 실제 API fixture의 반환 문자열과 대조해 공백·별칭을 카탈로그에 고정한다.
- 네 직업의 ArmorySkills에 직접 나오지 않는 아이덴티티·아크패시브 보석 대상명, 별칭, 복합 대상을 정적 게임 카탈로그에 추가한다.
- 일반 스킬은 기존 ArmorySkills 비교를 사용한다.
- 역할을 하나로 감지했을 때 그 역할 Snapshot만 갱신한다.
- 역할이 없거나 복수로 감지되면 자동 저장하지 않는다.
- 자동 갱신에서 직업의 일반·아이덴티티·아크패시브 대상으로 판별되지 않은 보석 효과가 있으면 정상 자동 Snapshot으로 게시하지 않는다. 카탈로그 누락과 실제 타 직업 보석을 UI에서 단정적으로 혼동하지 않고 확인 대상명을 보여준다.
- 기존 분석기는 아크그리드 Tooltip의 전용 1티어와 추가 아크패시브 활성 조건을 현재 장착한 `ArkPassive` 노드와 교차 검증한다. 서포터도 이 공통 검증을 그대로 사용하며 별도 검증 체계를 만들지 않는다.
- 1티어는 역할 판별 기준이고 4티어는 아크그리드 조건과 현재 아크패시브가 같은 세팅인지 확인하는 핵심 교차 검증 대상이다. 조건 불일치는 기존 정상 Snapshot을 자동으로 덮어쓰지 않는다.

시너지 카탈로그의 dealer 분기 데이터는 역할 판별의 증거가 아니다. Build 판별 카탈로그에 실제 API 노드와 보석 대상 근거를 별도로 등록한다.

## 8. 단계별 실행 규칙

각 작업 그룹은 앞 단계가 `dev`에 검증·병합된 뒤 최신 `dev`에서 별도 브랜치로 시작한다. A~F를 한 브랜치에서 한꺼번에 구현하지 않는다.

각 단계는 다음 순서를 공통으로 따른다.

```text
최신 dev 대조
→ 해당 단계 계약과 기존 코드 경로 확인
→ 단계 범위만 구현
→ 단계 표적 테스트
→ 변경 범위 analyze
→ 영향이 넓으면 전체 flutter test --no-pub
→ 필요한 실기기 확인
→ DEV_LOG와 NEXT_WORK 갱신
→ dev 병합·푸시
```

- 다음 단계의 스키마나 추상화를 미리 구현하지 않는다.
- 기존 API·로컬 Snapshot·Firestore 명령 계약을 재사용할 수 있으면 새 저장소나 서버 필드를 만들지 않는다.
- 계약과 실제 코드가 충돌하면 임의 재설계하지 않고 충돌 근거와 최소 선택지를 먼저 기록해 사용자 결정을 받는다.
- 테스트가 실패한 단계는 다음 단계로 넘어가지 않는다.
- G는 앞 단계 테스트를 대신하는 일괄 테스트 단계가 아니라 전체 통합·실기기 최종 확인 단계다.

## 9. 구현 중 계측 후 조정 가능한 값

- 5분 TTL과 최대 동시 3개는 초기 확정값이다. 실제 API·기기 계측에서 문제가 확인되면 해당 단계 결과와 함께 변경 승인을 받는다.
- 기존 정상 Snapshot에는 만료 제한을 추가하지 않는다. 마지막 정상 저장 시각 안내의 정확한 UI 문구·위치는 C/D/E 단계에서 기존 화면 구성에 맞춘다.
- 서버 신규 필드는 현재 요구사항이 아니다. 기존 필드만으로 타 사용자 표시나 Transaction 정합성을 충족할 수 없다는 코드·Rules 근거가 확인될 때만 F에서 최소안을 제안한다.

현재 남은 제품 구조 결정은 없다. 실제 API 반환 문자열 확인과 단계별 구현·검증을 진행하며, 위 계측 조정 항목을 이유로 A 착수를 막지 않는다.
