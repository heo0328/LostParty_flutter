# 개발 품질·데이터 흐름·사용자 경험 판단 기준

2026-10-23 사용자 토의·대표 코드 검토 기준. Flutter와 Python Backend에 공통으로 적용할 개발 판단 원칙이며, 현재 기능이나 API를 일괄 변경하는 작업 지시가 아니다. Backend 저장소의 실행 규칙을 이 문서만으로 변경한 것으로 간주하지 않으며, 관련 협업 시 이 기준과 소비 영향을 함께 전달한다.

사용자 명시 요청으로 [Backend Issue21](https://github.com/heo0328/lostparty-backend/issues/21)에 공통 원문·서버 자체 지침/문서 반영·네이티브 소비 영향/데이터 재사용·검증·릴리즈 후 최적화 안내 조건을 전달했다(2026-10-23, 게시원문MATCH). 현재 전달 완료·Backend 반영 문서/적용 범위 회신 대기이며, 구현 중인 레이드 계약 Issue13과 분리한다. 이 상태를 Backend 적용 완료로 표현하지 않는다.

## 1. 가장 먼저 판단할 것

기술의 과시, 패턴 이름, 적은 코드량보다 **사용자가 앱의 목적과 현재 페이지의 기능을 이해하고, 의도한 일을 쉽고 예측 가능하게 수행하는 것**을 우선한다. 보안·데이터 정합성은 이 경험을 지탱하는 필수 조건이다.

- 사용자가 이 페이지에서 무엇을 할 수 있는지, 현재 어떤 캐릭터·주차·방에 행동하는지 알아볼 수 있어야 한다.
- 로딩·저장 중·성공·실패·결과 불명을 구분한다. 저장 성공 뒤 재조회 실패를 저장 실패처럼 보여 중복 행동을 유도하지 않는다.
- 비동기 완료 때문에 화면이 불필요하게 움직이거나 입력이 사라지거나, 이전 회원·선택의 응답이 현재 화면을 덮지 않아야 한다.
- 내부 계약·토큰·세대·저장 구조의 복잡함을 추가 화면·클릭·장문 설명으로 사용자에게 떠넘기지 않는다.
- 기존 승인 UI/UX 유지·변경 동의 규칙은 [디자인 공통 원칙](../design/LOSTPARTY_DESIGN_SYSTEM_V1_REQUEST.md)을 따른다. 이 문서는 임의 리디자인의 승인이 아니다.

## 2. 코드와 패턴의 선택

짧은 코드·적은 파일·적은 API를 목표 지표로 사용하지 않는다. 필요한 검증을 생략한 짧은 코드도, 동일 정책을 여러 곳에 복제한 긴 코드도 품질을 보장하지 않는다. 변경 이유와 영향 범위, 정상 동작의 보존, 원인 추적 가능성으로 판단한다.

작업 전 관련 코드를 읽고 다음을 작업 규모에 맞게 몇 문장으로 설명한다. 모든 작은 수정마다 별도 설계서를 만들지는 않는다. 기존 계약을 재사용하면 근거 링크와 그 이유만 남긴다.

1. 해결할 사용자 문제와 보존할 기존 흐름은 무엇인가?
2. 데이터·정책·화면 상태·비동기 작업은 각각 누가 소유하는가?
3. 기존 패턴을 유지하거나 다른 방식을 쓰는 이유는 무엇인가? 실제 이점·비용과 영향받는 호출자는 무엇인가?
4. 무엇을 자동 시험하고, 무엇을 기기에서 확인하거나 측정해야 하는가?

Flutter는 현재 feature-first/MVVM 방향을 기본으로 View·ViewModel/Controller·Repository/Client·저장 책임을 구분한다. Python은 실제 라우터·서비스/명령·DB 트랜잭션 구조를 기준으로 권한·업무 정책·저장 경계를 명확히 한다. 특정 패턴을 모든 기능에 강제로 적용하거나 계층을 늘리는 것 자체를 개선으로 취급하지 않는다. 기존 계층과 다른 선택이 필요하면 이유와 책임 경계를 기록한다.

지시받은 함수만 고치는 데서 멈추지 않고 같은 데이터의 생산자·저장소·소비자와 관련 비동기 수명을 확인한다. 구조적 문제가 발견되면 근거·대안·후속 범위를 보고하며, 무관한 정상 기능까지 수정 범위를 넓히지 않는다.

## 3. API와 앱 데이터의 책임

독립된 목적·권한·수명을 가진 세분화 API는 유효하다. 전체 조회와 부분 조회가 함께 있는 것도 문제 자체는 아니다. API 수와 실제 요청 횟수, 서버 내부 정책 중복은 별개로 평가한다.

- 호출이 필요한 이유를 확인한다. 화면 진입 자체가 항상 새 요청의 이유가 되는 것은 아니다. 이미 받은 데이터·진행 중 요청을 재사용할 수 있는지 살핀다.
- 앱의 현재 상태를 관리하는 기준 저장소와 화면별 투영을 식별한다. 모든 데이터를 하나의 거대 저장소로 합치라는 뜻은 아니다. 도메인별 원본과 갱신 책임을 명확히 한다.
- 전체 응답을 별도로 보관하면 그것이 과거 시점 스냅샷인지 현재 상태인지 구분한다. 전체와 부분 데이터를 모두 수정 가능한 원본으로 유지해 이중 갱신 의무를 만들지 않는다.
- 전체/부분 조회의 반영, 쓰기 성공 이후 부분 갱신·무효화·재조회, 다른 화면 통지 방법을 정한다. 로컬 데이터에는 회원·환경·식별자·실제 주차·revision/유효 범위가 있어야 한다.
- 동일 진행 요청 공유와 응답 캐시 재사용은 구분한다. 명시 갱신·쓰기를 검증하는 재조회까지 무조건 합치거나 생략하지 않는다.
- 표시 설정·캐릭터 정보·타인이 바꾸는 남은 자리처럼 데이터별 변경 주체와 신선도 요구를 나눈다. 빠른 로컬 표시는 서버의 최신 참가·권한·동시성 검증을 대신하지 않는다.
- Endpoint별로 DB/정책을 중복 작성하지 않는다. 필요한 조회 형태는 달라도 공통 권한·업무 정책·원자적 명령 경계를 재사용할 수 있는지 판단한다.

초기 규모에서는 추정 트래픽 비용을 이유로 복잡한 캐시·이벤트 체계를 선제 도입하지 않는다. 실제 대기·중복 요청·상태 불일치와 개발/장애 비용부터 확인한다. 현재 규모를 근거로 불필요한 요청과 무제한 메모리 보관을 방치하지도 않는다.

## 4. 비동기·메모리·검증

- 화면 이탈·재진입, 회원 전환, 연속 선택, 중복 터치, 늦은 응답, 중도 실패·결과 불명에서 반영 대상과 종료 조건을 정의한다.
- 리스너·타이머·스트림·작업·캐시의 소유자와 해제/상한을 확인한다. 논리적으로 오래된 응답을 무시하는 것과 실제 네트워크 작업 취소·객체 해제를 구분한다.
- dispose 코드가 있다는 이유로 메모리 누수 없음으로 보고하지 않는다. 반복 진입/이탈·갱신 전후의 객체/메모리 추이를 실제 측정한 경우에만 그 결과를 주장한다. 성능도 요청 수·시간·응답 크기 등 측정 범위와 조건을 명시한다.
- 시험 횟수·개수보다 영향 경계와 회귀 보호를 설명한다. 구간 최종 시험은 권한·CAS·중복·원자성·저장/재시도 등 기기로 만들기 어려운 경계에 집중한다.
- 섹션 종료 시 조회→수정→다른 화면→복귀 흐름에서 같은 상태를 보는지 확인한다. 사용자 수동 검증과 자동 시험을 구분하고 같은 정상 UI 시험을 관성적으로 중복하지 않는다.
- 명확히 변경된 위험에 맞춰 검증하며 순수 문서 수정에 Flutter/Python 시험을 반복하지 않는다. 설치·기기 조작은 사용자 담당이다.

## 6. 서비스 복구 릴리즈 이후 최적화 검토

우선 목표는 기존 Firebase가 담당하던 실제 서비스 기능을 Python Backend와 앱으로 대체하고, 필수 결함·실회원/디바이스 검증을 마쳐 다시 서비스 가능한 릴리즈를 배포하는 것이다. 이 문서 추가로 그 완료나 릴리즈 승인을 선언하지 않는다. 현재 승인된 기능 구현·장애 복구 중에도 위 판단 기준을 적용하되, 전면 리팩토링을 끼워 넣지 않는다.

해당 릴리즈 배포와 안정 상태가 확인되는 종료 보고에서 사용자에게 다음을 안내한다.

> 서비스 복구 릴리즈가 배포됐습니다. 이후 필요하면 이 배포본의 `main` 커밋/태그를 기준으로 목적이 명확한 최적화 브랜치를 분기해, 측정과 회귀 보호를 갖춰 별도 개선할 수 있습니다.

최적화는 그 시점에 필요성과 범위를 판단해 착수한다. 지금 브랜치를 만들거나 자동 감시·예약 작업을 생성하지 않는다. 시작 시 릴리즈 태그/실제 main·dev 차이를 확인하고 `refactor/<목적>` 등 기존 이름 규칙을 따른다. **배포된 main 기준 분기**는 이 후속 최적화에 대한 사용자 지정이며, 일반 기능 개발의 dev 기준 흐름을 바꾸지 않는다. 완료 시 최신 dev와 정합성을 검토하고 기존 검증·통합·릴리즈 절차로 되돌린다. main 직접 수정·강제 이력 변경은 하지 않는다.

최적화 착수는 대표 사용자 흐름·요청 지도·데이터 소유/갱신 지도·시간/메모리 기준선부터 시작한다. 실제 근거가 있는 중복 요청·상태 불일치·수명 문제를 독립 구간으로 고치고 전후를 비교한다. API 합치기, 파일 분할, 패턴 교체를 사전 결론으로 두지 않는다.

이 문서는 현재 작업 브랜치에 코드·기획과 함께 보관하고, 해당 브랜치가 정식 절차로 dev·main에 통합될 때 함께 반영한다. 문서를 전달하기 위해 미완료 기능 브랜치를 조기에 병합하지 않는다.
