# Character Build 기본 무결성 검증 계약

## 1. 목적과 책임 범위

이 문서는 Lost Ark API의 전투력만으로 실제 사용 가능한 세팅을 단정하지 않고, 앱이 유지 가능한 범위에서 Character Build의 기본 무결성을 검증하는 기준이다.

높은 등급의 보석과 아크그리드 코어는 전투력을 높이지만, 같은 직업·같은 깨달음 안에서도 현재 사용하는 스킬과 맞지 않는 보석을 장착할 수 있다. 나이스단 Character에 본 Character의 고레벨 보석을 옮기면 실제 성능과 무관하게 전투력이 높아질 수 있으므로 `CombatPower`만으로 정상 세팅을 보증하지 않는다.

앱은 다음을 목표로 한다.

- 깨달음과 아크그리드 활성 조건의 기본 정합성을 확인한다.
- 질서의 해·달 필수 포인트를 확인한다.
- 보석 Tooltip의 직업과 현재 Character 직업을 비교한다.
- 현재 API 스킬 목록 또는 최소 특수 스킬 카탈로그에서 확인되는 보석을 구분한다.
- 명백한 타 직업 보석은 본인과 파티장에게 경고할 수 있는 최소 결과를 만든다.

앱은 다음을 보증하지 않는다.

- 직업별 최적 스킬트리, 트라이포드, 보석 배분 또는 아크그리드 국룰 조합
- 가능한 모든 해·달·별 조합의 우열
- 표시 전투력과 실제 레이드 성능의 비례 관계
- 패치마다 바뀌는 전체 빌드 메타의 자동 추적
- AI를 이용한 최적 빌드 판정

## 2. 유지보수 원칙

모든 직업의 전체 빌드와 아크그리드 조합을 수기 입력하지 않는다. 분기 또는 대규모 패치마다 전체 조합을 다시 작성해야 하는 구조는 채택하지 않는다.

정적 카탈로그는 다음의 작은 범위만 관리한다.

- 직업별 깨달음 1티어 두 분기와 역할
- 역할 판별과 조건 교차검증에 필요한 깨달음 4티어 이름
- `ArmorySkills`에서 직접 확인되지 않는 분기별 아이덴티티·아크패시브 보석 대상 1~2개
- 실제 API에서 확인한 대상명과 별칭

확인되지 않은 이름에 `스킬` 접미사를 추정해 일괄 추가하지 않는다. 진단 도구와 실제 Character 응답으로 확인한 값만 카탈로그 및 회귀 fixture에 반영한다.

## 3. 아크패시브와 역할 판정

- 깨달음 1티어 분기로 현재 Build 계열과 dealer/support 역할을 감지한다.
- 서포터 겸용 직업은 사용자가 선택한 역할이 아니라 현재 API의 활성 깨달음 근거와 교차 확인한다.
- 아크그리드 Tooltip이 요구하는 깨달음 1티어와 추가 아크패시브 조건을 현재 `ArkPassive.Effects`와 비교한다.
- 요구 조건이 없으면 해당 코어 조건 불일치로 기록한다.
- 전체 최적 조합을 판정하지 않고 API Tooltip에 명시된 활성 조건만 검증한다.

## 4. 아크그리드 최소 검증

정상 기본 조건은 다음과 같다.

- `질서의 해` 코어가 존재하고 14P 이상이어야 한다.
- `질서의 달` 코어가 존재하고 14P 이상이어야 한다.
- 해 또는 달이 없거나 14P 미만이면 기본 조건 미충족으로 기록한다.
- 유물 이상 해·달의 17P 미만 안내는 권장 효과 정보로 유지할 수 있지만 기본 무결성 실패로 사용하지 않는다.
- `질서의 별`은 직업과 조합에 따라 없어도 사이클이 가능하므로 필수 판정에서 제외한다.
- `혼돈의 해·달·별`은 공용 요소이며 이 계약의 필수 판정에서 제외한다.

현재 구현처럼 존재하는 해·달 코어의 점수만 순회해서는 안 된다. 해 또는 달 자체가 없는 경우도 명시적으로 검출해야 한다.

## 5. 보석 판정

각 보석은 `ArmoryGem.Gems.Slot`과 `ArmoryGem.Effects.Skills.GemSlot`으로 연결한 뒤 다음 순서로 판정한다.

1. `ArmoryProfile.CharacterClassName`에서 현재 Character 직업을 읽는다.
2. 장착 보석 Tooltip과 효과 설명/Tooltip의 보석 효과 구역에서 대괄호 직업명을 추출한다.
3. `[세레나데]`, `[풍요]`처럼 카탈로그 직업명이 아닌 대괄호 값은 직업으로 취급하지 않는다.
4. Tooltip 직업과 현재 Character 직업을 비교한다.
5. 직업이 일치하면 `ArmorySkills` 대상명과 직업별 최소 특수 스킬 카탈로그를 차례로 비교한다.

보석 결과는 다음 세 단계가 제품 기준이다.

### 정상 확인

- Tooltip 직업이 현재 Character 직업과 일치한다.
- 대상명이 API 스킬 목록 또는 현재 분기의 등록된 아이덴티티·아크패시브 보석 대상과 일치한다.

### 동일 직업·대상 미확인

- Tooltip 직업은 현재 Character 직업과 일치한다.
- 대상명이 API 스킬 목록과 등록 특수 스킬에서 확인되지 않는다.
- 다른 세팅의 일반 스킬 또는 아직 등록되지 않은 특수 스킬일 수 있으므로 아이덴티티라고 자동 확정하지 않는다.
- `해당 직업 보석은 맞지만 현재 스킬 또는 등록 특수 스킬에서 확인되지 않음`으로 안내한다.
- 빨간 타 직업 경고로 취급하지 않고 카탈로그 누락과 실제 세팅 불일치 가능성을 함께 남긴다.

### 다른 직업 보석

- Tooltip 직업이 현재 Character 직업과 다르다.
- 본인의 내 계정 화면에 빨간색 `다른 직업 보석 N개 · 확인 필요`를 표시한다.
- 타인이 보는 신청자·파티 구성원·그룹 Character 간략 카드에도 보석 확인 경고를 표시한다.
- 그룹의 **현재 구현 범위**는 membership 표시 Character Snapshot과 그룹 상세 **그룹원 목록 행**이다. 그룹원을 탭해 여는 **활동 Character 목록**에 원정대 다른 Character(예: 신청 A, 이상 보석 B)의 경고를 붙이는 요구는 별도 작업이며, **제품·아키텍처 정의를 먼저 확정한 뒤에만** 구현한다. 정의 전에는 착수하지 않는다.
- 동일한 대상명인 홀리나이트와 발키리의 `신앙 스킬`은 Tooltip 직업으로 구분한다.

Tooltip 직업 자체를 읽을 수 없는 응답은 다른 직업으로 단정하지 않고 별도 `검증 정보 없음`으로 처리한다.

## 6. 실제 API 교차검증 결과 — 2026-09-08

`tool/lost_ark_gem_probe.dart`로 4개 서포터 겸용 직업의 dealer/support 실제 Character를 각각 조회했다. 전체 8개 Build, 보석 88개에서 Tooltip 직업이 현재 Character 직업과 일치했고 다음 특수 대상명이 확인됐다.

| 직업·역할 | 실제 API 대상명 | 현재 카탈로그 판정 |
|---|---|---|
| 바드 support | `세레나데 스킬` | 정상 |
| 바드 dealer | `템페스트 스킬` | 정상 |
| 발키리 support | `신앙 스킬` | 정상 |
| 발키리 dealer | `종언의 빛` | 정상 |
| 홀리나이트 support | `신앙 스킬` | 정상 |
| 홀리나이트 dealer | `심판자 스킬` | 정상 |
| 도화가 support | `음양 스킬` | 정상 |
| 도화가 dealer | `떠오르는 달` | 정상 |

위 결과로 `신앙 스킬`이라는 이름만으로 직업을 확정할 수 없고 Tooltip의 `[홀리나이트]`·`[발키리]` 범위를 함께 비교해야 함을 확인했다.

## 7. 표시 정책

내 계정의 기본 표시는 다음과 같다.

- 전체 정상: 추가 경고 없음
- 동일 직업·대상 미확인: `동일 직업 보석 · 현재 스킬에서 미확인 N개`
- 다른 직업 보석: 빨간색 `다른 직업 보석 N개 · 확인 필요`

타인용 간략 카드는 원본 Armory나 전체 보석명을 노출하지 않고 다음 요약만 표시한다.

- `보석 확인 완료`
- `미확인 보석 N개`
- 빨간색 `다른 직업 보석 감지`

아크패시브·아크그리드 조건 미충족은 보석 직업 불일치와 별도 상태로 표시한다. `다른 직업 보석`만 보석 영역의 빨간 경고 조건이며 두 문제를 하나의 메시지로 합치지 않는다.

## 8. 서버 Snapshot 후보와 경계

타인이 보는 카드에 결과를 표시하려면 전체 Armory JSON 대신 최소 검증 요약만 역할별 Build Snapshot 또는 신청 시점 불변 Snapshot에 포함한다.

```text
gemValidationStatus
foreignClassGemCount
unverifiedSameClassGemCount
gemValidatedAt
catalogVersion
```

- 실제 저장 위치는 파티 신청 문서의 `submittedBuildSnapshot` 내부와, 파티·그룹 membership 문서의 `gemValidationSnapshot` 맵으로 확정했다.
- 승인 경로는 신청 Snapshot을 재사용하고, 직접 참가·참가 Character 변경·그룹 생성·초대코드 가입·그룹 본인 표시 갱신은 선택 Character의 최신 로컬 Build Snapshot에서 같은 다섯 필드를 만든다.
- 기존 문서에 필드가 없으면 검증 요약을 `null`로 읽어 기존 UI와 호환한다.
- 보석 이름, Tooltip 원문과 전체 장비 JSON은 서버에 올리지 않는다.
- 보석 요약은 클라이언트가 산출한 표시 정보라 Firestore Rules가 진위를 보장할 수 없다. Rules 복잡도와 Ruleset 저장 실패를 피하기 위해 이 다섯 필드의 스키마 검증을 추가하지 않고, 공식 앱의 쓰기 생성기와 방어적 읽기에서 완결성·타입·상태를 처리한다. 파티 Character 변경과 그룹 본인 Snapshot 갱신 Rules의 `affectedKeys` allowlist에 `gemValidationSnapshot`만 추가한다. 신청 권한·Character 소유권 등 기존 서버 경계는 그대로 유지한다.
- 앱 시작 갱신 결과와 파티 신청 시점 Snapshot의 시각이 다를 수 있으므로 검증 시각을 함께 보존한다.

## 9. 구현 순서

진행 상태: 2026-09-08 1~7단계와 8단계의 파티 신청자 카드 구간을 구현하고 자동·실기기 검증했다. 이후 Rules 경고 제거본도 2026-09-10 정상 배포했다. 2026-09-10 파티 membership·구성원 카드 전파를 구현하고 최신 Rules를 정상 배포했다. 그룹 membership 전파는 `cursor/group-membership-gem-snapshot`에서 구현·표적 자동 검증을 마쳤고, CLI `/test` 503 뒤 Firebase 콘솔 붙여넣기 게시로 운영 Rules를 반영했다. 두 기기 실기기 확인이 남았다.

1. 실제 API 진단 도구에 깨달음 1·4티어, 아크그리드 해·달 존재/포인트·조건, API 스킬과 보석 종합 결과를 추가한다.
2. Tooltip 직업 추출과 슬롯 연결을 운영 분석기로 옮긴다.
3. 해·달 존재 및 각 14P 이상 조건을 보강한다.
4. 2026-09-08 실제 결과로 4직업 특수 대상명과 회귀 fixture를 교정한다.
5. 정상, 동일 직업·대상 미확인, 다른 직업 보석 상태를 분리한다.
6. 내 계정 화면에 본인용 검증 결과를 적용한다.
7. 최소 서버 Snapshot과 Rules 변경안을 별도 검토한다. (완료)
8. 승인된 경우 신청자·파티 구성원·그룹 Character 간략 카드에 요약 경고를 적용한다. (신청자·파티·그룹 membership 구현·Rules 운영 반영 완료, 그룹 실기기 대기)
9. 여러 일반 딜러 직업으로 같은 기준을 실계정 검증한다.

2단계 구현 결과 운영 분석기의 각 보석은 `verified`, `sameClassTargetUnverified`, `foreignClass`, `unavailable`을 보존한다. 대괄호 값은 게임 카탈로그 직업명과 일치할 때만 직업으로 인정하며, 진단 도구도 운영 분석기와 같은 공용 추출기를 사용한다.

4단계 구현 결과 카탈로그 버전은 `2026.09.08`이며, 실제 API에서 확인한 위 8개 Build의 대상명을 분기별 최소 특수 대상으로 등록했다. 회귀 fixture도 `measuredAgainstLiveApi: true`로 교정했다.

3단계 구현 결과 운영 분석은 질서의 해·달 각각의 최고 포인트를 보존하고, 존재 여부와 각 14P 충족 여부 및 전체 충족 결과를 제공한다. 해·달 누락은 개별 warning이며 질서의 별과 혼돈 코어는 이 결과에 포함하지 않는다. 기존 유물 이상 17P 미만 안내는 권장 정보로 유지한다.

5~6단계 구현 결과 보석별 상태를 캐릭터 단위 개수와 대표 상태로 집계한다. 내 계정 카드는 선호 역할의 최신 로컬 Build Snapshot을 사용하며 정상은 추가 표시하지 않고, 동일 직업 대상 미확인은 중립 안내, 다른 직업은 빨간 경고, Tooltip 직업 정보가 없으면 중립 `보석 검증 정보 없음`으로 표시한다. 추가 네트워크 호출과 DB·Firestore 변경은 없다.

7단계 및 8단계 신청자 구간 구현 결과 지원 시 선택 역할의 로컬 Build Snapshot에서 최소 검증 요약을 생성해 `submittedBuildSnapshot`에 함께 저장한다. 신청자 카드에서는 정상은 숨기고 동일 직업 대상 미확인·검증 불가는 중립, 다른 직업 보석만 빨간 경고로 표시한다. 과거 신청과 불완전한 선택 필드는 검증 요약 없음으로 읽으며 신청 수치 자체는 유지한다.

8단계 membership 구간 구현 결과 승인·직접 참가·참가 Character 변경이 membership의 `gemValidationSnapshot`에 같은 다섯 필드를 기록한다. 파티 구성원 카드도 신청자와 같은 중립/빨간 경고 정책을 사용하며, 과거 membership과 검증 없는 Character는 아이템 레벨·전투력만으로 표시한다. 그룹 Snapshot은 이 구간에서 변경하지 않았다.

시너지 필터/슬롯 구현은 이 계약의 1~5단계 판정 경계를 고정한 뒤 진행한다.

## 10. 차후 확장 — 점진적 인게임 Build 별칭 카탈로그

상태: 아이디어와 영향 범위만 기록. 현재 기본 무결성 작업에는 포함하지 않는다.

모든 직업의 가능한 아크그리드 조합을 한 번에 수기 입력하지 않는다. 사용자가 실제 조합과 통칭을 확인할 때마다 정적 카탈로그에 하나씩 추가하는 점진적 방식을 사용한다.

예시 후보:

```text
직업: 소울이터
깨달음 분기: 만월
질서의 해: 망자의 발걸음
질서의 달: 소울 코어
질서의 별: 빙의
인게임 별칭: 망소빙
```

`붕쯔디트`처럼 널리 쓰이는 다른 별칭도 실제 직업·깨달음·해·달·별 구성 근거를 확인한 뒤 같은 방식으로 추가할 수 있다. 통칭만 먼저 등록하거나 이름에서 코어 조합을 추정하지 않는다.

별칭 판정 키 후보는 다음과 같다.

```text
classId
+ enlightenmentBranchId
+ orderSunCoreName
+ orderMoonCoreName
+ optional orderStarCoreName
```

- 별칭은 최적 Build 또는 성능 보증이 아니라 현재 API에서 확인된 조합의 표시 이름이다.
- 별이 없는 유효 조합과 별에 따라 별칭이 달라지는 조합을 모두 표현할 수 있어야 한다.
- 패치로 코어명이나 조건이 바뀌면 해당 엔트리만 수정하고 전체 직업 조합을 다시 작성하지 않는다.
- 카탈로그에 없는 조합은 오류가 아니라 `별칭 미등록`이다.
- 파티 상세의 간략 카드에는 이름·직업·전투력·아이템 레벨에 더해 등록된 경우에만 별칭 한 개를 짧은 chip으로 표시한다.
- 보석·아크그리드 검증 경고는 별칭과 분리한다. 다른 직업 보석은 빨간 경고, 동일 직업 대상 미확인은 중립 안내를 유지한다.

### 현재 데이터 경계와 서버 영향

- 소유자 기기의 `CharacterBuildSnapshots.rawJson`에는 역할별 Lost Ark API 원문이 로컬에 저장된다.
- `CharacterBuildAnalysis.catalogDetection`은 로컬 분석 시 `branchId`와 표시명을 만들지만 별도 서버 필드로 게시하지 않는다.
- 현재 파티 신청 `submittedBuildSnapshot`은 itemLevel·combatPower만 저장한다.
- 현재 파티 membership과 그룹 표시 Snapshot도 직업·역할·아이템 레벨·전투력을 중심으로 하며 깨달음 분기와 아크그리드 코어명을 포함하지 않는다.
- 따라서 타인의 카드에서 Build 별칭을 다시 계산할 수 없다. 전체 rawJson을 서버에 올리지 않고 소유자 기기에서 계산한 `buildAliasId`, `buildAliasLabel`, `buildCatalogVersion`, `buildValidatedAt` 정도의 최소 결과만 신청·membership Snapshot에 추가하는 방안을 검토한다.
- 이 추가는 Firestore 쓰기 필드 allowlist, Rules, write plan, read model과 구버전 null 호환 수정이 필요하므로 별도 승인 구간이다.

서버 변경량이 커지거나 기존 파티 명령의 Rules 복잡도를 유의미하게 높이면 타인 카드 별칭 표시는 보류하고 내 계정의 로컬 표시까지만 구현한다.

## 11. 차후 확장 — 사용자 개인 직업 메모

상태: 제품 아이디어와 최소 구현 경계만 기록. 현재 작업에는 포함하지 않는다.

직업·깨달음·질서 해·달·별 선택 페이지, 계층형 메모 합성, 파티 카드 표시와 사용자 간 공유의 최신 제품 구상은 [`../product/BUILD_MEMO_SHARING.md`](../product/BUILD_MEMO_SHARING.md)를 기준으로 한다. 아래 내용은 초기 범위 판단 기록이다.

사용자가 직업에 대해 기억하고 싶은 개인 평가를 짧게 저장하고, 해당 직업 Character가 파티에 신청하거나 참가했을 때 본인 화면에만 보여주는 기능이다.

예시:

- 무력화가 좋음
- 유틸이 좋고 트라이에 편함
- 숙제 파티에서 딜량이 좋음

### 1차 권장 범위 — 직업 단위 로컬 메모

- 카드에 이미 `classNameSnapshot`이 있으므로 타인의 추가 Build 데이터를 읽지 않아도 직업 메모를 찾을 수 있다.
- 메모는 로컬 Drift에 `playerId + classId`를 키로 저장한다.
- Firestore에 업로드하거나 다른 사용자에게 공개하지 않는다.
- 표시 문자열 대신 게임 카탈로그의 안정적인 `classId`를 키로 사용하고 알 수 없는 직업은 API 직업명 fallback을 둔다.
- 파티 신청자·파티 구성원 카드에서는 메모 전체를 상시 길게 노출하지 않고 메모 아이콘 또는 한 줄 요약으로 표시한다.
- 기기 삭제·앱 재설치 시 사라지는 개인 메모라는 점을 명시한다. 동기화·백업은 별도 요구가 생기기 전에는 만들지 않는다.

이 범위는 로컬 테이블·Repository·간단한 편집 UI와 카드 조회 연결만 필요하며 Firestore 스키마·Rules 변경은 필요하지 않다.

### 2차 후보 — 깨달음 분기 또는 Build 별칭별 메모

`소울이터 전체`가 아니라 `만월`, `그믐` 또는 `망소빙`처럼 세부 Build별로 다른 메모를 보여주려면 카드 데이터에 최소 `branchId` 또는 `buildAliasId`가 필요하다. 현재 신청·membership 서버 Snapshot에는 이 값이 없으므로 직업 단위 메모처럼 로컬만으로 구현할 수 없다.

- Build 별칭 최소 Snapshot이 먼저 승인·구현된 경우에만 `playerId + classId + branchId/buildAliasId` 키의 로컬 메모를 검토한다.
- 개인 메모 본문은 이 경우에도 서버에 올리지 않고 본인 로컬에만 둔다.
- 별칭이나 분기 정보를 받지 못한 과거 카드에는 직업 단위 메모만 fallback으로 표시한다.

## 12. 차후 확장의 결정 순서

1. 기본 무결성 판정과 보석 직업 경고를 먼저 완료한다.
2. 실제 사례가 생길 때마다 Build 별칭 카탈로그 엔트리를 점진적으로 추가한다.
3. 내 계정에서 로컬 별칭 판정이 안정적인지 검증한다.
4. 직업 단위 개인 메모는 서버 변경 없는 독립 작업으로 판단한다.
5. 타인 카드 Build 별칭에 필요한 최소 Snapshot·Rules 변경량을 산정한다.
6. 변경량이 허용될 때만 파티 신청·membership 카드 별칭을 구현한다.
7. 분기/별칭별 개인 메모는 최소 Snapshot 구현 후 다시 결정한다.
