## 목표와 현재 기준

최우선 제품 목표는 Rules 변경 때마다 수시간~수일의 수정·게시 재시도를 요구하는 상태를 끝내고,
복잡도를 낮춰 정상 변경을 무리 없이 게시할 수 있는 상태를 만들고 유지하는 것이다.
삭제한 검사·로컬 이전량·전체 크기/깊이는 이를 위한 중간 지표다. 수치 감소만으로 최종 성공을 판정하지 않는다.
최초 안정화에서는 최종 전체본의 실제 게시가 첫 시도에 성공하고 경고0·활성 source SHA 일치를 확인한다.
단 한 번의 성공으로 지속 안정성을 입증했다고 하지 않는다. 이후 실제 기능 변경의 게시 결과를 같은 기준으로 누적 확인한다.
안정성 확인을 위한 무의미한 재게시나 재시도는 하지 않는다.

목표는 서버가 불필요하게 반복하는 검증과 표시·선택 보조 처리를 제거하거나 앱으로 이전하여
실제 전체 Rules의 양과 호출 복잡도를 줄이는 것이다. 모든 기존 검사를 다른 구조로 옮기는 작업이 아니다.
Spark 무료 유지, 앱 업데이트·데이터 이행 허용, 기능·이력 보존이 전제다.

기존681건 검증은 활용 가능한 권한 회귀 근거이며 최적화 달성 수치가 아니다.

감소율이나 목표 바이트 수를 완료 조건으로 설정하지 않는다. 크기·깊이·삭제량은 변경 효과의 참고 지표다.
불필요한 서버 검사와 호출 구조를 간소화하되 기존 기능·권한을 유지하고 실제 게시 정상화로 판단한다.
로컬 preflight의 크기·깊이 상한은 기존 후보 대비 증가를 검토하게 하는 장치이며 축소 목표나 게시 성공 판정이 아니다.
게시 성공은 별도 결과다. 소스 감소만으로409/503 원인이나 해결을 확정하지 않는다.

## 자율 진행과 멈추는 조건

- 지정한 작은 단위 안의 일상 구현 선택·문서 갱신·로컬 검증은 이어간다. 다음 단위로 자동 확장하지 않는다.
- 요청 한도/컨텍스트 중단에는 마지막 완료 변경·현재 SHA·실행 중 프로세스·다음 명령·남은 검증을 기록한다.
  재개 시 동일 검증을 처음부터 반복하지 않고 해당 지점부터 계속한다.
- 보안/제품 계약 변경이 불가피하거나 운영 데이터·계정 접근이 필요한 경우만 필요한 결정을 좁혀 요청한다.
  독립적으로 진행 가능한 다른 승인 범위는 계속한다. 임의 기능 삭제·유료 서버 전환은 하지 않는다.
- 같은 실패의 명령 반복·근거 없는 조건 완화는 하지 않는다. 확인된 원인에 필요한 변경만 한다.
- 브랜치 생성·커밋·푸시·머지 금지는 유지한다. 현재 목적 브랜치의 미커밋 작업을 보존한다.
- 이번 계획과 그에 따른 로컬 구현 단계에는 운영 데이터 변경·배포를 포함하지 않는다.
  최종 후보 검증 후 운영 이행/게시 범위를 별도로 명시한다. 게시 실패 시1회 원인 조사 원칙을 유지한다.

## 완료 판정과 최종 보고

코드 구현 완료와 운영 문제 해결 완료를 분리한다. 전체 로컬 구현 단계의 완료 조건은 다음과 같다. 개별 단위 완료와 구분한다.

1. 어떤 서버 검사를 삭제했고 어떤 처리를 앱으로 이전했는지 실제 함수/필드·앱 경로로 설명할 수 있다.
2. 해당 변경이 연결된 **전체 Rules**와 실제 앱 코드가 있고, 기준 대비 순감소량·깊이·미포함 기능이 공개돼 있다.
3. 정상 기능의 실수 누락이나 보안 약화 없이 선택한 변경의 확인 범위를 통과했다. 실패를 성공으로 세지 않는다.
4. 데이터 이행·구버전 차단이 필요한 항목은 준비 여부와 운영 적용 순서가 분리돼 있다.
5. 사용자에게 구현 결과/기능 영향/실제 감소량/남은 운영·실기기 확인을 한 번에 보고한다.

감소율로 완료·미완료를 판정하지 않는다. 실제 간소화 내용과 남은 기능·권한·게시 확인 사항을 제시한다.
운영 해결 완료에는 이후 실제 게시 성공·경고0·활성 소스 일치·필요 실기기 인수가 추가로 필요하다.
§48 인증/Claim 동시성 미확인과 BUG-024 운영 미반영은 기존 미완료로 남기며 새 성공 수로 덮지 않는다.

## 게시 안정성 유지 기준

- 검증된 전체본의 source bytes·호출 깊이·가능한 원격 컴파일 지표·게시 단계별 결과·소요시간을 기준 기록으로 남긴다.
  특정 크기 이하이면 반드시 게시된다고 보장하거나 소스 크기를 compiled 크기로 환산하지 않는다.
- 후속 Rules 변경에는 기준 대비 증가량과 새 교차 조회/중복 validator/호환 분기 추가 이유를 확인한다.
  표시·정제·추천 로직이 서버 검증으로 다시 유입되지 않도록 책임 경계를 유지한다.
- 정상 기능 업데이트의 실제 게시에서 첫 시도 성공 여부·경고·활성 SHA·소요시간을 기록한다.
