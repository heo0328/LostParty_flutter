작업 브랜치 `fix/party-participation-consistency`. 설계 이후 사용자 승인으로 구현 진행 중이다. 현재 실행 상태는 NEXT_WORK를 따른다.
브랜치 종료 조건은 아래 네 흐름과 수동 완료의 상태 일치를 최소 수정으로 복구하고 관련 서버 경계·사용자 실기기 확인을 마치는 것이다.

## 1. 관찰 사실과 조사 범위

1. 8인 **정원** 공대에서 1파티의 딜러 공대장·딜러/서포터 공대원 구성 이후 공대원 자리 이동, 공대장의 서포터 캐릭터 변경이 자리 확인 실패로 막힘. 실제 참가 인원·이동 대상·정확한 메시지/실패 단계는 미확정이다.
2. 자리 변경을 하지 않은 경우도 발생했다고 추가 보고됐다. 자리 변경만을 공통 원인으로 가정하지 않는다.
3. 다음 주 함께하기로 새 주차 모집에 참가한 것으로 보이는 캐릭터에 금주 참가 ⓘ 표시가 없음.
4. 해당 캐릭터의 수동 완료가 “참가 기록을 안전하게 정리할 수 없습니다” 계열 메시지로 실패한다.
5. 사용자는 주간 경계를 일요일 15시 KST로 바꾸어 테스트 중이다. 로컬 `raid_cycle_schedule.dart`의 두 줄 변경은 보존하며 커밋·dev 병합에서는 제외했다. dev 기준은 수요일 06시다.

이번 범위: 자리 이동/교환, 참가 캐릭터 변경(일반 진행/완료 후 다음 주 준비), 현재 참가 표시, 반복 전환 이후 표시와 수동 완료의 연결.
제외: 운영 데이터 직접 수정/삭제·일괄 이행, 초기화 시간 변경/원복, 불필요한 Rules 재게시, 계정 복구키, 타 소유자 고아 관계 전체 정리, 신규 서버/요금제, 파티 구성 제품 정책 변경.

## 2. 실제 연결과 데이터 책임

경로는 저장소 루트 기준이다. 이하 사실은 정적 코드 조사 결과이며 사용자 방의 서버 데이터 재현 결과가 아니다.

| 흐름 | 현재 실제 연결/데이터 | 확인할 경계 |
|---|---|---|
| 상세·후보 | `party_read_detail_page.dart::_occupiedMembersForComposition`, `FirestorePartyReadRepository.watchRecruitmentMembers` → members 스트림 → 후보 서비스 → `PartyCompositionPolicy` | 멤버의 위치·역할·직업과 모집 revision/구성이 같은 시점인가 |
| 캐릭터 변경 | Router → `FirestorePartyAtomicMemberMutationRepository.changeCharacter` → `PartyAtomicMemberMutationWritePlan` | 서버 재조회한 모집 `partySlots`와 본인 membership/이전 state, 새 캐릭터 소유권/점유 |
| 자리 이동 | 같은 Repository의 `repositionMembers` → `PartyAtomicRepositionWritePlan` | 모집+1명 이동/2명 교환 membership+필요 listing+이벤트 원자 반영 |
| 반복 전환 | Router → `PartyAtomicCycleCommandAdapter` → `FirestorePartyAtomicCommandRepository` → 인증 후 `PartyAtomicWritePlan` | 이전 revision/주차/저장 경계, guard, 현재 슬롯의 대상 전원 state 쓰기 |
| ⓘ 표시 | Router → `FirestoreWeeklyRaidStatusRepository` → `watchCurrentOwnershipRecords` → `WeeklyRaidStatusProjector` → `MyAccountViewModel`/`WeeklyRaidStatusItem` → 카드 | 현재 cycleKey 쿼리, 소유권 필터, strict mapper 예외, 로컬/서버 캐릭터 ID 연결 |
| 수동 완료 | `MyAccountPage` → `MyAccountViewModel.inspectWeeklyRaidCompletionImpact` → `FirestoreWeeklyRaidStatusCommandRepository` → 확인 후 완료 Transaction | 사전 영향 조회와 최종 쓰기 실패를 구분; 원장·방·주차·멤버·소유권 연결 |

### 식별자·권한·수명

- Auth UID는 authBindings를 통해 영속 playerId로 해석한다. membership 문서 키는 playerId이며 로컬 Character ID와 서버 characterId를 혼용하지 않는다.
- 현재 개인 원장은 `players/{playerId}/raidStates/{characterId}_{raidId}`다. cycleKey는 문서 필드이며 같은 경로를 새 주차에 갱신한다. 난이도가 달라도 동일 raidId의 참가/완료 중복을 허용하지 않는다.
- `recruitments/{id}.partySlots`는 최대8명 현재 구성, `members/{playerId}`는 멤버 표시·상태다. 그룹 raidListings는 원장이 아닌 조회용 요약이다.
- 자리 이동은 원장 Character/role/주차를 바꾸지 않는다. 일반 캐릭터 변경은 이전/새 참가 state를 원자 교체한다. 완료 후 준비 변경은 이번 주 완료 원장을 지우지 않는다.
- availability-only stub은 참가/완료가 아니다. 전환 인증 중간 상태만으로 ⓘ 표시를 켜거나 완료를 허용하지 않는다.
- 공대장은 타인의 private state를 읽는 방식으로 검증하지 않는다. 기존 권한·소유 차수·최대 인원·원자성·완료 보존을 유지한다.

## 3. 현재 확인된 코드와 원인 후보

### A. 위치/캐릭터 변경

후보는 members의 `className/role/partyIndex/slotIndex`를 이용하지만 최종 Write Plan은 모집의 `partySlots.classKey/role/위치`를 이용한다. `resolveOccupancy`는 누락·중복 위치를 화면 계산 중 빈자리로 보정할 수 있다. 화면에 자리가 보이는 것만으로 저장 원장이 정상임을 입증하지 않는다.
`planReplacement`는 제자리→유효 빈자리→일반 멤버끼리 단일 교환 가능성을 검사하며 공대장 고정석은 옮기지 않는다. 유효한 서포터 자리가 남는 사례와 실제 정원 초과를 구분해야 한다.
자리 이동 Write Plan은 모집과 관련 membership을 함께 쓰고 state는 건드리지 않는다. 따라서 “이동했으니 개인 원장이 반드시 손상됐다”는 결론은 근거가 없다.
사용자 표현의 자리 확인 실패와 정확히 일치하는 문자열은 확인하지 못했다. 현재 UI의 구성 불완전/구성 불가, membership invalidComposition/permissionDenied 등을 실제 실패 단계로 매핑하는 것이 우선이다.

### B. ⓘ 누락/수동 완료

상태 Repository는 raidStates·legacy Claim·legacy assignment를 **요청 cycleKey와 동일한 문서만** 구독한다. 소유권 검증을 통과한 레코드만 projector에 넘긴다. 원장이 이전 주차이거나 잘못된 소유 차수이면 모집 참가 화면과 표시가 달라질 수 있다.
내 계정의 해당 오류 문구는 `WeeklyRaidClaimCommandFailure.stateInconsistent`에 대응한다. 사전 조회의 `_WeeklyRaidStateContractException`도 이 결과가 되므로 Rules가 실제 쓰기를 거절했다고 단정할 수 없다. 상세 화면의 고아 정리 오류 문구와도 구분한다.
완료 Repository의 사전 확인은 원장 주차/참조 방/현재 회차/멤버 목록을 대조한다. 정상 참가이면 탈퇴·승계/마지막1인 해산·완료를 원자 수행하는 기존 경로를 써야 한다. 상태 불일치를 자동 고아 삭제로 우회하지 않는다.

### C. 주차 전환과 임시 시간

`PartyAtomicWritePlan._advanceRaidState`는 현재 슬롯의 characterId/role/ownershipRevision과 nextCycleKey를 기록한다. 최종 Repository는 모집과 대상 state 쓰기를 같은 Transaction에 넣는다. 전환됐다는 UI 관찰과 실제 advance 성공/실패·인증만 성공한 상태를 구분한다.
`PartyCycleRuntime`은 경계 타이머와 resume 갱신을 갖추고 Router는 refreshListenable을 연결한다. `/account`에는 cycleKey 기반 ValueKey가 있다. ViewModel의 cycleKey가 final이라는 사실만으로 재구독 결함이라고 확정하지 않는다. 유지되는 다른 화면·이미 열린 확인창·비동기 후보 응답도 함께 확인한다.
`PartyCyclePolicy.fromKey`는 현재 설정 요일이 아닌 날짜 키를 거절한다. 일요일 테스트 설정으로 수요일에 생성한 방을 읽는 경우의 경계 불일치를 별도 변수로 둔다. 기존 방의 저장 cycleStartedAt/EndsAt은 앱 설정 변경만으로 이행되지 않는다. 문제를 시간 설정 탓으로 일괄 종결하지 않는다.
후보 서비스 DI에는 `FakeRecruitmentClock(DateTime.now())`가 존재한다. 재검토에서 이 clock은 저장된 currentTime을 반환하고 후보 load가 그 값으로 주차를 계산함을 확인했다. 상세와 부작용은 §6.1을 따른다. 이번 사용자 실패와의 직접 인과는 아직 미확정이다.

## 4. 조사·수정 의사결정

### 1구간 — 실패 단계와 같은 시점의 근거 확정

**구현 범위:** 우선 기능 불변의 진단만. 원본을 변경하지 않고 아래 관찰을 확보한다. 현재 턴은 정적 조사까지만 수행했다.

**확인 범위:** 문제가 난 방1개/본인 캐릭터 기준으로 모집 id/revision/status/currentCycleKey/저장 시각 경계/continueTogether, partySlots/memberPlayerIds/raidStateTargets, 해당 membership의 캐릭터·역할·위치·소유 차수, 본인 state의 같은 필드, 화면 조회 cycleKey를 비교한다. 자리 이동 직전→직후→변경 실패, 전환 직전→인증→최종 전환→표시/수동 완료 순서를 분리한다.

토큰·API키·전체 개인 데이터는 로그에 남기지 않는다. 서버 읽기 금지 자료를 편의상 가져오지 않는다. 실제 ID가 없는 지금 임의 방을 골라 운영 데이터를 변경하지 않는다. 로그가 필요하면 이 구간의 종료 시 사용자에게 해당 방/액션/시각과 필요한 최소 로그를 한 번 요청한다.

**완료 조건:** 구성 후보 실패/클라이언트 사전검사/서버 Transaction 거절/전환 미완료/표시만 실패 중 실제 분기를 구별한다. “같은 팝업”만으로 여러 버그를 하나로 묶지 않는다.

### 2구간 — 자리·캐릭터 변경의 최소 수정

**구현 범위:** 근거가 확인된 reader/후보 정책 입력/Write Plan 연결만 수정한다. Domain 배치 정책은 재사용한다. members와 partySlots 불일치가 확인되면 발생 writer와 읽기 시점부터 고치며 UI에 별도 자리 계산을 덧붙이지 않는다. 단순한 빈자리/정원 문제라면 기존 정책을 보존하고 원인 안내만 정확히 구분한다.

**확인 범위:** 후보에서 허용한 구성과 최종 서버 재조회 결과의 의미 일치, 위치 고유성, 리더 고정석, 새 캐릭터 소유권·완료/다른 방 점유 거절, 실패 시 이전 캐릭터/state 유지. 네트워크 지연으로 서로 다른 revision을 잠시 읽은 상태와 영구 저장 손상을 구분한다.

**완료 조건:** 보고 구성과 자리 이동 없는 경우 모두 원인별 정상 처리/정당한 거절이 설명되며 타인 자동 이동·권한 확대가 없다.

### 3구간 — 주차·참가 표시·수동 완료 연결 복구

**구현 범위:** 원장 쓰기가 틀리면 전환 writer/대상 식별자를, 원장은 맞고 표시만 틀리면 구독/소유권/ID 투영을 수정한다. stale 주차 요청이 원인이면 조회와 최종 명령의 주차 계약 및 오래된 확인창 처리를 정렬한다. 모든 경우를 넓은 허용 조건으로 해결하지 않는다.

**확인 범위:** 준비 전 완료자와 준비 변경 후 다음 주 참가자 구분, 전환 시 현재 대상 state 활성화, 현재 주차 ⓘ와 수동 완료 대상 일치, 최종 전환 Transaction의 핵심 상태 부분 쓰기 없음, 사전 인증만 남은 상태와 legacy/stub/손상 자료 구분. 자리 이동 유무를 이 흐름의 필수 전제로 삼지 않는다.

**완료 조건:** 같은 캐릭터·레이드·주차가 모집/개인 원장/표시/명령에서 일치하고 과거 완료 기록과 타인의 권한이 보존된다.

### 4구간 — 통합 확인·기록

**구현 범위:** 기능 수정 완료 후 관련 문서 정합성과 필요한 검증을 한 번 묶는다. 기존 동일 코드 검증은 재사용한다.

**확인 범위:** 실기기에서 만들기 어려운 위조 요청·원자성·경합·최대8인 경계만 자동 보완. 정상 사용자 흐름은 사용자 실기기 확인으로 인수하며 상세 테스트 목록은 채팅으로 제공한다. 반복 인원수별 전체 테스트는 하지 않는다.
관련 기준 파일: `party_composition_policy_test.dart`, `party_atomic_member_mutation_write_plan_test.dart`, `weekly_raid_status_projector_test.dart`, `my_account_view_model_test.dart`, `party_cycle_policy_test.dart` 및 실제 변경 경로의 Rules 계약 검증.

**완료 조건:** 실패 지점별 수정 근거와 결과·미확인 사항을 기록. Rules를 바꾸는 경우에만 TASK-11/생성 원본/계약을 확인하고 생성 동등성·경고0·권한 경계 검증 후 운영1회 게시 및 활성SHA 확인. 성공본을 불필요한 전체 조합 재검사/검증 중복으로 확장하지 않는다. 첫 게시 실패 시 즉시 반복하지 않는다.

## 6. 구현 전 재검토 — 2026-10-11

판정: 기존 §1~5의 방향은 유지하되 아래 누락을 반영해야 구현에 착수할 수 있다. 코드상 확인된 결함/계약 차이와 사용자 장애의 원인 확정은 구분한다. 이번 재검토는 읽기·문서 수정만 수행했다.

### 후속 확인 — 운영 자료와 역할 변경 경로

사용자는 다른 캐릭터로 변경과 같은 캐릭터 역할 변경 모두 실패했다고 확인했다. 따라서 §6.3의 역할만 변경하는 경로도 복구 설계 대상으로 확정한다. UI 필터만 해제하지 않는다.

- 운영 읽기 전용 확인: 현재 주차 노르딘 모집/이슈아이 방은 schemaVersion2/slotLedgerVersion2, revision10, 2026-10-11 회차다. 모집 partySlots와 세 membership의 캐릭터·역할·위치가 일치한다. 현재 서포터는 2파티에 있어 실패 당시 1파티 구성과 다르다. 과거 실패 원장 불일치는 확인된 사실이 아니다.
- 개인 state도 세 명 모두 현재 회차 active로 존재한다. 공대원 둘에는 전환 guard가 남아 있고, 공대장은 이후 캐릭터 변경으로 guard 없는 새 state다. guard 차이만으로 ⓘ 누락 원인이라고 단정하지 않는다. 사용자의 공대장 표시/공대원 둘 누락은 참고 관찰이며 다음 표시 구간에서 조회·소유권 필터와 대조한다.
- 일반 공대원의 1파티→2파티 서포터 변경은 기존 공용 정책에 빈자리 이동 경로가 있다. 리더 고정석과 타인 자동 이동 금지로 같은 구성의 공대장 변경은 거절 가능하다. 두 결과를 분리하는 최소 재현을 확보한다.
- 구현 범위: 현재 mutation의 FormatException/StateError가 상세 원인 없이 일반 실패로 바뀌므로 디버그 로그에 실패 종류·기존 진단 ID·예외 이유를 보존한다. 권한이나 성공/실패 반환값은 변경하지 않는다. 실기기 재현 시 기존 mutation 로그와 함께 원인 구분에 사용한다.

역할 전용 후속 구현 계약: 요청에 현재 모집과 교체 대상 캐릭터를 명시하고 서버 상태가 같은 모집의 본인 active일 때만 자기 점유를 후보 차단에서 제외한다. 같은 캐릭터·같은 역할은 계속 거절한다. 다른 방 점유/완료/소유권 차수는 우회하지 않는다. active 변경은 동일 raidState를 삭제·생성하지 않고 현재 revision을 증가시키는 update로 처리하며 role·membership·partySlots·목록·이벤트를 원자 반영한다. 완료 후 준비 변경은 state 쓰기0을 유지한다. 현재 Rules의 동일 문서 update 허용 경계를 먼저 검토하고, 필요한 Rules 변경은 게시 성공본의 검증·1회 게시 절차로 진행한다. 후보만 먼저 노출하는 부분 배포는 금지한다.

### 6.1 우선 조사: 후보 시계 고정과 주차 기준 분리

`app_router.dart`는 Router 구성 시 만든 `FakeRecruitmentClock(DateTime.now())`를 두 후보 서비스에 공유한다. `data/fakes/fake_recruitment_runtime.dart`의 now는 현재 시각이 아니라 currentTime을 반환한다. 조사한 실제 앱 연결에는 이를 advance하는 호출이 없다. `RecruitmentLeaderCandidateService.load`는 이 값으로 weekKey를 만들고 서버 주간 상태와 점유 조회에 사용한다.
이는 **Router 수명 중 경계 통과 시 후보 주차가 고정될 수 있는 코드상 결함**이다. `/account`의 cycleRuntime/ValueKey 갱신과는 별도다. 다만 이번 ⓘ/수동 완료 오류가 반드시 이 clock 때문이라고 볼 수는 없다. 두 흐름은 후보 clock을 직접 사용하지 않는다.

설계 보완: 원인 연결이 확인되면 운영 DI에 실제 현재 시각을 공급하되 테스트의 제어 가능한 시계는 유지한다. 공용 후보 서비스는 생성·신청·캐릭터 변경 모두가 사용하므로 한 화면만 보정하지 않는다. load 시작 시 시간/주차를 한 번 확정하고, 오래 열린 후보창·완료 확인창의 제출은 최신 주차/모집 revision과 다시 비교한다. 경계가 바뀌었다고 과거 방의 저장 경계를 재계산하거나 옛 요청의 완료 대상을 새 주차로 조용히 바꾸지 않는다.

### 6.2 위치 호환 플래그를 빠뜨리지 않는다

`party_read_document_mapper.dart`는 `slotLedgerVersion == 2`로 supportsPositionChanges를 만든다. 후보 서비스는 false이면 제자리 전용 정책, true이면 planReplacement를 쓴다. 반면 Atomic Write Plan은 planReplacement를 사용한다. 따라서 members/partySlots만 비교해서는 후보와 최종 판정 차이를 모두 잡지 못한다.

1구간의 관찰 필드에 schemaVersion/slotLedgerVersion/supportsPositionChanges와 공개 원본·그룹 listing의 해당 필드를 추가한다. 과거 flag 누락인지, 요약에서 누락됐는지, 실제 위치 원장 불완전인지 구분한다. **flag를 무조건 true로 하거나 기존 방 전체를 부분 bootstrap하지 않는다.** BUG-017의 다른 파티 빈자리 이동, 리더0:0 고정석, 수동 단일 교환 정책과 기존 일반 가입 배치를 함께 보존한다.

### 6.3 기존 역할 변경 계약 차이는 별도로 취급한다

제품 참가 정책은 같은 캐릭터의 반대 역할 변경을 허용하지만 실제 상세 UI는 같은 serverCharacterId를 후보에서 제외하고, 공용 Write Plan은 이전/새 state 경로가 같으면 거절한다. `party_atomic_member_mutation_write_plan_test.dart`도 같은 캐릭터는 throwsStateError를 기대한다. Repository 입구의 캐릭터+역할 비교만 보면 지원되는 것처럼 보이지만 전체 연결은 그렇지 않다.

이번 보고의 **다른 캐릭터로 딜러→서포터 변경**과 이를 혼동하지 않는다. 후보 필터만 제거하면 같은 문서를 delete→set하는 경로 및 본인 점유 충돌로 추가 실패할 수 있다. 이 기존 미완료 기능은 이번 복구 중 자동 활성화하지 않는다. 사용자 사례가 같은 캐릭터의 역할만 바꾸는 경우였음이 확인되면 별도 계약 범위를 결정한 뒤 state update 전용 경로·동일 문서 원자성까지 설계한다.

### 6.4 인증·최종 전환·수동 완료의 원자성 경계를 구체화한다

- `_certifyAdvance`는 대상별 Transaction이다. 일부 guard/stub 생성 뒤 중단될 수 있으며 이것은 최종 참가 확정이 아니다. 최종 전환은 모집·대상 state·목록·이벤트 한 Transaction으로 보호한다. 인증 잔존을 실패한 참가 기록으로 보고 자동 삭제하지 않는다.
- 현재 state가 guard를 포함할 수 있으므로 writer 수정 시 인증 무효화/소비 계약을 유지한다. 임의 필드 제거·guard 재사용으로 현재 소유권 또는 이번 주 완료 제한을 우회하지 않는다.
- 과거 completed 정리 후 수동 완료는 `createManualClaim`에 delete 후 제한된 재시도 구간이 있다. 이를 단일 Transaction이라고 설명하지 않는다. 중간 종료/재진입/다른 기기의 참가가 끼어들어도 최신 state와 observation을 다시 검증해야 한다.
- `_completeActiveState`는 확인 당시 recruitmentRevision, membership/slot의 characterId·ownershipRevision을 검사한다. 자리 이동이나 주차 전환이 확인창 이후 발생한 경우의 거절은 데이터 보호일 수 있다. 검사를 빼서 통과시키지 말고 상태 갱신·영향 재안내로 처리한다. 수동 완료의 탈퇴/승계/마지막1인 해산은 같은 핵심 Transaction에 유지한다.

### 6.5 표시 오류를 데이터 없음으로 바꾸지 않는다

주간 상태 스트림은 state/legacy Claim/assignment 모두 준비돼야 출력하며, strict mapper 오류·권한 오류·소유권 필터가 각각 별도 영향을 준다. `WeeklyRaidStatusProjector`는 canonical과 legacy가 겹치면 inconsistent로 판정한다.
ⓘ 누락 개선을 위해 조회 실패를 빈 목록으로 바꾸거나, legacy를 일괄 무시하거나, membership만으로 active를 합성하면 완료/중복 참가 차단까지 잘못될 수 있다. 실제 유효 state가 없음·조회 중·조회 실패·소유권 제외·불일치를 구별한다. 오래된 구독의 응답이 새 주차에 섞이지 않는지 확인하되, 근거 없이 모든 캐릭터나 모든 모집의 신규 실시간 구독을 추가하지 않는다.
같은 projector/상태 계약의 소비처인 생성·신청 후보·완료 체크 해제도 영향 범위에 포함한다. 개인 완료 해제는 공동 완료 취소나 과거 membership 복원이 아니다.

### 6.6 전환 순서·표시 갱신·기존 손상 데이터

LazyCycleReconciler는 방/목표 주차/관찰 revision을 기준으로 중복 요청과 관찰 결과를 보관하고 명시 새로고침에서 실패 재시도를 허용한다. UI에 새 주차 날짜가 보이는 것, membership이 유지되는 것, 최종 서버 전환 성공은 서로 다른 근거다. 실패 후 자동 무한 재시도나 전원 private state 읽기로 대체하지 않는다.
원인 writer를 고쳐도 이미 불일치한 문서는 저절로 복구되지 않는다. 1구간에서 **재발 방지 수정**과 **기존 문서 처리 필요 여부**를 별도로 판정한다. 후자가 필요하면 원본 백업·정확한 대상/불변식·멱등성·현재 소유권/완료 보호를 포함한 별도 복구안을 제시한다. 이번 설계는 운영 자료 자동 수정 권한을 포함하지 않는다.

### 13.2 공통 데이터 계약과 책임

- 참가의 기준은 모집 partySlots와 연결 membership이다. 개인 raidState는 참가/완료·점유 연결이며 listing은 표시용 projection이다. 표시가 없다는 이유로 참가 없음으로 판정하지 않는다.
- Auth UID와 playerId, 서버 characterId와 로컬 캐릭터 식별자를 구분한다. raidState 문서 키는 characterId와 raidId이고 주차는 필드다. 난이도가 달라도 같은 raidId의 점유 계약을 지킨다.
- 후보 조회, 주간 표시, 수동 완료는 같은 주차·소유권 의미를 사용한다. 기존 Domain 정책과 mapper를 조사해 재사용하고 화면별 예외 조건을 중복 추가하지 않는다. 공통화는 의미가 같은 분류에 한정하며 읽기 오류를 쓰기 허용으로 변환하지 않는다.
- 정렬·필터·후보 설명·표시용 결합은 로컬 책임이다. 소유권, 타인 기록 변경 금지, 자리 정원/역할 제한, 상태 전이, revision 경합과 원자 연결은 서버에서 보호한다. 로컬 검증만으로 서버 권한 검사를 대체하지 않는다.
- 서버 검사 제거는 같은 요청의 다른 문서 검증이 반드시 실행되고 같은 불변식을 보장하는 경우에만 한다. 삭제한 검사마다 대체 보장 위치와 부분 쓰기 거절 근거를 남긴다. 무조건적인 함수 인라인은 중복 본문과 평가량을 늘릴 수 있어 선택하지 않는다.

| 구독 로딩/권한 실패/형식 오류 | 미참가로 확정하지 않음 | 재조회 없이 정리 요청을 실행하지 않음 |

현재 `_stateRecord`는 active/completed 외 상태를 거절하고 수동 완료의 `_validateStateIdentity`도 해당 상태와 식별자를 검사한다. 따라서 정상 stub의 유입 여부, 조회 필터와 mapper 계약부터 확인한다. 이것만으로 stub이 실제 장애 원인이라고 확정하지 않는다. guard가 붙었다는 이유로 모든 기록을 건너뛰는 수정은 금지한다.

조회 경로는 router → ownership record stream → status repository → projector → view model → 화면 순으로 추적한다. 같은 시점의 playerId, characterId, raidId, cycleKey, ownershipRevision과 제외 이유를 비교한다. 공대장/공대원이라는 관찰 차이는 이 추적의 비교 사례다. 한 문서의 형식 오류가 전체 구독을 실패시키는 경우도 확인하되 손상 문서를 조용히 무시하여 이용 가능으로 보이게 하지 않는다.

수동 완료는 사전 영향 조회, 확인창, 최종 transaction을 구분한다. `stateInconsistent` 팝업은 로컬 계약 검사에서도 발생하므로 permission-denied로 단정하지 않는다. 확인창 이후 모집 revision·주차·소유권이 바뀌면 최종 transaction에서 재판정한다. 기존 과거 완료 정리와 새 기록 생성이 분리된 경로는 중도 실패 후 재진입을 확인하고 성공 표시를 앞당기지 않는다.

### 13.4 자리·캐릭터·역할 변경 계약

공용 PartyCompositionPolicy와 실제 mutation write plan이 동일한 입력으로 같은 배치 결론을 내리는지 확인한다. 후보는 안내이고 최종 transaction이 최신 revision으로 결정한다. 자리 이동은 room/membership/listing/event를 원자 반영하며 필요 없는 개인 state 쓰기를 추가하지 않는다.

- 일반 공대원: 현재 파티에 서포터 정원이 차도 다른 파티에 정책상 가능한 자리가 있으면 기존 자동 배치 경로로 판정한다. 단순 총 빈자리와 역할상 가능한 자리를 구분한다.
- 공대장: 현재 계약인 1파티 첫 자리 고정을 유지한다. 같은 파티 서포터 정원이 찼으면 다른 파티가 비어도 자동 이동이나 타인 강제 교환을 하지 않는다. 거절 이유를 정확히 전달한다. 이를 허용하도록 바꾸려면 별도 제품 정책 결정이 필요하며 버그 수정에 몰래 포함하지 않는다.
- 동일 캐릭터 다른 역할: 같은 state의 제한된 role/revision/updatedAt만 변경하고 createdAt·인증 정보를 유지한다. 동일 캐릭터 동일 역할은 무의미한 후보에서 제외한다.
- 다른 캐릭터: 이전 state 삭제/새 state 생성, 현재 소유권·점유·membership·이벤트가 함께 성립해야 한다. 역할 전용 분기로 다른 캐릭터 교체를 처리하지 않는다.
- 완료 후 다음 주 준비: 이번 주 완료 기록을 다시 쓰거나 지우지 않는다. 기존 state 쓰기0 계약을 보존한다.

후보 성능은 현재 최대4개 병렬 조회를 출발점으로 한다. 조회 소요를 소유권/점유/조합 단계로 구분한 뒤 병목이 입증된 곳만 개선한다. 오류를 숨긴 부분 목록, 무기한 캐시, 타인의 데이터를 넓게 가져오는 우회는 제외한다. 화면 닫힘·캐릭터/방 변경 후 늦게 도착한 결과가 새 선택을 덮어쓰지 않는지도 확인한다.

### 13.5 반복 전환과 주차 경계

PartyCycleRuntime의 경계 타이머·resume, 화면 cycle key 갱신, 실제 DI 시계와 writer의 nextCycleKey를 함께 대조한다. 임시 일요일15시 설정을 유지하고 기존 수요일 기록을 자동 이행하지 않는다. 과거 key의 요일 검증과 저장된 기간의 해석이 충돌하면 해당 경로를 특정한 뒤 최소 호환 처리를 설계한다.

인증 단계의 개별 transaction과 마지막 전체 advance transaction을 구분한다. 인증 후 실패한 잔존 guard가 있다고 일괄 삭제하지 않는다. 중단 후 재실행, 중복 advance, 전환 직후 역할 변경/수동 완료 경합에서 다음 주 참가와 이번 주 완료가 동시에 손상되지 않아야 한다. 정상 전환은 모든 대상 슬롯의 player/character/role/ownership과 개인 state가 같은 회차를 가리켜야 한다. 기존 데이터 정리가 필요하면 대상·조건·복구 가능성을 별도로 제시하며 운영 자료 자동 수정을 이번 범위로 간주하지 않는다.

### 13.6 의미 있는 Rules 이름과 게시 구조

`integrate_roster_rules.mjs`의 reviewed 소스를 compactExecutableRules로 바꾸어 배포하는 현재 경로를 변경 대상으로 삼는다. 생성 결과를 손으로 고치는 대신 함수·인수·지역 변수 이름을 보존하는 생성 규칙을 만든다. rf122만 개명하는 것으로 완료하지 않는다. 읽기 원본에도 남은 축약/실험 이름은 정의와 호출의 실제 책임을 확인해 의미 있는 이름으로 매핑한다. 문자열·필드명·문서 경로는 치환 대상이 아니다.

생성기/검사/manifest가 compact SHA를 가정하는 지점을 함께 변경한다. 이름 변경과 동작 변경의 diff 근거를 구분하고 중복 정의, 미해결 호출, 변수 가림, deterministic 재생성 일치를 확인한다. 임시 symbols.json이나 별도 readable 파일만 제공하고 콘솔에는 rf 이름을 유지하는 방식은 목표를 충족하지 않는다.

이름 복원은 가독성 작업이지 복잡도 감소 성과가 아니다. 소스 바이트는 증가할 수 있으므로 최종 산출물 크기를 측정한다. 서버에서 제공하지 않은 컴파일 크기나 원인을 추정 수치로 단정하지 않는다. 게시 구조는 기능별 직접 진입과 필요한 좁은 검증을 우선하고, 같은 검증을 반복하는 wrapper·fallback은 보장 근거가 있을 때만 합친다. 기능/권한을 지우고 게시만 성공시키는 후보는 운영 후보가 아니다.

### 13.9 완료 보고와 실기기 인수

보고에는 새로 가능해진 흐름, 보존 확인한 흐름, 삭제한 서버 검사와 그 대체 보장, 실제 로컬 이전 처리, 소스량·함수 구조 변화, 게시 결과와 활성 SHA, 미확인 항목을 구분한다. 이름 복원이나 테스트 개수를 기능 복구 성과로 계산하지 않는다.

사용자 확인 목록: 일반 공대원 다른 파티 빈자리로 서포터 변경, 같은 캐릭터 역할 변경, 공대장의 가능한 변경과 정책상 거절 안내, 자리 이동 후 재변경, 후보 목록 반응, 반복 경계 뒤 공대원/공대장 ⓘ, 연결된 수동 완료와 재진입, 완료 후 다음 주 준비의 이번 주 완료 보존. 빌드·설치·기기 조작은 사용자가 수행한다. 이 확인이 남으면 실기기 인수 미완료로 보고한다.

### 13.10 주차 화면 수명 결함과 최소 수정 (2026-10-12)

실제 go_router 17.2.0 소스에서 delegate는 같은 RouteMatchList를 받으면 재구성을 생략하고 StatefulShellBranch도 주소가 같으면 Navigator를 재사용한다. 현재 앱은 refreshListenable와 route builder 안의 ValueKey만 사용하므로 살아 있는 화면이 새 주차 key를 받는 것을 보장하지 못한다. 서버는 다음 주 active인데 내 계정 ViewModel은 이전 cycleKey로 조회/수동 완료를 요청하는 경로가 성립한다. 이는 코드상 결함이며 사용자의 실패 당시 기기 상태를 직접 확인했다는 의미는 아니다.

수정 범위: 주차에 묶인 내 계정/레이드 현황/모집 목록 route에 runtime 직접 구독을 연결한다. 주차가 바뀌면 기존 페이지의 cycle ValueKey로 ViewModel과 구독을 교체하고, 상세 route·현재 탭·Navigator 위치는 유지한다. 저장된 모집 회차와 임시 일요일 초기화 설정은 바꾸지 않는다. Router refresh 자체는 다른 기존 용도를 위해 유지한다. 열린 탭과 방문 후 숨겨진 탭의 동일 주소 갱신·이전 구독 dispose를 재현 검증한다.
