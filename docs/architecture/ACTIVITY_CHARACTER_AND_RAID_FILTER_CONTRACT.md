# 활동 캐릭터와 레이드 현황 필터 계약

## 1. 문서 상태

- 작성일: 2026-09-02
- 상태: 제품 결정 완료. A~필터 UX 구현. Android 실기기 확인 완료 (2026-09-03)
- 우선순위: 그룹 전용 레이드 자격 박탈과 레이드 필터보다 먼저 구현
- 목적: 인증 원정대 전체와 실제 앱 활동 캐릭터를 분리하고, 이후 그룹원·캐릭터 필터가 사용할 안정적인 데이터 경계를 확정한다.

## 2. 배경과 문제

한 사용자의 인증 원정대에는 검색·소유권 확인에 필요한 전체 Character가 포함되지만, 실제 레이드에 사용하는 Character는 그중 일부다. 전체 Character를 레이드·그룹 후보와 전투력 동기화 대상으로 사용하면 다음 문제가 생긴다.

- 레이드 생성·신청과 그룹원 목록에 사용하지 않는 Character가 과도하게 노출된다.
- 그룹원·Character 필터 후보가 불필요하게 길어진다.
- 전투력 상세 조회와 서버 동기화 범위가 실제 사용량보다 커진다.
- 로컬 `isVisible`, `displayLimit`과 서버 인증·소유권의 의미가 섞인다.

따라서 원정대 소속·인증과 앱 활동 여부를 별도 상태로 관리한다.

## 3. 핵심 개념

### 3.1 인증 원정대 Character

- 게임 계정 검색, 수동 인증, 소유권 검증과 이전에 사용하는 전체 Character다.
- 활동 캐릭터가 아니어도 Character 문서와 active 소유 관계를 유지한다.
- 비활성화는 삭제·숨김·인증 해제 또는 소유권 상실을 의미하지 않는다.

### 3.2 활동 캐릭터

- 사용자가 LOSTPARTY의 레이드·그룹 기능에서 실제로 사용할 Character다.
- 서버 Player 소유 관계의 활동 설정으로 저장한다. 쓰기 단위는 `players/{playerId}/characterActivity/{characterId}` 문서다. 문서가 있으면 `activityEnabled=true`와 같다.
- `true`인 Character만 새로운 레이드 생성·신청·참가·참가 Character 변경 후보, 그룹원 Character 후보와 일반 전투력 동기화 대상이 된다.
- 필드명은 구현 전 기존 Character 문서 소유 경계와 대조하되 의미를 `표시 여부`가 아닌 `앱 활동 허용`으로 유지한다.

### 3.3 로컬 표시 설정

기존 로컬 값은 활동 여부와 분리한다.

- `isVisible`: 기존 개인 표시 상태. 새 구조에서는 역할을 제거하거나 호환용으로만 유지할 수 있다.
- `displayOrder`: 활동 캐릭터의 내 계정 메인 표시 순서다.
- `displayLimit`: 정렬된 활동 캐릭터 중 내 계정 메인 화면에 노출할 개수다.

활동 캐릭터가 8명이고 `displayLimit`이 6이면 8명 모두 레이드·그룹에서 사용할 수 있고 메인 화면에는 순서 상위 6명만 보인다.

## 4. 데이터와 권한 계약

### 4.1 저장 위치와 소유 경계

- `activityEnabled`는 전역 Character 정체성이 아니라 현재 Player가 소유한 Character의 앱 사용 설정이다.
- 확정 저장 위치는 `players/{playerId}/characterActivity/{characterId}`다. 활동 Character마다 문서가 하나씩 있다. 가변 ID 목록을 한 문서에 넣지 않는다. Firestore Rules는 재귀와 가변 길이 목록 순회를 허용하지 않기 때문이다.
- 문서 필드: `schemaVersion`, `playerId`, `characterId`, `gameAccountId`, `updatedAt`. Character의 `ownerPlayerId`·`status`·인증 필드는 이 명령으로 쓰지 않는다.
- `characterActivity/{characterId}` 문서가 있는 Character만 활동 상태다. 문서가 없으면 비활동이다. 하위 컬렉션이 비어 있으면 아직 설정되지 않은 상태다.
- 각 쓰기는 `characters/{characterId}`의 소유자·상태·`gameAccountId`와 `playerGameAccounts/{playerId}_{gameAccountId}` 소유권을 확인한다. 같은 계정의 서버 대표 Character 활동 문서가 같이 있어야 한다.
- Repository 저장은 최종 선택 전체를 한 Transaction에서 검증한 뒤 활성 문서를 쓰고 해제된 문서를 삭제한다. 클라이언트 Repository는 보안 경계가 아니다.
- active 소유자인 Player 본인만 값을 변경할 수 있다.
- 다른 그룹원 화면의 활동 Character 후보는 `characterActivity` ID 목록과 기존 `characters/{characterId}` 표시 필드를 조합한다. Rules 복잡도 한도 때문에 별도 Projection 컬렉션과 그룹 교집합 검사는 쓰지 않는다.
- `characterActivity`의 `get`/`list`는 활성 Auth binding이 있는 사용자에게 허용한다. 쓰기는 계속 본인만 가능하다.
- 표시명·서버·직업·아이템레벨·전투력은 이미 공개 조회되는 Character 문서를 쓴다. `gameAccountId`는 활동 문서에 남아 있으나 그룹 UI는 이 값을 화면에 쓰지 않는다.
- 다른 그룹원 화면에서 인증 활성 Character 전체를 대체 자료로 노출하지 않는다. 활동 문서가 없으면 빈 목록이다.

### 4.2 서버 불변조건

- Player의 활동 캐릭터는 최소 1명이어야 한다.
- 서버 대표 Character는 활동 캐릭터여야 한다.
- 각 활동 Character ID는 현재 Player가 active 소유한 GameAccount에 속해야 하며 본·부계정 Character를 함께 선택할 수 있다.
- 허용 필드 외 Character 인증·소유권 필드는 활동 설정 명령으로 바꿀 수 없다.
- 복수 선택 저장은 최종 상태 전체를 검증한 뒤 원자적으로 반영한다. 중간 상태에서 0명이나 비활동 대표가 관찰되면 안 된다.

### 4.3 기존 데이터 처리

- 현재 운영 데이터는 사용자 단독 테스트 데이터이므로 과거 사용자 자동 마이그레이션과 호환 배치는 구현하지 않는다.
- `characterActivity` 하위 문서가 없으면 활동 Character는 아직 설정되지 않은 상태다. 누락 필드를 true로 간주하지 않는다.
- 새 계약 적용 시 테스트 데이터 재설정: 앱에서 사용할 캐릭터를 다시 저장하면 캐릭터별 활동 문서가 만들어진다. 기존 Character·소유권·membership·Claim 문서는 삭제하지 않는다.
- 실제 테스트 데이터 삭제와 Rules 배포는 이 저장 단위에서 하지 않는다.
- 신규 계정의 최초 활동 Character 선택 흐름과 기본값은 캐릭터 관리 UI 단위에서 명시하되, 서버 저장 전 최소 1명과 대표 포함을 반드시 만족한다.

## 5. 캐릭터 관리 UI 계약

화면 순서는 다음과 같다.

1. 앱에서 사용할 캐릭터 선택
2. 선택된 캐릭터의 대표 지정과 표시 순서
3. 메인 화면 표시 개수
4. 변경 취소·저장

### 5.1 앱에서 사용할 캐릭터 선택

- 인증 원정대 전체를 Character명 중심의 작은 선택 카드로 표시한다.
- 본인 화면이므로 이름을 기본 정보로 사용하고 직업 아이콘 등은 밀도를 해치지 않는 범위에서만 보조한다.
- 선택된 카드는 앱 시그니처 색상과 테두리로 강조한다.
- 여러 Character를 로컬 초안에서 즉시 선택·해제한다.
- `선택 수 / 전체 수`를 표시한다.
- 설명은 `선택한 캐릭터만 레이드, 그룹 및 전투력 동기화에 사용됩니다.`를 기준으로 한다.

### 5.2 대표 Character와 최소 1명

- 현재 대표 Character의 활동 선택은 비활성화해 직접 해제할 수 없게 한다.
- 대표를 활동 대상에서 제외하려면 다른 활동 Character를 먼저 대표로 지정해야 한다.
- 마지막 활동 Character의 해제 터치를 로컬 UI에서 막는다.
- UI 오류로 선택이 0명이 되더라도 저장 요청을 만들지 않는다.
- 0명 상태에서 저장을 누르면 `앱에서 사용할 캐릭터를 최소 1명 선택해 주세요.`를 표시한다.
- Repository는 빈 선택과 대표 누락 저장 명령을 거절한다. Rules는 각 캐릭터 쓰기에서 소유권과 해당 계정 대표 활동 문서 존재를 확인하고, 대표 활동 문서 삭제를 거절한다.

### 5.3 선택된 캐릭터 관리

- 대표·순서 목록에는 상단에서 활동 대상으로 선택한 Character만 표시한다.
- 기존 표시 여부 체크박스는 상단 활동 선택과 중복되므로 제거한다.
- 대표 지정과 드래그 순서 변경을 제공한다.
- 다시 활성화한 Character는 보존된 순서가 유효하면 복원하고, 없으면 목록 마지막에 둔다.

### 5.4 메인 화면 표시 개수

- 대표·순서 영역 아래로 이동한다.
- 범위는 1부터 활동 캐릭터 수까지다.
- 활동 캐릭터 수가 현재 표시 개수보다 작아지면 표시 개수를 자동 축소한다.
- 표시 개수는 레이드·그룹 사용 자격을 바꾸지 않는다.

### 5.5 저장 흐름

- 선택·순서·표시 개수 변경은 화면의 로컬 초안에 즉시 반영한다.
- 서버 쓰기는 `저장`에서 한 번 수행해 연속 터치마다 쓰기가 발생하지 않게 한다.
- 저장 중에는 중복 저장을 막는다.
- 실패하면 서버 반영 여부를 명확히 안내하고 로컬 영구 상태를 성공으로 확정하지 않는다.

## 6. 기능별 적용 범위

### 6.1 적용

- 새 레이드 생성의 파티장 Character 후보
- 레이드 신청·참가와 참가 Character 변경 후보
- 그룹 생성·가입 시 표시 Snapshot 후보
- 그룹 상세의 그룹원 Character 목록
- 레이드 현황의 그룹원·Character 필터 후보
- 내 계정 진입 등의 전투력 상세 조회와 서버 보강 대상

### 6.2 적용하지 않는 범위

- 원정대 검색 결과와 게임 계정 인증
- Character 소유권 확인·방어·이전
- 이미 저장된 완료 Snapshot과 로컬 히스토리
- 이미 참가 중인 레이드 membership의 자동 제거

### 6.3 기존 참가 Character 비활성화

- 활동 해제는 기존 레이드에서 자동 탈퇴시키지 않는다.
- 기존 참가·Claim·assignment·완료 Snapshot을 삭제하거나 바꾸지 않는다.
- 진행 중 레이드와 필터는 해당 방의 membership Snapshot으로 기존 참가자를 계속 인식한다.
- 이후 새 모집·신청·참가 Character 변경 후보에서는 제외한다.
- UI는 `현재 참가 중인 레이드에서는 유지되며 새로운 레이드 선택에서 제외됩니다.`를 안내한다.
- 전투력 동기화 최적화 시에도 현재 참가 데이터 보존에 필요한 Snapshot을 null로 덮어쓰지 않는다.

## 7. 레이드 현황 진행 중 필터

### 7.1 배치와 적용 화면

- `레이드 현황`의 `진행 중 / 신청 중 / 완료 기록` 전환 아래, 진행 중 목록 위에 `레이드 필터: 모든 레이드` 영역을 둔다.
- 최초 구현의 필터는 `진행 중`에 적용한다. 후속 모집 탭 목록 확장은 §13을 따른다. 신청 중·완료 기록은 제외한다.
- 영역을 누르면 다중 조건 필터 창을 연다.
- 필터 상태와 후보 데이터는 서버 조회 권한을 바꾸지 않고 이미 받은 원본 목록의 표시만 좁힌다.

### 7.2 공개 조건

선택 항목은 `전체`, `일반 공개`, `그룹 공개`다.

- 기본 진입은 세 항목이 모두 체크된 전체 상태다.
- `전체`는 일반 공개와 그룹 공개가 모두 선택되었다는 파생 상태다.
- 한 하위 항목을 해제하면 `전체` 체크도 해제한다.
- 일반 공개와 그룹 공개를 모두 해제하려 하면 빈 공개 조건을 허용하지 않고 자동으로 전체를 선택한다.
- `전체`를 선택하면 일반 공개와 그룹 공개를 함께 선택한다.
- 일반 공개는 `groupId`가 없는 기존 일반 레이드다.
- 그룹 공개는 현재 Player가 볼 수 있고 `groupId`가 있는 그룹 레이드다. 그룹 레이드가 전체 공개로 전환되어 `visibility=public`이어도 연결 `groupId` 기준으로 그룹 범주에 남는다.

### 7.3 레이드와 난이도

- 앱 카탈로그의 모든 레이드와 난이도를 시그니처 색상 타원형 칩으로 표시한다.
- 각 차원은 복수 선택할 수 있다.
- 해당 차원에서 아무것도 선택하지 않으면 전체 허용이다.
- 같은 차원의 선택은 OR, 서로 다른 차원은 AND다.

```text
(선택 레이드 중 하나)
AND
(선택 난이도 중 하나)
```

존재하지 않는 레이드·난이도 조합을 만들지 않고 실제 원본 항목이 두 조건을 모두 만족할 때만 표시한다.

### 7.4 그룹원과 Character

- 그룹 공개에서 그룹을 선택하면 그룹별 정상 멤버의 대표 Character명을 표시한다.
- 현재 Player 본인은 진행 중 목록에 항상 참가한 상태이므로 후보에서 제외한다.
- 그룹원 선택이 없으면 그룹원 조건을 적용하지 않는 전체 상태다.
- 그룹원을 선택하면 선택한 사용자들이 모두 참가한 레이드만 표시한다.
- 그룹원 아래 Character 칩 후보는 해당 Player의 활동 Character ID와 공개 Character 표시 문서를 조합한다. 활동 문서가 없으면 인증 활성 Character 전체로 확대하지 않는다.
- 한 사용자 안에서 선택한 여러 Character는 OR다.
- 서로 다른 사용자 사이는 AND다.

```text
(사용자 2의 Character 21 OR 24)
AND
(사용자 3의 Character 33 OR 35)
```

- 선택한 사용자에게 Character 선택이 없으면 그 사용자가 참가한 레이드를 허용한다.
- 현재 레이드 membership에 이미 참가한 비활동 Character는 §6.3에 따라 필터 판정에서는 계속 인식한다. 다만 새 필터 후보로 다시 제시하지 않는다.

### 7.5 실시간 결과 개수

- 필터 창 우측 상단에 현재 로컬 원본 중 일치하는 레이드 수를 즉시 갱신한다.
- 다음 서버 페이지가 남아 있으면 최종 총수가 아니므로 `현재 N개`로 표시한다.
- 모든 페이지가 끝났을 때만 `N개`를 최종 개수로 표시한다.
- 칩 조작은 서버 요청을 만들지 않는다.

### 7.6 필터 초기화와 조건부 그룹원 UI

- 필터 창 상단에 `초기화`를 제공한다.
- 초기화하면 공개 조건은 전체로 돌리고 레이드·난이도·그룹·그룹원·Character 선택을 모두 비운 뒤 로컬 저장 상태에도 반영한다.
- 그룹·그룹원·Character 선택 UI는 공개 조건이 `그룹 공개만` 선택된 경우에만 표시한다.
- 전체 또는 일반 공개가 포함되면 그룹 관련 선택 UI를 숨기고 숨은 선택값이 필터 판정에 남지 않도록 정규화한다.
- 필터 목록이 길어져도 상단의 고정된 드래그 영역을 충분히 확보해 아래로 끌어 창을 닫을 수 있어야 한다.

## 8. 페이징과 로컬 필터 안전 계약

- 공개 모집 목록의 서버 페이지 크기 20과 기존 cursor 순서를 유지한다. 진행 중 원본은 membership 스트림 전체이며 이 단계에서 20개 cursor로 바꾸지 않는다.
- 서버에서 받은 원본 목록과 화면 필터 결과를 별도 상태로 관리한다.
- 필터 일치 결과가 0개여도 cursor와 다음 페이지 존재 여부는 정상 갱신한다.
- 빈 필터 결과를 서버 데이터 종료로 판단하지 않는다.
- 한 페이지 요청 중에는 추가 요청을 합치거나 무시해 동시에 하나만 실행한다.
- 같은 cursor 중복 요청과 같은 recruitment ID 중복 삽입을 막는다.
- 통신 실패 시 cursor를 전진시키지 않고 같은 페이지를 재시도할 수 있게 한다.
- 필터 변경과 늦은 페이지 응답이 경합하면 원본에는 안전하게 병합하고 최신 필터로 결과를 다시 계산한다.
- 요청 generation/token으로 새로고침 이전의 늦은 응답이 새 목록에 섞이지 않게 한다.
- 일치 항목이 없는 페이지가 연속되어도 스크롤 이벤트당 자동 보충 한도를 둬 무한 호출을 막는다.
- 서버가 마지막 페이지임을 알려줄 때만 페이징을 종료한다.
- 새로고침은 cursor·원본·필터 결과·append 오류·요청 상태를 일관되게 초기화하되 사용자가 저장한 필터 선택은 정책에 따라 유지한다.

## 9. 그룹 전용 레이드 자격 상실과 정리 연결

- 그룹 탈퇴·추방·해산은 그룹 전용 레이드에서만 참가 자격 상실을 만든다.

## 13. 레이드 모집 탭 목록 필터 확장

### 13.1 상태와 대상

- 2026-09-03 사용자 확정: 대상은 `레이드 모집` 탭의 파티 모집 목록이다. `모집 만들기` 입력 화면에는 필터를 추가하지 않는다.
- 이 절은 다음 구현을 위한 계약이다. 기존 현황 필터 완료와 모집 필터 구현 완료를 혼동하지 않는다.
- 가입 전 조회 가능한 파티를 이미 받은 목록 안에서 좁히는 기능이다. 모든 서버 모집 검색이나 실제 가입 가능성 보장은 아니다.
- 내 책임자·확정 참가 방은 기존대로 제외하고 pending 신청 방은 유지한다. 주차·모집 중·빈자리 등 기존 목록 조건을 변경하지 않는다.

### 13.2 공통 UI와 선택 의미

- 현황과 동일한 필터 바·조건 요약·초기화·결과 개수·고정 상단 드래그 닫기를 제공한다.
- 일반/그룹은 기존처럼 `groupId` 유무로 분류한다. 그룹 연결 파티가 `visibility=public`으로 전환돼도 그룹 범주다.
- 전체는 일반·그룹을 함께 허용한다. 둘 다 해제된 빈 공개 조건은 전체로 복구한다.
- 레이드·난이도·그룹 ID는 각 차원 안에서 OR, 차원 사이는 AND다. 빈 선택은 해당 차원의 전체 허용이다.
- 그룹 공개만 선택했을 때 그룹·그룹원·Character 영역을 표시한다. 전체/일반으로 전환하면 숨은 그룹 관련 선택을 비워 판정에도 남기지 않는다.
- 후보 그룹은 내가 가입한 그룹, 후보 그룹원은 정상 멤버이며 현재 Player는 제외한다. Character 후보는 활동 ID 목록과 Character 표시 문서 조합을 재사용한다.
- 그룹원은 사용자 간 AND, 같은 사용자의 Character는 OR다. Character 미선택이면 해당 사용자의 확정 참가만 요구한다. pending 신청은 참가가 아니다.
- 활동 해제는 기존 membership을 수정하지 않는다. 사용자 단위 참가 조건은 기존 참가자를 계속 인식하고 새 Character 후보에는 비활동 캐릭터를 추가하지 않는다.

### 13.3 재사용과 선택 저장 경계

- 선택 모델·순수 matcher·카탈로그/후보·요약 라벨·필터 sheet를 공통화하되 모집 화면에서 현황 전용 ViewModel을 직접 사용하지 않는다.
- 공통화 시 기존 레이드 현황 동작을 보존하고 feature 사이 역방향 의존을 피한다.
- 로컬 선택 저장은 `Player + 화면 종류`로 분리한다. 모집에서 바꾼 조건이나 초기화가 현황 선택을 변경해서는 안 된다.
- 기존 현황 저장값은 유지하고 신규 모집 화면은 전체 기본값으로 시작한다. 손상 값·없어진 카탈로그/그룹/후보는 정규화한다.
- 초기화는 모든 선택을 기본값으로 복원하고 해당 화면의 영구 저장에도 반영한다. 새로고침과 필터 초기화는 별도 동작이다.

### 13.4 원본 데이터와 조회 권한

- 원본은 기존 공개 `recruitments` 첫 20개 실시간 구독·cursor 추가 조회와 가입 그룹별 `raidListings` 구독의 병합 결과다. 현재 그룹 listing 경로는 공개 목록과 동일한 20개 cursor를 사용하지 않는다.
- 기존 조회 조건·정렬·중복 제거·자기 방 제외를 유지한다. 필터 때문에 `recruitments` 그룹 전용 list 쿼리를 새로 만들지 않는다.
- 레이드·난이도·groupId는 기존 목록 데이터로 판정 가능하다. 참가 Player ID는 현재 공개 mapper가 내 방 제외에만 사용하므로 목록 모델에 전달할 경로를 추가한다.
- public 원본과 group listing의 참가 ID 필드 정합성을 검증한다. 누락/조회 실패를 정상적인 참가자 없음으로 간주하지 않는다.
- 기존 Rules는 활성 Player 연결 사용자에게 공개 파티 membership 읽기를, 해당 그룹원에게 그룹 전용 파티 membership 읽기를 허용한다. 레이드 가입 자체는 선행조건이 아니다.
- 위 권한을 재사용하며 읽기 범위를 확대하거나 비가입 그룹의 비공개 파티를 우회 조회하지 않는다. 실제 배포 Rules 차이가 있으면 권한 오류로 보고한다.

### 13.5 참가 Character 조회와 일치 판정

- 활동 Character 목록은 후보 제공용이다. 실제 참가 여부는 해당 파티 membership의 Player/Character ID로 판정한다.
- 현황 구현의 `Character 정보 미조회이면 조건 건너뛰기`를 모집에 그대로 적용하지 않는다.
- Character 조건을 선택한 경우 기본 조건과 참가 Player 조건을 통과한 파티에 한해 필요한 membership을 조회한다. 조건 선택이 없을 때 전체 파티의 membership을 일괄 선조회하지 않는다.
- 후보 목록/필터 선택 변경마다 동일 요청을 반복하지 않도록 캐시·중복 요청 방지·동시 조회 수 제한을 둔다.
- 조회 중인 방은 일치 결과에 섞지 않고 확인 중 상태를 표시한다. 실패한 방은 정상적인 불일치와 구분하고 재시도를 제공한다.
- 방 revision 변화·원본 갱신·새로고침·권한 상실에 따라 캐시를 재검증하거나 무효화한다. 필터/목록 세대가 바뀐 뒤 도착한 응답은 현재 결과를 덮어쓰지 않는다.
- 결과 수는 확인된 일치 건수다. 다음 페이지가 남으면 `현재 N개`, 참가 조건 확인 중/실패가 있으면 해당 상태를 함께 표시하며 확정 총수로 안내하지 않는다.

### 13.6 페이징과 빈 결과

- 원본 목록, 표시 결과, cursor, hasMore, 로딩/추가 오류 상태를 분리한다. 결과 0개는 서버 종료가 아니다.
- 필터 변경은 원본을 버리지 않고 받은 항목을 즉시 재계산한다. 공개 첫 페이지의 ID 집합 변경 시 기존 추가 페이지/세대 처리와 일관되게 갱신한다.
- 필터 결과가 비고 다음 페이지가 있으면 제한된 자동 보충을 허용한다. 기존 최대 3회 정책을 기준으로 시작·새로고침·명시적 조건 변경 시에만 예산을 새로 두고 재빌드/응답만으로 무한 재설정하지 않는다.
- 자동 보충 상한 이후에는 결과가 0개여도 `더 불러오기`와 오류 재시도 경로를 제공한다. 스크롤할 항목이 없어도 접근 가능해야 한다.
- 짧은 결과 목록이 화면을 채우지 못할 때도 추가 로딩 수단을 유지한다.
- 중복 ID, 연속 스크롤, 늦은 응답, 첫 페이지 재정렬, 그룹 목록 변경에서 중복 항목·중복 요청·cursor 역행을 방지한다.
- 서버 목록 자체가 빈 경우, 필터 때문에 빈 경우, 추가 페이지가 남은 경우, 참가 정보가 미확인인 경우를 구분한다. 빈 화면에서도 필터 바와 초기화를 사용할 수 있다.

- 실기기: 가입 전 공개/그룹 파티 검색, 선택 그룹원·Character 참가 결과, 화면별 독립 저장, 초기화/닫기, 빈 결과에서 다음 페이지 찾기.
- 제외: 모집 생성·수정 폼, 생성값 자동 전달, 신청 중·완료 기록 필터, 서버 전체 검색·집계, 신규 인덱스·권한 확대, Claim/역할/전투력 등 추가 가입 가능 필터, 기존 membership/Claim/완료 기록 변경.
- 구체적인 단계별 실행·완료 조건은 `../project/NEXT_WORK.md`를 따른다.
