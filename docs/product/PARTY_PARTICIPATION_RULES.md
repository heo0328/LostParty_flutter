# 파티 신청·참가·캐릭터 변경 규칙

## 1. 목적과 용어

이 문서는 한 사용자가 본계정과 부계정의 여러 캐릭터를 보유할 때 모집 생성, 신청, 승인, 즉시 가입, 탈퇴 및 캐릭터 변경을 일관되게 처리하기 위한 제품 규칙이다.

- `사용자`: Firebase Auth UID 하나로 식별되는 실제 플레이어 한 명
- `게임 계정`: 사용자가 로그아웃·로그인을 구분하기 위해 등록한 본계정 또는 부계정
- `캐릭터`: 게임 계정에 속한 실제 레이드 참가 단위
- `pending`: 가입 승인이 아직 확정되지 않은 신청
- `확정 참가`: 파티장, 승인된 파티원 또는 즉시 가입된 파티원
- `레이드 단위`: 난이도를 제외한 `raidId`; 노말·하드·나이트메어는 같은 레이드로 취급

본계정과 부계정은 서로 다른 사람이 아니다. 한 사용자가 소유한 모든 게임 계정과 캐릭터는 동일한 사용자에게 귀속된다.

## 2. 절대 규칙

### 동일 파티의 사용자 중복 금지

- 한 사용자는 하나의 모집에 한 자리만 가질 수 있다.
- 본계정 캐릭터와 부계정 캐릭터를 사용하더라도 같은 파티에 동시에 참가할 수 없다.
- 파티장인 사용자는 자기 모집에 다른 소유 캐릭터로 신청하거나 추가 가입할 수 없다.
- 서버의 멤버 문서는 UID를 고유 키로 사용해 동일 사용자의 중복 자리를 구조적으로 차단한다.

### 동시간대 참가 금지

- 한 사용자는 시간이 겹치는 둘 이상의 파티에 확정 참가할 수 없다.
- 이 제한은 본계정과 모든 부계정의 캐릭터를 합쳐 사용자 단위로 판정한다.
- 일정이 겹치지 않는 서로 다른 파티 참가는 허용한다.
- 일정 충돌 판정에 필요한 시작·종료 범위가 불명확한 모집은 안전하게 충돌 가능 상태로 표시하고 확정 전에 사용자 확인 또는 정책상 기본 시간을 적용한다.

### 캐릭터의 동일 레이드 확정 참가 금지

- 한 캐릭터가 특정 `raidId`의 파티장 또는 확정 파티원이면 같은 레이드의 다른 난이도 모집에 새로 확정 참가할 수 없다.
- 모집 생성도 확정 참가로 취급한다.
- 예: 이슈아이가 4막 노말 모집을 만들었다면 이슈아이로 4막 하드 모집을 만들거나 신청·가입할 수 없다.
- 예: 이슈아이가 세르카 하드 모집도 만들었다면 이슈아이로 세르카의 다른 난이도에도 신청·가입할 수 없다.
- 주간 완료 후에는 기존 주간 귀속 규칙이 추가 적용되어 같은 주차의 동일 레이드 전체 난이도에서 신청·가입·교체가 금지된다.

## 3. pending 신청과 확정 경쟁

### pending 허용 범위

- pending은 파티 자리를 예약하지 않는다.
- 확정 참가하지 않은 캐릭터는 같은 레이드의 여러 난이도·여러 모집에 동시에 pending 신청할 수 있다.
- 예: 이슈하이가 벨가르딘 나이트메어의 승인 대기 중이어도 벨가르딘 노말·하드의 승인형 모집에 추가 신청할 수 있다.
- 즉시 가입 모집은 신청 명령 안에서 바로 확정 참가하므로 pending 복수 신청 규칙의 대상이 아니다.

### 권장 확정 방식

최초로 성공한 모집 생성, 승인 또는 즉시 가입만 캐릭터의 해당 레이드 확정 점유권을 얻는다.

1. 서버 트랜잭션이 사용자, 캐릭터, 레이드, 일정, 주간 귀속 및 파티 조건을 다시 검증한다.
2. 충돌이 없으면 확정 점유 문서와 파티 멤버십을 같은 트랜잭션에서 생성한다.
3. 같은 캐릭터·레이드의 다른 pending 신청은 `superseded` 또는 `withdrawn`으로 자동 종료한다.
4. 동시에 두 파티장이 승인하더라도 확정 점유권을 먼저 만든 한 건만 성공한다.
5. 나머지 승인은 `이미 다른 파티 참가가 확정된 캐릭터입니다.`로 실패한다.

다른 pending 정리는 사용자 편의를 위한 후처리다. 정리가 지연되더라도 확정 점유 문서가 두 번째 가입을 반드시 막아야 한다.

### 신청 목록 표시

캐릭터 후보에는 같은 레이드 기준으로 다음 상태를 표시한다.

- `동일 레이드 신청 중 N개`
- `동일 레이드 참가 중`
- `동시간대 다른 파티 참가 중`
- `이번 주 동일 레이드 완료`

충돌 상태는 경고색과 아이콘을 함께 사용하고 색상만으로 의미를 전달하지 않는다. 사용자가 정리 가능한 상태와 절대 금지 상태를 구분한다.

## 4. 모집 생성 규칙

- 모집 생성자는 선택 캐릭터로 해당 모집에 즉시 확정 참가한다.
- 계정 대표 캐릭터는 모집 생성 화면의 최초 추천값일 뿐 파티장 캐릭터로 강제하지 않는다.
- 모집 생성 화면에서 본계정과 부계정을 포함한 모든 표시 캐릭터 중 실제 레이드에 참가할 캐릭터를 직접 선택할 수 있어야 한다.
- 파티장 캐릭터 후보에는 계정 표시명, 캐릭터명, 직업, 아이템 레벨, 선택 가능한 저장 역할과 참가 상태를 함께 표시한다.
- 선택한 레이드·난이도를 기준으로 입장 레벨, 저장 역할, 주간 완료, 동일 레이드 확정 참가 및 일정 충돌을 판정한다.
- 동일 레이드 pending은 선택을 막지 않고 신청 건수를 표시하며, 최종 생성 시 명시적 확인 후 종료한다.
- 레이드나 난이도를 바꿔 현재 선택 캐릭터가 조건을 만족하지 않게 되면 캐릭터를 자동 교체하지 않고 오류 상태를 표시해 사용자가 다시 선택하게 한다.
- 파티장 역할은 선택 캐릭터에 저장된 dealer/support 세팅만 제공한다. 한 캐릭터에 두 역할 세팅이 모두 있으면 사용자가 생성 시 역할을 선택한다.
- 같은 캐릭터가 동일 레이드의 다른 모집에 이미 확정 참가했다면 생성을 거절한다.
- 같은 사용자가 같은 모집에 이미 포함되어 있거나 동시간대 다른 파티에 확정 참가했다면 생성을 거절한다.
- 같은 캐릭터의 동일 레이드 pending 신청이 있으면 생성 확인 화면에서 신청 수와 대상을 보여준다.
- 사용자가 계속 진행하면 기존 pending 신청을 자동 철회한 뒤 모집 생성과 확정 점유권 획득을 원자적으로 처리한다.

## 5. 파티 내 캐릭터 변경

### 기본 변경

- 파티장과 파티원은 완료 전까지 자신이 소유한 캐릭터로만 변경할 수 있다.
- 본계정뿐 아니라 같은 사용자의 부계정 캐릭터도 선택할 수 있다.
- 파티 자리와 승인된 역할은 유지한다.
- 새 캐릭터는 역할 세팅, 입장 레벨, 선택 조건, 주간 귀속 및 변경 후 전체 파티 구성을 모두 만족해야 한다.

### 대상 캐릭터가 pending 신청 중인 경우

- 후보에 `동일 레이드 신청 중 N개`를 표시한다.
- 사용자가 `신청을 모두 취소하고 변경`을 명시적으로 선택할 수 있다.
- 변경 명령은 대상 캐릭터의 충돌 pending 철회와 현재 파티의 캐릭터 변경을 하나의 서버 명령으로 처리한다.
- 어느 단계든 검증에 실패하면 기존 파티 캐릭터와 pending 상태를 유지한다.

### 대상 캐릭터가 다른 파티에 확정 참가 중인 경우

다음 두 동작을 구분한다.

#### 이동

- 다른 파티를 탈퇴하고 현재 파티로 옮기는 동작이다.
- 기존 파티에 빈자리가 생기므로 자동 실행하지 않고 대상 파티, 일정 및 영향 범위를 확인받는다.
- 기존 파티가 완료되었거나 탈퇴 불가 상태면 이동할 수 없다.
- 서버가 기존 파티 탈퇴, 새 파티 조건 검증 및 캐릭터 변경을 원자적으로 처리할 수 있을 때만 허용한다.

#### 스왑

- 현재 파티의 캐릭터와 다른 파티에 들어간 같은 사용자 소유 캐릭터를 서로 교환하는 동작이다.
- 두 파티 모두 완료 전이고 캐릭터 변경을 허용해야 한다.
- 두 캐릭터가 각 상대 파티의 기존 역할, 입장 레벨, 선택 조건, 주간 귀속 및 파티 구성 조건을 모두 만족해야 한다.
- 양쪽 파티와 확정 점유 문서를 하나의 서버 트랜잭션으로 갱신할 수 있을 때만 성공한다.
- 한 조건이라도 실패하면 두 파티 모두 기존 상태를 유지한다.

초기 구현 권장은 `pending 취소 후 변경`을 먼저 제공하고, 확정 파티 간 `이동`과 `스왑`은 Firebase 트랜잭션과 탈퇴 정책이 준비된 뒤 별도 작업으로 구현하는 것이다.

## 6. 서버 데이터와 명령 권장안

확정 참가의 단일 진실 공급원으로 다음과 같은 서버 관리 인덱스가 필요하다.

```text
users/{uid}/activeRaidAssignments/{characterId_raidId}
  characterId
  raidId
  recruitmentId
  difficultyId
  role
  startAt
  expectedEndAt
  status
  updatedAt
```

- 모집 생성, 승인, 즉시 가입, 탈퇴, 캐릭터 변경, 이동, 스왑 및 완료 명령만 이 문서를 변경한다.
- 클라이언트 직접 쓰기는 금지한다.
- 사용자 단위 일정 충돌은 같은 UID의 활성 배정 전체를 조회해 검증한다.
- 캐릭터·레이드 확정 충돌은 문서 ID를 이용해 트랜잭션에서 원자적으로 차단한다.

권장 서버 명령:

- `createRecruitment`
- `applyToRecruitment`
- `approveApplication`
- `joinRecruitmentDirectly`
- `withdrawApplication`
- `leaveParty`
- `changePartyCharacter`
- `movePartyCharacter`
- `swapPartyCharacters`

## 7. 테스트 원칙

- Firebase 연결 전 로컬 테스트는 Domain, Repository 및 Widget 자동화 테스트로 검증한다.
- 승인 화면의 실제 다중 사용자 실기기 검증은 Firebase Authentication과 서버 명령 연결 후 진행한다.
- 동일 계정의 다른 캐릭터를 서로 다른 사용자처럼 사용해 승인 흐름을 테스트하지 않는다.
- 실물 디바이스 테스트가 필요한 경우 작업자는 최신 APK를 빌드하지 않고, 사용자가 빌드할 수 있는 정확한 브랜치와 검증 체크리스트를 제공한다.
- 사용자는 해당 브랜치에서 직접 빌드·설치한 뒤 결과를 전달한다.

## 8. 로컬 Domain 구현 상태

- `ActiveRaidAssignment`로 사용자, 캐릭터, 레이드, 난이도, 모집 및 참가 일정을 표현한다.
- `ParticipationConflictPolicy`가 같은 모집의 동일 사용자, 같은 캐릭터·레이드 및 사용자 단위 일정 겹침을 구분해 반환한다.
- 일정 종료 시각이 불명확하고 비충돌을 증명할 수 없으면 `uncertainSchedule`로 확정을 보류한다.
- 종료 시각과 다음 시작 시각이 같은 경계는 겹치지 않는 반열림 구간으로 판정한다.
- `ActiveRaidAssignmentRepository`가 확정 점유의 획득, 사용자별 조회 및 정확한 모집의 해제 계약을 제공한다.
- 인메모리 구현은 최초 확정만 저장하고 충돌하는 후속 확정을 거절한다.
- pending 신청은 확정 점유에 포함하지 않으며 복수 신청을 허용하고 최초 확정 시 충돌 pending을 `superseded`로 자동 종료한다.
- 모집 생성, 즉시 가입 및 승인 완료 전에 확정 점유를 획득하도록 로컬 명령 서비스 연결 완료
- 같은 캐릭터로 동일 레이드 모집을 다시 생성하면 `participationConflict`로 저장 전에 거절
- 최초 승인 또는 즉시 가입 성공 시 같은 사용자·캐릭터·레이드의 다른 pending을 `superseded`로 자동 종료
- pending 자동 종료 전에 승인 경쟁이 발생해도 기존 확정 점유가 두 번째 가입과 투표 저장을 차단
- 로컬 저장 충돌 시 먼저 획득한 점유를 해제하는 보상 처리를 사용하며 Firebase에서는 Aggregate, 점유 및 pending 종료를 하나의 서버 트랜잭션으로 처리해야 함
- 신청 후보 읽기 모델이 동일 레이드 pending 수, 동일 레이드 확정 참가, 사용자 일정 충돌, 불명확한 일정 및 주간 완료 상태를 구조화해 제공
- pending 상태는 신청을 막지 않는 안내이며 확정 참가, 일정 충돌·불명확 및 주간 완료는 신청 차단 상태
- 후보 Bottom Sheet는 차단 상태를 오류색 아이콘·테두리와 함께, pending 상태를 별도 안내색으로 표시
- Account Repository의 본계정·부계정 전체 조회 계약과 모든 소유 캐릭터의 신청 후보 통합 완료
- 모집 생성·즉시 가입 시 동일 레이드 pending 건수를 표시하고 사용자가 동의한 경우에만 기존 신청을 종료하는 확인 흐름 완료
- 승인형 모집의 추가 pending 신청은 기존 신청을 유지하고 확인 없이 허용
- 파티 내 캐릭터 변경 후보·조건 검증과 pending 취소 후 변경 명령 완료
- 변경 후보는 본계정·부계정 전체에서 현재 역할을 유지하는 저장 세팅만 제공하고 주간 완료·참가 충돌·파티 구성 조건을 재검증
- 확정 점유는 기존 캐릭터에서 새 캐릭터로 교체하며 저장 실패 시 기존 점유로 복구
- 다른 확정 파티 사이의 이동·스왑은 Firebase 서버 트랜잭션 단계에서 구현
- 모집 생성 화면은 현재 메인 계정 대표 캐릭터만 파티장으로 사용하므로, 전체 소유 캐릭터 선택 UI가 다음 우선 작업
