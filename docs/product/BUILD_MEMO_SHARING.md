# Build 메모 카드와 공유 기능 — 차후 제품 구상

## 1. 상태와 목적

상태: 차후 작업 아이디어와 데이터 영향 범위 기록. 현재 기본 무결성·시너지 작업에는 포함하지 않으며 상세 UX와 서버 구현은 착수 전에 다시 결정한다.

사용자가 Lost Ark 직업과 Build 특성을 모두 외우지 않아도 파티 신청자와 참가자의 간략 카드에서 본인이 작성하거나 공유받은 짧은 메모를 확인하는 기능이다. 메모 매칭에서 직업만이 아니라 다음 조합을 중요하게 사용한다.

```text
직업
+ 아크패시브 깨달음 분기
+ 질서의 해
+ 질서의 달
+ 선택적인 질서의 별
```

메모는 객관적인 성능 평가나 앱의 공식 추천이 아니다. 사용자가 개인적으로 기록하거나 다른 사용자에게 공유하는 참고 정보다.

## 2. 설정 페이지 구상

- 별도의 `Build 메모` 관리 페이지를 제공한다.
- 한 페이지 안에서 직업별로 카드 하나를 제공한다.
- 직업 카드 최상단에 직업명을 표시한다.
- 직업명 옆에 깨달음 두 분기와 `미선택`을 포함한 드롭다운을 둔다.
- 아래에 질서의 해·달·별 드롭다운을 각각 둔다.
- 각 드롭다운은 선택한 깨달음 분기에 속한 후보와 `미선택`을 제공한다.
- 깨달음과 해·달·별 네 선택값이 바뀔 때 현재 범위에 연결된 메모를 보여주고 편집한다.
- 메모의 초기값은 공란이다.
- 메모 하나는 약 5글자의 짧은 표식을 목표로 하며 정확한 제한과 Unicode 글자 수 계산 방식은 상세 설계에서 확정한다.

모든 직업의 깨달음·아크그리드 후보 데이터가 준비될 때까지 페이지 구현을 막지는 않는다. 카탈로그가 준비된 직업부터 설정 가능하게 하고 미등록 직업은 직업 공통 메모만 제공할 수 있다.

## 3. 계층형 메모와 매칭

메모는 하나의 완전한 조합 문자열에만 붙이지 않고 적용 범위를 계층적으로 가질 수 있어야 한다.

```text
직업 공통
직업 + 깨달음 분기
직업 + 깨달음 분기 + 질서의 해
직업 + 깨달음 분기 + 질서의 달
직업 + 깨달음 분기 + 질서의 별
```

디스트로이어 예시:

- 디스트로이어 공통: `무력좋음`
- 깨달음 분기 1: `딜좋음`
- 깨달음 분기 2: `유틸좋음`
- 특정 아크그리드 코어: `컨어려움`
- 다른 코어: `저점좋음`

분기 1 Character가 지원하면 `무력좋음`, `딜좋음`을 함께 표시한다. 해당 Character가 추가 메모가 연결된 해·달·별 코어를 사용하면 그 메모도 합쳐서 보여준다. 표시 순서 후보는 `직업 공통 → 깨달음 → 해 → 달 → 별`이며 중복 문구는 한 번만 표시한다.

`미선택`은 값이 없다는 뜻과 해당 하위 조건 전체에 적용한다는 뜻을 혼동하지 않도록 내부 모델에서 wildcard 범위를 명확히 정의해야 한다. 완전 조합에만 적용되는 메모가 필요한지는 상세 설계에서 별도로 결정한다.

## 4. 파티 카드 표시

대상 화면 후보:

- 파티 모집 상세 신청자 카드
- 파티 구성 참가자 카드
- 필요성이 확인되면 그룹 Character 간략 카드

기존 이름·직업·전투력·아이템 레벨 옆의 남는 공간에 다음 정보를 추가한다.

- 등록된 인게임 Build 별칭: `망소빙`, `붕쯔디트` 등
- 현재 사용자에게 매칭된 짧은 메모 chip
- 다른 직업 보석 등 기본 무결성 경고

카드 높이는 메모 개수에 따라 계속 늘리지 않는다. 카드 내부에 또 하나의 세로 스크롤을 넣으면 부모 목록과 스크롤 충돌 및 접근성 문제가 생길 수 있으므로 1차 후보는 고정 높이의 **가로 메모 chip rail**이다.

- 한 줄 `ListView` 또는 가로 `SingleChildScrollView`
- 좌우 스크롤로 추가 메모 확인
- 경고는 메모 chip보다 먼저 고정 표시
- 메모가 없으면 영역 자체를 숨김
- 긴 문장 입력을 제한해 카드 전체 레이아웃을 유지

실제 화면 폭과 접근성 검증 후 가로 스크롤, `더보기` 팝업 또는 접기/펼치기 중 최종 방식을 선택한다.

## 5. 파티 카드에 필요한 최소 Build Snapshot

현재 파티 신청과 membership Snapshot만으로는 타인의 깨달음과 해·달·별 조합을 알 수 없다. 타인의 카드에서 Build 별칭과 개인 메모를 매칭하려면 소유자 기기가 분석한 최소 Build 식별 결과를 신청·참가 시점 Snapshot에 포함해야 한다.

후보 구조:

```text
buildIdentitySnapshot
  classId
  enlightenmentBranchId
  orderSunCoreId
  orderMoonCoreId
  orderStarCoreId (nullable)
  buildAliasId (nullable)
  catalogVersion
  capturedAt
  detectionStatus
```

- 전체 Armory JSON, 전체 Tooltip과 사용자의 메모 본문은 서버에 올리지 않는다.
- 신청자 카드에는 신청 당시 Snapshot을 사용한다.
- 참가 Character 변경 시 membership의 최소 Build Snapshot도 함께 바꾼다.
- 기존 문서 또는 미분석 Character는 null을 허용하고 직업 공통 메모만 표시한다.
- 이 Snapshot은 클라이언트가 API 응답을 분석해 게시한 표시용 결과다. 서버가 Lost Ark API를 독립 재검증한 권위 값으로 간주하지 않는다.
- 향후 가입 차단 조건으로 사용하려면 현재의 클라이언트 신뢰 경계와 별도 서버 검증 필요성을 다시 검토한다.

추가 시 영향 범위:

- 파티 신청·재신청 write plan
- membership 생성·승인·Character 변경 write plan
- 공개 상세 read model과 UI
- Firestore Rules 필드 allowlist와 타입 검증
- 구버전 문서의 null 호환
- 그룹 카드까지 확장할 경우 그룹 Character/membership Snapshot

실제 변경량을 먼저 산정한다. Rules 복잡도 또는 생성·가입 명령 위험이 크면 Build Snapshot과 타인 카드 메모는 보류하고 로컬 내 계정 기능만 제공한다.

## 6. 로컬 메모 팩 모델 후보

메모는 Player별 로컬 Drift 데이터로 관리한다. 공유받은 팩과 직접 작성한 팩을 구분하고 여러 팩을 활성화·비활성화할 수 있어야 한다.

```text
MemoPack
  packId
  schemaVersion
  title
  authorLabel (optional)
  source: personal | imported
  gameCatalogVersion
  createdAt
  updatedAt
  enabled

MemoRule
  ruleId
  packId
  classId
  enlightenmentBranchId (nullable wildcard)
  coreSlot: sun | moon | star | none
  coreId (nullable wildcard)
  text
  displayOrder
```

- 사용자의 직접 작성 메모는 기본 개인 팩에 저장한다.
- 가져온 팩을 직접 수정할 경우 원본을 덮어쓰지 않고 개인 팩으로 복사하는 방안을 우선한다.
- 메모 매칭은 서버 조회 없이 카드의 Build Snapshot과 로컬 규칙으로 수행한다.
- 메모 본문은 plain text만 허용하고 HTML·실행 링크를 해석하지 않는다.

## 7. 공유 1차안 — JSON 내보내기·가져오기

첫 공유 방식으로 권장한다. 서버, 계정, 공개 권한과 운영 비용이 필요 없다.

- 선택한 MemoPack을 버전 있는 JSON 파일로 내보낸다.
- 운영체제 공유 시트를 통해 메신저·Drive·메일 등 사용자가 원하는 방식으로 전달한다.
- 받은 파일은 앱에서 미리보기 후 가져온다.
- 가져오기 전 팩 이름, 작성자 표기, 규칙 수, 대상 직업 수와 카탈로그 버전을 보여준다.
- 같은 `packId`의 새 버전은 업데이트, 다른 팩은 별도 추가로 처리하는 방안을 검토한다.
- 개인 팩과 가져온 팩의 동일 조건 메모가 겹치면 둘 다 표시하거나 팩 우선순위를 적용한다. 자동으로 한쪽을 삭제하지 않는다.
- 알 수 없는 class/core ID, 지원하지 않는 schemaVersion, 제한 초과 메모는 거부하거나 제외 내역을 보여준다.
- 가져오기 전체를 실행하기 전에 크기·항목 수·5글자 정책을 검증한다.

JSON은 사람이 직접 편집할 수 있는 교환 형식이지만 앱 내부 저장 구조와 완전히 동일할 필요는 없다. 안정적인 ID와 `schemaVersion`을 사용해 향후 마이그레이션할 수 있어야 한다.

## 8. 공유 2차 후보 — 서버 공유 코드

JSON 공유가 실제 사용자에게 불편하다고 확인된 경우에만 검토한다.

- 작성자가 MemoPack의 특정 버전을 서버에 게시한다.
- 서버는 짧은 공유 코드와 불변 또는 버전된 팩을 연결한다.
- 받는 사용자는 코드를 한 번 입력해 팩을 내려받고 로컬 Drift에 저장한다.
- 파티 카드를 볼 때마다 서버에서 메모를 읽지 않는다.
- 원본 작성자의 수정사항을 자동 실시간 동기화할지, 사용자가 명시적으로 업데이트할지는 별도 결정한다. 1차 서버안은 명시적 업데이트를 권장한다.
- 공개 팩 삭제, 신고, 악성 문구, 소유권, 코드 충돌, 읽기 권한과 Rules를 함께 설계해야 한다.

Firestore 문서 하나의 최대 크기는 1 MiB이므로 팩 전체를 무제한 단일 문서에 넣지 않는다. 실제 크기 측정 후 메타데이터 문서와 규칙 chunk/subcollection으로 분리할지 결정한다. 공식 기준: <https://firebase.google.com/docs/firestore/quotas>

서버 공유의 핵심은 저장 용량보다 공개 쓰기·읽기 Rules, 악성 콘텐츠와 버전 관리다. 이 운영 범위를 감당하지 않기로 하면 JSON 공유만 유지한다.

## 9. 권장 단계

1. 기본 Build 무결성과 최소 Build 식별 Snapshot 설계를 먼저 완료한다.
2. Build 메모 페이지의 정보 구조와 계층형 매칭 규칙을 확정한다.
3. 직업 공통·깨달음·해·달·별 로컬 메모와 카드 가로 chip 표시를 구현한다.
4. JSON export/import, 미리보기와 충돌 정책을 구현한다.
5. 실제 여러 메모 팩의 파일 크기와 카드 표시 밀도를 측정한다.
6. 최소 Build Snapshot의 서버·Rules 변경량을 검토하고 허용되는 경우 타인 카드 매칭을 연결한다.
7. JSON 사용성이 부족한 경우에만 서버 공유 코드와 게시 팩을 설계한다.

상세 화면, 글자 제한, wildcard 의미, 여러 팩 우선순위, 서버 공유와 실시간 업데이트는 차후 작업 착수 시 사용자와 다시 확정한다.
