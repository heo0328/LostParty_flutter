## 2. 배경

서비스 초기에는 전체 공개 모집보다 지인·고정 인원 중심의 그룹 사용자가 주요 사용층이 될 가능성이 높다. 그룹은 단순한 계정 관리 항목이 아니라 사용자가 반복적으로 방문하고 레이드 활동을 이어가는 핵심 공간으로 본다.

## 3. 확정된 화면 진입 구조

하단 내비게이션은 현재의 4개 구성을 유지한다.

1. 레이드 현황
2. 내 계정
3. 레이드 모집
4. 그룹

기존 `설정` 탭은 `그룹` 탭으로 교체한다. 설정 페이지와 기존 하위 기능은 제거하거나 구조를 변경하지 않고, `내 계정` 화면 상단의 톱니바퀴 버튼을 통해 진입한다.

모든 주요 페이지에 설정 버튼을 반복 배치하지 않는다. 이에 따라 기존 레이드 현황·레이드 모집 화면의 구조와 이동 흐름은 유지한다.

## 4. 그룹 기본 개념

그룹은 기존 레이드 모집·진행 시스템을 대체하지 않는다. 사용자들이 소속되는 별도의 공간이며, 그룹 안에서 생성되는 레이드도 생성·신청·가입·진행·완료·해산까지 일반 레이드와 같은 흐름과 규칙을 사용한다.

그룹 기능이 추가하는 범위는 다음과 같다.

- 사용자 간 그룹 소속 관계
- 사용자 초대·가입 신청·초대코드 즉시 가입
- 그룹에 속한 레이드
- 기존 레이드 목록에서 그룹 결과만 골라보는 필터

그룹 전용 레이드에 별도의 완료 방식이나 해산 규칙을 만들지 않는다. 기존 레이드 계약을 그대로 재사용하며 그룹 식별 정보만 추가한다.

## 5. 그룹 생성과 관리

- 그룹을 만들 때 그룹장이 그룹 이름을 정한다.
- 그룹 생성자는 active Player이며 서버 소유권이 확인된 Game Account와 인증 캐릭터를 하나 이상 보유해야 한다.
- 생성자는 자신에게 연결·인증된 캐릭터 중 하나를 `그룹 대표 캐릭터`로 선택한다.
- 그룹 대표 캐릭터명은 게임 내에서 그룹을 식별하기 위한 표시 정보다. 사용자의 현재 대표 캐릭터와 별개인 그룹 전용 기록으로 저장한다.
- 사용자가 내 계정의 대표 캐릭터를 변경해도 기존 그룹 대표 캐릭터 기록은 자동으로 바꾸지 않는다.
- 생성자가 그룹명을 직접 입력하지 않으면 기본 이름을 `${그룹 대표 캐릭터명}의 그룹`으로 정한다.
- 직접 입력한 그룹명은 앞뒤 공백을 제거한 뒤 1~20자로 제한한다.
- 줄바꿈과 제어문자는 허용하지 않고 한글·영문·숫자·공백·일반 기호는 허용한다.
- 자동 금지어 필터는 초기 범위에서 제외한다.
- 사용자가 입력하는 그룹명은 다른 그룹과 중복될 수 있다. 그룹은 내부 Group ID로 구분한다.
- 그룹 이름은 생성 이후 수정할 수 있다.
- 그룹장은 생성 이후 다른 그룹원으로 변경할 수 있다.
- 정상 상태에서 그룹장을 이전할 때는 현재 그룹장이 유효한 일반 그룹원 한 명을 선택해 즉시 지정한다. 대상 수락과 이전 요청 상태는 사용하지 않는다.
- 이전 Transaction은 현재 그룹장·대상 membership·group revision을 다시 검증하고 group leader와 두 membership 역할을 함께 교체한다. 동시 이전은 최초 한 건만 성공한다.
- 별도의 대상 선택 없이 승계해야 할 때는 가입 순서가 두 번째로 빠른 유효 그룹원을 후임 그룹장으로 정한다.
- 가입 시각이 같은 예외에는 서버의 안정적인 보조 정렬 키를 사용한다.
- 그룹 한 곳의 최대 인원은 50명이다.
- 한 사용자가 동시에 가입할 수 있는 그룹은 최대 50개다. 사용자가 그룹장인 그룹도 이 수에 포함한다.

그룹 대표 캐릭터는 게임 내에서 사용하는 “누구의 고정 파티”와 같은 명칭을 표현하기 위한 정보다. Player 또는 게임 계정의 소유권 식별 키로 사용하지 않는다.

## 6. 초대와 가입

- 그룹 가입 경로는 `그룹 초대`, `가입 신청`, `초대코드 즉시 가입` 세 가지다.
- 자유 가입 기능은 제공하지 않는다.
- 초대받은 사용자의 수락·거절 흐름과 가입 신청의 승인·거절 흐름을 제공한다.
- 그룹에는 초대코드를 표시한다. 유효한 초대코드를 입력하면 그룹장의 별도 승인 없이 즉시 가입한다.
- 초대코드 가입도 그룹 정원, 사용자 최대 가입 그룹 수, 신청 금지와 현재 membership을 서버 Transaction에서 검증한다.
- 초대와 가입 신청은 생성 후 24시간이 지나면 만료한다.
- 거절 또는 만료 후 재신청 대기시간은 두지 않는다.
- 그룹장은 들어온 신청을 거절하는 것과 별도로 해당 신청자의 이후 가입 신청을 금지할 수 있다.
- 가입 신청 목록에는 신청자가 해당 그룹에 신청한 누적 횟수를 Player 단위로 표시한다.

그룹 membership, 활성 가입 신청, 누적 신청 횟수와 신청 금지는 모두 `groupId + playerId`를 기준으로 처리한다. 같은 Player가 본계정·부계정 또는 다른 캐릭터로 신청해도 같은 신청자와 누적 횟수로 본다. 초대코드 즉시 가입은 가입 신청 횟수에 포함하지 않는다.

그룹은 캐릭터나 개별 원정대가 아니라 Player를 초대한다. 그룹원이 그룹 내 레이드에 참여할 때는 해당 Player에게 정상적으로 연결·인증된 본계정과 부계정의 모든 원정대 캐릭터를 사용할 수 있다. 캐릭터 선택과 참가 제한은 기본 레이드 모집 흐름과 동일한 규칙을 적용한다.

예를 들어 Player A가 `1~5` 캐릭터를 가진 본계정 원정대와 `11~55` 캐릭터를 가진 부계정 원정대를 모두 인증했다면, Player A의 그룹 membership 하나로 두 원정대의 캐릭터를 모두 사용할 수 있다. 실제 레이드에서는 선택한 캐릭터가 기존 레이드 가입 조건을 충족해야 한다.

### 6.1 캐릭터 검색 초대

그룹원은 정확한 캐릭터명으로 사용자를 검색해 초대할 수 있다. 기존 Player에 연결되고 active 소유권이 확인된 인증 캐릭터만 검색 결과에 포함한다. 검색 결과에는 대상을 확인할 수 있도록 다음 정보를 표시한다.

- 캐릭터명
- 서버명
- 직업
- 전투력
- 아이템 레벨

검색된 캐릭터는 초대 대상 사용자를 확인하기 위한 표시 수단이다. 실제 초대와 그룹 membership은 해당 캐릭터에 연결된 Player를 대상으로 한다.

### 6.2 그룹 요청 현황

그룹 탭에는 초대와 가입 신청을 확인하는 `그룹 요청 현황` 영역 또는 하위 탭을 둔다.

- 나에게 도착한 그룹 초대
- 내가 다른 그룹에 보낸 가입 신청
- 내가 그룹장인 그룹에 도착한 가입 신청

그룹장은 자신의 그룹에 들어온 신청을 이곳에서 승인하거나 거절한다. 일반 멤버에게는 그룹장 전용 신청 관리 항목을 표시하지 않는다.

### 6.3 초대·신청 충돌과 취소

- `groupId + playerId`당 활성 가입 관계 요청은 하나만 유지한다.
- 활성 초대가 있는 Player가 가입 신청을 시도하면 새 신청을 만들지 않고 기존 초대의 수락·거절 화면으로 이동한다.
- 활성 가입 신청이 있는 Player에게 초대를 시도하면 새 초대를 만들지 않고 그룹장에게 기존 신청을 승인하도록 안내한다.
- 초대코드 즉시 가입이 성공하면 같은 Player의 기존 초대·가입 신청을 종료한다.
- 이미 그룹원이면 초대·가입 신청·초대코드 가입을 모두 `이미 가입한 그룹`으로 종료한다.
- 신청 금지된 Player는 가입 신청·초대코드 가입·일반 멤버 초대를 모두 사용할 수 없다. 그룹장이 초대하려면 먼저 신청 금지를 해제한다.
- 초대를 보낸 일반 멤버는 자신이 보낸 활성 초대만 취소할 수 있고 그룹장은 그룹의 모든 활성 초대를 취소할 수 있다.
- 초대 대상은 초대를 수락하거나 거절할 수 있다.
- 초대를 보낸 멤버가 그룹에서 탈퇴하면 그 멤버가 보낸 활성 초대를 종료한다.
- 그룹 정원이 찬 상태에서는 초대 수락을 거절하되 해당 초대는 24시간 만료 전까지 유지한다.

### 6.4 그룹 검색과 접근

사용자는 다음 세 가지 방식으로 그룹에 접근할 수 있다.

- 그룹명 검색
- 생성 시 지정된 그룹 대표 캐릭터명 검색
- 초대코드 입력

일반 검색 화면은 그룹명 입력란과 대표 캐릭터명 입력란을 나누지 않는다. 하나의 검색어를 그룹명과 대표 캐릭터명에 함께 적용한다. 초대코드는 일반 검색과 구분된 코드 입력 동작으로 처리하고, 일치하면 확인 후 해당 그룹에 즉시 가입한다.

- 모든 로그인 사용자는 그룹을 검색할 수 있다.
- 검색 결과와 비회원 접근 화면에는 그룹명·그룹 대표 캐릭터·그룹장·현재 인원만 공개한다.
- 전체 멤버 목록과 그룹 내부 관리 정보는 현재 그룹원만 조회할 수 있다.
- 가입 신청자는 승인 전까지 그룹 기본 정보만 조회할 수 있다.
- 신청 금지 여부, 내부 Player ID와 Game Account ID는 일반 검색 결과나 비회원 화면에 노출하지 않는다.

## 7. 그룹 탭 첫 화면

그룹 탭은 `내 그룹`과 `요청 현황` 두 개의 내부 탭으로 구성하고 기본 진입은 `내 그룹`으로 한다.

### 7.1 내 그룹

- 그룹 검색 진입
- 초대코드 입력
- 가입한 그룹 목록
- 그룹별 그룹장·일반 멤버 역할 표시
- 그룹 생성
- 가입한 그룹이 없을 때 검색·코드 입력·생성 안내

관리 그룹을 별도 목록으로 중복 표시하지 않고 내 그룹 목록의 역할 배지로 구분한다.

### 7.2 요청 현황

- 나에게 도착한 그룹 초대
- 내가 다른 그룹에 보낸 가입 신청
- 내가 그룹장인 그룹에 도착한 가입 신청
- 처리할 요청이 있으면 탭에 숫자 배지 표시

- 정의: 필터는 조회·참가 권한을 바꾸지 않고 이미 받은 원본의 표시만 좁힌다.
- 적용 화면: `레이드 현황 > 진행 중`만. 모집 목록·신청 중·완료 기록은 제외한다. `DETAIL_IMPROVEMENTS.md`의 세 탭 공통 필터는 후속이다.
- 진행 중 원본: `watchActiveRaids`가 소유·참가 membership을 실시간으로 합친다. limit 20 cursor는 공개 모집 목록(`PublicRecruitmentListViewModel`)의 기존 계약이며 진행 중 쿼리를 20개로 바꾸지 않는다.
- 포함: 공개 조건·레이드·난이도, 원본/필터 결과 분리, 결과 개수, 선택 로컬 보존.
- 제외(D3에서 추가): 그룹원·Character 칩, 현재 Player 제외, 사용자 내부 OR / 사용자 간 AND.
- 상태 보존: Player별 Drift. 카탈로그에 없는 레이드·난이도는 제거하고 나머지를 유지한다. 그룹 선택은 가입 그룹 목록과 대조한다.
- 완료 조건: 기본 필터 판정·빈 결과와 원본 구분·페이징 안전 세션 테스트. 실기기 확인은 E다.

### 8.1 필터 버튼 상태

- `진행 중 / 신청 중 / 완료 기록` 전환과 진행 중 목록 사이에 `레이드 필터: 모든 레이드` 영역을 둔다.
- 기본 공개 조건은 전체·일반 공개·그룹 공개가 모두 선택된 상태다.
- 필터는 이미 받은 원본 목록의 표시만 좁히며 조회·참가 권한을 바꾸지 않는다.

### 8.2 그룹원·Character 선택

- 그룹 공개에서 그룹을 선택하면 현재 Player를 제외한 정상 그룹원을 대표 Character명으로 표시한다.
- 그룹원 아래 Character 칩 후보는 해당 Player의 활동 Character ID와 공개 Character 표시 문서다. 활동 문서가 없으면 인증 활성 Character 전체로 대체하지 않는다.
- 그룹·그룹원·Character 선택 UI는 공개 조건이 `그룹 공개만`일 때만 보인다. 전체 또는 일반 공개가 포함되면 숨기고 그 선택값은 필터 판정과 저장에서 지운다.
- 한 사용자 안에서 선택한 여러 Character는 OR, 선택한 사용자 사이는 AND다.
- 그룹원·Character 선택이 없으면 해당 차원의 전체를 허용한다.
- 이미 레이드에 참가 중인 비활동 Character는 필터 판정에서 인식하고 새 칩으로는 제시하지 않는다.

### 8.3 필터 적용 원칙

- 같은 조건 차원의 복수 선택은 OR, 공개 조건·레이드·난이도·그룹원 차원 사이는 AND다.
- 서버 20개 페이징은 유지하고 필터는 로컬 원본에 적용한다.
- 다음 페이지가 남아 있으면 일치 개수를 `현재 N개`, 마지막 페이지까지 받았으면 `N개`로 표시한다.
- 빈 필터 페이지를 마지막 페이지로 오인하거나 스크롤 중 같은 cursor를 중복 호출하지 않는다.

## 9. 그룹 레이드 생성

2026-08-31 최종 사용자 결정: 레이드 하나는 가입 그룹 하나에만 연결한다. 이전 다중 그룹 조건부 검토는 종료하며 아래 생성 화면 배치를 적용한다.

- 모집 생성 최상단에서 `일반 레이드 / 그룹 레이드`를 상호 배타적으로 선택한다. 두 개를 동시에 체크할 수 있는 독립 체크박스로 만들지 않는다. 기본값은 기존 흐름을 유지하는 일반 레이드다.
- 그룹 레이드 선택 시 바로 아래 드롭다운에 현재 가입한 유효 그룹 목록을 보여주고 선택하게 한다. 일반 레이드에서는 그룹 선택 영역을 숨기고 저장 대상에서 그룹값을 제외한다.
- 가입 그룹이 없으면 이유를 안내하고 그룹 레이드 생성은 허용하지 않는다. 제출 전에 그룹 선택 및 현재 소속을 검증한다.
- 그룹 선택은 가입 목록에서 하나만 선택하는 드롭다운이다. 모집 생성에서 다중 선택 체크박스는 제공하지 않는다.
- 기존 단일 groupId 설계를 유지한다. 일반 레이드는 groupId=null, 그룹 레이드는 선택한 그룹 ID 하나를 저장한다. 상세는 §9.2를 따른다.
- 그룹 레이드를 만들면 `그룹만 공개` 체크박스를 기본 선택 상태로 둔다. 생성 시점 저장은 구현되어 2026-09-01 실기기에서 확인했다.
- 해당 레이드의 파티장은 상세의 `그룹만 공개` 스위치로 그룹 전용과 전체 공개 사이를 전환할 수 있다. 생성 이후 전환은 구현되어 2026-09-01 실기기에서 확인했다.
- 전체 공개로 전환해도 레이드의 Group ID는 유지되며 그룹 필터 결과에 계속 포함한다.
- 그룹 전용 상태에서는 해당 그룹원만 레이드를 조회하고 신청할 수 있다.
- 전체 공개 상태에서는 기존 일반 레이드와 동일한 조회·신청 흐름을 사용한다.
- 그룹 전용 레이드에서는 그룹 탈퇴·추방 즉시 참가 자격을 상실한다.
- 전체 공개 레이드에서는 연결된 그룹을 탈퇴해도 일반 참가자로서 레이드 참가 자격을 유지한다. 화면에는 `그룹 탈퇴` 상태를 표시할 수 있으나 자격 상실로 처리하지 않는다.
- 전체 공개 레이드를 다시 그룹 전용으로 전환할 때 비그룹 참가자 또는 유효한 비그룹 신청이 있으면 전환을 거절하고 먼저 정리하도록 안내한다.

그룹이 지정되지 않은 레이드는 기존 일반 레이드로 처리하며, 그룹 레이드는 하나의 Group ID만 가진다. 다대다 배정으로 확장하지 않는다. 공개 전환·그룹 탈퇴 정책은 위 단일 그룹 기준을 유지한다.

### 9.1 모집 만들기 화면 배치 개선

기존 드롭다운이 세로로 이어져 스크롤이 길고 주요 설정을 한눈에 보기 어려운 문제를 함께 개선한다.

- 최상단: 일반/그룹 레이드 선택, 그룹 레이드일 때 가입 그룹 선택
- 파티장 캐릭터 / 역할: 한 줄. 캐릭터에 대부분의 너비를 배정하고 역할 드롭다운은 딜러·서포터 값이 읽히는 작은 너비만 사용
- 역할의 눈에 보이는 `파티장 역할` 라벨과 별도 설명 문구는 제거. 접근성 이름은 유지
- 딜러·서포터 역할을 모두 지원하는 직업만 역할 선택을 허용하며 유효한 저장 선호 포지션을 기본 선택. 선호 역할이 없거나 사용할 수 없는 경우 기존 유효 역할 선택 규칙을 유지하고 저장되지 않은 역할 세팅을 임의로 만들지 않음
- 단일 역할 캐릭터는 역할 선택을 요구하지 않고 별도 큰 입력 영역을 차지하지 않음
- 모집 제목: 기존 입력 UI와 수동 입력·자동 기본 제목 동작 유지. 제목을 없애거나 그룹명으로 강제 대체하지 않음
- 레이드 / 난이도: 한 줄에 각각 절반 너비
- 최소 전투력 / 숙련도: 한 줄에 각각 절반 너비

최상단 모드 선택을 추가하되 기존 제목과 다른 입력의 상대 순서를 불필요하게 바꾸지 않는다. 기본 순서는 모드·그룹 선택 → 캐릭터/역할 → 기존 제목 → 레이드/난이도 → 최소 전투력/숙련도다. 나머지 모집 옵션은 유지한다.

일반 휴대폰 폭에서는 요청한 한 줄 배치를 기본으로 한다. 작은 화면, 긴 캐릭터·레이드명과 접근성 글꼴 확대에서는 잘리지 않도록 반응형 배치·폭 배분·안전한 줄바꿈을 검증한다. 선택·검증 오류·요청 중 비활성 동작은 유지한다.

### 9.2 단일 그룹 매칭 확정

- 사용자는 그룹 가입·탈퇴가 쉬운 현재 흐름을 고려하여 단일 그룹 매칭으로 확정했다. 이전 다중 그룹 비용 검토는 실행하지 않는다.
- 한 레이드에 연결하는 그룹은 최대 하나다. 그룹 모드에서 선택은 필수이며 현재 가입한 유효 그룹만 지정한다.
- 생성 write plan은 일반 레이드 `visibility=public`/`groupId=null`, 그룹 레이드 선택 그룹 ID 하나와 생성 시 `그룹만 공개`면 `visibility=group`을 저장한다. 그룹만 공개 목록은 `groups/{groupId}/raidListings/{recruitmentId}` Projection으로 공개 모집 리스트에 합친다. 단건 get·신청은 그룹 멤버십으로 제한한다. 2026-09-01 실기기에서 그룹원 모집 리스트 노출을 확인했다.
- 생성 후 파티장의 `그룹만 공개` 전환은 구현되어 2026-09-01 실기기에서 확인했다. listing 자리·상태 동기화는 구현했고, 디바이스 미연결로 실기기 확인은 보류한다. listing이 없는 기존 방 보완은 별도다. 그룹 전용 레이드의 탈퇴 자격 상실과 제한적 정리는 D1에서 구현했다.
- listing은 이번 작업에서 새 축약 스키마로 바꾸지 않고 현재와 같은 모집 스냅샷 Projection을 유지한다. 목록 카드와 노출 판정에 영향을 주는 `status`, `currentCycleStatus`, `manualRecruitmentEnabled`, `memberCount`, `maxMemberCount`, `hasAvailableSlot`, 자리·멤버 Snapshot, `currentCycleKey`, 회차 시각, 수정 가능한 카드 표시 필드, `revision`, `updatedAt`을 원본의 Transaction 후 상태와 일치시킨다.
- 유효한 그룹 전용 모집을 변경하는 시점에 listing이 없으면 같은 Transaction에서 생성해 자연 복구한다. 생성 이후 한 번도 변경되지 않은 과거 방을 일괄 보완하는 작업은 별도 후속 단계로 유지한다.
- groupIds 배열, 다중 선택 체크박스, 여러 그룹으로 모집 복제는 이번 범위에서 제외한다.
- 목록 필터의 복수 그룹 선택은 별개 기능이므로 기존 기획을 유지한다. ‘여러 그룹의 모집을 모아 보기’와 ‘하나의 모집을 여러 그룹에 배정하기’를 혼동하지 않는다.

### 9.3 그룹장 전용 레이드 관리 (2026-09-16 후속 결정)

- 그룹 상세에서 **현재 그룹장에게만** `그룹 레이드 관리` 진입 버튼을 보여 준다. 해당 그룹의 레이드 참가 여부는 요구하지 않는다. 그룹장 이전 직후 관리 권한은 새 그룹장에게 이동한다.
- 관리 화면의 고정 대상은 모집 원본의 `groupId == 현재 그룹`, `visibility == group`, `status == active`인 방이다. 만석, 모집 일시 중단, 다른 주차 대기와 이번 주차 완료 상태여도 반복방이 활성 상태면 포함한다. `hasAvailableSlot`, `manualRecruitmentEnabled`, 현재 주차로 관리 대상을 좁히지 않는다.
- 1회성 완료방(`status == completed`), 해산방(`disbanded`), 전체 공개로 전환한 방은 제외한다. 반복방은 이번 주차가 완료되어도 `status == active`이면 그룹 해산을 막으므로 `이번 주 완료 · 반복방`처럼 상태를 분명히 표시한다.
- 각 카드에는 방 제목·레이드·난이도·현재 공대장·인원·반복 여부·현재 회차 상태를 표시한다. 그룹장에게는 해당 방의 `전체 공개 전환`과 `모집 해산`만 추가로 허용한다. 신청 승인, 파티 구성·캐릭터 변경, 완료, 반복 설정 변경 권한은 추가하지 않는다. 파티 전체 완료 취소 기능은 역할과 관계없이 제공하지 않으며 기존 모집 공대장의 나머지 권한과 참가 상태는 유지한다.
- 추가 권한은 **실행 시점**의 그룹 원본에서 `leaderPlayerId`를 확인하고 모집 원본의 `groupId`·`visibility`·`status`와 revision을 다시 확인한다. 공개 전환이 성공하면 그룹장 추가 권한은 종료되고 연결 `groupId`는 이력으로 남는다. 그룹장 관리 명령은 그룹원·raidState 참여자로 등록하거나 공대장 필드를 변경하지 않는다.
- 그룹 해산이 활성 모집 때문에 거절되면 이 관리 화면으로 이동할 수 있게 한다. 화면 목록은 그룹 해산을 막는 실제 모집 원본과 일치해야 한다. `raidListings`는 공개 모집 카드용 Projection이므로 관리 대상의 유일한 원장으로 삼지 않는다. 누락된 listing이나 집계 불일치가 있으면 빈 목록으로 정상 처리하지 않고 원본 조회·복구 경로를 제공한다.
- 그룹 전용방 공대장의 그룹 탈퇴를 막는 기존 임시 가드는 새 그룹장 관리 경로와 과거 orphan 방 복구가 실기기에서 통과한 뒤 재검토한다. 그룹 탈퇴 자체가 모집 해산·전체 공개 전환을 자동 실행하지는 않는다.

## 10. 역할과 권한

그룹 역할은 `그룹장`과 `일반 멤버` 두 가지만 사용한다. 관리자 역할은 제공하지 않는다.

| 기능 | 그룹장 | 일반 멤버 |
|---|---:|---:|
| 그룹 정보 수정 | 가능 | 불가 |
| 사용자 초대 | 가능 | 가능 |
| 가입 신청 승인·거절 | 가능 | 불가 |
| 멤버 추방 | 가능 | 불가 |
| 그룹장 이전 | 가능 | 불가 |
| 그룹 해산 | 가능 | 불가 |
| 본인 탈퇴 | 그룹장 이전 또는 해산 정책 필요 | 가능 |

일반 멤버가 행사할 수 있는 그룹 관리 동작은 본인 탈퇴와 사용자 초대뿐이다.

## 11. 초대코드 관리

- 초대코드는 그룹 생성과 동시에 자동 발급하지 않는다.
- 그룹 상세 화면에서 그룹장이 필요할 때 생성한다.
- 그룹당 유효한 초대코드는 최대 하나다.
- 코드가 없는 그룹도 정상 상태다.
- 생성된 코드는 복사할 수 있다.
- 초대코드는 시간이 지나 만료되지 않는다. 그룹장이 폐기하기 전까지 유효하다.
- 신규 코드는 혼동 문자를 제외한 영문 대문자·숫자 6자리다. 기존 20자리 활성 코드는 폐기 전까지 가입에 사용할 수 있다.
- 현재 활성 코드는 앱을 다시 열거나 그룹장이 바뀐 뒤에도 조회·복사할 수 있다.
- 그룹장은 체크박스로 초대코드를 일반 그룹원에게 공개할지 선택한다.
- 공개하지 않으면 그룹장만 코드를 조회·복사할 수 있다.
- 일반 그룹원은 초대 권한이 있더라도 비공개 초대코드를 조회할 수 없다.
- 코드 생성과 폐기는 별도 동작으로 제공하며, 폐기는 코드 재입력 없이 확인 Alert만 사용한다.
- 유효한 코드가 있으면 추가 생성할 수 없으며, 새 코드가 필요하면 기존 코드를 먼저 폐기한 뒤 다시 생성한다.
- 그룹 해산 시 유효한 코드를 함께 폐기한다.

초대코드는 민감한 인증 비밀이 아닌 단순 그룹 가입 수단이다. 원치 않는 가입자는 추방하고, 코드는 즉시 폐기한 뒤 필요하면 새로 생성한다.

## 12. 신청 금지 관리

그룹 상세 화면에서 그룹장에게만 `신청 금지 인원` 버튼을 표시한다. 버튼을 누르면 신청이 금지된 Player 목록을 팝업 또는 별도 관리 화면으로 표시한다.

각 항목에는 다음 정보를 간략히 표시한다.

- 신청에 사용된 캐릭터명
- 해당 그룹 누적 신청 횟수
- 아이템 레벨
- 전투력

그룹장은 이 화면에서 신청 금지를 해제할 수 있다. 신청 금지는 `groupId + playerId` 조합에만 적용하며 다른 그룹에는 영향을 주지 않는다. 금지된 Player는 인증된 본계정·부계정과 캐릭터를 바꿔도 같은 그룹에 새 신청을 만들거나 초대코드로 가입할 수 없다.

## 13. 그룹과 레이드 생명주기 분리

그룹 membership과 레이드 membership은 서로 독립적으로 변경한다.

- 그룹 탈퇴·추방만으로 기존 레이드방에서 자동 탈퇴시키지 않는다.
- 레이드방 탈퇴·추방만으로 그룹에서 자동 탈퇴시키지 않는다.
- 그룹 해산만으로 연결된 일반·반복 레이드방을 자동 해산시키지 않는다.
- 여러 레이드방 탈퇴와 그룹 탈퇴를 하나의 버튼으로 연쇄 실행하는 기능은 현재 보류한다.

그룹 탈퇴 또는 계정 자격 상실로 더 이상 함께할 수 없는 캐릭터는 레이드 상세에서 `그룹 탈퇴` 또는 `권한 상실` 상태로 표시한다. 자격 상실이 서버 데이터로 확인된 경우에는 해당 레이드방의 모든 정상 멤버에게 그 캐릭터를 방에서 제외하는 버튼을 제공할 수 있다.

그룹 탈퇴에 따른 참가 자격 상실은 현재 레이드가 그룹 전용일 때만 적용한다. 전체 공개 상태에서는 그룹을 탈퇴한 기존 멤버도 일반 참가 자격을 유지하므로 제한적 정리 버튼의 대상이 아니다.

이 버튼은 일반적인 추방 권한을 모든 멤버에게 부여하는 기능이 아니다. 서버가 대상의 자격 상실을 다시 검증한 경우에만 실행되는 제한적 정리 명령이어야 한다.

그룹에서도 자격을 잃은 멤버를 표시하고 정상 그룹원이 정리 요청을 실행할 수 있다. 실제 제거는 서버가 대상의 자격 상실과 요청자의 현재 membership을 같은 원자 작업에서 재검증한 경우에만 허용한다.

## 14. 그룹장 자격 상실과 승계

그룹장이 그룹 자격을 실제로 상실했다면 가입 순서가 두 번째로 빠른 유효 그룹원에게 그룹장을 승계하고 기존 그룹장을 제거한다.

- 클라이언트가 그룹 상세를 단순 조회했다는 이유만으로 상태를 변경하지 않는다.
- 상세 화면은 서버에서 확인된 자격 상실 상태가 있을 때 `그룹장 정리 및 승계` 동작을 표시할 수 있다.
- 정상 그룹원 누구나 이 동작을 요청할 수 있지만, 서버 Transaction이 기존 그룹장의 자격 상실·후임자의 유효 membership·가입 순서를 다시 검증한다.
- 여러 사용자가 동시에 요청해도 한 번만 승계되도록 멱등성과 revision 검증이 필요하다.
- 유효한 후임 그룹원이 없으면 자동 승계하지 않고 그룹 해산 대기 또는 복구 필요 상태로 전환한다.

이 승계 버튼은 기존 그룹장의 Player 자체가 삭제·정지되거나 그룹 membership의 필수 자격을 잃은 사실이 서버에서 확인된 경우 모든 정상 그룹원에게 제공한다.

그룹 대표 캐릭터가 삭제·숨김·인증 해제된 것만으로 Player의 그룹 자격이 상실되지는 않는다. 이 경우에는 대표 캐릭터를 `변경 필요`로 표시하고 그룹장에게 재선택을 요구하며, 다른 그룹원에게 승계 버튼을 제공하지 않는다.

정상 그룹장은 다른 그룹원에게 이전을 완료하거나 그룹을 해산하기 전에는 탈퇴할 수 없다. Player 또는 필수 소유권의 실제 자격 상실은 위 복구 승계 대상으로 처리한다. 장기 미접속만으로 그룹장 권한을 자동 회수하지 않으며, 1개월 미활동은 운영자 화면의 `오래됨` 표시와 정리 검토에만 사용한다.

정상 그룹장의 이전은 요청·수락 방식이 아니라 **현재 그룹장이 유효한 일반 그룹원 한 명을 선택해 즉시 지정하는 방식**으로 확정한다. 선택된 대상은 별도 수락 없이 즉시 그룹장이 되고, 기존 그룹장은 일반 멤버로 남는다. 기존 그룹장이 탈퇴하려면 이전 완료 후 일반 멤버 탈퇴를 별도로 실행한다. 이전과 탈퇴를 한 Transaction으로 묶지 않는다.

- `joinRelations`나 별도 이전 요청 문서를 만들지 않는다.
- 수락·거절·취소·만료 상태와 이전 알림은 이번 기능에 없다.
- 그룹장이 한 명뿐이면 이전할 수 없고 해산만 안내한다.
- 그룹 대표 Character는 그룹 정체성 값으로 유지하고 그룹장 표시 Character만 후임자의 membership Snapshot으로 변경한다.

## 15. 그룹 필터 상태 보존

- 첫 구현 범위는 `레이드 현황 > 진행 중`이며 모집 목록·신청 중·완료 기록에는 적용하지 않는다.
- 진행 중 필터 선택 상태는 앱을 종료하고 다시 실행해도 로컬에 보존한다. 공개 조건·레이드·난이도·그룹·그룹원·Character를 Player별 Drift에 저장한다.
- 복원할 때 현재 가입 그룹 목록과 다시 대조한다.
- 저장된 그룹이 탈퇴·추방·해산 등으로 유효하지 않으면 해당 선택을 제거하고 나머지를 유지한다.
- 모든 그룹 선택이 무효가 되거나 선택 데이터가 손상됐다면 전체 보기로 초기화한다.
- 초기화 이후 기존 전체 레이드 목록을 정상적으로 표시한다.

## 16. 설계 원칙

- 그룹은 개인 계정 설정과 분리된 공동 활동 공간으로 취급한다.
- 기존 레이드 생성·모집·참가·완료 흐름을 불필요하게 변경하지 않는다.
- 그룹 레이드에도 기존 레이드의 생성·진행·완료·해산 규칙을 동일하게 적용한다.
- 레이드 하나에는 최대 하나의 그룹만 연결한다.
- 그룹 가입은 사용자 단위이며 레이드 참여 캐릭터는 기존 캐릭터 선택 규칙을 따른다.
- 그룹 기능이 없는 사용자도 기존 레이드 기능을 계속 사용할 수 있어야 한다.
- 기존 4개 탭의 수와 전체적인 화면 밀도를 유지한다.

## 17. 활동 시각과 운영자 데이터 정리

서버 데이터가 무제한 누적되지 않도록 그룹 문서에 삭제 후보 판단용 활동 시각을 기록한다.

### 17.1 그룹 활동 시각

그룹에는 `lastActivityAt`을 서버 시각으로 저장한다. 그룹 정보 변경, 멤버 가입·탈퇴·추방, 초대·신청·금지 변경, 초대코드 관리, 그룹장 이전, 그룹 레이드 생성·공개 범위 변경처럼 의미 있는 서버 변경이 성공할 때 갱신한다.

단순 화면 조회와 실시간 listener snapshot 수신 때마다 그룹 원본 문서에 쓰지 않는다. 조회마다 쓰면 추가 snapshot과 쓰기를 반복해서 만들 수 있고 비용·경합·악의적인 보존 요청이 증가한다.

조회 흔적이 별도로 필요하면 원본 `lastActivityAt`과 분리한 `lastAccessAt`을 사용하고 Player별 또는 일정 시간 단위로 쓰기를 제한한다. `lastAccessAt`만으로 삭제 여부를 자동 판정하지 않는다.

### 17.2 운영자 정리 화면

운영자 페이지에서 그룹과 향후 일반 레이드 데이터를 목록으로 조회하고 오래된 데이터를 정리할 수 있어야 한다. 목록에는 이름·내부 ID·상태·생성 시각·마지막 변경/활동 시각·그룹장 또는 파티장·현재 인원·삭제 차단 요소를 표시한다.

운영자 삭제는 단일 문서만 바로 제거하지 않는다. 서버가 연결된 활성 레이드·membership·신청·초대 등 삭제 가능 여부를 다시 검사하고, 차단 요소가 있으면 이유를 보여준다. 삭제 확정 시 먼저 soft delete 상태로 전환하고 정해진 보존 기간 후 실제 삭제하는 방식을 사용한다.

- `lastActivityAt` 기준 1개월 동안 의미 있는 활동이 없으면 운영자 목록에서 `오래됨`으로 표시한다.
- 운영자가 삭제를 승인하면 soft delete 상태와 `deletedAt`을 서버 시각으로 기록한다.
- soft delete 후 28일 동안 보관한 뒤 실제 삭제 대상으로 분류한다.
- 28일 경과 후 실제 삭제를 자동화할 수 없는 운영 환경에서는 운영자 화면의 수동 정리 절차를 제공한다.

### 17.3 일반 레이드 적용 범위

일반 레이드에도 같은 `lastActivityAt`과 운영자 정리 목록이 필요하다. 이번 그룹 작업에서는 요구사항을 문서로만 기록하며 기존 일반 레이드 코드와 데이터에는 적용하지 않는다. 그룹 데이터에 먼저 적용한 뒤 별도 작업으로 확장한다.

### 17.4 그룹 관련 활동 기록 보관

그룹에 속한 레이드 완료, 파티원 변경, 그룹원 변경과 같은 이력성 문서에는 다음 정리 필드를 둔다.

- `groupId`: 소속 그룹 식별자
- `occurredAt`: 행위가 발생한 서버 시각
- `expireAt`: `occurredAt`부터 3개월 뒤의 정리 기준 시각

현재 상태를 나타내는 그룹 원본과 활성 membership은 단순히 3개월이 지났다는 이유로 삭제하지 않는다. 처리 완료된 신청·초대, 멤버·그룹장 변경 이력, 그룹 레이드 활동 이력처럼 계속 누적되는 기록을 발생 시점부터 3개월 보관한 뒤 정리 대상으로 분류한다.

정리 작업은 `groupId`와 `expireAt`으로 대상을 찾되 같은 Group ID라는 이유만으로 전부 삭제하지 않는다. 데이터 종류·현재 상태·연결 관계를 확인하고, 재실행해도 안전한 단계별 삭제로 처리한다.

### 17.5 일반 레이드와 사용자 데이터 후속 기반

그룹에서 먼저 도입하는 `소유/연결 ID + lastActivityAt + occurredAt + expireAt + soft delete` 기반은 향후 일반 레이드와 사용자 데이터 정리에도 공통으로 적용할 수 있어야 한다.

- 일반 레이드: `recruitmentId`와 필요 시 `groupId`를 기준으로 완료·구성 변경·신청·이벤트 기록을 정리한다.
- 사용자: `playerId`와 Game Account ID를 기준으로 계정 연결·인증·활동 기록의 보관 및 삭제 후보를 구분한다.
- 활성 사용자·활성 레이드·현재 membership은 미활동 기간만으로 자동 삭제하지 않는다.
- 일반 레이드와 사용자 데이터의 구체적인 보관 기간, 삭제 차단 조건과 개인정보 처리 기준은 각각의 후속 설계에서 확정한다.
- 이번 그룹 구현에서는 공통 필드와 정리 가능성을 고려하되, 기존 일반 레이드·사용자 코드와 데이터에는 변경을 적용하지 않는다.

## 18. Task-11 이후 후속 기능에서 결정할 정책

아래 항목은 Task-11 제품·계약·구현을 막지 않는다. 해당 후속 기능을 시작할 때 별도 범위로 확정한다.

### 18.1 그룹의 목적과 범위

- 그룹이 친목·고정 파티·길드 대체 중 어디까지 담당하는지
- 그룹 검색 결과의 정렬·페이지 처리와 별도 추천 기능 필요 여부

### 18.2 생성과 가입

- 없음. 검색 정렬·페이지 처리는 Task-11 기술 계약에서 확정한다.

### 18.3 역할과 권한

- 유효한 후임 그룹원이 없는 그룹장 자격 상실의 운영자 복구 정책

### 18.4 그룹과 레이드 연결

- 반복 레이드와 그룹 고정 파티의 역할 중복 처리
- 레이드 완료 기록을 그룹 활동에 표시할지 여부

### 18.5 멤버와 캐릭터

- 그룹 대표 캐릭터 `변경 필요` 상태가 장기간 유지될 때의 처리
- 인증 원정대 전체와 앱에서 실제 사용하는 활동 Character를 분리한다. 확정 계약은 [`../architecture/ACTIVITY_CHARACTER_AND_RAID_FILTER_CONTRACT.md`](../architecture/ACTIVITY_CHARACTER_AND_RAID_FILTER_CONTRACT.md)를 따른다.
- 그룹원 Character 목록과 레이드 필터 후보에는 활동 Character만 새로 노출한다. 이미 레이드에 참가 중인 비활동 Character Snapshot은 기존 참가 상태와 필터 판정을 위해 보존한다.

### 18.6 탈퇴·추방·해산

- 탈퇴 이후 레이드 membership과 신청의 처리
- 그룹 해산 전 확인해야 할 활성 데이터
- 해산 후 기록 보관 범위와 기간

### 18.7 알림과 활동 내역

- 알림 기능은 초기 그룹 구현 범위에서 제외하고 후속 작업으로 진행한다.
- 그룹 공지 기능은 초기 그룹 구현 범위에서 제외하고 후속 작업으로 진행한다.
- 후속 알림 범위와 읽음 상태·보관 기간
- 운영자 개입이 필요한 신고·분쟁 범위

### 18.8 운영과 안전

- 그룹명·소개·공지의 신고 및 제재 정책
- 악의적인 초대·가입 반복 방지
- 그룹장의 권한 남용 대응

## 19. Task-11 구현 범위

Task-11은 그룹 생성과 가입 기반만 구현한다.

### 포함

- 그룹 생성
- 캐릭터 검색 직접 초대
- 가입 신청
- 초대코드 즉시 가입
- 초대 수락·거절·취소
- 가입 신청 승인·거절·신청 금지와 해제
- Player 단위 membership과 정원·가입 그룹 수 검증

### 후속 그룹 관리 작업으로 분리

- 그룹 상세의 그룹원 목록(그룹장 우선 카드·터치 시 인증 캐릭터 목록)
- 일반 멤버 탈퇴와 그룹장 정상 탈퇴
- 멤버 추방
- 그룹장 즉시 지정 이전
- 그룹장 자격 상실 복구 승계
- 그룹 해산
- 그룹과 레이드 membership 정리

후속 범위의 제품 정책은 이 문서에 유지한다. Task-11에서 구현하지 않는다는 뜻이며 정책이 미정이라는 뜻은 아니다. Task-11 데이터 모델은 후속 상태와 명령을 추가할 수 있도록 ID·revision·membership 역할을 훼손하지 않는 구조로 설계한다.
