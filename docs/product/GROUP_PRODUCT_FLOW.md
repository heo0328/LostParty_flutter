# 그룹 제품 흐름

## 1. 문서 상태

- 상태: 초안 작성 중
- 작업 브랜치: `codex/group-product-design`
- 목적: 초기 핵심 사용자가 반복적으로 이용할 그룹 기능의 제품 흐름을 확정한다.
- 현재 단계에서는 제품 정책을 정리하며 구현 계약으로 사용하지 않는다.
- 확정되지 않은 항목은 추정하지 않고 `미결정`으로 유지한다.

## 2. 배경

서비스 초기에는 전체 공개 모집보다 지인·고정 인원 중심의 그룹 사용자가 주요 사용층이 될 가능성이 높다. 그룹은 단순한 계정 관리 항목이 아니라 사용자가 반복적으로 방문하고 레이드 활동을 이어가는 핵심 공간으로 본다.

## 3. 확정된 화면 진입 구조

하단 내비게이션은 현재의 4개 구성을 유지한다.

1. 레이드 현황
2. 내 계정
3. 레이드 모집
4. 그룹

기존 `설정` 탭은 `그룹` 탭으로 교체한다. 설정 페이지와 기존 하위 기능은 제거하거나 구조를 변경하지 않고, `내 계정` 화면 상단의 톱니바퀴 버튼을 통해 진입한다.

모든 주요 페이지에 설정 버튼을 반복 배치하지 않는다. 이에 따라 기존 레이드 현황·레이드 모집 화면의 구조와 이동 흐름은 유지한다.

## 4. 그룹 기본 개념

그룹은 기존 레이드 모집·진행 시스템을 대체하지 않는다. 사용자들이 소속되는 별도의 공간이며, 그룹 안에서 생성되는 레이드도 생성·신청·가입·진행·완료·해산까지 일반 레이드와 같은 흐름과 규칙을 사용한다.

그룹 기능이 추가하는 범위는 다음과 같다.

- 사용자 간 그룹 소속 관계
- 사용자 초대·가입 신청·초대코드 즉시 가입
- 그룹에 속한 레이드
- 기존 레이드 목록에서 그룹 결과만 골라보는 필터

그룹 전용 레이드에 별도의 완료 방식이나 해산 규칙을 만들지 않는다. 기존 레이드 계약을 그대로 재사용하며 그룹 식별 정보만 추가한다.

## 5. 그룹 생성과 관리

- 그룹을 만들 때 그룹장이 그룹 이름을 정한다.
- 생성자는 자신에게 연결된 캐릭터 중 하나를 `그룹 대표 캐릭터`로 선택한다.
- 그룹 대표 캐릭터명은 게임 내에서 그룹을 식별하기 위한 표시 정보다. 사용자의 현재 대표 캐릭터와 별개인 그룹 전용 기록으로 저장한다.
- 사용자가 내 계정의 대표 캐릭터를 변경해도 기존 그룹 대표 캐릭터 기록은 자동으로 바꾸지 않는다.
- 생성자가 그룹명을 직접 입력하지 않으면 기본 이름을 `${그룹 대표 캐릭터명}의 그룹`으로 정한다.
- 사용자가 입력하는 그룹명은 다른 그룹과 중복될 수 있다. 그룹은 내부 Group ID로 구분한다.
- 그룹 이름은 생성 이후 수정할 수 있다.
- 그룹장은 생성 이후 다른 그룹원으로 변경할 수 있다.
- 정상 상태에서 그룹장을 이전할 때는 대상 그룹원이 이전 요청을 수락해야 완료한다.
- 별도의 대상 선택 없이 승계해야 할 때는 가입 순서가 두 번째로 빠른 유효 그룹원을 후임 그룹장으로 정한다.
- 가입 시각이 같은 예외에는 서버의 안정적인 보조 정렬 키를 사용한다.
- 그룹 한 곳의 최대 인원은 50명이다.
- 한 사용자가 동시에 가입할 수 있는 그룹은 최대 50개다. 사용자가 그룹장인 그룹도 이 수에 포함한다.

그룹 대표 캐릭터는 게임 내에서 사용하는 “누구의 고정 파티”와 같은 명칭을 표현하기 위한 정보다. Player 또는 게임 계정의 소유권 식별 키로 사용하지 않는다.

## 6. 초대와 가입

- 그룹 가입 경로는 `그룹 초대`, `가입 신청`, `초대코드 즉시 가입` 세 가지다.
- 자유 가입 기능은 제공하지 않는다.
- 초대받은 사용자의 수락·거절 흐름과 가입 신청의 승인·거절 흐름을 제공한다.
- 그룹에는 초대코드를 표시한다. 유효한 초대코드를 입력하면 그룹장의 별도 승인 없이 즉시 가입한다.
- 초대코드 가입도 그룹 정원, 사용자 최대 가입 그룹 수, 신청 금지와 현재 membership을 서버 Transaction에서 검증한다.
- 초대와 가입 신청은 생성 후 24시간이 지나면 만료한다.
- 거절 또는 만료 후 재신청 대기시간은 두지 않는다.
- 그룹장은 들어온 신청을 거절하는 것과 별도로 해당 신청자의 이후 가입 신청을 금지할 수 있다.
- 가입 신청 목록에는 신청자가 해당 그룹에 신청한 누적 횟수를 원정대 단위로 표시한다.

여기서 원정대는 게임 안의 계정 단위 캐릭터 묶음이다. 하나의 캐릭터를 조회했을 때 함께 조회되는 동일 계정의 캐릭터들을 같은 원정대로 본다. 신청 횟수와 신청 금지는 표시 캐릭터명이 아니라 서버 Game Account ID를 기준으로 처리한다.

그룹은 캐릭터가 아니라 사용자를 초대한다. 그룹원이 그룹 내 레이드에 참여할 때는 본계정 캐릭터뿐 아니라 해당 사용자에게 정상적으로 연결·인증된 부계정 캐릭터도 사용할 수 있다. 캐릭터 선택과 참가 제한은 기본 레이드 모집 흐름과 동일한 규칙을 적용한다.

### 6.1 캐릭터 검색 초대

그룹원은 캐릭터명으로 사용자를 검색해 초대할 수 있다. 검색 결과에는 대상을 확인할 수 있도록 다음 정보를 표시한다.

- 캐릭터명
- 직업
- 전투력
- 아이템 레벨

검색된 캐릭터는 초대 대상 사용자를 확인하기 위한 표시 수단이다. 실제 초대와 그룹 membership은 해당 캐릭터에 연결된 Player를 대상으로 한다.

### 6.2 그룹 요청 현황

그룹 탭에는 초대와 가입 신청을 확인하는 `그룹 요청 현황` 영역 또는 하위 탭을 둔다.

- 나에게 도착한 그룹 초대
- 내가 다른 그룹에 보낸 가입 신청
- 내가 그룹장인 그룹에 도착한 가입 신청

그룹장은 자신의 그룹에 들어온 신청을 이곳에서 승인하거나 거절한다. 일반 멤버에게는 그룹장 전용 신청 관리 항목을 표시하지 않는다.

### 6.3 그룹 검색과 접근

사용자는 다음 세 가지 방식으로 그룹에 접근할 수 있다.

- 그룹명 검색
- 생성 시 지정된 그룹 대표 캐릭터명 검색
- 초대코드 입력

일반 검색 화면은 그룹명 입력란과 대표 캐릭터명 입력란을 나누지 않는다. 하나의 검색어를 그룹명과 대표 캐릭터명에 함께 적용한다. 초대코드는 일반 검색과 구분된 코드 입력 동작으로 처리하고, 일치하면 확인 후 해당 그룹에 즉시 가입한다.

## 7. 초기 그룹 화면의 방향

그룹 탭은 그룹 활동의 시작점 역할을 한다. 상세 배치와 우선순위는 아직 미결정이나 다음 진입 항목을 후보로 둔다.

- 내가 가입한 그룹
- 내가 관리하는 그룹
- 그룹 생성
- 초대 확인 또는 가입 신청
- 가입한 그룹이 없을 때의 안내

위 목록은 기능 확정 목록이 아니라 화면 구조 논의를 위한 초기 후보이다.

## 8. 그룹 레이드 목록 필터

레이드 모집 목록과 레이드 현황처럼 레이드가 나열되는 현재 화면에서는 가입한 그룹을 기준으로 결과를 필터링할 수 있다.

### 8.1 필터 버튼 상태

- 사용자가 가입한 그룹이 하나 이상이면 그룹 필터 버튼을 활성화한다.
- 사용자가 가입한 그룹이 없으면 버튼은 화면에 표시하되 비활성화한다.
- 그룹 미가입 상태에서 기존 레이드 목록의 조회와 사용에는 영향이 없어야 한다.

### 8.2 그룹 선택 팝업

활성화된 그룹 필터 버튼을 누르면 사용자가 가입한 그룹 목록을 팝업으로 표시한다. 각 행에는 다음 정보만 표시한다.

- 그룹명
- 그룹장
- 현재 인원
- 우측 선택 체크박스

체크박스로 하나 이상의 그룹을 선택하면 선택된 그룹에 해당하는 레이드만 현재 목록에 표시한다. 선택을 모두 해제하면 그룹 제한 없이 기존 목록 전체를 표시한다.

### 8.3 필터 적용 원칙

- 필터는 표시 결과만 좁히며 레이드의 가입 자격이나 권한을 바꾸지 않는다.
- 레이드 모집과 레이드 현황은 같은 그룹 선택 개념을 사용한다.
- 선택 상태는 레이드 모집·현황 화면이 공유하며 앱 재시작 후에도 복원한다.
- 그룹 탈퇴·해산으로 선택 대상이 사라지면 해당 선택값을 안전하게 제거하고 나머지 목록을 표시해야 한다.

## 9. 그룹 레이드 생성

레이드 생성 시 일반 레이드와 특정 그룹 레이드 중 하나를 선택한다.

- 모집 만들기 화면 최상단의 캐릭터 선택은 현재 위치를 유지한다.
- 캐릭터 선택 바로 아래에 그룹 선택을 배치한다.
- 한 레이드에는 그룹을 하나만 배정할 수 있다.
- 사용자가 여러 그룹에 가입했더라도 레이드 생성 시 복수 그룹을 선택할 수 없다.
- 복수 그룹 선택은 레이드 모집·현황 목록의 검색 필터에만 적용한다.
- 그룹 레이드를 만들면 `그룹만 공개` 체크박스를 기본 선택 상태로 둔다.
- 해당 레이드의 파티장은 `그룹만 공개` 체크를 변경해 그룹 전용과 전체 공개 사이를 전환할 수 있다.
- 전체 공개로 전환해도 레이드의 Group ID는 유지되며 그룹 필터 결과에 계속 포함한다.
- 그룹 전용 상태에서는 해당 그룹원만 레이드를 조회하고 신청할 수 있다.
- 전체 공개 상태에서는 기존 일반 레이드와 동일한 조회·신청 흐름을 사용한다.
- 그룹 전용 레이드에서는 그룹 탈퇴·추방 즉시 참가 자격을 상실한다.
- 전체 공개 레이드에서는 연결된 그룹을 탈퇴해도 일반 참가자로서 레이드 참가 자격을 유지한다. 화면에는 `그룹 탈퇴` 상태를 표시할 수 있으나 자격 상실로 처리하지 않는다.
- 전체 공개 레이드를 다시 그룹 전용으로 전환할 때 비그룹 참가자 또는 유효한 비그룹 신청이 있으면 전환을 거절하고 먼저 정리하도록 안내한다.

레이드와 그룹을 다대다 관계로 만들지 않는다. 그룹이 지정되지 않은 레이드는 기존 일반 레이드로 처리하고, 그룹이 지정된 레이드는 하나의 Group ID만 가진다.

### 9.1 모집 만들기 화면 배치 개선

기존 드롭다운이 세로로 이어져 스크롤이 길고 주요 설정을 한눈에 보기 어려운 문제를 함께 개선한다.

- 캐릭터 선택: 최상단 전체 너비 유지
- 그룹 선택: 캐릭터 선택 바로 아래 전체 너비
- 레이드 / 난이도: 한 줄에 각각 절반 너비
- 최소 전투력 / 숙련도: 한 줄에 각각 절반 너비

작은 화면, 긴 레이드명과 접근성 글꼴 확대에서 잘리지 않도록 반응형 배치 또는 안전한 줄바꿈을 검증한다.

## 10. 역할과 권한

그룹 역할은 `그룹장`과 `일반 멤버` 두 가지만 사용한다. 관리자 역할은 제공하지 않는다.

| 기능 | 그룹장 | 일반 멤버 |
|---|---:|---:|
| 그룹 정보 수정 | 가능 | 불가 |
| 사용자 초대 | 가능 | 가능 |
| 가입 신청 승인·거절 | 가능 | 불가 |
| 멤버 추방 | 가능 | 불가 |
| 그룹장 이전 | 가능 | 불가 |
| 그룹 해산 | 가능 | 불가 |
| 본인 탈퇴 | 그룹장 이전 또는 해산 정책 필요 | 가능 |

일반 멤버가 행사할 수 있는 그룹 관리 동작은 본인 탈퇴와 사용자 초대뿐이다.

## 11. 초대코드 관리

- 초대코드는 그룹 생성과 동시에 자동 발급하지 않는다.
- 그룹 상세 화면에서 그룹장이 필요할 때 생성한다.
- 생성된 코드는 복사할 수 있다.
- 그룹장은 체크박스로 초대코드를 일반 그룹원에게 공개할지 선택한다.
- 공개하지 않으면 그룹장만 코드를 조회·복사할 수 있다.
- 일반 그룹원은 초대 권한이 있더라도 비공개 초대코드를 조회할 수 없다.
- 코드 재발급 시 기존 코드의 즉시 폐기 여부는 후속 설계에서 확정한다.

초대코드는 그룹장이 승인 절차를 생략하고 가입을 허용하는 접근 권한으로 취급한다. 외부 노출 시 그룹장이 즉시 폐기하거나 재발급할 수 있어야 한다.

## 12. 신청 금지 관리

그룹 상세 화면에서 그룹장에게만 `신청 금지 인원` 버튼을 표시한다. 버튼을 누르면 신청이 금지된 원정대 목록을 팝업 또는 별도 관리 화면으로 표시한다.

각 항목에는 다음 정보를 간략히 표시한다.

- 신청에 사용된 캐릭터명
- 해당 그룹 누적 신청 횟수
- 아이템 레벨
- 전투력

그룹장은 이 화면에서 신청 금지를 해제할 수 있다. 신청 금지는 해당 그룹과 해당 Game Account ID 조합에만 적용하며 다른 그룹에는 영향을 주지 않는다.

## 13. 그룹과 레이드 생명주기 분리

그룹 membership과 레이드 membership은 서로 독립적으로 변경한다.

- 그룹 탈퇴·추방만으로 기존 레이드방에서 자동 탈퇴시키지 않는다.
- 레이드방 탈퇴·추방만으로 그룹에서 자동 탈퇴시키지 않는다.
- 그룹 해산만으로 연결된 일반·반복 레이드방을 자동 해산시키지 않는다.
- 여러 레이드방 탈퇴와 그룹 탈퇴를 하나의 버튼으로 연쇄 실행하는 기능은 현재 보류한다.

그룹 탈퇴 또는 계정 자격 상실로 더 이상 함께할 수 없는 캐릭터는 레이드 상세에서 `그룹 탈퇴` 또는 `권한 상실` 상태로 표시한다. 자격 상실이 서버 데이터로 확인된 경우에는 해당 레이드방의 모든 정상 멤버에게 그 캐릭터를 방에서 제외하는 버튼을 제공할 수 있다.

그룹 탈퇴에 따른 참가 자격 상실은 현재 레이드가 그룹 전용일 때만 적용한다. 전체 공개 상태에서는 그룹을 탈퇴한 기존 멤버도 일반 참가 자격을 유지하므로 제한적 정리 버튼의 대상이 아니다.

이 버튼은 일반적인 추방 권한을 모든 멤버에게 부여하는 기능이 아니다. 서버가 대상의 자격 상실을 다시 검증한 경우에만 실행되는 제한적 정리 명령이어야 한다.

그룹에서도 자격을 잃은 멤버를 표시하고 정상 그룹원이 정리 요청을 실행할 수 있다. 실제 제거는 서버가 대상의 자격 상실과 요청자의 현재 membership을 같은 원자 작업에서 재검증한 경우에만 허용한다.

## 14. 그룹장 자격 상실과 승계

그룹장이 그룹 자격을 실제로 상실했다면 가입 순서가 두 번째로 빠른 유효 그룹원에게 그룹장을 승계하고 기존 그룹장을 제거한다.

- 클라이언트가 그룹 상세를 단순 조회했다는 이유만으로 상태를 변경하지 않는다.
- 상세 화면은 서버에서 확인된 자격 상실 상태가 있을 때 `그룹장 정리 및 승계` 동작을 표시할 수 있다.
- 정상 그룹원 누구나 이 동작을 요청할 수 있지만, 서버 Transaction이 기존 그룹장의 자격 상실·후임자의 유효 membership·가입 순서를 다시 검증한다.
- 여러 사용자가 동시에 요청해도 한 번만 승계되도록 멱등성과 revision 검증이 필요하다.
- 유효한 후임 그룹원이 없으면 자동 승계하지 않고 그룹 해산 대기 또는 복구 필요 상태로 전환한다.

이 승계 버튼은 기존 그룹장의 Player 자체가 삭제·정지되거나 그룹 membership의 필수 자격을 잃은 사실이 서버에서 확인된 경우 모든 정상 그룹원에게 제공한다.

그룹 대표 캐릭터가 삭제·숨김·인증 해제된 것만으로 Player의 그룹 자격이 상실되지는 않는다. 이 경우에는 대표 캐릭터를 `변경 필요`로 표시하고 그룹장에게 재선택을 요구하며, 다른 그룹원에게 승계 버튼을 제공하지 않는다.

## 15. 그룹 필터 상태 보존

- 레이드 모집과 레이드 현황은 동일한 복수 그룹 선택 상태를 공유한다.
- 선택 상태는 앱을 종료하고 다시 실행해도 로컬에 보존한다.
- 복원할 때 현재 가입 그룹 목록과 다시 대조한다.
- 저장된 그룹이 탈퇴·추방·해산 등으로 유효하지 않거나 선택 데이터가 손상됐다면 전체 선택 상태를 기본 비선택으로 초기화한다.
- 초기화 이후 기존 전체 레이드 목록을 정상적으로 표시한다.

## 16. 설계 원칙

- 그룹은 개인 계정 설정과 분리된 공동 활동 공간으로 취급한다.
- 기존 레이드 생성·모집·참가·완료 흐름을 불필요하게 변경하지 않는다.
- 그룹 레이드에도 기존 레이드의 생성·진행·완료·해산 규칙을 동일하게 적용한다.
- 레이드 하나에는 최대 하나의 그룹만 연결한다.
- 그룹 가입은 사용자 단위이며 레이드 참여 캐릭터는 기존 캐릭터 선택 규칙을 따른다.
- 그룹 기능이 없는 사용자도 기존 레이드 기능을 계속 사용할 수 있어야 한다.
- 기존 4개 탭의 수와 전체적인 화면 밀도를 유지한다.
- 그룹 기능 추가가 Firebase Rules나 기존 레이드 데이터 권한을 암묵적으로 확장하지 않도록 한다.
- 문서 논의가 끝나기 전에는 데이터 구조와 권한 정책을 구현 기준으로 확정하지 않는다.

## 17. 활동 시각과 운영자 데이터 정리

서버 데이터가 무제한 누적되지 않도록 그룹 문서에 삭제 후보 판단용 활동 시각을 기록한다.

### 17.1 그룹 활동 시각

그룹에는 `lastActivityAt`을 서버 시각으로 저장한다. 그룹 정보 변경, 멤버 가입·탈퇴·추방, 초대·신청·금지 변경, 초대코드 관리, 그룹장 이전, 그룹 레이드 생성·공개 범위 변경처럼 의미 있는 서버 변경이 성공할 때 갱신한다.

단순 화면 조회와 실시간 listener snapshot 수신 때마다 그룹 원본 문서에 쓰지 않는다. 조회마다 쓰면 추가 snapshot과 쓰기를 반복해서 만들 수 있고 비용·경합·악의적인 보존 요청이 증가한다.

조회 흔적이 별도로 필요하면 원본 `lastActivityAt`과 분리한 `lastAccessAt`을 사용하고 Player별 또는 일정 시간 단위로 쓰기를 제한한다. `lastAccessAt`만으로 삭제 여부를 자동 판정하지 않는다.

### 17.2 운영자 정리 화면

운영자 페이지에서 그룹과 향후 일반 레이드 데이터를 목록으로 조회하고 오래된 데이터를 정리할 수 있어야 한다. 목록에는 이름·내부 ID·상태·생성 시각·마지막 변경/활동 시각·그룹장 또는 파티장·현재 인원·삭제 차단 요소를 표시한다.

운영자 삭제는 단일 문서만 바로 제거하지 않는다. 서버가 연결된 활성 레이드·membership·신청·초대 등 삭제 가능 여부를 다시 검사하고, 차단 요소가 있으면 이유를 보여준다. 삭제 확정 시 먼저 soft delete 상태로 전환하고 정해진 보존 기간 후 실제 삭제하는 방식을 사용한다.

- `lastActivityAt` 기준 1개월 동안 의미 있는 활동이 없으면 운영자 목록에서 `오래됨`으로 표시한다.
- 운영자가 삭제를 승인하면 soft delete 상태와 `deletedAt`을 서버 시각으로 기록한다.
- soft delete 후 28일 동안 보관한 뒤 실제 삭제 대상으로 분류한다.
- 28일 경과 후 실제 삭제를 자동화할 수 없는 운영 환경에서는 운영자 화면의 수동 정리 절차를 제공한다.

### 17.3 일반 레이드 적용 범위

일반 레이드에도 같은 `lastActivityAt`과 운영자 정리 목록이 필요하다. 이번 그룹 작업에서는 요구사항을 문서로만 기록하며 기존 일반 레이드 코드와 데이터에는 적용하지 않는다. 그룹 데이터에 먼저 적용한 뒤 별도 작업으로 확장한다.

### 17.4 그룹 관련 활동 기록 보관

그룹에 속한 레이드 완료, 파티원 변경, 그룹원 변경과 같은 이력성 문서에는 다음 정리 필드를 둔다.

- `groupId`: 소속 그룹 식별자
- `occurredAt`: 행위가 발생한 서버 시각
- `expireAt`: `occurredAt`부터 3개월 뒤의 정리 기준 시각

현재 상태를 나타내는 그룹 원본과 활성 membership은 단순히 3개월이 지났다는 이유로 삭제하지 않는다. 처리 완료된 신청·초대, 멤버·그룹장 변경 이력, 그룹 레이드 활동 이력처럼 계속 누적되는 기록을 발생 시점부터 3개월 보관한 뒤 정리 대상으로 분류한다.

정리 작업은 `groupId`와 `expireAt`으로 대상을 찾되 같은 Group ID라는 이유만으로 전부 삭제하지 않는다. 데이터 종류·현재 상태·연결 관계를 확인하고, 재실행해도 안전한 단계별 삭제로 처리한다.

### 17.5 일반 레이드와 사용자 데이터 후속 기반

그룹에서 먼저 도입하는 `소유/연결 ID + lastActivityAt + occurredAt + expireAt + soft delete` 기반은 향후 일반 레이드와 사용자 데이터 정리에도 공통으로 적용할 수 있어야 한다.

- 일반 레이드: `recruitmentId`와 필요 시 `groupId`를 기준으로 완료·구성 변경·신청·이벤트 기록을 정리한다.
- 사용자: `playerId`와 Game Account ID를 기준으로 계정 연결·인증·활동 기록의 보관 및 삭제 후보를 구분한다.
- 활성 사용자·활성 레이드·현재 membership은 미활동 기간만으로 자동 삭제하지 않는다.
- 일반 레이드와 사용자 데이터의 구체적인 보관 기간, 삭제 차단 조건과 개인정보 처리 기준은 각각의 후속 설계에서 확정한다.
- 이번 그룹 구현에서는 공통 필드와 정리 가능성을 고려하되, 기존 일반 레이드·사용자 코드와 데이터에는 변경을 적용하지 않는다.

## 18. 후속 논의가 필요한 제품 정책

### 18.1 그룹의 목적과 범위

- 그룹이 친목·고정 파티·길드 대체 중 어디까지 담당하는지
- 그룹 검색 결과의 정렬·페이지 처리와 별도 추천 기능 필요 여부

### 18.2 생성과 가입

- 그룹 생성 조건
- 초대코드의 재발급·노출·폐기 정책
- 캐릭터 검색 초대의 검색 범위와 동명이인 표시
- 누적 신청 횟수의 초기화 여부

### 18.3 역할과 권한

- 그룹장 이전 요청의 동시 요청·실패 복구 처리
- 그룹장 탈퇴·계정 삭제·장기 미접속 처리

### 18.4 그룹과 레이드 연결

- 반복 레이드와 그룹 고정 파티의 역할 중복 처리
- 레이드 완료 기록을 그룹 활동에 표시할지 여부

### 18.5 멤버와 캐릭터

- 그룹 대표 캐릭터 `변경 필요` 상태가 장기간 유지될 때의 처리

### 18.6 탈퇴·추방·해산

- 탈퇴 이후 레이드 membership과 신청의 처리
- 그룹 해산 전 확인해야 할 활성 데이터
- 해산 후 기록 보관 범위와 기간

### 18.7 알림과 활동 내역

- 알림 기능은 초기 그룹 구현 범위에서 제외하고 후속 작업으로 진행한다.
- 그룹 공지 기능은 초기 그룹 구현 범위에서 제외하고 후속 작업으로 진행한다.
- 후속 알림 범위와 읽음 상태·보관 기간
- 운영자 개입이 필요한 신고·분쟁 범위

### 18.8 운영과 안전

- 그룹명·소개·공지의 신고 및 제재 정책
- 악의적인 초대·가입 반복 방지
- 그룹장의 권한 남용 대응
- Firebase Rules에서 필요한 최소 읽기·쓰기 권한

## 19. 구현 전 필수 산출물

그룹 구현을 시작하기 전에 다음 문서를 이 초안에서 분리하거나 연결한다.

- 확정된 사용자 흐름과 화면 상태

- 그룹과 레이드 연결 계약
- 탈퇴·추방·해산 상태 전이와 예외 처리
- 자동 테스트 및 다중 디바이스 검증 시나리오
