# 직업 시너지 카탈로그와 신청자 스펙 표시 검토

> 기존 서비스 전용 항목은 [원문·출처 기록](../../legacy/firebase/extracted/docs/product/CLASS_SYNERGY_CATALOG.md)으로 분리했다. 남은 제품/협업 문맥의 신규 서버 적용 여부는 별도 설계에서 판단한다.

## 1. 출처와 이번 구현 범위

- 기준일: 2026-09-03. 데이터 출처는 사용자가 제공한 직업·시너지 표와 차원술사 방깎 정정이다. 공식 최신 밸런스나 실제 장착 스킬을 외부 검증한 자료는 아니다.
- 이번 구현: 30개 직업의 대륙/계열 표시 순서, 13개 시너지 변수, 역할·아크패시브 조건, 항상/선택 채용 구분을 네트워크 없는 Dart 카탈로그로 제공한다.
- 이 문서는 데이터 원본 의미, 코드 사용법과 상세 표시 검토를 한곳에 보존한다. 표시 정책은 §11 사용자 결정이며, 코드 구현은 승인된 단계만 진행한다.
- 이 문서가 시너지 활용·신청자 스펙 검토의 단일 기준이다. NEXT_WORK는 다음 작업 단계만 요약하고 다른 문서는 이 문서를 참조한다.

## 2. 데이터 의미와 표시 규칙

- 대륙/계열은 사용자에게 익숙한 정렬 단위다. 실린·데런·요즈 등을 실제 지리/권한 모델로 해석하지 않는다.
- 순서: 슈샤이어 → 실린 → 아르데타인 → 애니츠 → 데런 → 요즈 → 단독. 각 묶음 안의 직업 순서도 사용자 제시 순서를 따른다.
- 검은색 = `SynergyAdoption.always`, 하늘색 = `settingDependent`. UI 색은 데이터에 넣지 않고 UI에서 매핑한다.
- 항상 채용은 제공된 표의 분류이며 해당 신청자의 스킬을 실제 검사했다는 의미가 아니다. 선택 채용은 가능한 효과일 뿐 실제 보유/슬롯 조건 충족으로 단정하지 않는다.
- 주요 시너지는 방깎·피증·공증·치적·치피증·백헤드 피증이다. 사용자의 '5개' 설명과 달리 표에 별도로 존재하는 공증을 삭제하거나 피증에 합치지 않는다.
- 부가 시너지는 주요 효과 뒤 괄호로 표시할 수 있다. 전투 태세 워로드의 방깎+백헤드 피증은 둘 다 주요 효과다.
- 서포터 역할은 이 딜러 시너지 카탈로그의 필터/슬롯 배정 대상에서 제외한다. 서포터 스킬 자체의 시너지가 없다는 의미는 아니다.
- 역할을 모르면 시너지를 확정하지 않는다. 특성을 모르면 해당 직업의 명시된 공통 효과만 반환한다. 추정한 특성으로 선택 효과를 덧붙이지 않는다.
- `뎀감`은 받피감으로, `방깍`은 방깎으로 통일했다. 대륙 목록의 `데몬헌터`는 앞서 시너지 표에 제시된 데빌헌터의 별칭으로 처리한다.

## 5. 앱 내부 코드와 사용법

- 모델: `lib/shared/game_catalog/domain/entities/class_synergy.dart`
- 상수 데이터/조회: `lib/shared/game_catalog/data/catalogs/class_synergy_catalog.dart`
- 테스트: `test/shared/game_catalog/data/class_synergy_catalog_test.dart`
- 카탈로그 버전: `2026.09.03.user.v1`. 직업 ID와 특성 ID는 앱 내부 키이며 API 공식 ID로 간주하지 않는다.
- 기존 `assets/game_catalog/game_catalog.v1.json`에는 바드 계열·아이덴티티·보석 대상만 있고 아크그리드 프리셋은 비어 있다. 기존 판정 자산은 그대로 보존한다.
- 신규 30개 직업의 시너지 데이터는 별도 카탈로그다. 기존 빌드 판별기가 30개 직업의 보석/아크패시브/아크그리드를 판별하도록 확장한 것은 아니다. 제공되지 않은 판별 노드/프리셋은 추후 보충한다.
- 기존 바드 `bard` / `true_courage` 키와 `GameCatalogRole`을 재사용한다.
- `classes`는 표시 순서대로 읽는다. `resolve`는 직업 ID/이름, 역할, 확인된 특성 ID/이름을 받는다.
- 반환 상태: resolved / unknownClass / roleRequired / supportExcluded / branchRequired / unknownBranch. 빈 시너지 목록만 보고 '시너지 없음'으로 해석하지 않는다.
- `primary`는 주요 효과만, `alwaysAdopted`는 선택 채용 효과를 제외한 목록이다. 필터가 선택 채용 효과를 보유로 단정하지 않도록 adoption을 확인한다.

```dart
const catalog = ClassSynergyCatalog();
final result = catalog.resolve(
  classNameOrId: '호크아이',
  role: GameCatalogRole.dealer,
);
// branchRequired지만 공통 primary는 피증. 추가 네트워크 조회 불필요.
final labels = result.primary.map((effect) => effect.type.label);

final bard = catalog.resolve(
  classNameOrId: '바드',
  role: GameCatalogRole.dealer,
  branchNameOrId: 'true_courage',
);
// 방깎, 공속, 공깎, 마회, 받피감(선택 채용)
```

## 6. 신청자/상세 데이터의 실제 현재 경로

### 6.1 신청 Snapshot에는 수치 두 개가 이미 있다

`PartyApplicationWritePlan.create/reapply`는 다음을 저장한다.

- characterId, characterNameSnapshot, classNameSnapshot, requestedRole
- `submittedBuildSnapshot.itemLevel`: 신청 Transaction이 서버 Character의 itemAvgLevel을 읽어 사용
- `submittedBuildSnapshot.combatPower`: 신청 명령의 combatPower(누락 가능)
- 신청 상태·revision·createdAt·updatedAt 등

반면 `PartyReadDocumentMapper.toApplication`과 `PartyApplicationSummary`는 두 수치를 읽기 모델에 올리지 않는다. `party_read_detail_page.dart`의 신청자 행은 Character명·직업·역할을 표시한다. 즉 수치 저장이 전혀 없는 문제가 아니라 읽기/표시 연결이 빠져 있다. 값이 없는 과거 신청도 고려해야 하며, 누락 전투력을 0으로 바꾸면 안 된다.

아크패시브 특성·아크그리드·보석 원문은 이 신청 Snapshot에 저장되지 않는다. 요청 시점의 수치와 서버 최신 수치는 서로 다를 수 있다. combatPower를 권위 있는 외부 검증 수치로 단정하지 않는다.

### 6.2 서버 Character와 내 계정 상세는 같은 데이터가 아니다

- 서버 `characters/{characterId}`: 이름·직업·아이템 레벨·소유/상태 정보와 별도 보강된 전투력 등의 요약 경로.
- 내 계정 상세: `CharacterDetailViewModel.initialize` → `loadCharacterBuildSnapshots` → 로컬 저장 Snapshot.
- 세팅 새 조회: `createCharacterBuildDraft`가 Lost Ark Armory 응답을 받고 분석해 rawJson으로 보관, 확정 시 로컬 저장.
- 서버 조회는 신청에 이미 있는 안정적인 characterId를 사용해야 한다. 이름 재검색은 불필요하고 이름 변경/동일성 문제를 늘린다.

## 7. 성능 추정과 권장안 — 아직 설계 제안

실기기·실제 payload·네트워크 계측은 이번에 수행하지 않았다. 아래는 코드 구조에 따른 상대적 비용 추정이며 1초 이내를 보장하는 수치가 아니다.

| 방식 | 추가 비용/특성 | 판단 |
|---|---|---|
| 신청 직업·역할 + 로컬 시너지 표 | 서버 추가 요청 0, 작은 상수 목록 조회 | 호크아이 피증 같은 공통 효과 표시에 적합 |
| 신청에 작은 빌드 요약 Snapshot 추가 | 기존 신청 문서의 전송량 증가, 추가 문서 읽기 없이 표시 가능 | 특성별 표시를 위한 우선 검토안 |
| 신청자마다 서버 Character 요약 조회 | 신청자 수에 따라 추가 읽기/대기, 최신값과 신청값 혼재 | 목록에서 무조건 조회하지 말고 필요 시 캐시/지연 조회 |
| 신청마다 상세 rawJson 전체 복제 | 큰 데이터 반복 전송·저장·파싱, 구독 갱신 부담 | 신청 목록용으로 권장하지 않음 |
| 별도 상세 Snapshot 참조 후 탭 시 읽기 | 선택한 사람의 상세만 조회, 서버 저장/권한 설계 필요 | 전체 스펙 화면이 필요할 때 후속 검토 |

권장 구분:

1. 신청자 목록은 기존 작은 Snapshot과 로컬 시너지 카탈로그로 먼저 그린다. 호크아이·피증 표시는 상세 스펙 조회가 필요 없다.
2. 특성까지 필요하면 확인된 branchId, 역할, catalogVersion, buildCapturedAt/분석 상태 등 최소 요약을 신청 시 보존하는 안을 검토한다. 이는 현재 구현되지 않았다.
3. 선택 채용 효과는 특성만 알아도 실제 장착 여부는 확인되지 않는다. 하늘색 가능 효과로 남기거나 실제 스킬 증거를 별도 확보한다.
4. 전체 보석·아크패시브·아크그리드는 사용자가 신청자를 탭했을 때 별도 상세 영역에서 로드하는 방식을 권한다. 필요하다면 캐릭터/역할/세팅 버전별 상세 Snapshot을 저장하고 신청에는 참조만 둔다.
5. '신청 당시 세팅'과 '현재 세팅' 중 무엇을 보여줄지 먼저 결정한다. 전자는 버전 고정 Snapshot, 후자는 갱신 시각/변경 안내가 필요하다. 목록 수치와 상세 수치의 시점을 설명 없이 섞지 않는다.
6. 서버 신설이 필요하면 공개 최소 필드, 읽기 권한, 소유권/역할 일치, 스키마/크기 상한, 보존 기간, 실패/누락 상태를 먼저 계약한다. 원문 전체의 무조건 공개는 하지 않는다.

비동기 네트워크 응답에 1초 이상 걸리는 것과 UI가 멈추는 것은 다르다. 목록 렌더링을 상세 응답에 묶지 않으면 대기 중에도 스크롤/버튼을 유지할 수 있다. 다만 큰 JSON의 동기 파싱/분석/위젯 생성은 프레임 지연 위험이 있으므로 필요 시 분리·캐시·지연 계산한다. 서버 응답 시간과 UI 프레임은 별도로 확인해야 한다.

후속 검증 시 AI가 할 수 있는 일: 데이터 fixture 크기 측정, 요청 횟수 테스트, 지연/실패 fake에서 목록 조작 유지 확인, profile 성능 계측 준비. 디버깅을 모른다는 이유만으로 계측이 불가능한 것은 아니지만 실제 기기·서버 조건 없는 테스트를 실측 성능으로 보고하지 않는다.

## 8. 미결정 후속 항목

- 신청자 전투력·아이템 레벨과 직업 옆 주요 시너지 표시는 §11에서 목록 단계로 승인됐다. UI·읽기 모델 연결은 아직 구현하지 않았다.
- 전체 상세 저장 여부, 최소 요약 스키마, 갱신/보관/조회 권한, 서버 업로드는 4단계 전 추가 결정이 필요하다. 지금은 구현하지 않는다.

## 10. 권장 데이터 경계와 시점 정책

다음 내용은 설계를 선택할 때의 권장 기준이며 확정된 서버 스키마가 아니다.

### 10.1 목록과 상세의 역할

1. **목록:** 신청 당시의 작은 표시 요약을 사용한다. 이름·직업·신청 역할·수치와 판별 가능한 주요 시너지를 먼저 보여주고 전체 스펙 요청을 기다리지 않는다.
2. **상세:** 필요성이 확정되면 신청자가 제출한 세팅의 버전을 고정한 상세 Snapshot을 기본으로 권한다. 파티장이 본 정보가 신청자 세팅 변경만으로 조용히 바뀌지 않게 한다.
3. **최신 정보:** 필요하면 별도 명시적 새로고침/보기로 제공하고 '현재 세팅'과 조회 시각을 표시한다. 신청 당시 값 위에 덮어쓰지 않는다.
4. 현재 itemLevel은 서버 Character, combatPower는 신청 명령에서 가져온다. 두 값은 신청에 함께 저장되더라도 같은 Armory 조회 시점에서 얻은 한 세팅이라고 보장할 수 없다. 통합 상세를 제공하려면 동일 build 버전에서 나온 요약인지 별도로 검증해야 한다.

### 10.2 향후 최소 요약에 고려할 항목

- 기존 characterId, 이름/직업, requestedRole, itemLevel, combatPower를 우선 재사용한다. 표시 목적만으로 중복 이름 검색을 추가하지 않는다.
- branchId, 판별 상태, catalogVersion, buildCapturedAt, 필요 시 buildSnapshotId는 추가 검토 대상이다. 모두 신규 제안이며 현재 신청 스키마에 있는 필드라고 가정하지 않는다.
- 신청 역할과 세팅 판별 역할이 다르면 명시적으로 불일치 상태로 다룬다. 캐릭터의 '현재 선호 역할'을 과거 신청 역할 대신 사용하지 않는다.
- 지원하지 않는 직업/특성·구버전·누락 데이터는 unknown으로 남긴다. 예전 신청에 기본 특성을 임의로 채우지 않는다.
- application.revision은 신청 변경/재신청 버전이고 build 버전은 세팅의 버전이다. 둘을 같은 값으로 간주하지 않는다. 현재 재신청은 신청 문서를 갱신하므로 이전 신청까지 불변 보관된 것으로 해석하지 않는다.
- 상세가 별도 문서가 되면 characterId·역할·build 버전과 해당 신청의 연결을 검증해야 한다. ID 참조만 안다고 다른 신청자/비인가 사용자가 읽을 수 있게 하지 않는다.

### 10.3 카탈로그 버전과 캐시

- 현재 카탈로그 버전 문자열은 존재하지만 과거 버전 전체를 보관/조회하는 기능은 없다. 신청 당시 시너지 표시를 재현하려면 과거 카탈로그 유지 또는 판별 결과의 최소 Snapshot 보존 중 하나를 별도 결정해야 한다.
- 번역된 표시 문자열만을 권한·조건 판정 키로 저장하지 않는다. 안정적인 직업/특성/시너지 ID를 쓰고 알 수 없는 ID의 표시 정책을 둔다.
- 전체 상세 캐시 키는 최소 characterId·역할·build 버전을 구분하도록 설계한다. 이름만 같은 항목이나 역할이 다른 세팅을 재사용하지 않는다.
- 같은 상세를 연속 탭해도 요청은 합치고, 늦은 응답이 다른 신청자의 화면을 덮어쓰지 않도록 식별자/세대를 확인한다.
- 상세의 접근 권한 변경·삭제·만료는 별도 상태다. 실패 시 원래 목록 요약은 유지하되, 캐시된 민감 상세를 무조건 계속 공개하지 않는다.

## 11. 활용 단계와 구현 전 승인 항목

### 2026-09-03 사용자 결정

표시 정책(1단계)을 아래와 같이 확정한다. 이 기록은 목록 표시(2단계) 구현 승인이다. 특성 요약·전체 상세·시너지 슬롯은 각각 별도 승인 전까지 구현하지 않는다.


### 단계

- **1단계 — 표시 정책 확정:** 완료. 위 표가 기준이다. 전투력·아이템 레벨은 이 결정에 따라 2단계에서 연결한다.
- **2단계 — 가벼운 목록 표시:** 다음 구현. 기존 Snapshot 수치의 읽기/표시 연결과 로컬 공통 시너지 표시. 주요 시너지만 간결하게 쓰고 부가/선택 효과는 설명 영역에서 구분한다.
- **3단계 — 특성 요약:** 미승인. 필요한 직업부터 판별 근거와 최소 요약 스키마를 설계·검증한다. 모든 직업의 아크패시브 판별을 한 번에 완료했다고 간주하지 않는다.
- **4단계 — 전체 상세:** 미승인. 필요성이 확정된 경우에만 별도 저장·참조·읽기 권한·버전·보존 정책을 설계하고 탭 시 지연 조회를 구현한다.
- **5단계 — 시너지 필터/슬롯 활용:** 미승인. '직업상 가능'과 '실제 세팅에서 확인됨'을 구분하는 판정 계약부터 만든다. 선택 채용을 자동 가입 조건 충족으로 처리하지 않는다.

### 4단계 전에 남은 결정

전체 상세·서버 저장을 시작하기 전에 아래를 따로 결정한다. 2단계 목록 표시를 막지 않는다.

- 상세를 볼 수 있는 사람은 파티장만인가, 다른 권한 보유자도 포함하는가?
- 재신청/세팅 변경 시 무엇을 재제출하며 기존 제출값·참조는 언제 바뀌는가?
- 상세의 최소 필드, 크기 상한, 저장 실패 시 신청 허용 여부, 보존/삭제 정책은 무엇인가?

전체 rawJson 업로드, 신규 읽기 권한, 자동 세팅 동기화는 위 항목이 정해지기 전에 구현하지 않는다.

## 12. 성능·정합성 검증 체크리스트

- 목록 진입/스크롤에 신청자 수만큼 Character/Armory 전체 요청이 새로 발생하지 않는지 요청 횟수 테스트로 확인한다.
- 상세 응답을 1초 이상 지연시키거나 실패시켜도 목록·뒤로가기·닫기가 동작하는지 확인한다. 로딩 표시와 UI 정지를 구별한다.
- 실제 상세 fixture의 JSON 크기·파싱 시간, 기기 profile 모드의 프레임 지연을 확인한다. fake 테스트로 네트워크 실측 결과를 주장하지 않는다.
- 같은 신청자를 반복 탭하거나 빠르게 다른 신청자로 전환할 때 중복 요청과 응답 뒤바뀜이 없는지 확인한다.
- 과거 신청의 수치/특성 누락은 미확인으로 표시하고 0·임의 특성으로 바꾸지 않는다.
- 딜러/서포터 세팅 전환, 요청 역할 불일치, 이름 변경, 소유권 이전, 상세 만료/삭제, 카탈로그 버전 차이를 검증한다.
- 재신청 revision과 고정 상세 참조가 올바르게 바뀌며 과거 목록 요약과 최신 상세를 무표시로 혼합하지 않는지 검증한다.
- UI는 검은색/하늘색뿐 아니라 '선택 채용·미확인' 등의 보조 설명도 고려한다. 색상이 실제 보유 증명처럼 보이지 않게 한다.

현재 검증 완료는 카탈로그 코드의 표적 21개·전체 회귀 831개와 신규 파일 정적 분석이다. 위 후속 UI·서버·성능 체크리스트는 아직 실행하지 않았다.
