# 디테일 개선 항목

앱의 핵심 기능과 별개로 사용 중 발견한 UI·UX 보완 사항을 기록한다. 각 항목은 관련 기능 작업 시 우선순위를 다시 판단한다.

## 앞으로의 기능 우선순위

2026-08-31 최신 우선 작업은 **모집 생성 일반/그룹 선택과 실제 연결(B)** 다. 생성 화면 배치(A)는 완료했다. GROUP_PRODUCT_FLOW §9.2 및 NEXT_WORK를 우선하며, 아래 큰 기능 순서를 한 번에 구현하지 않는다.

현재 파티 흐름을 안정화한 뒤 다음 순서로 기능을 확장한다. 출시 단계나 차수로 구분하지 않고, 선행 기능과 데이터 의존성을 기준으로 우선순위를 관리한다.

1. 파티 가입·탈퇴·참가 캐릭터 변경을 포함한 자유로운 멤버십 흐름 — **완료** (Task-070)
2. 회차 완료·완료 취소·종료·해산 처리 — **완료** (Task-071)
3. 알림 서비스 별도 설계 — **완료** (Task-072)
4. 공통 파티 이벤트 기반 앱 내부 알림 구현 — **완료** (Task-073)
5. 개인 주간 완료 Claim과 내 계정 체크박스·파티 완료 재구성 (Task-074~) — **완료** (A~F, Task-081)
6. 레이드 모집에서 내 계정의 모집 제외 — **완료** (Task-082)
7. 운영자 계정 권한·페이지 설계 — **계약 완료** (Task-083)
8. 그룹 생성·가입·일반 탈퇴·멤버 전투력 표시 — **완료** (Task-11·11a 및 BUG-009 수정)
9. 모집 생성 UI 정리 — **완료**. 일반/그룹 선택 및 그룹 전용 모집 연결 — **다음 우선 범위**. 그룹은 하나만 매칭하는 방식으로 확정
10. 레이드 모집·레이드 현황 공통 필터
11. 빈 슬롯 역할·직업·시너지 조건
12. 파티 슬롯 이동·스왑
13. 파티 상세의 멤버 전용 최근 10개 텍스트 채팅
14. 참가 일정·신청 자동 만료

세부 기능의 의존 관계는 다음과 같다.

- 알림은 가입·탈퇴·승인·추방·완료·종료·해산 흐름을 먼저 완성한 뒤 서버 방식과 함께 별도 설계한다.
- 현재 파티 이벤트는 향후 앱 내부 알림함과 FCM 발송의 공통 원본으로 사용할 수 있게 유지한다.
- Spark 환경에서 공통 파티 이벤트 기반 앱 내부 알림을 먼저 구현하고, 향후 신뢰할 수 있는 서버가 같은 이벤트를 소비하여 FCM을 발송할 수 있게 확장한다.
- 앱 내부 알림과 FCM에 별도 메시지 원본을 만들지 않으며 상세 계약은 [`../architecture/PARTY_NOTIFICATION_CONTRACT.md`](../architecture/PARTY_NOTIFICATION_CONTRACT.md)를 따른다.
- 공개 파티 필터는 빈 슬롯의 역할·직업·시너지 조건이 저장되고 동일한 판정 규칙을 사용할 수 있어야 한다.
- 공개 파티 목록과 레이드 현황은 가능한 한 같은 필터 항목, 표현과 조작 방식을 사용한다.
- 같은 필터 UI를 사용하더라도 공개 모집, 가입, 신청과 완료 기록은 데이터 소스가 다르므로 조회 구현까지 하나로 강제하지 않는다.
- 진행 중 현황 필터 최하단에는 현재 사용자의 Character 다중 선택을 별도 구역으로 제공한다. 선택된 Character로 참가한 방만 현재 로컬 목록에서 좁히며 신청 중·완료 기록에는 적용하지 않는다.
- 진행 중 현황과 레이드 모집에는 참가 인원/남은 자리의 적은 순·많은 순 로컬 정렬을 제공한다. 기존 필터 요약 아래에 정렬 전용 행을 두고 Firestore query·필드·Rules·Indexes는 추가하지 않는다.
- 레이드 모집 정렬은 현재까지 내려받은 로컬 원본 범위에 적용한다. 다음 페이지를 병합할 때마다 현재 필터와 정렬을 재적용하며 아직 받지 않은 서버 전체의 전역 순서는 보장하지 않는다.
- 최근 10개 채팅은 상세 화면에서만 읽고 전송하며 목록 화면의 필터나 알림 구현과 결합하지 않는다.
- 개인 주간 완료의 최종 계약과 단계별 작업은 [`../architecture/WEEKLY_RAID_CLAIM_CONTRACT.md`](../architecture/WEEKLY_RAID_CLAIM_CONTRACT.md)를 따른다.
- 운영자 식별, 수동 인증·24시간 소유권 방어, 사용자 확인과 마지막 앱 접속은 [`../architecture/OPERATOR_AUTHORIZATION_CONTRACT.md`](../architecture/OPERATOR_AUTHORIZATION_CONTRACT.md)를 따른다. 사용자 삭제는 보류한다.

## 완료 참가자 평가와 한마디

- 같은 파티 회차를 함께 완료한 사실이 확인된 Player 사이에서만 평가를 허용하는 방향을 검토한다.
- 상대에게 한마디 평가 또는 평점을 남기는 기능을 후속 후보로 둔다.
- 평가 자격을 증명할 최소 서버 데이터가 필요할 수 있다.
- 악용, 보복 평가, 반복 평가와 다중 계정 조작 방지 정책이 필요하다.
- 공개 범위, 익명성, 수정, 삭제, 신고와 이의 제기 정책을 별도로 정한다.
- 초기 Firebase 전환에서는 구현하지 않고 별도 제품 설계 후 범위를 확정한다.

현재 종료된 1회성 파티 원본과 완료 회차 Snapshot은 28일 보관하고 반복 파티방은 해산할 때까지 유지한다. 평가 기능에 필요한 최소 완료 증명의 장기 보관 여부는 평가 기능 설계 시 결정한다.

- 회차 완료 후 해산 전·반복방 다음주 대기 시 모집 상세 `파티 구성` 옆에 `이번주 레이드완료`를 상단 모집 제목과 같은 크기·오류색으로 표시. **반영됨**.

- 모집 생성 화면에서 내 계정 페이지로 이동해 캐릭터 표시, 대표 캐릭터 또는 저장 세팅을 변경한 뒤 복귀하면 후보 목록이 즉시 최신화되지 않는다.

## 파티 구성과 가입 조건

- 현재 Firestore membership의 `partyIndex`는 파티 번호이며 파티 내부 자리 번호가 아니다. 상세 UI가 이를 전체 위치처럼 계산해 같은 1파티 멤버가 모두 `1자리`로 보이는 문제가 있다.
- 파티 번호 `partyIndex`와 파티 내부 자리 `slotIndex`를 분리한다. 화면 표시는 1부터 시작하고 내부 값은 기존 구조와 맞게 0부터 시작한다.
- 4인 레이드는 `1파티 1~4번`, 8인 레이드는 `1파티 1~4번`과 `2파티 1~4번`의 고정 슬롯으로 구성한다.
- `1파티 1번`은 4인 파티장, 8인 파티장 겸 공대장 자리로 항상 유지한다.
- 모집 상세는 가입된 멤버 목록만 나열하지 않고 정원 전체의 점유·빈 슬롯을 Card/Cell 구성판으로 표시한다.
- 점유 슬롯은 자리 번호, 책임자 배지, 캐릭터명, 직업, 전투력, 아이템 레벨과 역할을 표시한다.
- 빈 슬롯은 `빈자리`와 `현재 별도 참가 조건 없음`을 기본으로 표시해 향후 역할·직업군·시너지 조건을 같은 Cell에서 확장할 수 있게 한다.
- 반응형 구성판은 Card 열 수가 아니라 파티 그룹의 배치를 전환한다. 좁은 화면에서는 파티별 Card가 전체 폭의 1열을 사용하고, 넓은 화면에서는 4인 1파티를 왼쪽 절반에, 8인 1·2파티를 좌우 절반에 배치한다. 상세 기준은 [`../design/PARTY_COMPOSITION_RESPONSIVE_LAYOUT.md`](../design/PARTY_COMPOSITION_RESPONSIVE_LAYOUT.md)를 따른다.
- 탈퇴·추방 후 남은 멤버를 자동으로 앞자리로 당기지 않고 기존 위치를 유지한다. 캐릭터 변경도 기존 슬롯을 유지한다.
- 모집 상세에서 파티장이 파티원의 파티 및 슬롯 위치를 직접 조정할 수 있어야 한다.
- 8인 레이드는 4인 파티 두 개의 시너지 조합을 확인할 수 있도록 파티별 배치를 명확히 제공한다.
- 모집 중 남은 슬롯의 가입 조건을 직업 또는 시너지 기준으로 변경할 수 있어야 한다.

## 파티 상세 조율 채팅

- 핵심 파티 명령, 고정 슬롯, 그룹과 슬롯 조건 기능이 안정된 뒤 가장 마지막 후속 기능으로 구현한다.
- 파티 상세에 진입한 현재 멤버만 최근 메시지 약 10개를 실시간 조회하고 짧은 텍스트를 전송한다.
- 기본 표시는 `캐릭터명 또는 표시 ID — 채팅 내용`이며 파티 일정과 진행 방식을 간단히 조율하는 용도에 한정한다.
- 이미지, 파일, 음성, 읽음 상태, 전체 채팅 목록 미리보기와 FCM 알림은 초기 범위에서 제외한다.
- 메시지는 `recruitments/{recruitmentId}/messages/{messageId}`의 개별 문서로 저장하고 표시 Snapshot, 본문, 서버 생성 시각만 최소 보관한다. 권한 판정용 PlayerId는 UI에 노출하지 않는다.
- `createdAt desc`, `limit(10)`을 상세 화면에서만 구독하고 화면 이탈 시 listener를 해제한다. 모집 목록이나 다른 탭에서는 방별 채팅을 미리 읽지 않는다.
- 메시지 길이, 빈 문자열, 전송 중 중복 요청과 짧은 시간의 연속 전송을 제한한다.
- 파티 완료·해산 뒤 읽기 전용 유지 여부와 보관·삭제 정책은 TTL·Functions 없이 Spark 범위에서 구현 가능한 방식으로 채팅 작업 시작 전에 확정한다.

## 파티 신청 대기와 자동 취소

- 파티 신청 후 파티장 응답을 기다리는 유효 시간을 정의한다.
- 신청 유효 시간은 전체 공통값, 파티장 설정값 또는 모집별 설정값 중 어떤 방식으로 제공할지 기획한다.
- 제한 시간이 지나면 신청을 자동 취소할지, 만료 상태로 남겨 재신청을 허용할지 결정한다.
- 자동 취소 또는 만료 전에 신청자에게 남은 시간과 예정 동작을 명확히 안내한다.
- 파티장이 모집을 마감·취소하거나 가입 조건을 변경했을 때 대기 중인 신청을 유지할지 일괄 취소할지 규칙을 정의한다.
- 신청 취소, 자동 만료, 파티장 거절 및 모집 마감은 서로 구분되는 상태와 이력으로 기록한다.

## 참가자 수동 알림

- 이 항목은 즉시 구현 범위가 아니다. 핵심 파티 흐름 완료 후 알림 서버와 권한 구조를 결정할 때 함께 재검토한다.
- 모집 상세에서 파티장과 확정 파티원 모두 `알림 보내기` 버튼을 사용할 수 있어야 한다.
- 모집 내용 변경이나 참가 캐릭터 변경을 이유로 모든 참가자에게 자동 알림을 보내지 않고, 사용자가 필요할 때 수동으로 전송한다.
- 버튼을 누르면 `참가 인원에게 알림을 보냅니다.` 확인 알럿을 표시하고 확인한 경우에만 전송을 요청한다.
- 확인 후에는 전송 중 상태와 서버 기준 쿨다운을 적용해 연속 터치, 중복 전송 및 여러 기기에서의 우회를 방지한다.
- 실제 전송은 향후 Firebase 연결 시 인증된 서버 명령이 모집 참가 권한과 수신 대상을 검증한 뒤 FCM으로 처리한다.
- 발신자 본인은 수신 대상에서 제외하고 알림을 누르면 해당 모집 상세로 이동하도록 한다.

## 신청·가입 이후 변경

### 고아 참가 데이터의 사전 발견과 공대장 처리

- 이전 주차의 고아 `raidState`는 현재 주차 참가 표시 대상이 아니므로 사용자가 완료·모집 생성·신청 같은 쓰기 동작을 하기 전에는 존재를 알기 어렵다. 별도의 상시 경고나 계정 상태 점검 진입점을 제공할지는 후속 UX 후보로 둔다.
- 현재 복구 방향은 신청 저장 전에 신청자 본인의 exact state를 검사하고, 고아가 확인되면 신청을 만들지 않은 채 신청자에게 정리를 안내하는 것이다. 정상 신청이 공대장에게 도달하지 않게 하는 예방이 우선이다.
- 이미 접수된 신청이 신청 후 상태 변경 또는 과거 고아 데이터 때문에 승인될 수 없는 경우, 공대장 화면에서 해당 신청을 자동 거절하는 기능은 현재 구현돼 있지 않다. 현 기준은 원인을 안내하고 공대장이 기존 `신청 거절`을 명시적으로 선택하는 방식이다.
- 자동 거절을 도입하려면 일반적인 권한 오류와 실제 신청자 데이터 오류를 구분할 수 있어야 한다. 신청이 여전히 `pending`이고 revision·신청자·Character·raid 식별자가 모두 일치할 때만 제한된 거절 Transaction을 실행해야 하며, 판정이 불명확하면 신청을 유지한다.
- 자동 거절 여부, 거절 사유 표시, 신청자에게 전달할 복구 안내와 재신청 흐름은 핵심 모집 복구가 끝난 뒤 별도 제품·권한 설계를 거쳐 결정한다. 신청자의 private `raidState` 세부 내용은 공대장에게 노출하지 않는다.

- 신청자 행에 전투력·아이템 레벨이 필요하다. 현재 신청 문서의 `submittedBuildSnapshot`에는 두 수치가 있으나 읽기 모델/UI에 연결되지 않았다. 상세 스펙의 표시 범위와 신청 당시/현재 세팅 기준을 먼저 결정한 뒤 구현한다. 아직 UI 변경은 하지 않는다.
- 직업 옆 주요 시너지 표시는 로컬 카탈로그를 활용할 수 있다. 전체 스펙 저장/조회 비용과 미결정 항목은 [`CLASS_SYNERGY_CATALOG.md`](CLASS_SYNERGY_CATALOG.md) §6~8을 따른다.

- 신청자는 승인 전까지 신청 캐릭터, 저장 역할 또는 신청 메시지를 수정할 수 있어야 하는지 결정한다.
- 신청 내용 수정 시 기존 신청의 대기 순서와 유효 시간을 유지할지 다시 시작할지 정의한다.
- 파티장은 모집 수정 화면에서 모집의 레이드와 난이도를 변경할 수 있어야 한다.
- 레이드 또는 난이도를 변경하면 현재 파티장과 모든 신청자·확정 파티원의 저장 세팅 아이템 레벨을 새 `minItemLevel` 기준으로 즉시 다시 판정한다.
- 변경된 레이드·난이도에 입장할 수 없는 파티원은 파티 구성과 모집 수정 화면에서 경고 아이콘과 사유를 함께 표시해 파티장이 명확히 식별할 수 있어야 한다.
- 입장 불가능 상태가 된 신청자나 확정 파티원을 자동으로 제외하거나 다른 캐릭터로 교체하지 않고, 변경 확정 전 영향받는 인원과 후속 조치가 필요함을 안내한다.
- 가입 이후 캐릭터·역할 변경은 파티 구성, 주간 완료, 참가 충돌 및 가입 조건을 다시 검증한다.
- 파티장이 가입 이후 슬롯 위치, 요구 역할, 직업 또는 시너지 조건을 변경할 때 기존 파티원에게 미치는 영향을 안내한다.
- 조건 변경으로 기존 신청자나 파티원이 더 이상 조건을 충족하지 못하더라도 자동 퇴장시키지 않고 확인·동의 흐름을 우선 검토한다.
- 신청자와 파티장 양쪽에서 변경, 취소, 승인 및 거절 결과를 확인할 수 있는 상태 표시와 알림을 기획한다.

## 직업 시너지

- 변경 빈도가 낮은 직업별 인게임 시너지는 게임 카탈로그 코드로 관리한다.
- 가입 후보가 남은 슬롯의 요구 직업 또는 시너지를 충족하는지 판정한다.
- 모집 목록 필터에서 내 캐릭터의 직업 또는 시너지를 원하는 모집을 빠르게 찾을 수 있도록 활용한다.
- 파티장은 남은 슬롯마다 특정 직업, 직업군, 역할 또는 시너지 조건을 선택할 수 있어야 한다.
- 특정 직업 지정과 시너지 조건이 동시에 설정될 때 AND/OR 적용 방식과 우선순위를 명확히 정의한다.
- 동일 시너지 중복, 파티 단위 적용 범위 및 4인·8인 레이드의 파티별 시너지 판정을 구분한다.
- 신청 화면에서 선택 캐릭터가 조건을 충족하는 이유와 충족하지 못하는 항목을 함께 표시한다.

## 모집 목록 조건 필터

- 모집 목록에서 레이드·난이도·관문 외에 역할, 특정 직업 및 요구 시너지 조건으로 필터링할 수 있어야 한다.
- 내 표시 캐릭터 중 현재 모집 조건을 충족하는 캐릭터가 있는 모집만 보는 필터를 제공한다.
- 여러 직업 또는 시너지 조건 선택 시 모두 충족과 하나 이상 충족을 사용자가 구분할 수 있도록 한다.
- 파티의 현재 구성으로 이미 충족된 조건과 아직 필요한 조건을 구분해 필터 결과와 모집 카드에 표시한다.
- 모집 조건이 가입 이후 변경되면 목록·상세·신청 화면의 필터 판정이 동일한 기준으로 즉시 갱신되어야 한다.

## 레이드 현황 공통 필터

- 레이드 현황의 `진행 중`, `신청 중`, `완료 기록`에서 같은 위치와 조작 방식의 필터를 제공한다.
- 사용자가 가입한 파티, 가입을 신청한 파티와 완료 기록을 각각 현재 상단 페이지의 데이터 안에서 필터링한다.
- 공통 필터 후보는 레이드, 난이도, 관문, 캐릭터와 기간이며 페이지별로 의미가 없는 항목은 비활성화하거나 숨긴다.
- 역할·직업·시너지 필터가 레이드 현황에도 유효한지는 공개 파티 목록 필터를 구현하며 함께 확정한다.
- 필터 선택값의 표현과 초기화 동작은 세 페이지에서 동일하게 유지한다.
- 필터 상태는 개인 UI 설정으로 로컬에 유지할 수 있으며, 페이지 간 완전 공유 또는 페이지별 마지막 값 기억 여부는 구현 전에 확정한다.
- 공개 파티 목록과 같은 필터 컴포넌트 및 값 객체를 재사용할 수 있도록 설계하되 서로 다른 Firestore query와 Drift 완료 기록 조회를 하나의 Repository로 합치지 않는다.
