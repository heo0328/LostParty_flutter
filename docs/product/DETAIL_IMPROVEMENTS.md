# 차후 수정안

## 문서 목적과 기록 범위

현재 개발된 동작을 유지하면서 나중에 바꿀 확정 수정안, 사용자 보류, 재현 확인이 필요한 개선 제보와 미채택 아이디어를 한곳에서 확인하는 대장이다. 같은 기능의 후속 지시는 기존 항목을 수정하며 지시마다 새 문서/항목을 만들지 않는다. 장기 기능의 현재 정책은 해당 제품 문서, 현재 실행 순서는 NEXT_WORK, 완료/대체 경과는 DEV_LOG가 담당한다. 제목은 특정 기능의 그때그때 작업명이 아니라 이 역할을 유지한다.

각 항목에는 현재 동작·변경 목표·확정/제안/보류 상태·담당·착수 조건·완료 조건·근거를 남긴다. ‘차후 변경 예정’만으로 현재 구현을 새 정책으로 바꾸거나 완료/폐기로 취급하지 않는다. 이후 다른 변경과 충돌하면 현재 구현·기존 확정 정책·예약된 수정안을 함께 대조하고, 필요한 결정 후 해당 항목/제품 계약을 교체한다. 대체된 안을 현재 목록 뒤에 누적하지 않으며 DEV_LOG에 출처/대체 이유만 보존한다.

현재 제품의 구현 계약·버그 원인 상세·비활성 기능 대장을 여기로 복제하지 않고 각각 링크한다. 표에서 ‘연결 설계’는 미구현 명령을 이미 제공한다는 뜻이 아니다. 아래 장기 아이디어/과거 표현의 현재 서버 적용 여부는 착수 시 확인한다.

기존 서비스 전용 원문은 [레거시 출처](../../legacy/firebase/extracted/docs/product/DETAIL_IMPROVEMENTS.md)에 보관한다. 과거 실행 지시를 현재 승인으로 사용하지 않는다.

## 첫 공개 베타·포트폴리오 기술 진단 및 개선 인계

### 목적·현재 상태·권한

2026-10-30 사용자 요청: Flutter Android와 Python Backend를 함께 진단하고, 1인 유지 가능성·사용자 흐름/데이터/권한 정확성·이해/변경 용이성·첫 베타 비용/회귀 위험·기술 선택 설명 가능성을 기준으로 개선 순서를 정한다. Backend는 문서 개편을 이미 완료해 운영 중이며 자체 기술 진단·계획도 별도로 진행한다. 이를 미완료 개편으로 되돌리거나 Flutter가 Backend 코드를 대신 수정하지 않는다.

문서 운영 합의는 완료다. Backend 원본 `c1fa205db709f97c1d34817c4417b84144a5dde3`, Flutter 참조 반영 `4bdec0e6e71517e5893d29ba48f76397b4ae358e`, [최종 대조 회신](https://github.com/heo0328/lostparty-backend/issues/29#issuecomment-6520322169)을 기준으로 한다. 이는 기술 진단 전체나 개별 결함 개선 완료를 의미하지 않는다. 이번 인계에서는 코드 재검토·개선 구현을 수행하지 않았으며 아래 후보를 확정 결함으로 간주하지 않는다. 기존 감사도 현재 코드에서 재확인한다.

현재 우선 작업은 사용자 재확인·승인한 주차별 레이드 그룹 변경·승계다. 종합 기술 개선은 해당 그룹 기능 정리 이후 별도로 진행하며 최신 실행/서버 계약 대기는 NEXT_WORK를 따른다. 아래 인계의 조사 후보를 근거로 그룹 구현·기기 인수를 뒤로 미루지 않는다. 당시 문서 인계 완료 이력은 DEV_LOG에 보존한다. 이 인계만으로 전면 리팩터링·배포·데이터 삭제·브랜치 통합·Issue 종료를 승인하지 않는다. 사용자 확정 UX와 정책09 D08을 유지하고 개발자료 보존형 이행/복원 리허설이나 별도 구/신 운영을 새 필수 조건으로 만들지 않는다.

### 다음 탭의 시작 순서

1. AGENTS → ai_rules → NEXT_WORK → AI_CONTEXT → docs/README와 관련 계약·D08을 읽는다. 현재 checkout·HEAD·미커밋 변경·local/origin·관련 기존 브랜치를 확인하고, 두 저장소의 조사 기준 SHA와 전체 구조를 기록한다. 과거 SHA를 최신으로 가정하지 않는다.
2. 인계 시 Flutter 브랜치는 `feature/group-backend-integration`이다. 이후 사용자 지시로 통계35의 유효 회신 기록은 보관하고, 미추적 Firebase 실험 소스·Rules 백업은 legacy/firebase/local-experiments-2026-10-30으로 원본 해시와 함께 이관했다. 빈 DevTools 설정·과거 tools 로그/의존성은 정리했다. 다음 탭은 당시 미커밋 목록을 재사용하지 말고 최신 상태를 확인한다. 다른 탭과 동일 파일을 동시에 수정하지 않는다. 조사 자체를 위해 새 브랜치나 조기 dev 통합을 만들지 않는다.
3. Backend 최신 진단·계획과 관련 Issue의 최신 댓글을 먼저 읽고 중복 조사를 줄인다. 원격에서 확인할 수 없는 Backend 로컬 계획은 미확인으로 표시하고 필요한 내용만 협의한다. #29는 문서 운영 완료 근거이며 기능 개선 요청을 뒤섞지 않는다.
4. 핵심 흐름과 조사 영역을 먼저 정리한 뒤 상세 조사한다. 대표 흐름은 Google 로그인/세션 복원, 원정대 등록·인증/캐릭터·활동, 모집 생성·검색·신청/참가, 배정·일정·완료/탈퇴, 그룹 연결·권한 변경이다. 사용자 행동 → 일반 앱 DI/Router → 요청/인증 → 서버 정책/트랜잭션/DB → 응답/오류 → 성공 후 화면·캐시 갱신을 실제 코드로 연결한다.

### 개선 순서와 분류

1. **지침 조기 수정:** 현재 판단을 실제로 왜곡하는 지침 충돌·과거 전제만 근거를 확보해 최소 수정한다. #29 완료 기준을 다시 개편하지 않는다.
2. **베타 전 필수 / Flutter 독립 작업:** 사용자 손실·권한·기능 실패·출시 차단 등 확인된 위험을 우선한다. 서버 계약 변경 없이 고칠 수 있는 단위를 선택하고 회귀 보호 범위를 정한다.
3. **Backend 협의 작업:** API·권한·저장/멱등 계약 등 상대 변경이 필요한 항목은 기존 관련 Issue에서 합의하고 담당·선행 조건·호환/적용 순서·완료 조건을 기록한다. 협의 준비는 2단계와 독립적으로 진행할 수 있으며 모든 네이티브 정리를 끝낼 때까지 미루지 않는다.
4. **Backend 반영 후 Flutter 마무리:** 게시된 고정 계약·실제 반영 상태를 확인한 뒤 앱을 연결하고 성공 후 갱신·오류/복구까지 검증한다. 부품 구현·앱 연결·서버 반영·기기 인수를 구분한다.
5. **관련 기능 수정 시 / 베타 이후 / 현행 유지 권장:** 실익이 작은 구조 변경·패턴 차이는 베타 필수로 부풀리지 않는다. 각 발견을 이 세 범주 또는 위 두 시점 범주로 분류한다. 이 순서는 일괄 구현 승인이 아니라 의존성과 위험에 따른 계획 틀이다.

### 발견 사항과 작업 그룹의 기록·완료 기준

각 발견은 구체 코드/문서 위치와 기준 SHA, 현재 문제/사용자·개발 영향, 확인 원인과 원인 가설, 문서 자체/해석·적용/구현 문제 구분, 현행 유지/최소 개선/구조 변경의 장단점, 규모·회귀 위험·선행 조건, 권장 시점·검증 방법, 확신도·미확인 사항을 남긴다. 관행·패턴 차이·코드 길이만으로 결함을 선언하지 않는다. 보고에는 전체 조사 범위와 실제 깊게 확인한 범위를 구분한다.

발견 상세는 이 인계 항목을 갱신하거나 해당 기능의 기존 개선 항목에 연결한다. 날짜별 계획 문서를 늘리지 않는다. 실제로 선택한 한 작업 그룹만 NEXT_WORK에 목표·포함/제외·보호 흐름·순서·완료 조건을 기록한다. 완료 경과는 DEV_LOG로 이관한다. 기존 보류 항목을 자동 착수하거나 해결 완료로 바꾸지 않는다.

코드 변경 시 위험에 맞는 권한·동시성·원자성·중복/결과 불명·저장 실패·늦은 응답 경계를 검증한다. 순수 문서 변경은 링크/내용·diff check를 확인하고 기능 시험을 반복하지 않는다. 실기기 설치·조작은 사용자가 하며 기존 그룹 기기1~5/Penpot 대기는 별도 유지한다. 기존 검증 재사용은 코드·계약·환경·검증 범위의 변경 영향을 대조한 뒤 판단한다.

## 차후 보완 — 제안의 시간 정밀도 판정 1건 (현재 착수 안 함)

- 근거: Backend는 실제 대상 `BetaSchedule.session_id`를 기준으로 분 단위 출발을 허용한다. 현재 Native `cycle_schedule.dart`의 제출 검증과 `schedule_command_page.dart`의 입력/정책은 `plan.betaData != null`만으로 정밀도를 구분한다.
- 착수 조건: 사용자가 차후 네이티브 보완 구간을 다시 시작할 때 최신 계약·코드를 대조한 뒤 실제 대상 세션 판정을 보완한다. 현재 작업/다음 즉시 작업/현재 베타 인수의 선행 조건으로 두지 않는다. 미수정 기록은 유지하되 지금 설계·구현·추가 시험을 시작하지 않는다.
- 보호/완료: 사용자가 통과한 일반 비5분 제안·수락/확정, 개인 시간표·자동 탐색/진행시간의 5분, 원요청/ACK/복구를 유지한다. 불일치·값 없음·대상 변경 등 직접 경계를 자동 검증하고, 실제 정상 UX에 영향이 있을 때만 좁은 기기 확인을 안내한다. 지금 전체 모집 재시험은 요구하지 않는다.

## 차후 보완 — API·기능 오류 안내와 재시도 행동

- 상태·담당: 2026-10-29 사용자 지시로 차후 개선 항목에 등록. Flutter 담당. 그룹의 요청 없음 상시 버튼·허위 성공 안내는 기기 피드백 수정에서 해소했으며, 다른 구간의 안내/행동 정리는 차후 작업으로 유지한다. 그룹에 한정하지 않고 API 통신·기능 오류가 표시되는 각 구간을 대상으로 한다. 베타 이후로 시점을 별도 확정한 것은 아니다.
- 현재 확인: 수정 전 그룹 화면은 저장된 미확정 요청 유무와 관계없이 `미확정 요청 결과 확인` 버튼을 표시하고, 확인할 요청이 없어도 누르면 `원요청 처리를 확인했습니다`라고 안내한다. 다른 구간의 일반적인 조회 실패·명령 결과 불명까지 같은 문제로 단정하지 않고 착수 시 각각 대조한다. 근거는 사용자 그룹 화면 제보와 `backend_group_page.dart`의 상시 버튼, `BackendGroupViewModel.recover`의 무조건 성공 안내다.
- 변경 목표: 내부 용어를 공통 재시도 문구로 노출하지 않고, 어느 기능에서 무엇이 실패했고 버튼을 누르면 무엇을 하는지 알 수 있게 구간별로 정리한다. 조회 실패의 재조회, 결과가 불명인 변경 요청의 원요청 결과 확인, 이미 성공한 변경 후 화면 갱신 실패를 구분한다. 문구는 해당 행동에 맞게 정하며 최종 표현은 해당 개선 구간에서 검토한다.
- 표시 기준: 실제 확인할 요청이나 오류가 있을 때만 필요한 안내·버튼을 보여준다. 정상·빈 목록에 미확정 요청이 있는 것처럼 표시하거나, 확인할 요청이 없는데 처리 완료로 안내하지 않는다. 단순 조회 오류에 변경 명령 재전송 버튼을 제공하지 않는다.
- 착수·다음 행동: 차후 오류 안내/재시도 UX 개선 구간에서 화면·상태·버튼의 실제 호출을 대응시켜 기존 항목을 갱신하고 구현한다. 지금 그룹 기능 확인이나 전체 기기 인수의 새 선행조건으로 추가하지 않는다.
- 보호·완료 조건: 원본문·멱등 키 보존, 중복 실행 방지, 성공 명령 재실행 금지, 회원/환경 변경·늦은 응답 보호는 유지한다. 요청 없음·조회 실패·결과 불명·성공 후 갱신 실패에서 표시와 실행이 일치하고 사용자가 다음 행동을 이해할 수 있어야 완료다. 상태 분기·중복 실행 경계는 자동 검증하고 문구/버튼 정상 UX는 필요한 화면에서만 확인한다.

## 파티 구성과 가입 조건

- 파티 번호 `partyIndex`와 파티 내부 자리 `slotIndex`를 분리한다. 화면 표시는 1부터 시작하고 내부 값은 기존 구조와 맞게 0부터 시작한다.
- 4인 레이드는 `1파티 1~4번`, 8인 레이드는 `1파티 1~4번`과 `2파티 1~4번`의 고정 슬롯으로 구성한다.
- `1파티 1번`은 4인 파티장, 8인 파티장 겸 공대장 자리로 항상 유지한다.
- 모집 상세는 가입된 멤버 목록만 나열하지 않고 정원 전체의 점유·빈 슬롯을 Card/Cell 구성판으로 표시한다.
- 점유 슬롯은 자리 번호, 책임자 배지, 캐릭터명, 직업, 전투력, 아이템 레벨과 역할을 표시한다.
- 빈 슬롯은 `빈자리`와 `현재 별도 참가 조건 없음`을 기본으로 표시해 향후 역할·직업군·시너지 조건을 같은 Cell에서 확장할 수 있게 한다.
- 반응형 구성판은 Card 열 수가 아니라 파티 그룹의 배치를 전환한다. 좁은 화면에서는 파티별 Card가 전체 폭의 1열을 사용하고, 넓은 화면에서는 4인 1파티를 왼쪽 절반에, 8인 1·2파티를 좌우 절반에 배치한다. 상세 기준은 [`../design/PARTY_COMPOSITION_RESPONSIVE_LAYOUT.md`](../design/PARTY_COMPOSITION_RESPONSIVE_LAYOUT.md)를 따른다.
- 탈퇴·추방 후 남은 멤버를 자동으로 앞자리로 당기지 않고 기존 위치를 유지한다. 캐릭터 변경도 기존 슬롯을 유지한다.
- 모집 상세에서 파티장이 파티원의 파티 및 슬롯 위치를 직접 조정할 수 있어야 한다.
- 8인 레이드는 4인 파티 두 개의 시너지 조합을 확인할 수 있도록 파티별 배치를 명확히 제공한다.
- 모집 중 남은 슬롯의 가입 조건을 직업 또는 시너지 기준으로 변경할 수 있어야 한다.

## 파티 상세 조율 채팅

- 핵심 파티 명령, 고정 슬롯, 그룹과 슬롯 조건 기능이 안정된 뒤 가장 마지막 후속 기능으로 구현한다.
- 파티 상세에 진입한 현재 멤버만 최근 메시지 약 10개를 실시간 조회하고 짧은 텍스트를 전송한다.
- 기본 표시는 `캐릭터명 또는 표시 ID — 채팅 내용`이며 파티 일정과 진행 방식을 간단히 조율하는 용도에 한정한다.
- 메시지는 `recruitments/{recruitmentId}/messages/{messageId}`의 개별 문서로 저장하고 표시 Snapshot, 본문, 서버 생성 시각만 최소 보관한다. 권한 판정용 PlayerId는 UI에 노출하지 않는다.
- `createdAt desc`, `limit(10)`을 상세 화면에서만 구독하고 화면 이탈 시 listener를 해제한다. 모집 목록이나 다른 탭에서는 방별 채팅을 미리 읽지 않는다.
- 메시지 길이, 빈 문자열, 전송 중 중복 요청과 짧은 시간의 연속 전송을 제한한다.

## 파티 신청 대기와 자동 취소

- 파티 신청 후 파티장 응답을 기다리는 유효 시간을 정의한다.
- 신청 유효 시간은 전체 공통값, 파티장 설정값 또는 모집별 설정값 중 어떤 방식으로 제공할지 기획한다.
- 제한 시간이 지나면 신청을 자동 취소할지, 만료 상태로 남겨 재신청을 허용할지 결정한다.
- 자동 취소 또는 만료 전에 신청자에게 남은 시간과 예정 동작을 명확히 안내한다.
- 파티장이 모집을 마감·취소하거나 가입 조건을 변경했을 때 대기 중인 신청을 유지할지 일괄 취소할지 규칙을 정의한다.
- 신청 취소, 자동 만료, 파티장 거절 및 모집 마감은 서로 구분되는 상태와 이력으로 기록한다.

## 참가자 수동 알림

- 이 항목은 즉시 구현 범위가 아니다. 핵심 파티 흐름 완료 후 알림 서버와 권한 구조를 결정할 때 함께 재검토한다.
- 모집 상세에서 파티장과 확정 파티원 모두 `알림 보내기` 버튼을 사용할 수 있어야 한다.
- 모집 내용 변경이나 참가 캐릭터 변경을 이유로 모든 참가자에게 자동 알림을 보내지 않고, 사용자가 필요할 때 수동으로 전송한다.
- 버튼을 누르면 `참가 인원에게 알림을 보냅니다.` 확인 알럿을 표시하고 확인한 경우에만 전송을 요청한다.
- 확인 후에는 전송 중 상태와 서버 기준 쿨다운을 적용해 연속 터치, 중복 전송 및 여러 기기에서의 우회를 방지한다.
- 발신자 본인은 수신 대상에서 제외하고 알림을 누르면 해당 모집 상세로 이동하도록 한다.

## 신청·가입 이후 변경

### 고아 참가 데이터의 사전 발견과 공대장 처리

- 이전 주차의 고아 `raidState`는 현재 주차 참가 표시 대상이 아니므로 사용자가 완료·모집 생성·신청 같은 쓰기 동작을 하기 전에는 존재를 알기 어렵다. 별도의 상시 경고나 계정 상태 점검 진입점을 제공할지는 후속 UX 후보로 둔다.
- 현재 복구 방향은 신청 저장 전에 신청자 본인의 exact state를 검사하고, 고아가 확인되면 신청을 만들지 않은 채 신청자에게 정리를 안내하는 것이다. 정상 신청이 공대장에게 도달하지 않게 하는 예방이 우선이다.
- 이미 접수된 신청이 신청 후 상태 변경 또는 과거 고아 데이터 때문에 승인될 수 없는 경우, 공대장 화면에서 해당 신청을 자동 거절하는 기능은 현재 구현돼 있지 않다. 현 기준은 원인을 안내하고 공대장이 기존 `신청 거절`을 명시적으로 선택하는 방식이다.
- 자동 거절을 도입하려면 일반적인 권한 오류와 실제 신청자 데이터 오류를 구분할 수 있어야 한다. 신청이 여전히 `pending`이고 revision·신청자·Character·raid 식별자가 모두 일치할 때만 제한된 거절 Transaction을 실행해야 하며, 판정이 불명확하면 신청을 유지한다.
- 자동 거절 여부, 거절 사유 표시, 신청자에게 전달할 복구 안내와 재신청 흐름은 핵심 모집 복구가 끝난 뒤 별도 제품·권한 설계를 거쳐 결정한다. 신청자의 private `raidState` 세부 내용은 공대장에게 노출하지 않는다.

- 신청자 행에 전투력·아이템 레벨이 필요하다. 현재 신청 문서의 `submittedBuildSnapshot`에는 두 수치가 있으나 읽기 모델/UI에 연결되지 않았다. 상세 스펙의 표시 범위와 신청 당시/현재 세팅 기준을 먼저 결정한 뒤 구현한다. 아직 UI 변경은 하지 않는다.
- 직업 옆 주요 시너지 표시는 로컬 카탈로그를 활용할 수 있다. 전체 스펙 저장/조회 비용과 미결정 항목은 [`CLASS_SYNERGY_CATALOG.md`](CLASS_SYNERGY_CATALOG.md) §6~8을 따른다.

- 신청자는 승인 전까지 신청 캐릭터, 저장 역할 또는 신청 메시지를 수정할 수 있어야 하는지 결정한다.
- 신청 내용 수정 시 기존 신청의 대기 순서와 유효 시간을 유지할지 다시 시작할지 정의한다.
- 파티장은 모집 수정 화면에서 모집의 레이드와 난이도를 변경할 수 있어야 한다.
- 레이드 또는 난이도를 변경하면 현재 파티장과 모든 신청자·확정 파티원의 저장 세팅 아이템 레벨을 새 `minItemLevel` 기준으로 즉시 다시 판정한다.
- 변경된 레이드·난이도에 입장할 수 없는 파티원은 파티 구성과 모집 수정 화면에서 경고 아이콘과 사유를 함께 표시해 파티장이 명확히 식별할 수 있어야 한다.
- 입장 불가능 상태가 된 신청자나 확정 파티원을 자동으로 제외하거나 다른 캐릭터로 교체하지 않고, 변경 확정 전 영향받는 인원과 후속 조치가 필요함을 안내한다.
- 가입 이후 캐릭터·역할 변경은 파티 구성, 주간 완료, 참가 충돌 및 가입 조건을 다시 검증한다.
- 파티장이 가입 이후 슬롯 위치, 요구 역할, 직업 또는 시너지 조건을 변경할 때 기존 파티원에게 미치는 영향을 안내한다.
- 조건 변경으로 기존 신청자나 파티원이 더 이상 조건을 충족하지 못하더라도 자동 퇴장시키지 않고 확인·동의 흐름을 우선 검토한다.
- 신청자와 파티장 양쪽에서 변경, 취소, 승인 및 거절 결과를 확인할 수 있는 상태 표시와 알림을 기획한다.

## 직업 시너지

- 변경 빈도가 낮은 직업별 인게임 시너지는 게임 카탈로그 코드로 관리한다.
- 가입 후보가 남은 슬롯의 요구 직업 또는 시너지를 충족하는지 판정한다.
- 모집 목록 필터에서 내 캐릭터의 직업 또는 시너지를 원하는 모집을 빠르게 찾을 수 있도록 활용한다.
- 파티장은 남은 슬롯마다 특정 직업, 직업군, 역할 또는 시너지 조건을 선택할 수 있어야 한다.
- 특정 직업 지정과 시너지 조건이 동시에 설정될 때 AND/OR 적용 방식과 우선순위를 명확히 정의한다.
- 동일 시너지 중복, 파티 단위 적용 범위 및 4인·8인 레이드의 파티별 시너지 판정을 구분한다.
- 신청 화면에서 선택 캐릭터가 조건을 충족하는 이유와 충족하지 못하는 항목을 함께 표시한다.

## 모집 목록 조건 필터

- 모집 목록에서 레이드·난이도·관문 외에 역할, 특정 직업 및 요구 시너지 조건으로 필터링할 수 있어야 한다.
- 내 표시 캐릭터 중 현재 모집 조건을 충족하는 캐릭터가 있는 모집만 보는 필터를 제공한다.
- 여러 직업 또는 시너지 조건 선택 시 모두 충족과 하나 이상 충족을 사용자가 구분할 수 있도록 한다.
- 파티의 현재 구성으로 이미 충족된 조건과 아직 필요한 조건을 구분해 필터 결과와 모집 카드에 표시한다.
- 모집 조건이 가입 이후 변경되면 목록·상세·신청 화면의 필터 판정이 동일한 기준으로 즉시 갱신되어야 한다.

## 레이드 현황 공통 필터

- 레이드 현황의 `진행 중`, `신청 중`, `완료 기록`에서 같은 위치와 조작 방식의 필터를 제공한다.
- 사용자가 가입한 파티, 가입을 신청한 파티와 완료 기록을 각각 현재 상단 페이지의 데이터 안에서 필터링한다.
- 공통 필터 후보는 레이드, 난이도, 관문, 캐릭터와 기간이며 페이지별로 의미가 없는 항목은 비활성화하거나 숨긴다.
- 역할·직업·시너지 필터가 레이드 현황에도 유효한지는 공개 파티 목록 필터를 구현하며 함께 확정한다.
- 필터 선택값의 표현과 초기화 동작은 세 페이지에서 동일하게 유지한다.
- 필터 상태는 개인 UI 설정으로 로컬에 유지할 수 있으며, 페이지 간 완전 공유 또는 페이지별 마지막 값 기억 여부는 구현 전에 확정한다.
