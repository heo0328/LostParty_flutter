# 원정대 재인증 변경 안내

기준일: 2026-10-05. 독자: 앱 사용자이자 개발자인 프로젝트 담당자.
현재 작업 브랜치: `fix/roster-reauth-isolation`.

이 문서는 이번 기능 수정과 Rules 게시 문제 해결을 한 흐름으로 설명한다.
앞부분은 사용자가 보게 되는 변경, 뒷부분은 개발 기록과 근거를 다룬다. 실행할 테스트 목록은 채팅에서만 안내한다.
과거 시도 전체는 복제하지 않고 기존 설계·진단 기록으로 연결한다.

## 1. 이번 작업의 목적

이전 사용자 A가 쓰던 원정대 R을 새 사용자 B가 인증했을 때, B가 이전 신청·참가·완료
기록 때문에 막히지 않고 R로 앱을 사용할 수 있도록 하는 작업이다.

예를 들어 A에게 원정대 R과 S가 있을 때 B가 R만 인증하면, B는 R로 새 모집을 만들거나
다른 모집에 참가할 수 있어야 한다. A의 S와 그 정상 참가 관계는 그대로 남아야 한다.
B에게 A의 그룹 가입, 그룹장·공대장 권한, 과거 완료 기록을 넘기는 기능은 아니다.
로그인 계정 복구와 기존 사용자 전체 복원도 이번 범위가 아니다.

이와 별도로, 기능을 서버에서 허용할 Rules가 게시되지 않던 문제를 해결했다.
**운영 게시 성공과 새 기능의 실기기 통과는 서로 다른 완료 조건**이다.

초기화 설정은 사용자 변경으로 보존하며 이 문서 작업에서 수정하거나 커밋하지 않는다.

## 3. 사용자가 보게 되는 변경

### 3.1 새로 인증한 원정대를 사용할 수 있게 함

- 실제 소유자가 바뀐 원정대의 과거 점유·완료를 새 사용자의 현재 참가 제한으로 승계하지 않는다.
- 기존 방을 모두 찾아 정리해야만 새 사용자가 이용할 수 있는 방식으로 만들지 않는다.
- 같은 사용자가 같은 원정대를 다시 인증하면 정상 참가 관계를 불필요하게 초기화하지 않는다.
- A→B→A로 다시 인증해도 최초 A 시절의 신청·참가가 자동으로 부활하면 안 된다.
- 신청 승인, 가입, 캐릭터 변경, 완료, 반복방 재참가에서도 현재 소유권을 기준으로 처리한다.

### 3.2 ‘다음 주 참가 자격 확인’ 버튼

현재 구현은 **완료 상태이고 ‘다음 주도 함께하기’가 켜진 방**에서 기존 참가자가 상세 화면을
열면 참가자별 확인 항목을 표시한다. 서버에서 멤버 목록을 읽는 중이거나 캐시만 있는 경우는 제외한다.
표시 자체는 대상의 소유권 상실 판정이 아니다. 정상 참가자에게도 항목이 보일 수 있다.

확인을 누르면 서버의 현재 소유권과 참가 당시 정보를 대조한다.

| 확인 결과 | 기대 동작 |
|---|---|
| 현재도 유효한 참가자 | 정리하지 않음. 소유권 상실이 확인되지 않았다는 안내 가능 |
| 소유권이 바뀐 일반 참가자 | 실행자 자격까지 확인 후 ‘다음 주 참가 정리’ 확인창 |
| 소유권이 바뀐 공대장 | 첫 유효 후임 조건을 확인하고 승계 대상 이름을 안내 |
| 마지막 1인의 소유권이 바뀜 | 기존 마지막 공대장 본인이 확인 후 해산 가능 |
| 조회 실패·소유권 판단 불가·실행 권한 없음 | 정리하지 않음. 실패를 소유권 상실로 취급하지 않음 |

일반 참가자는 본인 또는 유효한 공대장이 정리할 수 있다. 공대장도 무효가 된 경우에는
유효한 기존 참가자가 앞순번의 무효 참가자를 한 명씩 정리하고 승계 조건을 만들 수 있다.
정상 공대장이 있는 방에서 일반 참가자가 다른 사람을 임의로 정리하는 기능은 아니다.
후임 조건이 맞지 않으면 뒤순번 사람을 임의로 골라 건너뛰지 않는다.

정리 확인창에서 취소할 수 있다. 정리는 자동 일괄 삭제가 아니며, 기존 완료 기록·그룹 가입·
새 소유자의 새 참가 기록은 보존해야 한다. 마지막 1인 해산도 기록 보존을 전제로 하는 별도 경로다.

### 3.3 ‘참가 정리 처리 결과’ 화면

정리 요청 후 연결이 끊기거나 앱이 종료돼 결과가 불명확할 때 확인하기 위한 기능이다.
현황 상단에서 접근하며 상세 화면에도 ‘참가 정리 처리 결과 다시 확인’이 표시될 수 있다.

- 이미 성공했다면 같은 정리를 다시 적용하지 않고 성공 결과를 확인한다.
- 결과를 확인하지 못하면 요청을 보관하고 재확인할 수 있다.
- ‘기기 기록 지우기’는 이 기기의 요청 기록만 지운다. 서버 정리를 취소하거나 되돌리지 않는다.
- 재설치나 다른 기기로 이 요청 기록을 옮기는 기능은 아니다.

### 3.4 기존 고아 참가 기록 정리와의 차이

기존 ‘참가 기록 정리’는 방 부재 등으로 남은 참가 기록을 정리하는 흐름이다.
새 ‘다음 주 참가 자격 확인’은 **방은 존재하지만 원정대 소유권이 바뀐 완료 반복방 참가 관계**를
확인하는 흐름이다. 둘을 같은 버튼·같은 삭제 조건으로 이해하면 안 된다.

## 4. 이번 권한 관련 오류의 해석

현재 보고만으로 주간키 변경이 원인이라고 확정하지 않는다. 다음을 구분해야 한다.

1. 정상 참가자를 확인해서 ‘소유권 상실이 확인되지 않아 정리하지 않습니다’가 나온 경우:
   정상적인 정리 거절일 수 있다.
2. 다른 참가자를 정리할 실행 권한이 없거나 후임 조건이 맞지 않은 경우:
   대상·실행자 관계를 확인해야 한다.
3. Firebase의 `permission-denied`나 일반적인 연결/권한 안내가 나온 경우:
   조회 단계인지 확인창 이후 저장 단계인지부터 구분해야 한다.
4. 과거 방의 주차 정보·누락 필드·현재 초기화 설정이 맞지 않는 경우:
   가능성은 있으나 현재 증거로 확정하지 않는다.

다음 재현에서 **버튼의 정확한 문구, 오류 전문, 누른 사용자/대상 캐릭터, 방 ID, 완료 여부,
소유권을 실제로 이전했는지, 확인창 전후 어느 단계인지, 발생 시각**을 남긴다.
오류 사례에 한해 터미널 로그를 함께 확인한다. 원인 확인을 위해 기존 방을 삭제하지 않는다.
주간키를 수동 변경하거나 Rules를 완화하는 조치는 아직 하지 않는다.

## 5. 개발 기록: 무엇을 수정·추가했는가

### 기능 버그 해결을 위한 변경

| 변경 묶음 | 목적과 저장 경계 |
|---|---|
| 소유권 변경 차수 | 같은 소유자 재인증은 유지, 실제 이전 때 증가. 과거 참가와 현재 권한을 구분 |
| 인증·참가 쓰기 연결 | 자동 장비 인증/운영자 수동 인증 및 참가 관계에 소유권 기준 연결. 구버전의 차수 누락 쓰기는 거절될 수 있음 |
| 점유·완료·신청 판단 | 과거 소유권 기록을 새 사용자의 제한으로 사용하지 않으며 오래된 신청 승인·반복 재참가 차단 |
| 완료 반복방 단건 정리 | 일반 참가자·공대장 승계·마지막1인 해산. 모집/멤버 권한/그룹 모집 목록/이벤트를 명령에 맞춰 함께 저장 |
| 중단 요청 복구 | 요청 식별자·관찰 버전을 기기에 보관하고 서버 처리 결과 확인. 응답 유실 시 중복 실행 방지 |
| 기존 기능의 소유권 경계 보완 | 캐릭터 변경·자리 이동·완료/취소·고아 정리·주차 전환에서 다른 소유권 시점의 기록 혼용 방지 |

과거 차수 필드가 없는 데이터는 별도 호환 규칙으로 취급하며, 단순 조회 실패를 소유권 상실로
해석하지 않는다. 인증할 때 모든 방을 순회하거나 다른 원정대 기록을 일괄 삭제하지 않는다.

### Rules 게시 및 평가 한도 해결을 위한 변경

| 변경 | 사람 관점의 의미 | 구분 |
|---|---|---|
| 중복 검사 공통화·명령별 분기·문서별 검증 범위 조정 | 같은 요청을 과하게 반복 검사하던 부담 축소. 필수 권한·동시 저장 조건 유지 | 기능 조건 보존을 목표로 제한 검증 |
| 함수 배치 범위 축소 | 해당 기능이 쓰는 함수를 필요한 범위에 배치 | 화면·저장 형식 변경 없음 |
| 그룹 표시 스냅샷 대조 축소 | 앱이 저장한 표시용 직업·수치가 원본과 같은지 서버가 반복 대조하는 일부 검사 제거 | **의도한 계약 변경** |
| 주석·공백 제거와 함수/인자/지역변수 이름 축약 | 기능 조건을 그대로 둔 채 배포 파일과 실행 코드 부담 축소 | 마지막 게시 성공을 만든 변환 |

표시 대조 축소에서도 최소 타입, 본인/방장/그룹장 권한, 소유권, 자리 충돌, revision,
필수 다중 문서 저장은 유지한다. 그룹 표시용 직업과 파티 배치에 쓰는 직업·역할은 구분한다.
공유 데이터 저장과 구독을 로컬 전용으로 옮긴 것은 아니다. 공대장·그룹장 변경은 서버에 저장해
다른 기기에서도 확인하도록 유지한다. 모든 변경을 단순 이름 변경이라고 설명하면 부정확하다.

최종 이름 축약 단계만은 직전 소스의 조건·필드·문자열·경로·순서를 보존한다.
이름을 역치환한 비주석 토큰 전체가 일치하는지 생성 시 확인한다.
