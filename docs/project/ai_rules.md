# AI Collaboration Rules - LOSTPARTY (2026)

이 문서는 LOSTPARTY 프로젝트에서 AI 도구(Cursor, ChatGPT 등)와 협업할 때 따를 규칙을 정의한다.

---

## 1. Project Intent

이 프로젝트는 일반적인 Flutter 학습 프로젝트가 아니다.

핵심 목표:
- 로스트아크 레이드 파티를 사전에 모집/지원할 수 있는 앱 구현
- AI 에이전트 기반 개발 실험
- 개발자는 직접 코딩보다 아래 역할에 집중한다:
  - 작업 분해
  - 프롬프트 설계
  - 결과 검토
  - 구조 통제
  - Git 기록 관리

중요:
- AI는 “한 번에 완성된 기능”을 만드는 것이 아니라
  “작은 단위로 나누어 구현”해야 한다.

---

## 2. Product Context

LOSTPARTY는 로스트아크 유저를 위한 앱이다.

핵심 기능:
- 캐릭터 인증 (API 한계로 인해 우회 방식 사용)
- 레이드 파티 모집
- 레이드 파티 지원
- 사전 예약 기반 파티 구성

특징:
- 캐릭터 단위 레이드 구조
- 그룹 기반 모집 가능성
- 주간 숙제 관리 기능 예정

제약:
- 로스트아크 API는 계정 소유 인증을 지원하지 않는다
- 캐릭터 인증은 인게임 상태 변경 기반으로 검증한다

## 3. MVP Principle (매우 중요)

초기 개발 범위는 아래로 제한한다:

- 캐릭터 인증 (간단 버전)
- 모집글 목록
- 모집글 작성
- 모집글 지원
- 최소 계정 그룹과 그룹 전용 모집글

금지:
- 알림 시스템
- 소셜 로그인
- 채팅
- 복잡한 필터

원칙:
- “확장 가능한 구조”는 유지
- “미리 다 구현”은 절대 금지

## 4. AI Usage Roles

역할 분리:

### Codex
- 에이전트 설계와 기술 계약 정리
- 작업 분해와 Cursor 인수인계
- 문서 간 정합성 및 실제 Git 상태 점검
- 데이터 흐름, 권한, 검증과 완료 조건 정의
- 필요한 경우 소규모 코드 수정과 검증 수행

### Cursor
- 주 코드 구현과 빌드
- 파일 생성·수정과 표적 테스트
- 구현 중 발견한 설계 충돌과 개선안 제안

규칙:
- Cursor에는 `NEXT_WORK.md`에 포함·제외 범위와 완료 조건이 정리된 작업만 전달한다
- 한 번의 구현 작업은 독립 검증과 롤백이 가능한 단위로 제한한다
- Codex의 코드 수정을 금지하지 않고 Cursor의 설계 제안을 금지하지 않는다
- 코드·문서·실제 Git 상태가 다르면 작업을 확장하기 전에 충돌을 기록하고 기준을 갱신한다

## 5. General Principles

- AI가 생성한 코드는 반드시 검토 후 반영한다
- 의미 없는 자동 생성 코드는 사용하지 않는다
- 항상 “왜 이 코드가 필요한지” 설명 가능해야 한다
- 작은 단위로 점진적으로 구현한다
- 나중에 읽고 학습 가능한 코드를 유지한다
- 제목·표시명 등 자유 입력에는 입력 예시 또는 적용될 기본 문구를 안내한다
- 자유 입력이 비어 있더라도 기능을 불필요하게 막지 않고 문맥에 맞는 기본값을 적용한다
- 자동 기본값은 기존 데이터와 충돌하지 않도록 순번 등 안정적인 구분자를 사용한다
- 식별자처럼 반드시 고유해야 하는 값은 기본값 여부와 관계없이 저장 계층에서 중복을 검증한다

## 6. Architecture Principles

Flutter + MVVM 기반

- View: UI와 이벤트 전달
- ViewModel: 상태 관리 및 로직
- Repository: 데이터 처리
- API 호출은 View에서 직접 하지 않는다
- 기능 단위(feature-first) 구조 사용
- 네트워크 요청을 시작하는 버튼은 요청 진행 중 비활성 또는 동일 동작 무시로 연타·중복 요청을 막는다. 화면별 예외를 두지 않는 공통 규칙이다.

## 8. Task Execution Rules

- `ai_rules.md`는 모든 작업의 기본 행동 규칙이며 `NEXT_WORK.md`나 채팅 지시를 실행할 때도 먼저 적용한다. 작업 지시가 이 규칙과 충돌하거나 위반 가능성이 있으면 임의로 진행하지 말고 충돌 지점과 필요한 예외를 사용자에게 확인한다.
- 사용자가 예외를 명시적으로 확정한 경우에만 해당 범위·해당 시점에 한해 적용한다. 과거 예외나 유사한 지시를 이후 작업의 포괄 권한으로 재사용하지 않는다.
- Firebase Rules가 변경된 기능 섹션은 로컬 테스트·정적 분석·Rules 계약 검사를 마친 뒤 **AI가 최신 추적본을 실제 운영 프로젝트에 정확히 1회 배포 시도**한다. 배포 전 현재 브랜치, `firebase.json`의 Rules 경로, diff와 대상 프로젝트를 다시 확인한다.
- 기본 절차에서 `--dry-run`과 실제 배포를 연속 실행하지 않는다. 실제 배포 자체가 원격 컴파일을 포함하므로 요청 횟수를 중복시키지 않는다. 사용자가 원격 컴파일만 요청한 경우에만 dry-run 한 번으로 대체한다.
- 첫 배포가 실패하면 즉시 같은 명령을 반복하거나 503을 없애기 위해 정상 기능을 임의로 수정·삭제하지 않는다. 실패 단계(`/test`, `/rulesets`, `/releases`), 로컬 컴파일 경고, 콘솔 게시 시각·활성 소스, 직전 성공본과 현재 diff를 먼저 대조해 원인을 보고한다.
- 실패 후 재배포는 사용자가 진단 결과를 확인하고 다시 지시한 경우에만 한 번 수행한다. 과거 배포 지시나 첫 시도 정책을 무제한 재시도 권한으로 사용하지 않는다.
- Rules가 바뀌지 않은 기능은 배포하지 않는다. Indexes·Functions·Hosting 등 Rules 이외 Firebase 배포는 계속 사용자의 현재 시점 명시 지시가 있을 때만 수행한다.
- Firebase 콘솔에서 복사한 Rules Snapshot은 배포 원본으로 사용하지 않는다. `firebase.json`이 지정한 추적 파일과 행·내용을 먼저 비교하고 Snapshot은 `.gitignore`된 로컬 대조 자료로만 보존한다.
- Rules의 `map`·`string` 인자에 문서 부재를 뜻하는 `null` sentinel을 전달하지 않는다. 생성·수정 경로는 이전 목록·revision·시각 등 실제 타입 값을 명시적으로 전달하고, nullable 반환 대신 존재 여부와 소유 여부를 boolean으로 판정한다.
- Rules 컴파일 경고는 배포 성공 여부와 별개로 0개를 완료 조건으로 삼는다. 경고 행, 원인 함수, 기능 동등성 검증과 배포 결과를 작업 문서에 기록한다.
- 503만으로 특정 기능이나 Rules 복잡도를 원인으로 단정하거나 정상 기능을 제거하지 않는다. 동일 소스의 컴파일 결과, 콘솔 게시본과 로컬 원본 비교, 실패 단계(`test`/`rulesets`/`releases`)를 확보한 뒤 수정한다.
- 한 번에 큰 기능 구현 금지
- 작업은 반드시 단계별로 나눈다
- 각 단계는 테스트 가능해야 한다

좋은 예:
1. 모델 생성
2. Repository 생성
3. ViewModel 생성
4. UI 생성
5. 연결

금지:
- 한 번에 전체 기능 생성

## 8-1. Work Group Cycle and Test Strategy

새 채팅에서도 사용자가 매번 다시 설명하지 않아도 되도록 아래 사이클을 기본 작업 방식으로 사용한다.

### 기본 단위

- 하나의 작업 그룹은 독립적으로 검토, 구현, 검증 및 기록할 수 있는 가장 작은 기능 단위다.
- 한 채팅에서는 원칙적으로 하나의 작업 그룹만 완료한다.
- 장기 아이디어 전체를 한 번에 구현하지 않고 `NEXT_WORK.md`에 정의된 첫 번째 작업 단위부터 진행한다.
- 구현 중 다음 작업 후보가 발견되면 현재 범위를 넓히지 않고 문서에 기록한다.

### 1단계: 구현 전 검토와 작업 분해

- 코드·문서 수정 전에 `docs/project/ai_rules.md`를 처음부터 끝까지 읽고, `NEXT_WORK.md`, `AI_CONTEXT.md`, `docs/README.md` 및 작업 영역의 제품·아키텍처 계약 문서를 확인한다. Rules를 건드리는 작업은 `TASK-11-FIRESTORE-RULES-COMPLEXITY.md`의 최신 상태와 해당 Rules 계약 테스트도 반드시 확인한다.
- 문서를 확인하지 않은 상태에서는 구현·커밋·배포를 시작하지 않는다. 새 채팅, 다른 AI 도구, 작업 재개 및 브랜치 전환 뒤에도 같은 확인 절차를 다시 적용한다.
- 작업 시작 보고에는 확인한 핵심 문서, 현재 브랜치, 작업 트리 상태, 새로 만들 기능 브랜치 이름과 이번 포함/제외 범위를 짧게 명시한다.
- 프로젝트 문서와 Git 브랜치 및 작업 트리 상태를 먼저 확인한다.
- 관련 코드와 테스트를 읽어 문서가 실제 구현과 일치하는지 확인한다.
- 사용자가 검토할 기능 목록을 제시한 단계에서는 코드를 수정하지 않는다.
- 데이터 구조, 데이터 소유 경계, 화면 흐름, 작업 순서, 적절한 작업 단위 및 제외 범위를 먼저 제시한다.
- 구현 대상은 사용자가 승인하거나 지시한 첫 번째 작업 단위로 제한한다.

### 기존 기능 회귀 방지 게이트

- 신규 기능·버그 수정 전에 변경 지점이 사용하는 Repository, Rules 권한(`get`/`list` 포함), 식별자, 주차 및 데이터 생명주기를 먼저 확인한다.
- 영향받는 기존 사용자 흐름을 회귀 보호 목록으로 작성한다. 최소한 정상 상태뿐 아니라 과거 데이터, 미완료 종료, 반복방, 재진입 및 다른 난이도·파티 구성처럼 같은 저장 경로를 공유하는 상태를 포함한다.
- 새 정책을 별도 조건문으로 복제하지 않고 기존 Domain 정책·Validator·Write Plan을 재사용하거나 동일 결과를 계약 테스트로 고정한다.
- 실제 앱 연결은 단위 서비스 테스트만으로 완료 처리하지 않는다. 라우터/DI가 운영 Repository와 실제 Player 식별자를 연결하는지, Security Rules가 허용하는 조회 방식인지 함께 확인한다.
- 기존 구현을 교체하거나 공용 서비스를 변경할 때는 직전 실기기 통과 항목과 직접 영향 테스트를 먼저 회귀 목록에 포함한다. 신규 기능 성공만 확인하고 기존 흐름 검증을 생략하지 않는다.
- 회귀가 발생하면 후속 증상을 임의로 덧대지 않는다. 직전 변경 diff → 실패 단계 → 서버/로컬 데이터 근거 순으로 인과관계를 확인하고, 원인과 무관한 정상 명령·Rules·스키마는 변경하지 않는다.
- 기능 섹션 완료 보고에는 `새로 가능해진 흐름`, `보존 확인한 기존 흐름`, `미확인 실기기 항목`을 구분해 기록한다.

### 2단계: 첫 번째 작업 단위 구현

- 최신 기준 브랜치에서 작업 단위별 브랜치를 생성한다.
- 문서와 기존 아키텍처를 유지하며 승인된 첫 번째 작업 단위만 구현한다.
- 구현 중에는 테스트 코드를 변경과 함께 작성하되, 테스트 실행은 개별 A/B/C 작업 구간마다 반복하지 않는다.
- 디바이스에서 최종 확인 가능한 하나의 기능 섹션은 모든 구현 구간을 연결한 뒤 자동 테스트를 한 번 모아 실행한다.
- 각 중간 구간은 코드 포맷, `git diff --check`, 변경 내용 검토를 기본 확인으로 하고 `구현 완료 · 테스트 실행 대기`로 기록한다.
- 다음 경우에만 작업을 멈추고 사용자에게 보고한다:
  - 제품 또는 데이터 설계 결정이 필요한 경우
  - 선택에 따라 구현 결과가 크게 달라지는 경우
  - 실제 API, 계정 또는 실기기 확인 없이는 결론을 낼 수 없는 경우
  - 권한이나 외부 작업 승인이 필요한 경우
- 그 외의 구현 세부사항은 문서와 기존 구조를 기준으로 합리적으로 결정하고 계속 진행한다.
- 이 단계에서는 사용자가 요청하지 않은 커밋이나 푸시를 하지 않는다.
- 사용자가 중간 실행을 명시적으로 요청하거나 아래 예외 조건에 해당할 때만 좁은 검증을 먼저 실행하며, 이후 코드가 바뀌지 않으면 3단계 최종 검증에 재사용한다.

### 3단계: 최종 검증

- 실기기 검증이 가능한 기능은 관련 A/B/C 구간마다 디바이스 테스트를 요청하지 않는다. 배포 가능한 기능 섹션 전체가 연결되고 자동 검증이 끝난 뒤 체크리스트를 한 번 전달한다.
- 기능 섹션 종료 시 그동안 작성해 둔 신규 표적 테스트와 영향받는 기존 테스트를 한 번 묶어 실행하고, 변경 파일 정적 분석도 한 번 실행한다.
- 실기기 검증 결과를 받은 뒤 실제 구현 결과와 검증 내용을 문서에 반영한다.
- 커밋 직전 검증은 변경 범위와 위험도에 맞춰 선택하며, 전체 `flutter test`를 모든 작업에 일률적으로 요구하지 않는다.
- 저장 스키마·공용 Domain·라우팅·의존성처럼 영향 범위가 넓거나 여러 feature를 함께 변경한 경우에는 최종 코드 상태에서 `flutter analyze`와 전체 `flutter test`를 각각 한 번 실행한다.
- 한정된 UI 또는 독립 로직 변경은 관련 테스트와 `flutter analyze`가 통과했고 실기기 확인까지 완료됐다면 전체 `flutter test`를 생략할 수 있다.
- 실기기 테스트는 UI와 실제 사용 흐름을 확인하는 수단이며 자동 회귀 테스트를 대체하지 않는다. 반대로 동일 코드 상태의 자동 테스트 통과 후 실기기 확인만 추가됐다면 자동 테스트를 반복하지 않는다.
- 2단계 종료 또는 실기기 검증 대기 전에 전체 검증을 이미 실행했더라도 이후 코드가 변경되지 않았다면 같은 전체 검증을 반복하지 않는다.
- 테스트 이후 문서만 변경한 경우 Flutter 검증을 다시 실행하지 않는다.
- 검증 실패 시 실패 원인을 해결하고 영향받은 테스트를 먼저 실행한 뒤, 수정 영향이 넓을 때만 최종 상태에서 전체 검증을 다시 실행한다.
- 실패 수정 중에는 전체 묶음을 매번 반복하지 않고 실패한 테스트와 직접 영향 테스트만 재실행한다. 최종 코드 변화가 넓을 때만 섹션 종료 시 전체 묶음을 한 번 더 확인한다.

### 4단계: 문서화 및 기능 브랜치 Git 반영

- 3단계 검증 결과를 현재 작업 결과 문서와 다음 채팅 인계 문서에 반영한다.
- 작업 구간이 완료되면 `NEXT_WORK.md`의 완료된 상세 과정과 `AI_CONTEXT.md`의 완료 상세를 `DEV_LOG.md`로 이동한다.
- `DEV_LOG.md`는 앱 전체 개발 이력의 영구 기록이다. 작업 목적·구현·결정·검증·브랜치/커밋·운영 확인을 빠뜨리지 않고 기록하며, 중요도에 따라 상세 기록과 간략 기록을 함께 사용한다.
- `AI_CONTEXT.md`는 전체 프로젝트 지도이자 작업 타이틀 모음으로 유지한다. 완료 항목은 제목·핵심 상태·상세 문서 또는 `DEV_LOG.md` 연결만 남기고 긴 구현 경과를 유지하지 않는다.
- `NEXT_WORK.md`는 완료된 작업 설명을 유지하는 누적 로그로 사용하지 않는다.
- 완료 기록을 `DEV_LOG.md`로 옮긴 뒤 `NEXT_WORK.md`를 다음 작업 그룹의 목표, 상세 근거, 포함 범위, 제외 범위, 작업 순서 및 완료 조건으로 교체한다.
- 문서 우선순위는 사용자 최신 지시 → 이 문서 → `NEXT_WORK.md` → `AI_CONTEXT.md` → 기능별 제품·아키텍처 계약 → `DEV_LOG.md`의 과거 이력이다. 하위 문서의 오래된 상태 문구가 상위 기준을 덮지 못한다.
- 동일 사실을 여러 문서에 자세히 복제하지 않는다. 행동 원칙은 이 문서, 현재 실행 상세는 `NEXT_WORK.md`, 전체 상태와 링크는 `AI_CONTEXT.md`, 기능의 장기 계약은 제품·아키텍처 문서, 완료 경과와 장애 타임라인은 `DEV_LOG.md` 또는 전용 진단 이력에 둔다.
- 보류 검증은 현재 작업 완료를 막는 항목과 차후 통합 테스트에 묶을 항목을 구분한다. 후자는 `NEXT_WORK.md`의 현재 완료 조건에 남겨 작업을 계속 열린 상태로 만들지 않는다.
- 코드, 테스트 및 문서를 같은 검증 단위의 커밋에 포함한다.
- 간단한 UI·소규모 수정·기획처럼 한 번에 끝나는 작업은 기능 브랜치를 원격에 푸시하지 않아도 된다. 검증 후 `dev`에 병합하고 `dev`만 푸시한다.
- 여러 스텝으로 진행하거나 되돌림·비교 가능성이 있는 작업은 완료한 피처 단위마다 작업 브랜치를 원격에 푸시해 복구 지점을 남긴다.
- 작업 브랜치 푸시는 진행 중 백업·복구 지점이며 `dev` 병합 완료를 의미하지 않는다.

### 5단계: dev 직접 병합 및 최신화

- 첫 릴리즈 전까지 Pull Request를 사용하지 않는다.
- 현재 작업 구간이 끝나고 최종 테스트·문서 정리까지 완료됐을 때 작업 브랜치를 `dev`에 직접 병합한다.
- 원격 `dev` 상태를 확인하고 최신 `dev`를 기준으로 기능 브랜치를 병합한다.
- 충돌이 발생하면 임의로 우회하지 않고 변경 의도와 문서 상태를 대조해 해결한 뒤 필요한 검증을 다시 실행한다.
- 병합 결과에 코드 변화가 없으면 기능 브랜치에서 완료한 최종 검증을 재사용한다.
- 병합 커밋 또는 fast-forward 결과를 원격 `dev`에 푸시한다.
- 원격 `dev`와 로컬 `dev`가 같은 최종 커밋을 가리키고 작업 트리가 깨끗한지 확인해야 작업 그룹이 완료된다.
- 하나의 페이지 또는 큰 기능 단위가 완료되고 `dev`의 검증 상태가 확정되면 `dev`를 `main`에 병합하고 `main`도 원격에 푸시한다.
- 진행 중이거나 회귀 수정이 남은 구간을 포함한 채 `main`을 최신화하지 않는다.
- 다음 채팅은 원격과 동기화한 최신 `dev`의 `NEXT_WORK.md`와 실제 Git 상태를 대조한 뒤 다시 1단계부터 시작한다.

### 테스트 실행 최소화 원칙

```text
각 작업 구간 구현 중
→ 테스트 코드는 함께 작성
→ 코드 포맷 + git diff --check + 변경 검토
→ 자동/디바이스 테스트는 실행 대기
→ 기능 브랜치 체크포인트 커밋·푸시

하나의 기능 섹션 구현 완료
→ 작성한 신규 표적 테스트를 한 번에 실행
→ 영향받는 기존 테스트를 한 번에 실행
→ 변경 파일 flutter analyze 1회
→ 영향 범위가 넓을 때만 전체 flutter test 1회

실패 발생
→ 실패 테스트와 직접 영향 테스트만 수정·재실행
→ 전체 묶음 반복 실행 금지

배포·실기기 확인
→ Rules 변경 시 AI가 최신 추적본을 실제 배포로 정확히 1회 시도
→ 첫 실패 시 반복·추측 수정 금지, 실패 단계·콘솔 게시본·diff 조사
→ 재시도는 사용자의 새 지시 후 1회
→ Rules 외 Firebase 배포는 사용자의 명시 지시 필요
→ 기능 섹션 전체 디바이스 체크리스트 1회
→ 동일 코드 상태에서 이미 통과한 검증은 재사용
→ 문서 최신화
→ 단순 작업: 작업 브랜치 로컬 커밋
→ 단계 작업: 완료한 피처 단위마다 작업 브랜치 커밋 및 원격 푸시
→ 현재 구간 최종 테스트·문서 정리 후 dev 직접 병합
→ dev만 원격 푸시
→ 로컬/원격 dev 최신화 확인
→ 페이지·큰 기능 단위 완료 시 dev를 main에 병합하고 main 푸시
```

### 중간 테스트 실행 예외

- 공용 인터페이스·라우팅·의존성 변경으로 이후 모든 구현이 컴파일되지 않을 가능성이 큰 경우
- 인증·소유권·데이터 삭제·Security Rules처럼 잘못된 기반 위에 후속 작업을 쌓으면 복구 비용이 큰 경우
- 사용자 보고 차단 버그의 원인을 구분하려면 최소 재현 테스트가 반드시 필요한 경우
- 사용자가 특정 구간의 테스트 실행을 명시적으로 요청한 경우

예외 실행도 가장 좁은 단위 하나로 제한하고 같은 검증을 다음 구간에서 반복하지 않는다. 단순히 안심하기 위한 중간 전체 테스트나 매 구간 `flutter analyze`는 실행하지 않는다.

- 문서만 변경한 경우 Flutter 코드 검증이 필요한지 변경 영향으로 판단한다.
- 코드와 의존성에 변화가 없는 순수 문서 수정은 `git diff --check`와 문서 내용 검토를 기본 검증으로 한다.
- 전체 테스트 실행 여부와 근거는 작업 결과에 짧게 기록한다.
- 실행하지 않은 중간 테스트는 `미검증`이 아니라 `테스트 코드 작성 완료 · 기능 섹션 종료 시 실행 대기`로 구분해 기록한다.
- 테스트 출력 전체를 문서나 답변에 반복하지 않고 통과 여부, 테스트 수 및 핵심 실패만 요약한다.

## 10. Git Rules

### Branch
- 모든 작업은 작업 단위별 브랜치에서 진행한다
- 작업 시작 전에 반드시 현재 브랜치와 작업 트리 상태를 확인하고, 채팅/터미널 출력으로 실제 브랜치 이름을 남긴다
- 첫 릴리즈 전 통합 기준 브랜치는 `dev`다
- 작업 시작 전에 `dev`로 이동해 원격 `origin/dev`를 확인하고 최신화한다
- 모든 새 작업 브랜치는 최신 `dev`에서 분기한다
- `dev` 또는 `main`에서 직접 파일을 수정하지 않는다
- 통합 브랜치에서 작업을 시작해야 하면 먼저 작업 내용에 맞는 새 브랜치를 생성한다
- 브랜치 생성 명령의 성공 출력과 `git branch --show-current` 결과를 확인하기 전에는 파일을 수정하지 않는다. AI가 브랜치를 만들었다고 추정하는 것만으로 진행하지 않는다
- 하나의 브랜치에는 하나의 명확한 작업 범위만 포함한다
- 다른 작업 단위로 넘어갈 때는 현재 변경의 검증과 Git 상태를 확인한 뒤 별도 브랜치가 필요한지 판단한다
- Codex가 생성하는 브랜치는 기본적으로 `codex/` 접두사를 사용한다
- 첫 릴리즈 전에는 PR을 만들지 않고 검증이 끝난 기능 브랜치를 `dev`에 직접 병합한다
- 간단한 UI·소규모 수정·기획 브랜치는 원격 푸시를 생략할 수 있다
- 여러 스텝 작업은 완료한 피처 단위마다 작업 브랜치를 원격에 푸시해 복구 지점을 남긴다
- 현재 구간의 최종 테스트와 문서 정리가 끝났을 때 작업 브랜치를 `dev`에 병합한다
- 병합된 `dev`를 `origin/dev`에 푸시한다
- 작업 그룹의 최종 종료 브랜치는 최신화된 `dev`다
- 로컬과 원격 `dev`의 최종 커밋 일치를 확인한다
- 하나의 페이지 또는 큰 기능 단위가 완료되면 검증된 `dev`를 `main`에 병합하고 `origin/main`을 최신화한다
- 진행 중 작업이나 회귀 수정이 남은 `dev`는 `main`에 병합하지 않는다
- PR 사용 재개 여부는 첫 릴리즈 준비 시점에 별도로 결정한다

### Commit
형식:
- type: message

예:
- feat: 모집글 목록 UI 추가
- chore: 초기 프로젝트 설정

금지:
- update code
- fix bug
- misc
