# AI Collaboration Rules - LOSTPARTY (2026)

> 기존 서비스 전용 항목은 [원문·출처 기록](../../legacy/firebase/extracted/docs/project/ai_rules.md)으로 분리했다. 남은 제품/협업 문맥의 신규 서버 적용 여부는 별도 설계에서 판단한다.

이 문서는 LOSTPARTY 프로젝트에서 AI 에이전트와 협업할 때 따를 상세 규칙을 정의한다. 모든 에이전트의 자동 작업 진입점과 핵심 실행 게이트는 저장소 루트의 [`../../AGENTS.md`](../../AGENTS.md)다. `AGENTS.md`를 먼저 적용하고 이 문서에서 배경·세부 절차를 확인한다.

## 1. Project Intent

목표는 사용자가 이해하고 편리하게 사용할 수 있는 실제 레이드 모집·지원 앱을 완성하고 테스트·포트폴리오에 활용하는 것이다. 기술/패턴의 표현이나 작업 분해 자체를 목표로 삼지 않는다. 작은 구현 파트는 완성까지 가는 방법이며 최종 사용자 흐름을 끊는 근거가 아니다.

개발 환경·운영 방침·확정 UX를 설계에 먼저 반영하고 기술 선택의 근거·영향·완료 경로를 확인하는 것은 에이전트 책임이다. 사용자는 기능 흐름과 제품 결과를 판단한다. 사용자의 진행 승인이 누락된 기본 조건을 검수했다는 뜻은 아니다.

## 2. Product Context

현재 1인 개발이며 Firebase 구현 제거 후 자체 Python Backend를 사용한다. 회원 식별/로그인은 단일 Google 로그인을 사용한다. 원정대 소유 인증은 별개로 인게임 장비 상태 변경을 통해 검증한다. 로스트아크 API 자체는 계정 소유 인증을 지원하지 않는다.

현재 환경에서 개발·연동하고 관련 앱/Backend 구현 후 테스트한다. 개발자료는 베타 시작 직전 비우고 베타 이후 자료는 보존한다. 개발 중 구자료 마이그레이션/호환 운영을 임의로 필수화하지 않는다. 구체 수명·실제 삭제 실행 경계는 [정책09 D08](../backend-migration/09-migration-decisions.md#d08-개발--베타--운영-데이터-수명--사용자-확정)을 따른다.

## 3. Product Scope

현재 모집/신청·가입·일정·완료/해산·두 주차와 그룹 기능의 확정 범위는 제품 계약과 NEXT_WORK의 실제 남은 작업을 대조한다. 승인된 로그인/필터를 포함한 최신 제품 범위를 적용한다. 채팅·알림 등 승인되지 않은 후속은 자동 확장하지 않는다.

## 4. Agent Responsibilities

에이전트는 도구명에 따른 설계/구현 역할 분리 없이 현재 승인된 조사·설계·구현·검증·문서 관리를 수행한다. 제품 의도·규칙·실제 코드가 다르면 실행계획을 수정하며 필요한 제품 결정만 사용자에게 요청한다. 지시가 바뀌면 충돌하는 이전 조항을 교체하고 과거 이력은 실행 문서에서 분리한다.

## 5. General Principles

- AI가 생성한 코드는 반드시 검토 후 반영한다
- 의미 없는 자동 생성 코드는 사용하지 않는다
- 항상 “왜 이 코드가 필요한지” 설명 가능해야 한다
- 작은 단위로 점진적으로 구현한다
- 나중에 읽고 학습 가능한 코드를 유지한다
- 제목·표시명 등 자유 입력에는 입력 예시 또는 적용될 기본 문구를 안내한다
- 자유 입력이 비어 있더라도 기능을 불필요하게 막지 않고 문맥에 맞는 기본값을 적용한다
- 자동 기본값은 기존 데이터와 충돌하지 않도록 순번 등 안정적인 구분자를 사용한다
- 식별자처럼 반드시 고유해야 하는 값은 기본값 여부와 관계없이 저장 계층에서 중복을 검증한다

## 6. Architecture Principles

사용자 이해·UI/UX를 우선하고, 패턴/책임·API와 캐시 사용을 근거로 판단하는 상세 기준은 [개발 품질·데이터 흐름·UX 기준](../architecture/DEVELOPMENT_QUALITY_AND_UX_STANDARD.md)을 따른다. 기존 구조를 쓰거나 다른 방식을 채택하는 이유·소유권/비동기 수명·회귀/측정 범위를 작업 규모에 맞게 설명한다. 관련 정상 기능의 전면 재작성이나 패턴·계층 수 증가를 기본 해법으로 삼지 않는다. 서비스 복구 릴리즈 배포 확인 시 같은 문서 §6의 main 기준 후속 최적화 가능 시점을 사용자에게 안내한다.

### 과거 Firebase 구현의 재사용 판단

2026-10-29 사용자 확정. 과거 그룹 기능이 한 차례 동작했더라도 당시 기록·설계·코드를100% 신뢰하거나 같은 구조로 재현해야 한다고 판단하지 않는다. Firebase 제약 아래 기능을 성립시키기 위한 우회·비틀린 구조가 포함될 수 있다.

- 먼저 현재 사용자 목적·확정 제품 정책·관찰 가능한 UX와 당시 기술 수단을 분리한다. 과거 개발 완료·기기 통과는 현재 Backend 구조의 타당성이나 현재 연결 완료를 보증하지 않는다.
- 기존 Repository/Domain/Validator/WritePlan도 적합성을 검토한 뒤 재사용한다. Firestore 구독·역방향 Projection·클라이언트 쓰기 계획·분산 카운터/중복 스냅샷 등은 현재 HTTP·서버 원장/트랜잭션·canonical UUID·세션 권한에 필요한지 확인하며 같은 추상화로 옮기는 것 자체를 목표로 삼지 않는다.
- 자체 Backend 연결에 직접 관련된 Firebase 의존·우회 구조는 원인과 영향 범위를 확인해 제거·교체·정상화한다. 사용자 목적을 만족하는 더 단순한 구조를 선택하고 관련 문서에 변경 이유·보존할 동작·검증 범위를 남긴다.
- 보존할 것은 최신 확정 제품 의도·필요 UX·기록/권한의 의미다. 새 Backend 구현도 이 기준으로 대조하며 DTO가 제공됐다는 이유만으로 자동 채택하지 않는다. 실제 UI/사용 단계가 달라지는 제안은 기존 UX 협의 기준을 따르고, 무관한 리팩터링은 현재 범위에 섞지 않는다.

Flutter + MVVM 기반

- View: UI와 이벤트 전달
- ViewModel: 상태 관리 및 로직
- Repository: 데이터 처리
- API 호출은 View에서 직접 하지 않는다
- **기존 명령의 단일 호출·원자성 유지 (2026-10-30 사용자 확정):** 이미 정상 작동하는 생성/수정 기능을 확장할 때 같은 사용자 명령에 속하는 데이터는 해당 기존 명령 API의 한 번 호출로 함께 처리한다. 예를 들어 모집 생성의 그룹 연결·공개범위는 기존 생성 요청에 포함하며, 생성 후 별도 그룹 연결/설정 API를 이어 호출해 완성하는 구조를 만들지 않는다. 서버 검증·쓰기·성공 결과는 같은 명령의 원자적 처리 범위로 유지한다. 클라이언트 순차 호출·부분 성공 보정으로 대체하지 않는다.
- 필요한 사전 조회/선택·검토와 변경 명령은 구분한다. 위 원칙은 모든 조회를 없애라는 뜻이 아니며, 응답 유실 시 동일 원본문/멱등 키로 결과를 복구하는 재전송도 별개의 업무 명령이 아니다. 이미 생성된 모집을 나중에 사용자가 명시적으로 변경하는 행동은 별도 수정 명령으로 처리하되, 그 변경 자체의 그룹 연결·공개범위도 한 요청에서 원자 처리한다.
- 기존 API로 필요한 변경을 담을 수 없으면 Backend와 기존 명령 계약 확장을 먼저 협의한다. 기능을 연결하기 쉽다는 이유로 클라이언트에서 복수 쓰기 API를 조합하지 않는다. 이 지침 보완은 현재 목적 브랜치에서 다음 관련 구현·검증 파트와 함께 커밋/푸시하며, 기록 한 건만으로 별도 보관 파트를 만들지 않는다.
- 기능 단위(feature-first) 구조 사용
- 네트워크 요청을 시작하는 버튼은 요청 진행 중 비활성 또는 동일 동작 무시로 연타·중복 요청을 막는다. 화면별 예외를 두지 않는 공통 규칙이다.
- 확인 알럿의 취소/부정 동작은 왼쪽, 동의/긍정 동작은 오른쪽에 배치한다(2026-10-15 사용자 확정). 기능별 문구가 달라도 같은 배치 원칙을 적용한다.

## 8. Task Execution Rules

- 기존 서비스의 기술·배포 세부 절차는 [보관 문서](../../legacy/firebase/README.md)를 따른다. 과거 실행 지시는 현재 신규 서버 구현이나 외부 배포의 승인이 아니다. 현재 작업 범위는 사용자 최신 지시와 NEXT_WORK를 먼저 적용한다.

- 루트 `AGENTS.md`는 모든 작업의 핵심 실행 게이트이며 이 문서는 상세 행동 규칙이다. `NEXT_WORK.md`나 채팅 지시를 실행할 때 함께 적용한다. 작업 지시가 안전·권한·배포 규칙과 충돌하거나 위반 가능성이 있으면 임의로 진행하지 말고 충돌 지점과 필요한 예외를 사용자에게 확인한다.
- 사용자가 예외를 명시적으로 확정한 경우에만 해당 범위·해당 시점에 한해 적용한다. 과거 예외나 유사한 지시를 이후 작업의 포괄 권한으로 재사용하지 않는다.
- 기본 절차에서 `--dry-run`과 실제 배포를 연속 실행하지 않는다. 실제 배포 자체가 원격 컴파일을 포함하므로 요청 횟수를 중복시키지 않는다. 사용자가 원격 컴파일만 요청한 경우에만 dry-run 한 번으로 대체한다.
- 실패 후 재배포는 사용자가 진단 결과를 확인하고 다시 지시한 경우에만 한 번 수행한다. 과거 배포 지시나 첫 시도 정책을 무제한 재시도 권한으로 사용하지 않는다.
- 구현은 목적·완료 조건이 있는 파트로 나누되 최종 사용자 흐름과 관련 기능을 함께 고려한다. 모델/Repository/VM/UI 분리는 내부 구현 순서이며 단계마다 사용자 승인이나 커밋을 요구하는 기준이 아니다.

## 8-1. Work Group Cycle and Test Strategy

### 1. 설계와 착수

- AGENTS의 필수 문서·Git 확인 순서를 따른다. 현재 개발/운영 방침과 확정 UX를 설계의 선행 조건으로 적용하고, 해결할 사용자 문제·소유/권한/식별자/비동기 수명·일반 앱 경로·관련 전체 흐름을 조사한다.
- NEXT_WORK에는 하나의 현재 파트의 목표·근거·포함/제외·순서·완료 조건과 직접 회귀/검증 범위를 둔다. 계획이 확정 제품 정책과 다르면 그 계획을 바로잡는다. 사용자가 모든 기술 조항을 읽고 충돌을 찾아줄 것으로 가정하지 않는다.
- 영향받는 기존 정상 흐름과 누락/경계 자료·재진입·중복·늦은 응답을 보호한다. 비활성 기능은 다시 사용하지 않으며 호출차단/원요청 경계가 관련된 경우만 검증한다. 새 정책을 중복 조건문으로 복제하지 않고 기존 Domain/Validator/서버 경계를 확인한다.

### 2. 구현과 완료 상태

- 현재 대단원 브랜치를 유지하며 파트를 구현한다. 관련 문서/지침·버그 기록·UI 수정도 같은 브랜치에서 수행하고 별도 목적의 파트로 기록할 수 있다. 상세 Git 기준은 AGENTS §3만 따른다.
- 기반 부품 구현/실제 앱 연결/자동 검증/사용자 인수는 별도 상태다. 실제 앱 연결은 일반 main→DI/Router→화면→조회/명령→성공 후 화면/자료 갱신을 확인한다. 테스트 주입 전용이나 기본 경로 비활성 상태를 기능 연결 완료로 보고하지 않는다.
- 코드 포맷·diffcheck·diff 검토는 기본 확인이다. 제품 결정·실제 외부 확인/권한이 필요한 경우에만 그 지점을 알리고, 이미 확정된 기준/일상 구현 판단을 재질문하지 않는다.

### 3. 검증 단위와 재사용

- 사용자 수동1~5구간(생성/가입/방내부/완료·해체/주차분리)은 테스트 분량 구분이다. 구현·영향분석에서 다른 관련 흐름을 제외하는 기준이 아니다. 전체 연결과 Backend 준비 후 해당 구간의 소수 항목을 안내하고 기기 조작은 사용자가 수행한다.
- 기능 흐름이 연결되는 최종 상태에서 권한·동시성·멱등·원자성·저장 실패·식별자/늦은 응답 등 직접 경계를 묶어 검증한다. 관련 구현 파트마다 같은 묶음을 반복하지 않는다. 파트 보관 자체가 전체 시험 의무를 만들지 않는다.
- 중간 시험은 컴파일 위험·재현/원인 분리·사용자 명시 요청처럼 필요한 좁은 범위에 한정한다. 실패 후 실패/직접 영향 시험을 먼저 재실행한다. 코드가 그대로면 결과를 재사용하고, 문서 변경만이면 Flutter 시험/분석을 반복하지 않는다.
- 전체 시험은 공용 영향이 표적으로 설명되지 않을 때 최종 상태에서 확대한다. 같은 인원수 확장은 최대8인 대표를 기본으로, 마지막1인·승계/권한처럼 상태 전이가 다르면 별도 경계만 둔다. 용량별 정책이 실제로 다른 경우의 검증을 생략하는 규칙은 아니다.
- NEXT_WORK에 직접 보호할 흐름·검증/확대 근거를 짧게 기록한다. 아직 실행 전인 시험은 실행 대기로 표시하고 통과로 주장하지 않는다. 시험 개수로 실제 앱 연결이나 실회원/기기 성공을 대신하지 않는다.

### 4. 문서 교체와 파트 보관

- NEXT_WORK는 현재 계획/유효 후속만, AI_CONTEXT는 현재 전체 지도/상태·상세 링크만 유지한다. 완료/해소된 대기·폐기 계획은 DEV_LOG 또는 출처가 있는 history로 옮기고 현재 지시에서 제거한다. 정정 문단을 상단에 덧붙이는 것으로 갱신을 대신하지 않는다.
- 설계/제품 계약은 현재 정책을, DEV_LOG/history는 당시 결정/검증을 보관한다. 확정 제품/개발 정책·AGENTS/이 문서는 실행계획의 선행 조건이며 NEXT_WORK/AI_CONTEXT가 이를 덮지 못한다. 최신 사용자 변경은 충돌 조항을 교체해 반영한다.
- 파트 완료 시 새로 가능한 흐름·보존 확인·미확인 실기기·실행 검증을 구분하고 코드/시험/문서를 목적 하나로 묶어 커밋·푸시한다. 메시지·회신·한 줄 수정마다 커밋하지 않는다. 독립된 지침 정리나 UI 수정 파트는 하나의 커밋이 될 수 있다.
- 작업 브랜치 보관과 대단원 dev 통합/릴리즈는 별개다. 소분류 종료를 dev 병합이나 최종 종료 브랜치 dev의 조건으로 취급하지 않는다. 통합 절차는 AGENTS §3을 참조하며 여기서 중복 정의하지 않는다.

## 8-2. Flutter ↔ Backend GitHub Issues 협업·콜백

2026-10-14 사용자 확정. 다른 협업툴이나 공유 방식을 추가 채택하기 전까지 [Backend GitHub Issues](https://github.com/heo0328/lostparty-backend/issues)를 공식 협업 채널로 사용한다. Flutter 저장소는 `heo0328/LostParty_flutter`, Backend 저장소는 `heo0328/lostparty-backend`다. 여기서 콜백은 요청에 대한 확인·진행 결과·테스트 결과·미해결 사항을 관련 Issue 댓글로 회신하는 것을 뜻한다.

### 요청이 필요한 경우

피드백·테스트 요청은 협업상 필요할 때만 한다. 계약·요구사항의 불명확함, Backend 수정/준비 필요, 실제 연동 결과 확인처럼 현재 구간을 진행하거나 완료 판단하는 데 필요한 항목에 한정한다. 모든 작업마다 상대 측 검토·피드백·재테스트를 요구하지 않는다. 자체 검증으로 판단 가능한 작업이나 이미 확인한 결과에는 추가 요청을 만들지 않는다. 필요한 요청은 구간 단위로 묶고, 기존에 받은 요청에 대응한 결과와 상대 측 작업에 영향을 주는 인계는 빠뜨리지 않고 회신한다. 아래 절차는 해당 협업 요청·인계가 있는 구간에 적용하며, 독립적인 로컬 작업마다 Issue 댓글을 의무적으로 남기는 절차가 아니다.

### 요청을 받고 작업하는 순서

1. 해당 구간의 기존 Issue 본문과 최신 댓글을 읽어 요청·질문·합의된 계약·담당 측·완료 조건을 확인한다. 코드가 push되었는지와 실행 버전도 필요한 범위에서 대조한다. 기존 Issue가 있으면 동일 구간은 그 안에서 이어간다.
2. 상대 측이 피드백·작업·테스트를 요구하면 각 항목을 NEXT_WORK에 Issue/댓글 링크와 함께 정리한다. 바로 대응할 수 있는 항목은 수행하고, 결정이나 상대 측 준비가 필요한 항목은 필요한 답변·준비 내용을 Issue에 남긴다.
3. 현재 승인 범위에서 수행한 구현·검토·자동 검증과 사용자가 보고한 수동 검증 결과를 관련 Issue에 회신한다. 구현 인계는 실제 커밋/브랜치·push 여부와 계약 버전을, 테스트 인계는 대상 동작·기대/실제·통과/실패·미확인 범위를 포함한다. 미커밋·미push 결과를 상대 측이 받을 수 있는 구현으로 보고하지 않는다.
4. 상대 측 후속 작업이 필요하면 무엇을 누가 확인/수정/시험해야 하는지와 완료 조건을 구체적으로 적는다. 회신이나 조건 충족이 필요한 동안은 대기 사유를 기록하고 다음 착수 시 최신 댓글부터 확인한다. 별도 모니터링 승인이 없는 상태에서 자동 감시나 일정 작업을 만들지는 않는다.
5. 게시 뒤 댓글을 재조회해 내용과 링크를 확인한다. NEXT_WORK에는 현재 요청/회신·대기 상태, DEV_LOG에는 완료 인계와 검증 근거를 기록한다. 사용자에게만 완료를 보고하고 Backend 회신을 누락한 채 협업 요청을 완료로 처리하지 않는다.

### 회신 내용과 권한

- 완료된 요청에 연계 후속 기능·미확인 릴리즈 인수만 남아 있으면 기존 Issue를 무기한 열어 두지 않는다. Flutter가 주관해 후속 작업의 출처·담당·현재 상태·다음 행동·완료 조건을 연결 계획/NEXT_WORK에 기록한다. 기존 요청의 완료와 미완료 범위 이관을 구분해 종료 댓글을 남기고 사용자 승인 범위에서 닫는다. 후속에서 실제 Backend 변경이 필요하면 별도 Issue로 요청하며, 미구현 기능을 완료로 표시하지 않는다. 2026-10-14 사용자 지시가 이번 Issue3/4/5 정리의 종료 승인이다.

- 기존 요청에 대한 검토 결과, Flutter 구현 인계, 사용자 테스트 결과, 장애 재현·수정 결과, 미해결 질문과 테스트 준비/수행 불가 사유는 모두 콜백 대상이다. 결과가 없거나 실행하지 못했다면 그 상태와 필요한 다음 행동을 회신한다. 변화 없는 상태를 반복 댓글로 게시하지 않는다.
- 사용자 지시로 현재 승인된 구간의 협업 댓글 작성은 상시 승인된다. 해당 범위의 요청/피드백/테스트 결과 회신마다 게시 허가를 다시 묻지 않는다. 구간과 무관한 요구, 새 작업 범위, Issue 종료·PR 변경·배포·원격 데이터 변경은 별도 승인 범위를 따른다.
- 결과는 확인된 근거만 게시한다. 자동 검증과 실제 서버/사용자 수동 검증을 구분하고 미확인 항목을 통과로 확대하지 않는다. 필요한 경우 HTTP status/error.code/request_id 등 재현 식별 정보를 사용하되 토큰·인증정보·개인정보·원본 민감 응답은 게시하지 않는다.
- 로컬 문서는 설계·진행·완료 이력이고, Issue 댓글은 상대 측이 읽을 요청과 회신이다. 한쪽 기록으로 다른 쪽을 대신하지 않는다. 같은 상세 내용을 여러 문서에 복제하기보다 Issue/댓글 링크와 핵심 상태를 남긴다.

## 9. Code Generation Rules

- UI/UX의 기본값은 기존 디자인과 승인된 사용자 흐름의 유지다. 기술 구조 개선을 사용자 경험 개선으로 간주하지 않는다. API/저장 연결 작업에서 버튼·관리 진입을 없애거나 추가 중간 화면·클릭·입력을 만들지 않는다. 기존 레이아웃·조작 방식을 바꾸려면 변경 전후와 사용자 이점을 먼저 제안하고 승인된 범위만 반영한다. 이미 승인된 변경/기존 흐름 복구는 매번 허가를 다시 묻지 않는다(2026-10-17 사용자 확정). 상세 기준은 [디자인 공통 원칙](../design/LOSTPARTY_DESIGN_SYSTEM_V1_REQUEST.md)을 따른다.
- 과도한 추상화 금지
- 읽기 쉬운 코드 우선
- 불필요한 라이브러리 추가 금지
- 기존 구조 우선 존중
- 설명 없는 대규모 변경 금지
- 서버 전환·기능 미연결을 이유로 기존 카드/그리드·하단 체크박스 영역을 목록 행으로 축소하지 않는다. 아직 연결하지 않은 기능의 영역/확장 자리를 보존하고, 실제 동작 연결과 디자인 변경을 분리한다(2026-10-17 사용자 재확인).
- 앱의 버튼·안내는 핵심 행동과 현재 상태만 간결하게 쓴다. 내부 구현 설명과 반복 안내를 사용자 화면에 나열하지 않는다. 인게임 용어·UX 세부 표현은 사용자 조정을 따른다(2026-10-16 확정).
- 서버 등록·조회·변경 시각의 사용자 표시는 초까지만 표시하고 소수점 초는 노출하지 않는다. 저장/전송 시각의 정밀도는 변경하지 않는다(2026-10-16 확정).

## 10. Git Rules

브랜치·커밋/푸시·통합의 단일 기준은 [AGENTS §3](../../AGENTS.md#3-git과-작업-브랜치)이다. 1인 개발의 대단원/소분류 운영과 현재 브랜치 문서/UI 작업도 이 기준을 따른다. 첫 릴리즈 전 PR 없이 통합 시점의 직접 병합을 사용하며, 소분류 종료마다 병합하지 않는다.

## 11. Commit Strategy

한 커밋은 하나의 의미 있는 파트 결과다. 형식은 `type: 구체 결과`로 쓰고 `update code`/`fix bug`/`misc`처럼 목적이 드러나지 않는 메시지를 피한다. 관련 구현·회귀 시험·문서는 같은 파트에 포함하고 별개의 지침 정리/구조 변경은 그 목적대로 묶는다. 세부 저장 시점은 AGENTS §3.4를 따른다.
