# NEXT WORK — Rules 책임 축소와 로컬 이전

## 현재 상태: Rules 보존 체크포인트 · 의심 함수군1~3 선정

사용자 요청은 불필요한 서버 크로스체크 제거, 로컬로 충분한 처리의 앱 이전, 전체 Rules의 실질적 축소다.
최우선 성공 기준은 복잡도를 낮춰 Rules 변경 후 수시간~수일의 수정/재시도 없이 정상 게시하고 그 상태를 유지하는 것이다.
삭제량·로컬 이전량·크기/깊이는 중간 지표다. 최종 전체본의 첫 시도 게시 성공·경고0·활성 SHA 일치가 필요하며,
후속 실제 업데이트에서도 게시 결과/소요시간을 기록한다. 한 번의 성공만으로 지속 안정성을 입증하지 않는다.
이전 D-X1 기능별 후보 확장은 중단한다. 다음 수동완료 기능을 계속 이식하는 순서는 더 이상 현재 계획이 아니다.
구체 실행 기준은 [Rules 책임 축소·로컬 이전 실행 계획](../architecture/RULES_LOCALIZATION_EXECUTION_PLAN.md)이다.
감소율 목표는 두지 않는다. 사용자가 지정한 작은 단위까지만 구현·확인·기록하고 종료한다.
사용자의 진행 지시로4번 운영 단계를 시작했다. 모든 기기가 최신 작업 코드 사용 중이라는 답변을 확인했다.

로컬 전체 Rules는 줄맞춤 후fd90aa93/187865bytes·깊이5이며 내용 기준8b39db36과 동일하다. 실제 firestore.rules에 반영했고 생성 결과 일치 및 필요한 경계를 확인했다.
삭제 검사·로컬 이전·부작용·구버전 영향·복구·실기기 항목은 실행 계획의「2-2~3-2 로컬 통합 결과」를 따른다.
이는 로컬 단계 완료이며 운영 게시 정상화 완료가 아니다.

의심군 제거 비교 우선순위:1 주차 인증/전환 guard,2 완료 후 준비 변경,3 guard 일반 교체/참가 호환.
실제 함수명·선정 근거·기능 영향은 실행 계획의「보존 체크포인트와 제거 비교 우선순위」를 따른다.
이번에는 후보 함수 선정만 하며 제거·게시 실험은 실행하지 않는다.

게시 정상화와 새 Rules의 실기기 인수는 미완료다. 재게시에는 진단 확인 후 새 지시가 필요하다.
사용자가 코드를 일일이 검토하는 절차를 전제하지 않는다. 각 단위의 결과와 남은 항목을 보고한다.

- 구현 범위: 표시 전용 원본 대조, listing 중복 투영, 필수 쓰기에 이미 묶인 동일 명령 검사, 실제 중복 저장/호환 경로 축소.
  로컬 필터·정제는 권한상 조회 가능한 자료의 제한된 페이지 안에서 처리한다. 이미 로컬인 기능은 절감으로 계산하지 않는다.
- 확인 범위: 소유권/권한·비공개 읽기·중복 참가/완료·원자성·8인/마지막1인/승계·기존 완료 이력·구버전/이행 영향.
  각 구현 범위와 확인 범위의 상세 대응은 실행 계획 표를 따른다.
- 제외: 근거 없는 schema3 전면 이식, 새 기능 확대, 유료 서버, 임의 기능 삭제, 자동 실기기 조작, 운영 자료 이행 및 Rules 외 배포.
- 검증: 변경된 경계의 최소 검증 후 최종 통합본에서 필요한 회귀를 한 번 실행. 동일 코드 전체 반복 금지.
- 완료: 실제 삭제/이전 목록·앱 연결·전체 Rules 순감소/깊이·확인 결과·이행/롤백·수동 확인 목록이 갖춰진 상태.
  이는 로컬 구현 단계 완료다. 운영 게시 안정화 미확인 상태를 전체 작업 완료라고 보고하지 않는다.
  운영 미검증을 숨기지 않는다. 감소율이나 테스트 개수로 게시 정상화를 대신하지 않는다.

## 별도 후속 과제 — 현재 Rules 구간과 분리

아래 과제는 기존 합의를 보존한 설계 대기 항목이며 이번 문서 정리로 구현 승인을 추가하지 않는다.

## 1. 복구키를 통한 기존 앱 사용자 복구 — 설계 필요

### 목적과 현재 합의

같은 사람의 앱 재설치·데이터 삭제·기기 변경을 해결한다. 새 익명 로그인에서 복구키를 검증한 뒤
기존 앱 사용자(Player)에 다시 연결하여 현재 유효한 원정대·그룹·레이드 관계를 사용한다.
현재 authBindings의 Auth UID→playerId 구조를 활용하는 방향이며, Firebase 익명 계정 자체 이전과 구분한다.
A의 데이터를 B로 복사·병합하거나 과거 시점의 스냅샷을 덮어쓰는 기능이 아니다.
복구 시 원정대를 무조건 미인증으로 만들지 않고 서버의 현재 인증·소유권 상태를 따른다.
이미 다른 사용자에게 넘어간 원정대는 이전 복구키로 소유권을 되돌릴 수 없어야 한다.

### 구현 전에 결정할 사항

복구키 발급·저장·검증·재발급·폐기와 유출/분실 처리, 신뢰된 서버 검증 방식,
기존 기기 접속 유지/차단, 복구 전 새 Player의 참가·인증 데이터 처리, 중복 요청과 중도 실패,
캐시·구독·세션 전환을 확정한다. 이미 활동한 새 Player의 데이터는 임의 삭제·자동 병합하지 않는다.
원정대 인증만으로 기존 Player 전체를 복구하는 방식은 채택하지 않는다.

### 완료 기준과 제외

설계 승인 후 서버 권한과 실제 앱 연결을 구현하고 사용자 복구의 데이터 보존·중복 처리 경계를 확인한다.
이전된 원정대 권한이 복구로 부활하지 않아야 한다. 실기기 결과는 별도 확보한다.
소셜 로그인 또는 사용자 전체 병합은 자동 포함하지 않는다. 현재 복구키 구현/검증 완료가 아니다.

## 2. 이전 소유자에게 남은 원정대 고아 관계 처리 — 설계 필요

### 목적과 기존 정책

다른 사용자가 원정대를 인증한 경우, 새 인증자는 기존 사용자의 그룹·참가·완료를 승계하지 않고
과거 기록에 막히지 않게 이용한다. 이 정책은 유지한다. 동시에 기존 방의 무효 참가가 방을 막거나
동일 캐릭터의 이전·새 참가를 모두 정상 인원으로 취급하지 않도록 처리한다.
새 사용자가 과거 방을 찾아 정리해야만 이용할 수 있게 만들지 않는다.

### 조사·결정 범위

이전 신청의 승인 차단, 진행 중 방의 참가 정리, 공대장 권한 상실 시 승계, 완료 반복방의 다음 주
제외, 마지막1인 해산, 동일 방 중복 가입을 연결해서 조사한다. 정리 시점·실행 주체·확인 UI·동시 요청
처리와 조회 실패 상태를 설계로 확정한다. 인증 시 모든 방 일괄 순회·삭제를 기본안으로 가정하지 않는다.
현재 완료 반복방의 단건 정리/복구 기능은 재사용 후보이며 활성방 전체 문제를 해결한 것으로 보지 않는다.
다른 원정대·정상 그룹 가입·과거 완료 이력·새 소유자의 새 참가 데이터는 보존한다.

### 근거와 완료 기준

재인증 후 동일 캐릭터가 같은 방에 두 명으로 보인 사용자 관찰을 대표 조사 사례로 삼는다.
새 사용자 이용과 남은 참가자의 방 정상 이용을 모두 확인해야 완료다. 실제 중복 데이터가 어떤
소유권 차수/참가 상태인지 확인 전 자동 교체나 삭제 방법을 확정하지 않는다.
기존 반복방 자격 확인 버튼의 오류는 이 조사에서 실패 단계와 권한을 구분한다.

## 두 작업 외 관찰·검증 한계의 취급

그룹 반복방 동일 직업 자리 교환 오류는 재가입 후 성공했고 원인은 미확정이다. 별도 구현 작업으로
착수하지 않고 재발 시 조사할 관찰로 보존한다. 기존 반복방 확인 버튼의 13시 이후 결과는 미보고다.
이전 전체 테스트22건 실패/analyze51건 및 수동 인증 만료 취소 정책 기대 불일치는 기존 참고 기록으로
남기며 해결로 바꾸지 않는다. 이것들을 현재 예정 기능 두 개와 혼합하거나 숨기지 않는다.
테스트 실행 목록은 사용자 요청에 따라 문서에 추가하지 않고 채팅에서 제공한다.
