# NEXT WORK — 모집 브랜치의 실행 기준 정리와 실제 앱 연결 정정

## 직전 파트 — 작업 지시 문서 정상화 완료

브랜치 `feature/raid-recruitment-scheduling` 유지. 감사6716325a와 사용자 후속 설명을 반영해 초기 지시를 삭제하고 충돌 조항을 직접 교체했다. 이번 파트는 문서만 변경하며 실제 앱 활성화/기능코드·서버/DB·dev/main은 변경하지 않는다.

- 단일 Google 로그인/자체 Backend와 개발→베타→운영 자료 정책을 설계 선행 조건에 반영한다.
- 대단원 브랜치/소분류 커밋·푸시/대단원 통합을 구분하고 현재 브랜치에서 문서·지침·UI 파트도 처리한다. 채팅/회신/한 줄 수정 단위의 저장을 금지한다.
- 현재 계획/전체 지도에서 끝난 작업·해소된 대기를 제거하고 유효 후속만 아래에 둔다. 이전 원문은 [이력](history/instruction-state-before-normalization-2026-10-25.md), 완료 경과는 [DEV_LOG](DEV_LOG.md)에 보관한다.
- '꺼져도 기능 완료'라는 명시 규칙이 있다는 감사 설명은 정정한다. 실제 문제는 부품 구현/시험과 일반 앱 연결의 완료 기준이 분리되지 않았던 것이다.

검증: 기존 상충 조항 교체·초기 로그인/역할 제한 삭제·현재 문서의 이력 분리·유효 미완료 보존·내용/근거·링크/diffcheck를 확인했다. 기능코드 불변이므로 Flutter 시험/분석은 반복하지 않았다. 상세 완료 경과는 DEV_LOG이며 문서는 이 정상화 파트 하나로 보관한다.

## 다음 기능 파트 — 실제 앱 연결 정정 설계

1. 기존 A/B의 legacy 기본 유지/별도 활성화 계획을 현재 개발 방침으로 재사용하지 않는다. 일반 앱에서 새 확정 계약을 사용하는 경로와 생성→검색/내 목록→신청/가입→캐릭터 변경→일정/완료·해산→C/N의 관련 호출자를 대조한다.
2. 모드만 켜지 말고 아직 구계약인 쓰기/조회·원요청/ACK·권한/실제 주차 경계를 확인해 실제 앱 연결을 완성할 범위/순서를 정한다. 개발자료 보존을 위한 호환 작업과 제품에 필요한 재전송·회원격리를 구분한다.
3. 아래 후속을 포함한 최종 목표를 유지하며 첫 구현 파트를 선정한다. 앱/Backend 해당 흐름이 준비되면 사용자 수동1~5구간을 소수 항목으로 안내한다. 이미 전달한 방침/UX의 재확인은 요구하지 않는다.

이 절은 다음 설계 범위이며 이번 문서 파트에서 기능 수정까지 실행하지 않는다.
