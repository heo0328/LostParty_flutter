# NEXT WORK — 나이스단 설정·앱 실행 자동 갱신 설계 준비

2026-10-14. 사용자 지시로 전투력 연결 구간의 문서 최신화·커밋·dev 머지/push 후 2번 작업을 준비한다. 현재는 설계 착수 준비이며 자동 갱신 구현·새 Backend API 요청은 시작하지 않는다. 전투력 완료 이력은 DEV_LOG, [연결 계약22](../backend-migration/22-character-combat-power-flutter-contract.md), [Issue5 사용자 확인](https://github.com/heo0328/lostparty-backend/issues/5#issuecomment-6167529348)을 따른다.

## 현재 기준과 목표

- 전투력 수동 갱신/캐시 GET·로컬 카드/역할 우선·회원 격리의 신규3흐름은 사용자 정상 확인 완료. Backend 소비 SHA39188d5dca2d394f4e8b3fcbfe332274812285bf, Flutter 기능 구현과 최초 요청/회신 문서를 같은 구간으로 정리한다.
- 기존 [자동 갱신 계약](../architecture/CHARACTER_INTERACTION_AUTO_REFRESH_CONTRACT.md)의 확정 방향은 페이지 매진입이 아니라 앱 실행당1회다. 아이템레벨1700 공통상수·본부계정 전체 동일직업2명 이상 나이스단·허용OFF면제외/ON이면포함 기준을 재사용한다.
- 현재 BackendApp에는 시작/수동 runner와 나이스단 설정 Repository/playerId가 주입되지 않는다. 기존 클래스와 UI가 남아 있어도 실행/설정 저장 연결은 없다. 내 계정 initialize의 siblings 요약 갱신은 전투력/전체빌드 갱신이 아니다.
- 이전 시작 조정기는 전체Armory→분석→역할별Snapshot 저장이며 active 소유와 서버CharacterID를 요구한다. 새 전투력 API는 미인증 등록도 조회할 수 있다. 두 경로를 그대로 합치거나 이전 식별자를 새 회원 ID처럼 취급하지 않는다.

## 다음 설계 순서

1. 최신 관련 Issue에 미처리 요청이 있는지 먼저 확인한다. #5의 전투력 적용SHA/통합 인계를 마무리하고 이미 통과한3흐름은 반복 요구하지 않는다.
2. 나이스단 설정의 저장 위치/수명을 확정한다. 기존 제품 정책은 사용자 전체에 적용하는 로컬 설정이다. 신규 Backend회원 user_id를 구분키로 사용하는 로컬 저장과 원격 동기화 필요성을 대조하고, 원격 저장 요구가 없으면 새 API를 만들지 않는다. 구 Firebase Player ID/자료 이관은 없다. 초기 기본OFF·저장 실패/회원변경/재실행에서의 읽기 기준을 정리한다.
3. 앱 실행 1회 트리거와 실제 Router/DI를 설계한다. 인증/등록·로컬 로딩/첫 화면 준비와 비차단 실행 순서, 처음 guest에서 로그인하는 경우·회원 변경·재로그인/탭 재진입·백그라운드 복귀·중도 실패 시 재실행 여부를 명시한다. 구현 전에 한번 실행 가드의 범위를 확정한다.
4. 전투력 profile-only 갱신과 전체Armory/역할별Build 갱신 중 이번 복원 범위를 구분해 기록한다. 기존 역할Snapshot을 갱신해야 하는지, 현재서버 관찰값만 갱신하는지 결정하지 않은 채 자동 쓰기를 연결하지 않는다. 소유/서버ID 선행 조건은 각 경로의 현재 계약에 맞춰 판단한다.
5. 기존 NiceGroupPolicy/1700정책과 조정기·불변요청복구/20명·시간예산·캐시/미처리 UI를 재사용할 부분을 판별한다. 같은 캐릭터 중복요청, 수동/자동 충돌, 회원/late 응답, 나이스단 제외·실패 시 기존값/역할별값을 회귀 목록에 둔다.
6. 포함/제외·데이터흐름·설정 계약·검증/완료 조건을 먼저 문서로 확정한다. Backend 보완이 실제로 필요할 때만 협업 요청한다. 기능 구현과 신규 사용자 인수는 이후 해당 설계 범위에서 진행한다.
