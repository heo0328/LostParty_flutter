## 코드 조사로 확인된 사실

1. 3df755b 이후 준비 시작점 75bedb9까지 lib 변경은 없다. Rules 수정 중 Flutter 동기화 코드가 삭제됐다는 근거는 없다.
2. GroupLocalMemberDisplayLookup은 로컬 AccountRepository의 character.combatPower를 가져온다. 생성·신청·코드 가입 Repository에 연결되어 있다.
3. 그룹원 목록은 membership.combatPowerSnapshot을 우선하고 Character.combatPower를 보조로 읽는다.
4. 그룹 상세 진입 시 본인 membership만 로컬 값으로 self-refresh한다. 타인 membership을 대신 갱신하지 않는다.
5. self-refresh Repository는 예외를 삼킨다. 화면에서 실패와 정상 완료를 구분하기 어렵다. 로컬 null이 기존 숫자를 덮는 경로도 확인해야 한다.
6. 상세 인증 캐릭터 목록은 Character.combatPower를 읽지만 Character 최소 정보 동기화는 그 필드를 저장하지 않는다. membership 동기화와 다른 경로다.
7. 초대 수락·신청 승인은 요청의 Snapshot을 membership에 복사하므로, 요청 당시 누락과 본인 갱신 시점을 함께 확인한다.

위 내용은 조사 사실이다. 신규 그룹의 실제 누락 원인이 하나로 확정된 상태는 아니다.

## 다음 실행 순서

1. **재현과 값 추적**: 로컬 전투력 → 생성/가입 명령 → membership Snapshot → self-refresh → 목록/상세 표시를 연결해 검토한다. 정상 기존 그룹과 신규 그룹 차이를 확인할 수 있는 최소 진단을 마련한다. 토큰·AuthUid·민감 데이터는 로그에 남기지 않는다.
2. **최소 수정**: 숫자가 있는데 저장·표시에 빠지는 경로를 고친다. null 또는 일시적 조회 실패로 기존 유효 전투력을 지우지 않도록 검토한다. 갱신 실패를 조회 성공으로 오인하지 않도록 처리하되 그룹 목록 자체를 막지 않는다.
3. **상세 데이터 연결**: 회원 대표 캐릭터 Snapshot과 전체 인증 캐릭터의 전투력을 구분한다. 대표 전투력을 다른 캐릭터에 복사하지 않는다. 서버 Character 동기화가 필요하면 해당 필드·소유자 권한·갱신 경로만 최소 확장한다. 데이터 계약/스키마 변경은 먼저 영향과 대안을 정리하고 구현 범위를 확정한다. 화면에서 외부 API를 직접 호출하거나 임의로 전체 캐릭터 조회를 추가하지 않는다.
4. **회귀 검증**: 로컬 숫자/없음, 기존 서버 숫자 보존, 신규 생성, 초대 수락·신청 승인·코드 가입, 본인 갱신 성공/실패, 대표 및 다른 인증 캐릭터 상세를 검증한다. 실제 실패를 재현하는 회귀 테스트를 우선하며 구현 문자열 검사만으로 완료를 주장하지 않는다.
5. **실기기 확인**: 사용자에게 신규 그룹 본인·그룹원 목록/상세, 기존 그룹 유지, 탈퇴·재가입의 짧은 체크리스트를 제공한다. 상대 사용자 데이터는 상대 앱의 정상 동기화 시점을 구분한다.

## 범위와 제외

- 포함: 그룹 전투력 표시 누락, 관련 Snapshot 저장·갱신·조회, 필요한 최소 계정 동기화 연결, 표적 회귀 테스트.
- 제외: Rules 전체 최적화 R0~R6, 프로브 배포, 레이드 정책 변경, 그룹 전용 모집/채팅/필터, 소셜 로그인, 새 유료 서비스, 기존 데이터 전체 재작성, 브랜치 삭제·강제 푸시.
- 기존 레이드 흐름과 그룹 생성·가입·탈퇴 권한을 유지한다. 전투력 표시를 고치기 위해 권한 검증을 완화하지 않는다.
- Rules 배포는 지금 하지 않는다. 실제 Rules 수정이 필요해진 뒤 사용자에게 배포 명령과 확인 항목을 안내하고 결과를 확인한다.
- 실기기 조작은 사용자가 수행한다. 현재 준비 요청은 자동 기능 구현·main 병합 권한으로 확대하지 않는다.
