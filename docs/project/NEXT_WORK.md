# NEXT WORK

## 현재 단계

제품 결정과 구현 전 계약은 완료됐다. 상세 정책은 [`../architecture/ACTIVITY_CHARACTER_AND_RAID_FILTER_CONTRACT.md`](../architecture/ACTIVITY_CHARACTER_AND_RAID_FILTER_CONTRACT.md)가 기준이다.

현재 실행 대상은 **앱에서 사용할 캐릭터 지정(활동 Character)** 이다. 그룹 전용 레이드 자격 박탈과 레이드 현황 필터보다 먼저 이 구조를 완료한다.

바로 구현하는 단위는 **A만** 이다. A가 `main`에 통합되기 전에 B 이후 코드를 수정하지 않는다.

## 구현 방식

이미 협의된 작업 사이클과 계약 규칙을 그대로 따른다. 새 구현 방식을 만들지 않는다.

- 한 작업 단위는 독립 브랜치에서만 구현한다. `main`에서 직접 수정하지 않는다.
- 한 채팅·한 브랜치에는 아래 표의 한 단위만 넣는다. 다음 단위 코드를 미리 넣지 않는다.
- 구현 시작 전에 관련 코드·Rules·테스트를 읽어 문서와 실제 구현을 대조한다.
- 구현 중에는 변경 영역의 표적 테스트만 실행한다.
- 저장 스키마·공용 Domain·여러 feature가 함께 바뀌는 단위의 최종 상태에서만 `flutter analyze --no-pub`와 전체 `flutter test --no-pub`를 한 번씩 실행한다.
- 실기기 확인이 필요한 단위는 표적 테스트 통과 후 사용자 확인을 기다린다. 실기기 확인은 자동 테스트를 대체하지 않는다.
- 문서만 바꾼 경우에는 Flutter 검증을 다시 하지 않는다.
- Rules 배포, 테스트 데이터 실제 삭제·초기화, Emulator·FCM·유료 기능은 해당 단위에 명시되거나 사용자가 지시하기 전에는 하지 않는다.
- 기존 MVVM, feature-first, Repository, 클라이언트 Transaction + Security Rules 구조를 유지한다.
- 활동 Character 불변조건은 UI·Repository·Rules에서 같이 검증한다. 한 계층만 막았다고 완료하지 않는다.
- 과거 사용자 자동 마이그레이션은 하지 않는다. 현재 데이터는 사용자 단독 테스트 데이터이므로 새 기준에 맞게 다시 설정할 수 있다.

## 작업 순서

순서는 의존성 때문이다. 뒤 단계가 앞 단계의 저장 의미와 권한을 사용한다.

```text
A 저장·Domain·Rules
→ B 캐릭터 관리 UI
→ C1 레이드 후보 적용
→ C2 그룹 후보·전투력 적용
→ D1 그룹 전용 자격 박탈
→ D2 진행 중 기본 필터·페이징
→ D3 그룹원·Character 필터
→ E 실기기·회귀 확인
```

| 순서 | 단위 | 목적 | 시작 조건 |
|---|---|---|---|
| 1 | A | 활동 Character를 서버에 저장하고 권한으로 강제한다 | 현재 실행 단위 |
| 2 | B | 사용자가 앱에서 쓸 캐릭터를 지정·저장한다 | A가 `main`에 통합된 뒤 |
| 3 | C1 | 새 레이드 생성·신청·참가 Character 변경 후보를 활동 Character로 제한한다 | B 완료 후 |
| 4 | C2 | 그룹 Snapshot·그룹원 Character 목록·일반 전투력 보강을 활동 Character로 제한한다 | C1 완료 후 |
| 5 | D1 | 그룹 탈퇴·추방·해산 시 그룹 전용 레이드 자격을 제한적으로 정리한다 | C2 완료 후 |
| 6 | D2 | 진행 중 공개 조건·레이드·난이도 필터와 20개 페이징 안전성을 구현한다 | D1 완료 후 |
| 7 | D3 | 그룹원·Character 필터, 실시간 일치 개수, 필터 상태 보존을 구현한다 | D2 완료 후 |
| 8 | E | 자동 회귀와 실기기에서 A~D3 누적 결과를 확인한다 | D3 완료 후 |

A+B가 “앱에서 사용할 캐릭터 지정”의 구현 범위다. C부터는 그 지정을 다른 기능이 소비하거나, 원래 남아 있던 후속 기능이다.

## 단위별 구현 범위

### A — 저장 위치·Domain·Rules

구현 시작 전 최신 Character DTO, Firestore 경로, Rules, 대표 Character 동기화 코드를 대조한다. `activityEnabled` 의미를 `표시 여부`가 아닌 `앱 활동 허용`으로 유지하고, 현재 Player의 active 소유 관계와 함께 검증할 수 있는 저장 위치를 확정한다.

포함:

- 현재 Player가 active 소유한 Character의 `activityEnabled` 저장 위치 확정
- 활동 Character 전체 최종 상태를 저장하는 Domain 명령·DTO·Repository 경계
- 최소 1명, 대표 Character 포함, active 소유권, 허용 필드만 변경하는 검증
- 복수 변경 중 0명이나 비활동 대표가 보이지 않게 하는 원자 저장
- 현재 사용자 단독 테스트 데이터를 새 기준으로 재설정하는 절차 문서화
- Repository·Rules 계약 테스트

제외:

- 캐릭터 관리 UI
- 레이드·그룹 후보 필터링
- 전투력 동기화 변경
- 그룹 전용 레이드 자격 박탈
- 레이드 현황 필터
- Rules 배포
- 테스트 데이터 실제 삭제·초기화

완료 조건:

- 실제 코드와 Rules를 근거로 저장 경로와 쓰기 단위를 확정한다.
- 활동 Character 0명과 비활동 대표 Character를 Repository와 Rules가 거절한다.
- 인증·소유권 필드는 활동 설정 명령으로 변경되지 않는다.
- 표적 테스트와 `flutter analyze --no-pub`이 통과한다.

### B — 캐릭터 관리 UI

A의 저장 명령을 화면에서만 사용한다. 레이드·그룹 후보 소비 경로는 아직 바꾸지 않는다.

포함:

- 인증 원정대 전체의 Character명 중심 선택 카드와 `선택 수 / 전체 수`
- 선택·해제·대표·순서·표시 개수를 로컬 초안에 즉시 반영하고 `저장`에서 한 번만 서버에 쓴다
- 대표 Character 선택 비활성화, 마지막 1명 해제 차단, 0명 저장 요청 거부
- 선택된 Character만 대표 지정·드래그 순서 목록에 표시
- 기존 표시 여부 체크박스 제거
- 메인 화면 표시 개수를 1~활동 Character 수로 제한하고, 활동 수가 줄어들면 표시 개수를 자동 축소
- 저장 중 중복 요청 차단, 실패 시 서버 미반영 안내, 로컬 영구 상태를 성공으로 확정하지 않음
- ViewModel·관련 Widget 테스트

제외:

- 레이드 생성·신청·참가 Character 변경 후보 교체
- 그룹 Snapshot·그룹원 목록·전투력 보강 범위 변경
- 레이드 현황 필터
- Rules 배포

완료 조건:

- 캐릭터 관리 화면이 전체 선택 → 대표·순서 → 표시 개수 → 취소·저장 흐름을 따른다.
- 대표 해제와 마지막 1명 해제가 UI에서 막히고, 0명 저장은 요청 자체가 나가지 않는다.
- 저장 성공 후에만 서버·재진입 상태가 바뀐다.

### C1 — 레이드 후보 적용

포함:

- 새 레이드 생성의 파티장 Character 후보
- 신청·참가·참가 Character 변경 후보
- 기존 참가 Character를 비활성화해도 membership·Claim·assignment·완료 Snapshot을 유지하는 회귀 테스트

제외:

- 원정대 검색·게임 계정 인증·소유권 방어/이전
- 그룹 목록·전투력 보강
- 자동 레이드 탈퇴

완료 조건:

- 새 레이드 선택 후보에 활동 Character만 나타난다.
- 이미 참가 중인 비활동 Character는 해당 방에서 유지된다.

### C2 — 그룹 후보와 전투력 적용

포함:

- 그룹 생성·가입 표시 Snapshot 후보
- 그룹 상세의 그룹원 Character 목록
- 내 계정 진입 등의 일반 전투력 상세 조회와 서버 보강 대상을 활동 Character로 제한
- 현재 참가 데이터 보존에 필요한 Snapshot을 null로 덮어쓰지 않음

제외:

- 그룹 전용 레이드 자격 박탈
- 레이드 현황 필터
- 인증·소유권 내부 값의 그룹원 공개

완료 조건:

- 그룹의 새 선택 후보와 일반 전투력 보강이 활동 Character만 사용한다.
- 비활동 Character의 기존 참가 Snapshot은 유지된다.

### D1 — 그룹 전용 자격 박탈

포함:

- 그룹 탈퇴·추방·해산 시 그룹 전용 레이드의 참가 자격 상실과 제한적 정리
- 해당 레이드에 정상 참가 중인 유효 그룹원도 정리 요청 가능
- 같은 원자 작업에서 요청자 자격과 대상의 실제 자격 상실 재검증

제외:

- 전체 공개 상태인 그룹 연결 레이드의 참가 자격 박탈
- 활동 Character 해제를 그룹 자격 상실과 동일 취급
- `recruitments` list에 그룹 membership `exists`나 `visibility==group` 쿼리 추가

완료 조건:

- 그룹 전용 레이드에서만 자격 상실 정리가 동작한다.
- 전체 공개 그룹 연결 레이드는 그룹 탈퇴만으로 기존 참가 자격을 잃지 않는다.

### D2 — 진행 중 기본 필터와 페이징

포함:

- 레이드 현황 `진행 중`의 공개 조건·레이드·난이도 필터
- 서버 20개 페이징과 원본 목록 유지
- 빈 필터 결과, 중복 스크롤, 늦은 응답, 통신 재시도 방어

제외:

- 그룹원·Character 필터
- 완료 기록 필터
- 서버 집계 기반 전체 결과 수
- 신청 중 탭 필터

완료 조건:

- 공개 조건 기본값은 전체·일반 공개·그룹 공개가 모두 선택된 상태다.
- 일반·그룹 공개가 모두 해제되려 하면 전체로 복귀한다.
- 레이드와 난이도는 차원 내부 OR, 차원 사이 AND다.
- 필터 일치 0개를 서버 데이터 종료로 오인하지 않는다.

### D3 — 그룹원·Character 필터

포함:

- 그룹 공개에서 그룹원 선택. 현재 Player는 후보에서 제외
- 활동 Character만 새 필터 후보로 표시
- 한 사용자의 복수 Character는 OR, 서로 다른 사용자는 AND
- 필터 창의 실시간 일치 개수. 다음 페이지가 있으면 `현재 N개`
- 필터 상태 보존

제외:

- 서버 쿼리 권한 변경
- 비활동이지만 이미 참가 중인 Character를 필터 판정에서 제거
- 구현 직전 재확인이 끝나기 전의 코드 수정

완료 조건:

- 사용자 내부 OR·사용자 사이 AND가 자동 테스트로 고정된다.
- 칩 조작은 서버 요청을 만들지 않고 이미 받은 원본 목록만 좁힌다.

### E — 회귀와 실기기 확인

포함:

- 저장 스키마와 여러 feature가 누적 변경된 최종 상태의 `flutter analyze --no-pub`와 전체 `flutter test --no-pub`
- 캐릭터 관리 저장, 재진입 유지, 레이드 후보 제한, 그룹원 필터와 결과 개수의 실기기 확인

제외:

- 새 기능 추가
- 장애·권한 실패 등 개별 시나리오까지 실기기로 확대하는 것을 기본 완료 조건으로 두지 않음

## 확정된 제품 기준

아래는 이미 확정된 내용이며 구현 중 재협의 대상이 아니다. 상세는 계약 문서를 따른다.

### 활동 Character

- 인증 원정대 전체는 검색·인증·소유권을 위해 유지한다.
- 활동 Character만 새 레이드·그룹 후보와 일반 전투력 동기화에 사용한다.
- 최소 1명이며 대표 Character는 항상 활동 상태다.
- 대표 Character의 활동 선택은 비활성화하고 마지막 1명 해제를 로컬에서 막는다.
- 0명 상태는 저장 요청 전, Repository와 Rules에서 다시 거절한다.
- 기존 참가 Character를 비활성화해도 membership·Claim·완료 기록은 유지한다.
- 과거 사용자 데이터 자동 마이그레이션은 하지 않는다.

### 캐릭터 관리 화면

- 상단: 전체 인증 원정대의 Character명 중심 선택 카드와 선택 수
- 중단: 선택된 Character만 대표 지정·드래그 순서 관리
- 하단: 메인 화면 표시 개수와 변경 취소·저장
- 선택은 로컬 초안에 즉시 반영하고 서버에는 저장 시 한 번 반영한다.

### 레이드 현황 진행 중 필터

- `진행 중 / 신청 중 / 완료 기록` 전환과 목록 사이에 `레이드 필터: 모든 레이드`를 둔다.
- 공개 조건 기본값은 전체·일반 공개·그룹 공개가 모두 체크된 상태다.
- 일반·그룹 공개가 모두 해제되려 하면 전체로 복귀한다.
- 레이드와 난이도는 차원 내부 OR, 차원 사이는 AND다.
- 그룹원 필터에서 현재 Player는 제외한다.
- 한 사용자의 복수 Character는 OR, 서로 다른 사용자는 AND다.
- 필터는 서버 20개 페이징 결과에 로컬로 적용하고 다음 페이지가 있으면 개수를 `현재 N개`로 표시한다.

### 그룹 전용 자격 상실 정리

- 그룹장뿐 아니라 해당 레이드에 정상 참가 중인 유효 그룹원도 정리를 요청할 수 있다.
- 서버는 요청자 자격과 대상의 실제 그룹 자격 상실을 같은 원자 작업에서 재검증한다.
- 전체 공개 상태인 그룹 연결 레이드는 그룹 탈퇴만으로 기존 참가 자격을 박탈하지 않는다.

## 전체에서 제외하는 범위

- 과거 운영 사용자 데이터 자동 마이그레이션
- 인증 Character 삭제 또는 소유권 계약 변경
