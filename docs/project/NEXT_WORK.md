# NEXT WORK — 레이드 모집·일정의 현재 실행 기준

## 현재 단계 — 모집 연결 구현 보관 후 사용자 디바이스 인수

참가 명령 재시작 복구 파트는 일반 앱에 연결하고 자동 검증을 마쳤다. 기준은 `feature/raid-recruitment-scheduling`의 0fe8846f 이후 변경이며 Backend d95e3827 / beta-recruitment-wire-2를 유지한다. 구현·복구 수명/검증의 장기 근거는 설계37 §37.76, 완료 경과는 DEV_LOG다.

관련 모집 연결(생성·기본표시·후보/신청/승인·변경·일정/그래프·메모/문구·필터·참가 명령 영속 복구)의 미연결 후속을 대조했고 이번 복구까지 연결했다. 다음은 새 설계를 반복하는 단계가 아니라 실제 개발서버/회원과 사용자 기기로 전체 흐름을 인수하는 단계다. Backend 개발반영 인계는 Issue13 [6396368027](https://github.com/heo0328/lostparty-backend/issues/13#issuecomment-6396368027), 이번 구현 인계는 [Issue13](https://github.com/heo0328/lostparty-backend/issues/13)에서 추적한다. 추가 서버 계약 변경/배포 대기를 만들지 않는다.

### 다음 순서와 확인 범위

1. 사용자가 빌드·설치·기기 조작을 수행한다. 기존 테스트 분량 구분인 ①생성 ②신청/가입 ③방내 변경/일정 ④완료/탈퇴/해산 ⑤이번주/다음주 독립 순으로 소수 항목씩 안내한다. 이 구분은 연결된 다른 기능을 구현/영향 분석에서 배제하는 기준이 아니다.
2. 첫 확인은 C/N 단독·동시 생성, 주차별 기본 출발/조기조율·모집번호, 성공한 주차 상세 진입과 새 생성 진입이다. 이후 후보/역할·메모/승인 → 그래프/내 일정 갱신·제안/응답 → 완료·탈퇴·승계/해산·기록 → 양 주차 독립을 이어 확인한다.
3. 복구는 통신 결과를 받지 못한 요청이 있는 경우 앱 재실행 후 자동 전송 없이 기존 배너에서 같은 요청을 확인하는지, 성공 뒤 중복 이동/변경이 없는지 확인한다. 재현이 어려운 저장 실패·늦은 응답·24h/손상/회원환경 경계는 자동 시험 결과를 사용하며 사용자에게 무리하게 재현을 요구하지 않는다.
4. 결과별 직접 영향만 수정/재확인하고 관련 코드·검증·문서를 한 파트로 보관한다. 사용자 인수 전 전체 기능/성능/메모리 통과로 선언하지 않는다. Penpot02 구현 화면 최신화는 실제 대조 이후다.

완료 검증: 모집 기능1179PASS(당시 복구 시험36 포함). 최종 배너 상태 안내·거절 복원 뒤 새 요청 성공 보완 후 복구/일정 직접64PASS 재확인(합산하지 않음). 변경10Dart 분석0, 최종3Dart 재분석0·포맷/diff 검토. 생성·문구의 기존 저장 형식/원요청·DB 테이블/계정DB는 유지했다.

웹소켓·BUG-025·비활성 IF-001·별도 그룹/계정/출시 작업은 아래 후속에서 분리한다. 서버/DB 배포·개발자료 삭제/변환·dev/main 통합은 현재 파트에 포함하지 않는다.
