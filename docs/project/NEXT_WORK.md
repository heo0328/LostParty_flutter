## 2026-09-07 재인증 이후 생성·인증 연쇄 장애 진단

### 확인된 사용자 증상 순서

1. 잘못 연결된 계정이 있던 상태에서 게임 계정을 재인증했다.
2. 재인증 전에는 파티 모집의 내 Character 후보가 없었으나, 재인증 후 후보 목록이 다시 표시됐다.
3. 그룹 생성과 레이드 모집 생성은 `계정 정보를 확인해 주세요` Alert로 계속 차단됐다.
4. 내 계정은 로컬의 `serverOwnershipStatus == active`와 서버 ID를 기준으로 인증 완료 표시를 계속 유지했다.
5. 게임 계정 인증을 다시 시작하거나 확인하는 과정에서 차례로 `인증 요청을 처리하지 못했습니다`, `인증 시간이 만료되었습니다`, `캐릭터 또는 장비 정보를 처리할 수 없습니다`가 표시됐다.
6. 마지막 재시도 시 Character는 이전 Challenge 수행을 위해 일부 장비를 해제한 상태였다.

### 코드에서 확인된 동작

- 파티·그룹 후보는 로컬 계정에 active 소유권 상태와 서버 Character ID가 있으면 다시 노출될 수 있다. 후보 노출만으로 서버의 Player·게임 계정·소유권·Character 연결 전체가 정상이라는 뜻은 아니다.
- 내 계정의 인증 완료 표시는 로컬 바인딩을 기준으로 하며 서버 자료 삭제를 자동 반영하지 않는다. 따라서 현재 표시와 서버 생성 가능 상태가 서로 다를 수 있다.
- 그룹 생성은 `authBindings/{uid}` → `players/{playerId}` active → `characters/{characterId}` → `playerGameAccounts/{playerId_gameAccountId}` active를 Transaction 안에서 다시 확인한다. 이 중 하나가 없거나 맞지 않으면 새 Alert 대상 결과가 된다.
- 레이드 모집 생성도 auth binding과 서버 Character 소유자를 다시 확인한다. 로컬 후보가 보여도 이 검증에서 실패할 수 있다.
- 인증 시작은 Lost Ark API에서 원정대와 Armory를 동시에 읽고 **무기·투구·어깨·상의·하의·장갑 6부위가 모두 장착된 기준 Snapshot**을 요구한다. 장비가 하나라도 빠진 상태에서 새 인증을 시작하면 `FormatException('Incomplete equipment.')`이 발생한다.
- 현재 화면은 모든 `FormatException`을 `캐릭터 또는 장비 정보를 처리할 수 없습니다`로 합쳐 표시한다. 따라서 이번 마지막 메시지는 장비 미착용과 일치하지만 사용자에게 필요한 행동을 설명하지 못한다.
- Challenge는 10분 후 만료된다. 소유권 Claim Transaction이 예외로 끝나면 `_activeChallenge`가 즉시 정리되지 않아 같은 화면에서 다시 확인할 수 있고, 시간이 지난 뒤에는 `expired` 결과가 나올 수 있다.
- 인증의 `_claimOwnership()`은 `authBindings` 존재와 playerId 문자열만 확인하고 연결된 Player 문서의 존재·active 상태는 확인하지 않는다. 반면 그룹 생성은 Player 문서를 확인하므로 인증 일부가 진행돼도 그룹 생성은 계속 실패할 수 있다.
- `characterIdentityClaims`가 존재하면 해당 Claim의 `gameAccountId`를 재사용한다. Claim이 가리키는 `gameAccounts/{id}`가 삭제된 경우 `Claimed game account does not exist.` StateError로 인증이 중단된다.
- 위 StateError를 포함한 일반 예외는 모두 `인증 요청을 처리하지 못했습니다`로 뭉쳐지고 로그도 남지 않으므로, 현재 메시지만으로 정확히 어느 서버 연결이 끊겼는지는 확정할 수 없다.

### 가능성이 높은 서버 상태

아래는 코드와 증상으로부터의 추정이며 Firestore 실측 전 확정하지 않는다.

1. 현재 `authBindings/{uid}`는 남아 있으나 연결된 `players/{playerId}`가 없거나 비활성이다. 실행 중 앱은 메모리의 PlayerSession과 로컬 자료로 화면을 계속 열 수 있지만 그룹 생성은 실패한다.
2. 원정대 Character의 `characterIdentityClaims` 일부가 남아 있으나 연결된 `gameAccounts` 또는 `characters` 문서가 삭제돼 고아 참조가 됐다. 이 경우 새 인증의 소유권 Claim Transaction이 일반 StateError로 실패할 수 있다.
3. 여러 Character Claim이 서로 다른 gameAccountId를 가리키는 충돌 상태일 수 있다. 이 경우도 현재 UI에는 동일한 일반 실패 문구만 표시된다.
4. 인증 서버 쓰기는 성공했지만 이후 로컬 `_saveBinding()`에서 최신 원정대와 기존 로컬 Character가 일치하지 않아 실패했을 가능성도 있다. 이 경우 서버와 로컬이 부분적으로 갱신돼 다음 시도의 상태가 더 복잡해질 수 있다.

### 중요한 정정

- 앱 재설치나 앱 데이터 삭제는 Firebase 익명 UID와 로컬 DB를 새로 만들 수 있지만 서버의 고아 `characterIdentityClaims`·`gameAccounts` 참조까지 삭제하지 않는다.
- 따라서 고아 Claim이 원인이라면 기존 Alert의 재설치·앱 데이터 삭제 안내만으로 해결되지 않을 수 있다. 서버 관계를 먼저 정리하거나 인증 로직이 고아 Claim을 안전하게 처리해야 한다.
- 현재 Alert가 오류를 새로 만든 것은 아니지만, 여러 불일치 결과를 같은 안내로 합쳐 실제 원인과 필요한 조치를 충분히 설명하지 못한다. 디바이스 검증 완료로 처리하지 않는다.

### 수정 전 필수 확인

개인정보 값은 문서에 기록하지 않고 존재 여부·상태·서로 참조하는 ID 일치 여부만 확인한다.

1. 현재 Firebase Auth UID에 대응하는 `authBindings/{uid}`의 존재, status, playerId.
2. 해당 `players/{playerId}`의 존재와 active 상태.
3. 원정대 각 Character의 `characterIdentityClaims/{serverName+characterName key}` 존재 및 gameAccountId·characterId.
4. Claim이 가리키는 `gameAccounts/{gameAccountId}`와 `characters/{characterId}`의 존재 및 ownerPlayerId 일치.
5. `playerGameAccounts/{playerId_gameAccountId}` 존재와 active 상태.
6. 동일 원정대 Claim들이 하나의 gameAccountId로 모이는지 여부.
7. 인증 실패 순간의 실제 예외 종류. 현재 코드에는 일반 예외 로그가 없으므로 재현 전 최소 진단 로그가 필요할 수 있다.

### 확인 후 필요한 수정 후보

## 2026-09-07 차후 작업 — 서버 데이터 무결성·복구 절차 점검

- 희박한 예외만을 위한 새 전역 상태 관리 계층

### 차후 점검 목록 — 서버 데이터 무결성

- 저장소의 현재 `firestore.rules`는 `gameAccounts`, `characters`, `characterIdentityClaims`에 `allow read, write: if signedIn()`을 사용한다. 현재 규칙 문구만 보면 익명 로그인을 포함한 모든 인증 사용자의 생성·수정·삭제 범위가 넓다.
- 먼저 이 규칙이 실제 운영 프로젝트에 배포된 버전과 같은지 확인한다. 최근 Rules 배포는 HTTP 503으로 실패한 이력이 있으므로 저장소 파일만 보고 운영 상태를 단정하지 않는다.
- 운영 Rules에도 동일하다면 정상 클라이언트가 삭제 명령을 제공하지 않더라도 변조된 클라이언트에서 다른 사용자의 계정·Character·Claim을 덮어쓰거나 삭제할 수 있는지 Emulator로 검증한다.
- 다음 문서들의 생성·수정·삭제 주체와 불변 조건을 정한다.
  - `gameAccounts/{gameAccountId}`: 현재 소유 Player 또는 검증 Challenge Transaction만 변경 가능해야 하는지
  - `characters/{characterId}`: 연결된 원정대 소유권과 인증된 Claim을 만족할 때만 변경 가능한지
  - `characterIdentityClaims/{claimId}`: Character 정체성 키와 gameAccountId·characterId 연결을 임의 변경·삭제할 수 없어야 하는지
  - `playerGameAccounts/{playerId_gameAccountId}`: 현재 Player와 계정 소유권 관계 밖의 쓰기를 차단하는지
- Rules를 강화할 때는 현재 게임 계정 인증 Transaction, 소유권 이전, 원정대 최신화, 대표·활동 Character, 그룹·레이드 생성 경로가 필요한 쓰기를 계속 수행할 수 있는지 함께 검증한다.

- 진행 중 레이드 목록은 `watchActiveRaids()` 스트림을 사용하지만 카드 배지의 원본은 이 스트림에 포함되지 않는다.

6. 배지의 목적이 실시간 알림인지, 다음 화면 확인을 돕는 주기적 상태 표시인지 제품 기준을 정한다.

### 비교할 구현 후보 — 아직 선택하지 않음

**후보 A: 사용자 이벤트 컬렉션 하나만 전면 실시간 구독**

- 참가방별 Listener를 만들지 않고 `players/{playerId}/events` 하나만 레이드 현황이 활성화된 동안 구독한다.

**후보 B: 화면 생명주기 기반 단발 sync**

- 레이드 현황 재진입, 하단 탭 재선택, 앱 foreground 복귀, 상세에서 목록 복귀 같은 제한된 시점에 기존 `sync()`를 호출한다.
- 구조 변경과 상시 구독 비용은 작지만 사용자가 화면을 계속 보고 있을 때는 새 배지가 늦게 나타난다.
- 여러 생명주기 이벤트가 겹칠 때 single-flight와 최소 재호출 간격이 필요한지 판단해야 한다.

**후보 C: 제한된 주기 polling**

- 레이드 현황이 전면에 있을 때만 일정 간격으로 사용자 이벤트를 동기화한다.
- 실시간 Listener보다 구현이 단순할 수 있으나 갱신 간격만큼 지연되고 불필요한 전체 조회가 반복될 수 있다.
- 앱 백그라운드·화면 dispose 시 즉시 중지, 서버 오류 시 backoff, 기존 조회가 전체 이벤트를 매번 읽는 문제를 함께 해결해야 한다.

**후보 D: 명시적 사용자 새로고침**

- pull-to-refresh 또는 작은 갱신 액션에서 기존 event sync와 unread 재계산을 수행한다.
- 성능 영향과 구조 변경이 가장 작지만 알림 배지가 자동으로 나타난다는 기대와 어긋날 수 있다.

**후보 E: 서버에 방별 unread 집계 또는 푸시 신호 추가**

- 이벤트 생성과 동시에 Player 단위 방별 count를 갱신하거나 FCM 등으로 갱신 신호를 보낸다.
- 조회 효율 또는 백그라운드 알림에는 유리할 수 있지만 서버 스키마·Rules·동시성·읽음 동기화 범위가 크게 늘어나므로 현재의 최소 변경 요구와 맞는지 먼저 판단해야 한다.

### 기술 조사 항목

- 사용자별 events 컬렉션의 실제 평균·최대 문서 수, 만료 및 삭제 정책, 한 이벤트가 수신자별로 몇 개 생성되는지 확인한다.
- 기존 `.get()`이 매 sync마다 전체 이벤트를 다시 읽는지, 마지막 동기화 시각 또는 document cursor 이후 증분 조회로 바꿀 수 있는지 확인한다.
- 단일 사용자 events Listener로 필요한 네 `isRoomAttentionEvent` 유형만 서버에서 필터링할 수 있는지와 추가 인덱스 필요 여부를 확인한다.
- Drift receipt 저장 후 UI가 DB watch를 사용하지 않고 수동 `_refreshUnread()`에 의존하는 현재 경계를 확인한다. Firestore 구독과 별개로 로컬 count 반응형 구독만 추가하는 경우의 범위를 비교한다.
- 진행 중 카드 목록이 변경될 때 현재 방별 count Map과 사라진 모집방 이벤트를 어떻게 처리할지 확인한다.
- 상세 진입의 sync → 해당 방 읽음 처리 → 목록 복귀 순서에서 race와 순간적인 잘못된 badge 표시가 없는지 확인한다.
- offline cache, 앱 foreground 복귀, Listener 재연결, 동일 eventId 멱등 저장이 기존 오프라인 표시와 충돌하지 않는지 확인한다.
- 후보별 Firestore 읽기 수, 배터리, 메모리, 코드 복잡도와 예상 갱신 지연을 같은 조건으로 비교한다.

### 1. 로컬 계정과 서버 데이터 불일치 표시

- 정상 서버 데이터 상태의 디바이스 흐름은 통과했다. 서버 데이터가 삭제되거나 관계가 끊긴 예외 기기만 별도 대상으로 다룬다.
- 내 계정의 `계정 인증 완료`와 수동 인증 차단은 로컬 `serverOwnershipStatus == active`를 기준으로 하지만, 그룹·레이드 생성은 서버의 authBinding·Player·Character·playerGameAccount 관계를 다시 검사해 표시가 서로 어긋날 수 있다.
- 서버 조회가 성공했고 필요한 관계가 실제로 없을 때만 `서버 데이터 불일치 · 앱 재실행 또는 재인증 필요`를 표시하는 방향을 협의한다. 오프라인·503·permission-denied는 불일치로 판정하지 않는다.
- 수동 인증의 `이미 인증한 계정` 차단을 로컬 active만으로 유지할지, 확인된 서버 불일치에서는 재인증 안내로 교체할지 정한다. Player·소유권 자동 복구와 자동 로컬 삭제는 이번 협의에 포함하지 않는다.

- 내 계정은 인증 완료 대신 `서버 데이터 불일치 · 앱 재실행 또는 재인증 필요`를 표시하고, 수동 인증 화면은 등록된 원정대 Character를 그대로 선택해 요청할 수 있게 했다.
- 일반 장비 인증과 운영자 승인 수동 인증은 Character Claim이 가리키는 `gameAccount`만 삭제된 고아 상태에서도 같은 ID로 계정·Character·소유관계를 재생성한다. 정상 소유와 타인 소유 흐름은 유지한다.

- 로컬 연결 실패는 같은 화면 재빌드에서 무한 반복하지 않고 한 번만 안내하며, 화면을 다시 열었을 때 재시도한다. 관련 표적 테스트 46개와 전체 테스트 928개, 변경 파일 정적 분석이 통과했다.

- Firebase Authentication 사용자를 콘솔에서 삭제해도 기존 Firestore `authBindings`는 Rules상 자동 삭제·재연결되지 않는 고아 기록으로 남을 수 있다. 새 UID는 자기 문서 ID의 새 binding을 만들며 과거 binding을 사용할 수 없다. 이 예외는 이번 로컬 서버 ID 복구와 별개이며, 현재 정책대로 앱 데이터 삭제 후 새 익명 사용자 생성 및 필요 시 소유권 이전 인증으로 복구한다.
- 문제 기기에 수정 빌드를 설치한 뒤 추가 인증 절차 없이 서버 상태가 `active`로 복구됐고 그룹 생성과 레이드 모집 생성도 성공했다. 서버 관계 정상·로컬 상태 불일치 사례의 실기기 검증을 통과로 판정한다.

## 2026-09-09 차후 작업 — 주차 경계와 레이드 회차 전환 전수 점검

### 추천 구현 방향

- **채택:** 최초 접근 시 방 단위 지연 전환. 별도 예약 서버 없이 앱 사용자의 정상 조회·명령 흐름이 만료된 방을 발견하면 보정한다.
- 모든 진입점은 하나의 Reconciler를 사용하고 한 화면의 중복 요청은 single-flight로 합친다.
- Rules는 `request.time >= cycleEndsAt`, 기존 cycle/status/revision, 정확한 다음 cycle 경계와 허용 필드만 검증한다. 접근 권한이 있는 어떤 사용자가 먼저 실행해도 결과가 같아야 한다.
- 회차 기록은 `cycles/{oldCycleKey}`에 고정하고 반복방 recruitment만 새 `currentCycleKey`로 이동한다. 이전 회차 기록과 현재 활성 방을 혼동하지 않는다.
- 보정 실패는 해당 방 하나로 격리하고 다른 목록과 새 주차 활동을 막지 않는다. 다음 접근에서 다시 시도한다.
- 향후 Blaze 전환 시에도 같은 방 단위 Reconciler를 예약 함수에서 재사용할 수 있게 전환 계약과 실행 주체를 분리한다.

### 멱등 조건 요약

- 전환 식별 기준은 `recruitmentId + oldCycleKey`다.
- recruitment가 이미 다음 주차면 성공 no-op로 처리한다.
- `cycles/{oldCycleKey}`에 종료 기록이 있으면 다시 생성하거나 이벤트를 중복 발행하지 않는다.
- Transaction의 revision 또는 현재 회차가 달라지면 최신 상태를 다시 읽고 종료한다.
- 여러 주 동안 접근하지 않은 반복방은 빈 중간 회차를 만들지 않고 마지막 미처리 회차만 종료한 뒤 현재 주차로 직접 승계하는 방식을 우선안으로 둔다.

- 생성은 기존 초기 점유 검증, 직접 참가·승인은 기존 가입 점유 검증을 다시 통과해야 Rules가 교체를 허용한다. 정책·Rules 계약·생성 점유·가입 쓰기 계획 표적 테스트 18건과 수정 후 정책 테스트 4건, 변경 Dart 분석이 통과했다. 사용자는 기존 실패 데이터를 유지한 채 Rules 배포·최신 앱 설치 후 같은 승인 경로를 우선 재검증한다.

### 예상 회귀와 대응

1. **같은 레이드 방 무한 생성:** 난이도별 점유 키를 만들거나 현재 주차 assignment까지 stale로 판정하면 발생한다. 난이도 없는 canonical assignment ID와 Transaction 경쟁 테스트로 차단한다.
2. **반복방 참가자의 이중 점유:** 반복방 승계 전에 old cycle assignment를 지우면 새 방을 만들 수 있다. 반복방은 assignment를 삭제하지 않고 새 cycle로 갱신한다.
3. **늦은 정리 요청이 새 점유 삭제:** old recruitment ID를 비교하지 않고 삭제하면 발생한다. 삭제 전 assignment의 recruitmentId·cycleKey를 Transaction에서 재검증한다.
4. **부분 전환:** recruitment만 갱신되고 listing·assignment 일부가 남을 수 있다. 방 단위 원자적 전환을 우선하고, Transaction 한도를 넘는 방은 명시적 단계/checkpoint와 재시도 계약을 둔다.
5. **동시 접근 중복 이벤트/회차:** 두 기기가 같은 만료 방을 보정하면 발생한다. `recruitmentId + oldCycleKey`, revision, cycle 문서 존재 여부를 멱등 키로 사용한다.
6. **클라이언트 시각 조작:** 기기 시간이 빠르면 조기 종료될 수 있다. 클라이언트 시각은 후보 탐색에만 사용하고 Rules의 `request.time >= cycleEndsAt`이 실제 전환을 확정한다.
7. **오프라인 캐시 오판:** 캐시의 만료 상태만으로 서버 쓰기 성공을 가정하면 목록과 점유가 어긋난다. 오프라인에서는 로컬 표시만 정리하고 온라인 Transaction 성공 후 서버 전환 완료로 본다.
8. **여러 주 미접속 반복방의 잘못된 중간 기록:** 빈 주차마다 허위 미완료 기록이 생길 수 있다. 마지막 실제 미처리 회차만 종료하고 현재 주차로 직접 승계한다.

### 필수 자동 테스트

- 동일 Character·동일 raidId·동일/다른 difficulty로 두 방 동시 생성 시 정확히 하나만 성공한다.
- 만료된 1회성 방 점유는 새 주차 생성·신청·참가를 막지 않는다.
- 만료된 반복방 참가자는 승계 후 같은 raidId의 다른 방을 생성·참가할 수 없다.
- 서로 다른 raidId는 같은 Character로 각각 정상 생성·참가할 수 있다.
- old 보정과 새 방 생성이 동시에 실행돼도 최종 assignment는 새 방 하나만 가리킨다.
- 완료 Claim이 있는 Character는 미완료 종료 보정과 관계없이 현재 주차 동일 raidId의 모든 난이도가 차단된다.

### 작업 범위

- 배포 앱에 디버그 화면을 추가하지 않는다.

- 전체 정상은 카드에 추가 문구를 표시하지 않는다. 동일 직업 미확인과 검증 정보 없음은 중립 안내, 다른 직업 보석만 빨간색 `다른 직업 보석 N개 · 확인 필요`로 표시한다.
- 선호 포지션이나 해당 역할 Snapshot이 없으면 판정을 추정하거나 다른 역할 결과로 대체하지 않는다.
- DB schema·Firestore·Rules·타인 카드 Snapshot은 변경하지 않았다. 실제 디바이스에서 정상·동일 직업 미확인·다른 직업 보석과 좁은 카드 말줄임을 확인해야 한다.
- 관련 표적 테스트 48개와 전체 테스트 917개가 통과했고 변경 파일 표적 analyze도 통과했다.
- 다음 서버 Snapshot·Rules 및 타인 카드 반영은 계약 7~8단계의 별도 승인 구간이며, 변경량을 먼저 산정한다.

### 차후 별도 작업 — Build 별칭과 개인 직업 메모

현재 기본 무결성 및 시너지 작업에는 포함하지 않는다. Build 식별 및 무결성 기준은 `CHARACTER_BUILD_INTEGRITY_CONTRACT.md` §10~12, 설정 페이지·계층 메모·공유 제품 구상은 [`../product/BUILD_MEMO_SHARING.md`](../product/BUILD_MEMO_SHARING.md)를 따른다.

- `망소빙`처럼 사용자가 실제 코어 구성과 통칭을 확인할 때마다 직업·깨달음·질서 해·달·선택 별 조합을 정적 카탈로그에 점진적으로 추가한다. 모든 직업 조합을 선행 수집하지 않는다.
- 등록된 별칭은 최적 Build 보증이 아니라 현재 API 조합의 간략 표시다. 파티 상세 카드에는 보석·아크그리드 경고와 별도로 짧게 표시한다.
- 현재 깨달음 분기와 아크그리드 원문·분석은 소유자 기기의 역할별 Build Snapshot에만 있고, 파티 신청·membership 서버 Snapshot에는 직업·역할·아이템 레벨·전투력만 있다.
- 타인 카드에 Build 별칭을 표시하려면 전체 rawJson이 아니라 계산된 별칭 ID/표시명/카탈로그 버전/검증 시각의 최소 Snapshot과 Rules 변경량을 먼저 산정한다. 서버 변경이 크면 내 계정 로컬 표시까지만 한다.
- 사용자 개인 메모의 1차 범위는 직업 단위다. 파티 카드의 기존 `classNameSnapshot`으로 조회 가능하므로 `playerId + classId` 키의 로컬 Drift 메모로 구현하고 서버에는 올리지 않는다.
- 깨달음 분기 또는 `망소빙` 같은 Build별 개인 메모는 현재 서버 카드 데이터만으로 불가능하다. 최소 `branchId`/`buildAliasId` Snapshot이 승인된 뒤 별도 판단한다.
- 최종 목표는 직업 카드별 설정 페이지에서 깨달음과 질서 해·달·별을 각각 선택하고 짧은 메모를 기록해, 파티 신청자·참가자 카드에서 현재 Build에 매칭되는 직업 공통·깨달음·코어 메모를 합쳐 보여주는 것이다.
- 사용자 간 공유는 서버 없이 가능한 버전형 JSON export/import를 1차로 검토한다. 서버 공유가 필요하면 팩을 코드로 한 번 내려받아 로컬에 저장하고 카드마다 서버 조회하지 않는 2차 구조를 검토한다.
