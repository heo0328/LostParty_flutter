# NEXT WORK — 모집 브랜치의 실행 기준 정리와 실제 앱 연결 정정

## 직전 파트 — B 일반 앱 연결 완료

A 모델·저장/재전송 기반을 유지하고 BackendApp의 계약 선택을 betaWire2로 고정했다. 구계약 선택용 앱 생성자 인자는 제거했다. 생성/목록/상세의 기존 beta DI를 일반 main 경로에서 사용하고, CycleInteractionRepository의 기존 읽기/쓰기에는 전용 계약 경계로 profile/닫힌 wire 검증·기존 의미 파서를 연결했다. 본문/요청 키는 변경하지 않는다.

검증: 직접11파일413PASS 뒤 보강한 최종 신규11PASS를 확인했으며 중첩 제외 고유415PASS다. 실제 앱 기본 선택, join/apply/change context/POST·동일본문/키, 탈퇴·해산 ACK, 잘못된 본문 HTTP0·잘못된 응답 거절과 A/B·기존 직접 회귀다. 변경4파일 analyze0·포맷/diffcheck/리뷰. 실서버 정상회원/기기 성공은 미확인이다. 상세 결과 DEV_LOG/설계37 §37.70.

## 다음 파트 — 기존 일정/관리 화면의 베타 입력 연결

B를 다시 설계하거나 A를 걷어내지 않는다. 이미 구현한 생성/기본표시는 일반 앱에서 선택되며, 아래 기존 후속의 승인 UX를 연결한다. 특히 일정/설정 변경과 다음주 새 개방은 새 필수 config 입력이 필요한 계약이므로 다음 화면 연결에서 해당 입력을 처리해야 한다. 이번에 기본 시간을 합성하거나 기존 본문을 암묵적으로 변환하지 않았다. 이를 전체 모집 기능 완료/테스트 준비 완료로 보고하지 않는다.

다음 착수 시 승인 Penpot03/§37.63/65/67과 실제 일정·관리 호출자의 필요한 입력을 대조해 다음 의미 있는 파트를 정하고 구현한다. 디바이스 인수는 관련 화면/Backend 흐름 준비 후 수동1~5구간으로 안내한다. 서버/DB 초기화·배포·dev/main 통합은 이 연결 파트에서 실행하지 않았다.
