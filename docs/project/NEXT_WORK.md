[구현/계약 인계](https://github.com/heo0328/lostparty-backend/issues/4#issuecomment-6163357170), [통합 인계](https://github.com/heo0328/lostparty-backend/issues/4#issuecomment-6163855526). 원본 계약 SHA d3cb697bb6ebb988b63bd99c588bc1b64a93650d, 통합 a6d25aa, 조사 당시 Backend dev40aea9b의 추가 변경은 협업 문서다.

Flutter는 아직 등록 시 기본 이름 문자열을 전송하고 빈 label 입력/응답을 거절한다. 다음 목표는 서버에도 미입력 이름을 빈값으로 저장하고, 현재 본·부계정 위치로 표시 이름을 계산하는 것이다. 입력한 이름은 그대로 표시한다. 로컬 동일 규칙은 이미 구현되어 있으며 다시 만들지 않는다. 장기 기준은 [이름 계약20](../backend-migration/20-account-auto-label-contract.md).

## 확정 계약과 데이터 흐름

- POST label 생략/빈 문자열/공백은 저장·응답 label="". Flutter는 빈 입력을 그대로 전달하며 자동 이름 문자열을 저장 요청에 넣지 않는다.
- PATCH label 생략은 유지, 명시 빈값/공백은 자동 표시로 전환, 지정 문자열은 입력 이름이다. null/숫자/boolean/40자 초과는 거절한다. 응답 DTO는 label 빈 문자열만 추가 허용하고 다른 필드 검증은 완화하지 않는다.
- 표시: 빈 label의 is_main=true는 메인 계정. 전체 GET의 created_at ASC·registration_id ASC 순서에서 본계정을 제외한 모든 부계정(지정 이름 포함)을 세어 빈값에 부계정 N을 표시한다. 페이지마다 번호를 다시 시작하지 않는다. 본계정 변경은 이름값을 교환하거나 수정하지 않는다.
- 기존 BackendApp Router/DI → 공통 Dio transport → 등록 ViewModel/읽기 Repository를 유지한다. 서버 UUID와 로컬 정수 PK는 별개다. 수정창에는 저장된 이름만 넣고 자동 표시 문구를 입력값으로 재저장하지 않는다.

## 작업 순서

1. 기존 feature/account-backend-registration의 dev 포함 상태를 확인해 적합하면 최신 dev에서 재사용한다. 종료 조건은 새 빈 이름 계약 연결·검증·필요한 사용자 인수·#4 결과 회신이다.
2. 최신 #4 댓글과 d3cb697 원본 OpenAPI를 다시 대조하고 새 snapshot/계약 변경을 기록한다. 기존 snapshot은 과거 계약 근거로 유지한다.
3. 등록/수정 입력과 응답 DTO를 새 계약에 맞추고, 전체 목록 기반 표시 이름을 공통 정책으로 계산해 화면에 전달한다. 기존 로컬 정책을 중복 구현하지 않는다.
4. 빈 응답/불량 타입·불변 key/payload 재전송·전체 목록 번호/본부전환·세션 변경과 늦은 응답 등 직접 영향 경계를 묶어 검증한다. 변경 범위에 맞춘 분석/포맷/diff check, 사용자가 설치할 debug 빌드를 제공한다. 공용 연결 영향이 넓어지면 전체 검증 필요성을 판단한다.
5. 신규 이름 흐름만 사용자에게 한 번에 확인 요청한다: 이름 미입력 등록, 지정 이름 저장·비워서 전환, 본부전환 후 자동 이름/지정 이름, 지정 이름이 섞인 부계정 번호. 기존 등록·재로그인·갱신 통과를 반복 요구하지 않는다.
6. 적용 커밋/push·소비 계약 SHA·자동 검증·사용자 결과·미확인 사항을 같은 #4에 회신하고 문서 정리 후 dev 통합한다. 확인된 서버 차이가 있을 때만 Backend 보완을 요청한다.

## 회귀 확인과 완료 조건

기존 로그인/로그아웃·회원 세대 격리, preview/TTL·등록/삭제/204·refresh wrapper, 업무403과401 처리, Retry-After·동일 key/body 복구, 본계정 전환 뒤 전체 재조회, 로컬 캐릭터/빌드/표시 순서를 유지한다. 새 계약으로 빈 이름 등록/전환과 목록 표시가 정상이고 지정 이름은 그대로여야 한다. nullable 전투력을 0으로 바꾸거나 소유 인증 완료로 표시하지 않는다.

이미 확인된 실제 등록·삭제·같은 회원 재로그인 뒤 원정대 표시 및 최신 갱신 안내는 유지 근거로 사용한다. 서버 이름 신규 인수와 삭제 후 로컬 자료 보존 등 미확인 항목은 통과로 확대하지 않는다. #3/#4 종료는 별도 판단한다.
