## 최신 지시 — 깊이 개선 통합 계획 확정·다음 A1 검증 기준 정합화

사용자 지시에 따라 호출 깊이 개선을 남은 구간에 통합했다. 전체 순서·영향·전환/복구는
[축소 설계 §25](../architecture/FIRESTORE_RULES_REDUCTION_DESIGN.md#25-깊이-개선을-포함한-잔여-구간-실행-계획-2026-10-08)가 기준이다.
A1 fixture 정합화 → A2 R1 잔여 안전성 → B 깊이/반복 호출 → C 구형 계약 종료 →
D canonical target proof → E 최종 전환 묶음 → F 게시·실기기 인수 순서다.
B/C의 작은 감소를 대폭 축소 완료로 세지 않는다.30% 목표의 추가42727bytes 감소는 여전히 미입증이다.

다음 단일 작업 A1:
1. cleanup proof의 slot/member 소유권 차수를 실제 writer 사전검사와 맞춘다.
2. advance fixture에 현재 앱의 사전 인증 순서를 반영하고 구형 직접 쓰기와 구분한다.
3. R1에서 정리/receipt/advance·peer 후 승계를 연산별로 검증한다. 최대8인 대표와 다른 상태 전이만 사용한다.
4. 기준 승계1000식이 남으면 실패 연산·자료·호출 경로를 기록해 독립 최소 수정 구간을 정한다.
완료 조건: 최신 writer 계약에 맞는 재현 입력, 정상/거절/한도 오류 구분, 기준 결함 목록·다음 수정 범위.
제외: 미채택R3 재실험, 권한 완화, 앱/Rules 변경, 대용량coverage, 다른 후보 구현,

### 완료된 조사 구간 — R3 원본/파생 명령 검증 책임과 제거량 설계

목표: member/event와 모집 원본의 중복 명령 검증을 함수/호출별 크기로 분해하고,
가장 효과가 큰 한 명령군의 최소 후보 설계를 확정한다. 이번에는 코드 전환/배포를 하지 않는다.

1. R1 가독본을 기준으로 명령별 actor·허용필드·필수동시쓰기·대상검사 표를 만든다.
2. source가 target 쓰기를 강제하고 target이 같은 원본 revision/time/ID를 확인하는지 대조한다.
3. 중복 제거 전후의 소스 크기를 계산하고 남길 권한/점유/소유권/8인 원자성 검사를 명시한다.
4. 최대효과 한 그룹만 다음 구현 대상으로 고르고 정상/위조/누락/재진입 검증 조건을 기록한다.

완료 조건: 근거 위치가 있는 책임표, 정적 감소량과 compiled 미확인 구분, 기존 BUG-022~024 보호,
단일 구현 후보의 포함/제외·롤백·서버경계 검증 명세. 기존 R1 미참조함수/인수 잔여를 묻지 않는다.
제외: R2 자료이행·구버전 차단, R3 전체 동시구현, Firebase 원격요청/게시, APK 설치, dev/main 통합.
진행은 파일에 작은 체크포인트로 기록하고 이전 검증은 코드 무변경이면 재실행하지 않는다.

## 1. 복구키를 통한 기존 앱 사용자 복구 — 설계 필요

### 목적과 현재 합의

같은 사람의 앱 재설치·데이터 삭제·기기 변경을 해결한다. 새 익명 로그인에서 복구키를 검증한 뒤
기존 앱 사용자(Player)에 다시 연결하여 현재 유효한 원정대·그룹·레이드 관계를 사용한다.
현재 authBindings의 Auth UID→playerId 구조를 활용하는 방향이며, Firebase 익명 계정 자체 이전과 구분한다.
A의 데이터를 B로 복사·병합하거나 과거 시점의 스냅샷을 덮어쓰는 기능이 아니다.
복구 시 원정대를 무조건 미인증으로 만들지 않고 서버의 현재 인증·소유권 상태를 따른다.
이미 다른 사용자에게 넘어간 원정대는 이전 복구키로 소유권을 되돌릴 수 없어야 한다.

### 구현 전에 결정할 사항

복구키 발급·저장·검증·재발급·폐기와 유출/분실 처리, 신뢰된 서버 검증 방식,
기존 기기 접속 유지/차단, 복구 전 새 Player의 참가·인증 데이터 처리, 중복 요청과 중도 실패,
캐시·구독·세션 전환을 확정한다. 이미 활동한 새 Player의 데이터는 임의 삭제·자동 병합하지 않는다.
원정대 인증만으로 기존 Player 전체를 복구하는 방식은 채택하지 않는다.

### 완료 기준과 제외

설계 승인 후 서버 권한과 실제 앱 연결을 구현하고 사용자 복구의 데이터 보존·중복 처리 경계를 확인한다.
이전된 원정대 권한이 복구로 부활하지 않아야 한다. 실기기 결과는 별도 확보한다.
소셜 로그인 또는 사용자 전체 병합은 자동 포함하지 않는다. 현재 복구키 구현/검증 완료가 아니다.

## 2. 이전 소유자에게 남은 원정대 고아 관계 처리 — 설계 필요

### 목적과 기존 정책

다른 사용자가 원정대를 인증한 경우, 새 인증자는 기존 사용자의 그룹·참가·완료를 승계하지 않고
과거 기록에 막히지 않게 이용한다. 이 정책은 유지한다. 동시에 기존 방의 무효 참가가 방을 막거나
동일 캐릭터의 이전·새 참가를 모두 정상 인원으로 취급하지 않도록 처리한다.
새 사용자가 과거 방을 찾아 정리해야만 이용할 수 있게 만들지 않는다.

### 조사·결정 범위

이전 신청의 승인 차단, 진행 중 방의 참가 정리, 공대장 권한 상실 시 승계, 완료 반복방의 다음 주
제외, 마지막1인 해산, 동일 방 중복 가입을 연결해서 조사한다. 정리 시점·실행 주체·확인 UI·동시 요청
처리와 조회 실패 상태를 설계로 확정한다. 인증 시 모든 방 일괄 순회·삭제를 기본안으로 가정하지 않는다.
현재 완료 반복방의 단건 정리/복구 기능은 재사용 후보이며 활성방 전체 문제를 해결한 것으로 보지 않는다.
다른 원정대·정상 그룹 가입·과거 완료 이력·새 소유자의 새 참가 데이터는 보존한다.

### 근거와 완료 기준

재인증 후 동일 캐릭터가 같은 방에 두 명으로 보인 사용자 관찰을 대표 조사 사례로 삼는다.
새 사용자 이용과 남은 참가자의 방 정상 이용을 모두 확인해야 완료다. 실제 중복 데이터가 어떤
소유권 차수/참가 상태인지 확인 전 자동 교체나 삭제 방법을 확정하지 않는다.
기존 반복방 자격 확인 버튼의 오류는 이 조사에서 실패 단계와 권한을 구분한다.
