## 다음 작업 그룹 — 다수 활동 Character 저장 권한 한도 수정

### 현재 구현 상태

- `codex/fix-activity-character-batch-limit`에서 최종 선택 전체 선검증, 기존 정상 문서 생략, 대표 Character 우선, 최대 4개 단위 추가·갱신 후 삭제 순서를 구현했다.
- 8→15 활성화는 기존 8개를 다시 쓰지 않고 신규 7개만 `4 + 3`으로 저장한다. 15→8 축소도 삭제를 `4 + 3`으로 나누며, 두 번째 묶음 실패 후 같은 명령 재시도로 15명 상태에 수렴하는 회귀를 추가했다.
- Repository·Write Plan·Domain·ViewModel 표적 37건, 계정 기능 전체 256건, 그룹·모집·레이드 활동 Character 소비 경로 26건과 변경 파일 정적 분석이 통과했다.
- 실제 운영 Rules Emulator 검증 코드는 15명 분할 저장 사례를 포함하도록 확장했으나, 전체 `firestore.rules` 로딩 단계의 기존 `503 Network closed for unknown reason` 때문에 요청 실행 전 차단됐다. 문자열 계약으로 대체 통과 처리하지 않는다.
- `firestore.rules`는 변경하지 않았으며 Rules 배포도 필요하지 않다. 남은 완료 조건은 아래 실기기 확인이다.

### 실기기 확인

1. 기존 8명 상태에서 15명을 선택하고 저장했을 때 권한 오류 없이 완료되는지 확인한다.
2. 화면을 나갔다 다시 들어와 15명 선택이 유지되는지 확인한다.
3. 레이드 생성·신청·참가 Character 변경과 그룹 Character 목록에 새 활동 Character가 후보로 나타나는지 확인한다.
4. 다시 8명으로 줄여 저장하고 재진입 시 해제한 7명이 제외되는지 확인한다.
5. 기존 진행 중 레이드 membership·Claim·그룹 membership이 그대로 유지되는지 확인한다.

### 재현과 원인

- 사용자가 기존 활동 Character 8명 저장은 정상이나 15명 활성화 저장에서 `permission-denied`가 발생함을 실기기에서 확인했다.
- 현재 Repository는 최종 선택 Character 문서를 한 Transaction에서 모두 다시 쓴다. Rules는 각 문서마다 Auth binding, Character 소유권, GameAccount 소유권과 대표 Character 활동 상태를 확인하므로 다수 Character에서 Firestore Rules의 원자 작업당 문서 접근 20회 한도를 넘는다.
- 기존 Emulator 계약은 대표와 부캐 2명만 저장해 다수 Character 경계를 보호하지 못했다. Rules 미배포나 그룹 권한 충돌로 확정하지 않고 저장 묶음 크기 문제로 수정한다.

### 포함 범위

1. 최종 선택 전체를 먼저 Domain 정책으로 검증한다.
2. Rules 접근 한도보다 충분히 작은 고정 크기 묶음으로 활동 문서 쓰기를 분할한다.
3. 각 GameAccount 대표 Character 추가를 일반 Character보다 먼저 처리한다.
4. 추가·갱신을 모두 끝낸 뒤 비활성 Character 삭제를 처리해 중간 실패가 기존 활동·대표 상태를 먼저 훼손하지 않게 한다.
5. 이미 목표 상태인 문서는 불필요하게 다시 쓰지 않는다.
6. 부분 성공 후 재시도해도 같은 최종 상태로 수렴하도록 멱등성을 유지한다.
7. 15명 활성화, 15명에서 축소, 본·부계정 대표, 중간 실패와 기존 1~2명 정상·거절 경로를 회귀 테스트한다.

### 원자성과 실패 계약

- Firestore Rules 접근 한도 때문에 임의 개수 Character 전체의 단일 Transaction 원자 저장은 유지할 수 없다.
- 여러 묶음 중 실패하면 로컬 저장 성공으로 확정하지 않고 서버 상태를 다시 읽을 수 있는 실패를 반환한다.
- 쓰기 순서는 `대표 포함 추가 → 나머지 추가·갱신 → 비활성 삭제`다. 따라서 부분 실패 시 서버에 일부 새 활동 Character 또는 해제 예정 Character가 더 남을 수 있지만 대표·최소 1명과 기존 레이드·그룹 참가 데이터는 보존된다.
- 같은 최종 선택으로 재시도하면 남은 차이만 반영해 수렴한다.

### 제외 범위

- Character·GameAccount 소유권 조건 완화
- 그룹·파티·Claim 저장 구조와 후보 정책 변경
- 기존 참가 Character 자동 탈퇴 또는 Snapshot 삭제
- Firestore Rules 배포. Rules 소스 변경 여부를 먼저 확정하고, 변경될 때만 별도 배포 게이트를 적용한다.

### 완료 조건

- 15명 이상 저장이 Rules 접근 한도를 넘는 단일 원자 쓰기를 만들지 않는다.
- 대표 Character 포함, 최소 1명, active 소유권 검증이 유지된다.
- 부분 성공·재시도와 축소 저장이 안전하게 목표 상태로 수렴한다.
- Repository·Write Plan·ViewModel 영향 테스트와 실제 Rules Emulator 다수 문서 계약이 통과한다.
- 실기기에서 8→15 저장, 재진입 유지, 15→8 축소와 레이드·그룹 후보를 확인한다.
