## 이번 작업 그룹의 목표

모집 생성 화면에서 메인 계정 대표 캐릭터로 고정된 파티장을 본계정·부계정 전체의 표시 캐릭터 중 사용자가 직접 선택할 수 있게 한다. 선택 캐릭터에 저장된 역할 세팅과 레이드 참가 조건을 검증하고, 실제 참가할 캐릭터와 역할을 모집 생성 결과에 반영한다.

## 확정된 제품 규칙

- 대표 캐릭터는 최초 추천값으로만 사용하며 파티장으로 강제하지 않는다.
- 본계정과 부계정은 같은 사용자의 소유 캐릭터 집합으로 취급한다.
- 파티장 후보는 각 계정의 표시 캐릭터만 제공한다.
- 후보는 선택한 레이드·난이도의 입장 레벨, 저장 역할, 주간 완료 및 참가 충돌 조건을 판정한다.
- 동일 레이드 pending 신청은 선택을 막지 않고 신청 수를 안내하며, 생성 시 명시적 확인 후 종료한다.
- 확정 참가, 주간 완료 및 일정 충돌은 선택 또는 생성을 차단한다.
- 선택 캐릭터에 dealer/support 세팅이 모두 있으면 사용자가 파티장 역할을 선택한다.
- 레이드나 난이도 변경으로 현재 선택이 무효가 되면 자동으로 다른 캐릭터를 선택하지 않고 재선택을 요구한다.
- 모집 생성은 선택한 캐릭터의 확정 참가이며 기존 확정 점유·pending 종료 규칙을 그대로 사용한다.

## 포함 범위

- 모집 생성용 파티장 후보 읽기 모델 또는 기존 후보 판정 로직의 재사용 경계 확정
- 본계정·부계정의 표시 캐릭터를 계정별로 구분한 선택 Bottom Sheet
- 후보별 계정 표시명, 캐릭터명, 직업, 아이템 레벨 및 저장 역할 표시
- 후보별 입장 레벨, 주간 완료, pending 수, 확정 참가 및 일정 충돌 상태 표시
- dealer/support 복수 세팅 캐릭터의 파티장 역할 선택
- 대표 캐릭터 최초 추천과 사용자 선택 유지
- 레이드·난이도 변경 후 현재 선택의 재검증과 무효 상태 안내
- 선택한 파티장 캐릭터·역할을 기존 모집 생성 명령에 전달
- pending 종료 확인과 모집 생성 성공·실패의 한글 안내
- 관련 Domain/Service/ViewModel/Widget 테스트와 최종 전체 검증

## 구현 전 확인 항목

1. 현재 모집 생성 ViewModel과 생성 명령이 대표 캐릭터를 주입받는 위치를 확인한다.
2. 신청 후보와 캐릭터 변경 후보 서비스에서 계정 통합 조회 및 참가 상태 판정 로직을 재사용할 수 있는지 확인한다.
3. 모집 생성에 필요한 후보 상태와 기존 읽기 모델의 차이를 정리한다.
4. 기존 모집 생성 테스트에서 대표 캐릭터 고정을 전제로 한 항목을 식별한다.
5. 재사용으로 책임이 섞이면 모집 생성 전용 후보 서비스 또는 읽기 모델을 최소 범위로 추가한다.

## 작업 순서

1. 관련 코드와 테스트를 대조해 구현 단위와 재사용 경계를 확정한다.

3. 후보별 참가 조건과 차단·경고 상태를 계산해 화면용 읽기 모델로 제공한다.
4. 계정별 캐릭터 선택 Bottom Sheet와 역할 선택 UI를 구현한다.
5. 대표 캐릭터 추천, 사용자 선택 유지 및 레이드·난이도 변경 후 재검증을 연결한다.

10. 검증 결과와 다음 작업을 문서화한 뒤 기능 브랜치 저장 및 `main` 통합 여부를 사용자 지시에 따라 처리한다.

## 완료 조건

- 모집 생성 화면 진입 시 메인 계정 대표 캐릭터가 유효한 경우 최초 추천값으로 표시된다.
- 사용자는 본계정·부계정의 다른 표시 캐릭터로 파티장을 변경할 수 있다.
- 선택 UI에서 캐릭터의 계정, 기본 정보, 저장 역할 및 참가 상태를 구분할 수 있다.
- 선택 캐릭터에 두 역할 세팅이 있으면 dealer/support 중 하나를 직접 선택할 수 있다.
- 저장된 역할 세팅이 없거나 입장 레벨을 충족하지 않는 역할로 모집을 생성할 수 없다.
- 주간 완료, 확정 참가 및 일정 충돌 후보는 생성에 사용할 수 없다.
- 동일 레이드 pending은 차단하지 않으며 생성 전 확인 후 기존 규칙대로 종료된다.
- 레이드·난이도 변경으로 선택이 무효가 되면 자동 대체 없이 오류와 재선택 요구가 표시된다.
- 생성된 모집의 파티장 캐릭터와 역할이 사용자의 최종 선택과 일치한다.
- 기존 대표 캐릭터 기반 정상 흐름과 기존 참가 충돌 규칙이 훼손되지 않는다.
- 관련 테스트, `flutter analyze` 및 전체 `flutter test`가 통과한다.
- 코드 변경이 필요했던 경우 사용자 실기기 체크리스트 결과가 기록된다.
- 완료 이력은 `DEV_LOG.md`, 전체 현재 상태는 `AI_CONTEXT.md`, 다음 작업은 새 `NEXT_WORK.md`에 반영된다.
