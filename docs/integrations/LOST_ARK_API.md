# LOST ARK Open API 사용 설계

## 1. 문서 목적
LOSTPARTY에서 Lost Ark Open API를 사용하기 위한 1차 설계 문서다.
현재까지 공식 API 문서와 실제 캐릭터 조회 결과로 확인한 내용, 그리고 프로젝트에서 사용할 조회/저장/갱신 정책을 정리한다.
상세 응답의 모든 필드를 미리 모델링하지 않고, 실제 화면에서 필요한 데이터가 확정되면 필요한 필드만 추가 분석 및 모델링한다.

## 2. API 인증
Lost Ark Open API 호출에는 발급받은 JWT가 필요하다.

```text
Authorization: bearer {JWT}
Accept: application/json
```

JWT는 조회 대상 게임 계정의 인증 정보가 아니다. 특정 캐릭터 소유자의 로그인은 필요하지 않으며 API 개발자에게 발급된 JWT를 요청 Header에 넣는다.
JWT를 클라이언트 앱에 직접 포함하는 방식은 노출 위험이 있으므로 실제 배포 구조를 정할 때 별도 검토한다.

## 3. 호출 제한
현재 확인한 공식 문서 기준 API 호출 제한은 분당 100회다. 제한 초과 시 HTTP 429가 발생할 수 있다.
프로젝트에서는 불필요한 반복 호출을 피하기 위해 로컬 캐싱과 자동/수동 갱신 정책을 사용한다.

## 4. 계정 캐릭터 목록 조회
Endpoint:

```text
GET /characters/{characterName}/siblings
```

예:

```text
GET /characters/이슈아이/siblings
```

캐릭터 이름 하나를 전달하면 해당 캐릭터와 같은 계정에 속한 캐릭터 목록이 반환된다. 실제 테스트에서는 서버가 다른 캐릭터도 함께 반환되었다. 요청 시 서버명은 별도로 전달하지 않는다.

확인된 응답 데이터:

```text
ServerName
CharacterName
CharacterLevel
CharacterClassName
ItemAvgLevel
```

프로젝트 흐름:

```text
사용자 캐릭터명 입력
→ siblings API 호출
→ 동일 계정 캐릭터 목록 확보
→ CharacterSummary 생성
→ 로컬 저장
→ 캐릭터 카드 목록 표시
```

주의: API가 실제 계정 ID를 제공하는 것은 현재 확인하지 않았다. 앱 내부에서 하나의 캐릭터 그룹처럼 취급할 수 있지만 실제 Lost Ark 계정 고유 ID가 확보된 것으로 간주하지 않는다.

## 5. 캐릭터 상세 조회
Endpoint:

```text
GET /armories/characters/{characterName}
```

예:

```text
GET /armories/characters/이슈아이
```

실제 이슈아이 캐릭터 조회 결과 현재 LOSTPARTY에서 필요하다고 판단한 상세 데이터가 하나의 응답에 포함되는 것을 확인했다.

확인된 최상위 데이터:

```text
ArmoryProfile
ArmoryEquipment
ArmoryAvatars
ArmorySkills
ArmoryEngraving
ArmoryCard
ArmoryGem
ArkPassive
ArkGrid
ColosseumInfo
Collectibles
```

현재 프로젝트에서 우선 사용할 항목:

| 프로젝트 데이터 | API 응답 |
| --- | --- |
| 캐릭터명 | ArmoryProfile.CharacterName |
| 서버명 | ArmoryProfile.ServerName |
| 캐릭터 레벨 | ArmoryProfile.CharacterLevel |
| 직업 | ArmoryProfile.CharacterClassName |
| 아이템 레벨 | ArmoryProfile.ItemAvgLevel |
| 전투력 | ArmoryProfile.CombatPower |
| 장비 | ArmoryEquipment |
| 스킬 | ArmorySkills |
| 각인 | ArmoryEngraving |
| 카드 | ArmoryCard |
| 보석 | ArmoryGem |
| 아크패시브 | ArkPassive |
| 아크그리드 | ArkGrid |

현재 설계에서는 각각의 개별 API 대신 종합 상세 API 1회를 우선 사용한다.

### 상세 세팅 검증 규칙

캐릭터 스킬 슬롯은 일반 스킬 8개, 초각성 스킬 1개, 각성기 1개로 구성한다.
각성기와 초각성 스킬은 일반 스킬 레벨 기준을 적용할 수 없으므로 스킬 레벨만으로 장착 여부를 판정하지 않는다.

> 2026-09-08 이후 깨달음·아크그리드 최소 조건과 보석의 동일 직업 미확인/타 직업 판정은 [`../architecture/CHARACTER_BUILD_INTEGRITY_CONTRACT.md`](../architecture/CHARACTER_BUILD_INTEGRITY_CONTRACT.md)를 기준으로 한다.

- 일반 스킬에 장착할 수 있는 룬은 최대 8개
- 룬이 8개가 아니면 세팅 확인 경고를 표시
- 경고는 정보 제공 목적이며 파티 지원 제한에는 사용하지 않음
- 보석은 `ArmoryGem.Gems.Slot`과 `ArmoryGem.Effects.Skills.GemSlot`으로 연결
- 보석 효과는 피해 증가, 재사용 대기시간 감소, 지원 효과 증가 문장을 구조화
- 일반 스킬 목록에 없는 보석은 즉시 오류로 처리하지 않음
- 아크패시브, 아이덴티티 또는 클래스 고유 스킬 특징이 있으면 별도 유형으로 분류
- 어느 유형에도 연결할 수 없을 때만 확인 경고 표시
- 아크그리드의 `코어 옵션 발동 조건`을 정제해 활성 `ArkPassive.Effects`와 비교
- 필수 아크패시브가 없으면 확인 경고 표시
- `질서의 해`, `질서의 달` 코어는 14P 미만이면 필수 효과 미활성 경고 표시
- 유물 이상 `질서의 해`, `질서의 달` 코어는 14P 이상이어도 17P 미만이면 17P 효과 미활성 경고 표시
- `질서의 별`, `혼돈의 해/달/별`은 포인트 상태를 표시하되 필수 포인트 경고 대상에서 제외
- 아크그리드 포인트로 아직 열리지 않은 옵션은 오류가 아닌 정보로 취급

현재 API에는 일반 스킬의 명시적인 장착 슬롯 또는 `IsEquipped` 필드가 없다. 룬 유무나 스킬 레벨은 보조 정보로만 사용하며, 판정이 불명확하면 잘못된 단정보다 확인 경고를 우선한다.

## 6. 상세 API 호출량
siblings 결과가 18명이라면:

```text
siblings 조회    1회
상세 조회       18회
--------------------
전체            19회
```

종합 상세 API를 사용하면 개별 상세 Endpoint를 각각 호출하는 것보다 호출량을 크게 줄일 수 있다.

## 7. 데이터 저장 기본 정책
캐릭터 상세 데이터는 API 호출에 성공하면 로컬에 저장한다.
수동 갱신과 자동 갱신의 저장 로직은 동일하며 차이는 API 호출을 발생시키는 트리거뿐이다.

```text
refresh(character)
→ Lost Ark 상세 API 호출
→ 응답 디코딩
→ CharacterDetail 생성/갱신
→ 로컬 데이터 저장
→ 화면 갱신
```

## 8. 수동 갱신
현재 정책안:

```text
수동 갱신 쿨타임: 10초
```

```text
[수동 갱신]
→ 10초 쿨타임 확인
→ 상세 API 호출
→ 성공 시 즉시 최신 데이터로 로컬 저장
→ 화면 갱신
```

별도의 미확정 데이터를 유지하지 않는다. 수동 조회에 성공한 데이터도 즉시 최종 데이터로 저장한다.

## 9. 자동 갱신
자동 갱신은 캐릭터별 ON/OFF 설정으로 관리한다.
현재 정책안:

```text
자동 갱신 주기: 30분
```

자동 갱신이 ON인 캐릭터의 상세 화면에 진입했을 때 마지막 API 갱신 시간을 확인한다.

```text
캐릭터 상세 진입
→ 자동 갱신 OFF: 저장 데이터 표시
→ 자동 갱신 ON: 마지막 갱신 후 30분 경과 여부 확인
    → 미경과: 저장 데이터 표시
    → 경과: API 호출 → 로컬 저장 → UI 갱신
```

30분은 API 자체 Rate Limit이 아니라 불필요한 반복 조회를 줄이기 위한 프로젝트 내부 캐시 정책이다.

## 10. 수동 갱신과 자동 갱신 관계
두 기능은 서로 독립적인 트리거다. 자동 갱신 후 30분이 지나지 않았더라도 사용자는 수동 갱신을 실행할 수 있다.

```text
자동 갱신 TTL     : 30분
수동 갱신 쿨타임 : 10초
```

이 값들은 구현 과정에서 변경 가능하다.

## 11. Lost Ark API 데이터 특성 고려
Lost Ark 캐릭터 API 데이터는 항상 앱에서 원하는 대표 세팅과 일치한다고 가정하지 않는다.
여러 캐릭터가 보석을 공유하는 사용자는 종료 전에 보석을 빼둘 수 있고, API에는 그 상태가 반영될 수 있다.

따라서 모든 캐릭터에 자동 갱신을 강제하지 않는다.

```text
보석 등을 공유하는 캐릭터 → 자동 갱신 OFF 사용 가능
항상 현재 세팅을 유지하는 캐릭터 → 자동 갱신 ON 사용 가능
```

잘못된 상태에서 수동 갱신한 경우 정상 세팅으로 변경하고 API 데이터가 갱신된 뒤 다시 수동 갱신하여 수정할 수 있다.

### 2026-09-04 교류 행동 자동 갱신 후속 기준

위 30분 자동 갱신 기록은 기존 Character 상세 갱신 구상이며, 그룹·파티 교류 행동에서 사용하는 Build 자동 갱신에는 적용하지 않는다. 교류 갱신의 단일 기준은 [CHARACTER_INTERACTION_AUTO_REFRESH_CONTRACT.md](../architecture/CHARACTER_INTERACTION_AUTO_REFRESH_CONTRACT.md)다.

- 원정대 siblings 요약 자동 갱신은 기존 `CharacterSummarySyncService` 정책을 유지한다.
- 그룹·파티 후보 및 명령 직전 Armory Build 자동 갱신 성공 TTL은 5분이다.
- Armory API 최대 동시 요청은 3개다.
- 등록한 본·부계정 전체에서 아이템 레벨 1700 이상 동일 직업이 2명 이상이면 그 직업군 전체를 나이스단으로 판정하고 기본 자동 갱신에서 제외한다.
- 나이스단 전체 자동 갱신 허용 설정은 로컬에만 저장한다.
- 기존 정상 Snapshot은 기간 만료시키지 않고 실패 시 마지막 정상 저장 시각만 안내한다.

## 12. 현재 예상 데이터 개념
정확한 클래스/파일 구조는 실제 프로젝트 구조를 확인한 뒤 결정한다.

CharacterSummary (siblings):

```text
serverName
characterName
characterLevel
characterClassName
itemAvgLevel
```

CharacterDetail (종합 상세 API):

```text
profile
equipment
skills
engraving
card
gem
arkPassive
arkGrid
```

로컬 관리 메타데이터 후보:

```text
autoRefreshEnabled
lastFetchedAt
```

구체적인 Domain/Data Model 분리는 기존 프로젝트 아키텍처에 맞춰 결정한다.

## 13. JSON 모델링 시 주의사항
API 응답 전체를 그대로 앱 Domain Model로 만들지 않는다.
실제 응답은 매우 크며 일부 데이터는 Tooltip 문자열 내부에 추가 JSON/마크업 구조가 포함되어 있다.

예를 들어 장비 외부 구조는 다음과 같다.

```text
Type
Name
Icon
Grade
Tooltip
```

품질, 세부 옵션, 개별 아이템 레벨 등의 일부 정보는 Tooltip 내부에 포함되어 있다.

구현 원칙:

```text
화면/기능에서 필요한 데이터 결정
→ API 응답에서 위치 확인
→ 필요한 DTO 필드만 모델링
→ 필요한 경우 Tooltip 추가 파싱
→ Domain Model로 변환
```

상세 JSON 전체를 처음부터 모델로 변환하지 않는다.

## 14. ItemAvgLevel / CombatPower 타입 주의
실제 응답에서 다음 값은 숫자처럼 보이지만 문자열로 전달된다.

```json
"CombatPower": "3,382.29",
"ItemAvgLevel": "1,766.66"
```

비교/필터링/계산에 사용할 경우 쉼표 제거 후 숫자 타입으로 변환해야 한다. API DTO에서는 원본 타입을 유지하고 Domain 변환 과정에서 숫자화하는 방식도 고려한다.

## 15. Rate Limit 관리
자동 30분과 수동 10초 정책은 API Rate Limit 자체를 대체하지 않는다.
향후 API 호출 계층에서는 HTTP 429를 정상적으로 처리해야 한다.

추가 검토 항목:

```text
최근 API 호출량 관리
429 처리
재시도 정책
API 응답 Header의 Rate Limit 정보 활용
```

현재는 종합 상세 API 1회로 필요한 상세 데이터를 대부분 확보하므로 불필요하게 개별 상세 Endpoint를 병렬 호출하지 않는다.

## 16. 인증 토큰 보안 TODO
현재 API 테스트에서는 직접 발급한 JWT를 사용한다.
실제 앱 배포 시 JWT를 모바일 앱 바이너리 또는 일반 로컬 설정에 그대로 포함하면 토큰 추출 가능성이 있다.

배포 전에 다음 구조를 결정한다.

```text
앱에서 Lost Ark API 직접 호출
vs
자체 Backend/Proxy를 통한 호출
```

현재 미확정이다. JWT를 Git Repository에 커밋하지 않는다.

## 19. 사용 API 요약
계정 캐릭터 목록:

```text
GET /characters/{characterName}/siblings
```

용도: 최초 캐릭터 그룹 등록, CharacterSummary 확보.

캐릭터 종합 상세:

```text
GET /armories/characters/{characterName}
```

용도: 프로필, 전투력, 장비, 스킬, 각인, 카드, 보석, 아크패시브, 아크그리드.

현재 LOSTPARTY의 캐릭터 상세 갱신은 이 종합 Endpoint 1회를 기본으로 한다.

## 20. 직업 고유 스킬과 정적 게임 기준정보
실제 바드 상세 응답에서 `용맹의 세레나데`, `구원의 세레나데`는 `ArmorySkills`의 독립 스킬 항목으로 제공되지 않았다. 해당 이름은 능력치, 아크패시브 및 아크그리드 Tooltip 설명에서만 확인된다.

따라서 API 스킬 목록에 없는 대상을 즉시 잘못된 세팅으로 판정하지 않는다. 다음 정보를 앱에 포함된 직업별 정적 게임 기준정보로 보완한다.

이 문장은 API 일반 스킬 목록에 없는 아이덴티티·아크패시브 대상을 정적 카탈로그와 추가 대조한다는 의미다. 교류 자동 갱신에서는 그 추가 대조까지 끝난 뒤에도 현재 직업 대상으로 확인되지 않은 보석 효과가 있으면 정상 Snapshot으로 자동 저장·게시하지 않는다.

```text
직업명
깨달음 1티어 노드명
인게임 통칭
기본 역할(dealer/support)
직업 고유 아이덴티티 스킬
아크패시브 추가 스킬
주요 아크그리드 조합과 조건
```

정적 기준정보는 Git으로 버전 관리한다. 사용자가 작성하는 조합 메모, 선호 여부 및 평가는 별도 로컬 DB에 저장해 앱 데이터 업데이트와 분리한다.

분석 시 판정 순서는 다음을 기본으로 한다.

```text
ArmorySkills의 일반/각성 스킬
→ API 구조와 아이콘으로 식별되는 아크패시브 스킬
→ 직업별 아이덴티티/아크패시브 기준정보
→ 어느 항목에도 없을 때 확인 경고
```

수기 기준정보를 `ArmorySkills`에 직접 합치지 않는다. 실제 장착 스킬과 직업 고유 스킬의 의미가 다르므로 별도 카테고리로 유지한다.

실기기에서는 하나의 보석 대상 표시명이 여러 아이덴티티 스킬 효과를 함께 나타내는 경우도 확인됐다. 서포터 바드의 세레나데 보석은 용맹과 구원의 세레나데를 함께 강화하므로 두 개별 스킬명과의 단순 문자열 일치만으로 정상 여부를 판정하지 않는다.

이런 대상은 직업별 조건문으로 하드코딩하지 않고 정적 카탈로그에 API 보석 대상 별칭 또는 복합 효과 그룹과 관련 특수 스킬 ID 목록을 정의한다. 분석기는 해당 데이터 관계를 통해 `passiveOrIdentity`를 판정한다.

## 21. 깨달음 계열과 아크그리드 조건
깨달음 1티어 노드는 직업 내 세팅 계열과 역할을 추론하는 기준으로 사용한다. 예를 들어 바드는 다음과 같이 분류할 수 있다.

```text
완벽한 화음 → 서포터 계열
진실된 용맹 → 딜러 계열
```

추론 결과는 저장 역할 검증과 화면 안내에 사용하지만 저장을 강제로 제한하지 않는다. 사용자가 선택한 역할과 감지 역할이 다르면 확인 메시지를 표시하고 최종 선택은 사용자에게 맡긴다.

아크그리드 발동 조건은 깨달음 1티어 계열만으로 끝나지 않을 수 있다. 실제 fixture에는 `진실된 용맹 전용`과 함께 `아크 패시브 4티어 템페스트 필드 활성화 필요`가 존재한다. 따라서 계열 조건과 추가 노드 조건을 각각 판정한다.

## 22. 상세 갱신 저장 흐름
현재 상세 화면의 세팅 저장/갱신은 실제 종합 상세 API를 호출하고 선택한 dealer/support 역할에 전체 JSON 스냅샷을 저장한다. 자동 테스트 fixture는 앱 런타임에서 사용하지 않는다.

다음 개선에서는 API 응답을 즉시 덮어쓰지 않고 먼저 메모리에서 분석한다.

```text
세팅 갱신
→ 실제 API 응답 수신
→ 분석 결과 미리보기
→ 감지된 계열/역할과 경고 표시
→ dealer/support 저장 위치 또는 덮어쓰기 확인
→ 사용자 승인 후 로컬 DB 저장
```

## 23. 아크그리드 조합 상세 관리의 후속 범위
1차 앱에서는 아크그리드 코어의 세부 조합 통칭과 사용자 평가를 판정하지 않는다. 다음 기본 검증만 제공한다.

```text
코어 옵션에 명시된 깨달음 계열 조건 확인
추가 아크패시브 노드 활성 조건 확인
질서의 해/달 코어 14P 최소 효과 확인
유물 이상 질서의 해/달 코어 17P 효과 확인
```

직업별 깨달음 1티어 노드는 각각 사용할 수 있는 질서의 해/달/별 코어가 있으며 조합 경우의 수가 많다. 서포터 세팅은 여러 조합을 실사용할 수 있고, 일부 딜러 세팅은 특정 코어 조합을 요구할 수 있으므로 통상 조합을 앱에서 임의로 단정하지 않는다.

앱 1차 완성 이후 다음 기능을 별도 단계로 구현한다.

```text
직업별 전체 아크그리드 코어 기준정보 수기 입력
해/달/별 코어의 인게임 UI 순서 기록
사용자가 선호하는 3코어 조합 선택 및 이름 지정
통상 조합명과 숫자 순서 별칭 표시
조합별 사용자 메모와 평가 저장
파티 지원자의 장착 코어와 선호 조합 일치 여부 표시
```

예를 들어 소울이터의 만월 계열에서 `망자의 발걸음`, `소울`, `빙의` 코어 조합을 `망소빙소울` 또는 UI 순서에 따라 `231소울`로 부를 수 있다. 사용자는 해당 조합에 `딜 포텐셜 좋음, 컨트롤 어려움`과 같은 개인 메모를 연결하고 지원자 확인 시 함께 볼 수 있다.

이 조합명, 숫자 별칭 및 사용자 평가는 공식 API의 단일 판정값이 아니다. 정적 코어 기준정보와 사용자 선택/메모를 분리하고, 지원자 화면에서는 실제 장착 코어에서 계산한 일치 결과임을 명확히 표시한다.
